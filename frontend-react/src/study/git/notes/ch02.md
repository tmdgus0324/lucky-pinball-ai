Git을 설치하고 처음 한 번 해야 하는 설정입니다. 설정을 빠뜨리면 커밋 작성자가 엉뚱하게 남거나, 윈도우와 리눅스 사이에서 모든 줄이 바뀐 것처럼 보이는 일이 생깁니다. 사내망이라면 프록시와 인증서 설정도 필요할 수 있습니다.

## 1. 설정은 세 군데에 저장된다

| 범위 | 옵션 | 파일 | 적용 대상 |
|---|---|---|---|
| 시스템 | `--system` | Git 설치 폴더의 `etc/gitconfig` | 이 PC의 모든 사용자 |
| 전역 | `--global` | 내 사용자 폴더의 `.gitconfig` | 내 계정의 모든 저장소 |
| 저장소 | `--local`(생략 가능) | 저장소의 `.git/config` | 그 저장소 하나 |

같은 설정이 여러 곳에 있으면 좁은 범위가 이깁니다(저장소 > 전역 > 시스템). 지금 값이 어디서 왔는지는 `git config --list --show-origin`이나 `git config --show-origin 설정이름`으로 봅니다(실행 결과 참고).

## 2. 처음 한 번 할 설정

```bash
git config --global user.name "김개발"
git config --global user.email "dev@example.com"
git config --global init.defaultBranch main
git config --global core.quotepath false
```

- `user.name`, `user.email`은 커밋마다 작성자로 남습니다. 회사에서 정한 이름과 메일을 씁니다. 회사 저장소와 개인 저장소에 다른 메일을 쓰려면 저장소 안에서 `--global` 없이 설정합니다.
- `init.defaultBranch`는 `git init`으로 만든 저장소의 첫 브랜치 이름입니다. 이미 있는 회사 저장소는 그 저장소의 이름(main 또는 master)을 따릅니다.
- `core.quotepath false`를 주지 않으면 한글 파일 이름이 `"\354\230\210..."`처럼 숫자로 보입니다.

## 3. 줄바꿈(core.autocrlf)

윈도우는 줄 끝에 CRLF, 리눅스와 맥은 LF를 씁니다. 줄바꿈이 섞이면 한 줄만 고쳐도 파일 전체가 바뀐 것처럼 보입니다.

| 값 | 커밋할 때 | 꺼낼 때 | 쓰는 곳 |
|---|---|---|---|
| `true` | CRLF → LF | LF → CRLF | 윈도우 |
| `input` | CRLF → LF | 그대로 | 맥, 리눅스 |
| `false` | 그대로 | 그대로 | 변환하지 않음 |

Git for Windows는 설치할 때 보통 `true`를 시스템 설정에 넣습니다. 그래서 LF로 된 파일을 add하면 아래 안내가 나옵니다. 오류가 아니라 "다음에 꺼낼 때 CRLF로 바꾸겠다"는 뜻입니다.

```
warning: in the working copy of 'README.md', LF will be replaced by CRLF the next time Git touches it
```

팀 전체를 맞추려면 각자의 설정에 맡기지 말고 저장소에 `.gitattributes` 파일(`* text=auto`)을 두는 방법이 더 확실합니다.

## 4. 저장소 받기(clone)

```bash
git clone https://git.company.example/team/reservation.git
git clone git@git.company.example:team/reservation.git      # SSH 방식
```

- clone은 SVN의 checkout에 해당하지만, 파일뿐 아니라 이력 전체를 받아 옵니다.
- 받아 온 곳은 `origin`이라는 이름으로 기억합니다(`git remote -v`, 7장).
- HTTPS 주소는 처음 push·pull할 때 로그인 창이 뜨고, Git for Windows의 자격 증명 관리자(Git Credential Manager)가 저장해 둡니다. SSH 주소는 SSH 키를 만들어 서버에 등록해 두고 씁니다.

## 5. 사내망에서 막힐 때

| 증상 | 확인할 것 |
|---|---|
| clone이 시간 초과로 실패 | 프록시가 필요한지: `git config --global http.proxy http://프록시주소:포트` |
| `SSL certificate problem: unable to get local issuer certificate` | 사내 인증서. 윈도우라면 `http.sslBackend schannel`로 윈도우 인증서 저장소를 쓰거나, `http.sslCAInfo`로 인증서 파일을 지정 |
| 로그인이 계속 실패 | 비밀번호 대신 토큰(Personal Access Token)을 쓰라는 서버가 많다. 사내 Git 서버의 안내를 확인 |
| 한글 커밋 메시지·파일 이름이 깨짐 | `core.quotepath false`, 터미널 인코딩(UTF-8) |

인증서 검사를 끄는 설정(`http.sslVerify false`)은 쓰지 않습니다. 통신 내용을 가로채도 알 수 없게 됩니다.

명령의 안내 메시지는 환경에 따라 영어나 한국어로 나옵니다. 이 사이트의 실행 결과는 검색하기 쉽도록 영어로 맞췄습니다.

## 확인 문제

1. 전역에는 `user.email=a@company.example`, 저장소에는 `user.email=b@personal.example`이 있습니다. 그 저장소에서 커밋하면 어느 메일이 남나요?
2. 지금 적용된 설정이 어느 파일에서 왔는지 보려면?
3. 윈도우에서 `LF will be replaced by CRLF` 안내가 떴습니다. 고쳐야 하는 오류인가요?
4. 사내망에서 clone할 때 `SSL certificate problem`이 납니다. 확인할 것 두 가지는?
5. `http.sslVerify false`로 인증서 검사를 끄면 안 되는 이유는?

## 정답

1. 저장소 설정인 `b@personal.example`입니다. 좁은 범위가 이깁니다.
2. `git config --list --show-origin`(또는 `git config --show-origin user.email`)입니다.
3. 오류가 아닙니다. `core.autocrlf true`라서 꺼낼 때 CRLF로 바꾸겠다는 안내입니다.
4. 사내 인증서를 쓰도록 설정했는지(`http.sslBackend schannel` 또는 `http.sslCAInfo`), 프록시가 필요한지입니다.
5. 중간에서 통신을 가로채는 공격을 알아챌 수 없게 되기 때문입니다.

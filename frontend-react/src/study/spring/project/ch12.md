핀볼 게임 백엔드에서 트랜잭션 때문에 생긴 버그와, 일부러 트랜잭션을 나눈 곳입니다.

## 오류 로그는 REQUIRES_NEW

```java
// common/ErrorLogStore.java
/**
 * REQUIRES_NEW: 호출한 쪽 트랜잭션이 롤백돼도 오류 기록은 남아야 하고, 반대로 기록 실패가 호출한 쪽
 * 트랜잭션을 rollback-only로 만들어서도 안 되므로 독립된 트랜잭션에서 저장한다.
 */
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void record(String path, String message, String traceId) { ... }
```

정리 6절의 대표적인 예입니다. 처리 중 오류가 나서 본 작업이 롤백되더라도, "이런 오류가 났다"는 기록은 관리자 화면에 남아야 합니다.

## 트랜잭션이 없어서 조용히 실패한 삭제 쿼리

오류 로그는 최근 1000건만 남기고 오래된 것을 지웁니다. 처음엔 지우는 쿼리에 `@Transactional`이 없었습니다.

```java
// common/ErrorLogJpaRepository.java
// @Query로 직접 만든 수정 쿼리는 save() 같은 기본 메서드와 달리 트랜잭션이 자동으로 붙지 않는다 — 호출하는 쪽이
// 트랜잭션 안에 있다고 가정하지 않도록 여기서 직접 건다.
@Transactional
@Modifying
@Query("delete from ErrorLogEntity e where e.id <= :maxIdToDelete")
int deleteOlderThanOrEqual(long maxIdToDelete);
```

트랜잭션 없이 수정 쿼리를 실행하면 `TransactionRequiredException`이 납니다. 그런데 오류 로그 저장 코드가 "로그 저장 실패가 사용자 응답을 망치면 안 된다"며 예외를 잡아 경고만 남기고 있어서, 삭제가 계속 실패하는 줄 모르고 지나갈 뻔했습니다. 정리가 실제로 되는지 확인하는 테스트를 만들다가 발견했습니다(devhelp/09).

교훈 두 가지입니다.

- `save`, `findById` 같은 기본 메서드에는 트랜잭션이 이미 걸려 있지만, `@Modifying @Query`로 직접 만든 수정 쿼리에는 없습니다. 실행 결과 4번에서 `SimpleJpaRepository.save`가 혼자 트랜잭션을 연 것이 기본 메서드 쪽입니다.
- 예외를 잡아서 삼키는 코드는 이런 문제를 숨깁니다. 잡더라도 로그는 꼭 남깁니다.

## 조회용 트랜잭션

```java
// game/JpaGameRepository.java
@Override
@Transactional(readOnly = true)
public Optional<GameSession> findById(String gameId) {
    // toDomain()이 participants/ranks(LAZY)를 읽으므로, 세션이 열려있는 동안(@Transactional)
    // 변환까지 끝내야 한다 — 아니면 "no session" LazyInitializationException이 난다.
    return gameJpaRepository.findById(gameId).map(this::toDomain);
}
```

조회만 하므로 `readOnly = true`를 붙였습니다. 트랜잭션을 건 다른 이유는 지연 로딩입니다. 13장에서 이어서 봅니다.

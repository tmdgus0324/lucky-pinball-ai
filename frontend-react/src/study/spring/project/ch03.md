핀볼 게임 백엔드에서 DI가 가장 잘 드러나는 부분은 "AI 운세를 만드는 쪽을 인터페이스로 나눈 것"입니다.

## 인터페이스로 받기

운세 조회 서비스는 운세를 만드는 쪽을 구체 클래스가 아니라 인터페이스(`FortuneService`)로 받습니다.

```java
@Service
public class FortuneQueryService {

    public FortuneQueryService(PlayerService playerService,
                               FortuneService fortuneService,          // 인터페이스
                               FortuneResultJpaRepository fortuneResultJpaRepository,
                               ErrorLogStore errorLogStore,
                               @Value("${fortune.fallback-enabled:true}") boolean fallbackEnabled) {
        ...
    }
}
```

`FortuneService`를 구현한 클래스는 두 개지만, 빈으로 등록된 것은 하나뿐입니다.

| 클래스 | 빈인가 | 쓰임 |
|---|---|---|
| `ClaudeFortuneGenerator` | `@Service` | 실제 Claude API 호출 |
| `MockFortuneGenerator` | 아님 | 테스트와 장애 때 임시 점수 |

그래서 스프링은 `FortuneService` 자리에 `ClaudeFortuneGenerator`를 넣습니다. 처음에는 `MockFortuneGenerator`가 빈이었고, Claude를 붙일 때 빈만 바꿨기 때문에 `FortuneQueryService` 코드는 고치지 않았습니다.

## 테스트에서 빈 바꿔 끼우기

통합 테스트는 실제 Claude를 부르면 안 되므로(비용), 가짜 구현을 `@Primary` 빈으로 등록합니다. 같은 타입의 빈이 두 개가 되지만 `@Primary`가 붙은 쪽이 주입됩니다.

```java
@TestConfiguration
static class FakeAiConfig {
    @Bean
    @Primary
    CountingFortuneService countingFortuneService() {
        return new CountingFortuneService();   // 호출 횟수를 세는 가짜
    }
}
```

## 싱글톤이라 조심한 곳

관리자 로그인 토큰을 보관하는 `AdminSessionStore`는 빈 하나를 모든 요청이 같이 씁니다. 그래서 일반 `HashMap` 대신 여러 스레드가 동시에 써도 안전한 `ConcurrentHashMap`을 썼습니다.

## 생명주기 이벤트

`ClaudeFortuneGenerator`는 서버 시작이 끝난 직후(`ApplicationReadyEvent`)에 Claude 클라이언트를 미리 만들어 둡니다. 첫 사용자가 클라이언트 생성 시간까지 기다리지 않게 하려는 것입니다. `@PostConstruct`보다 늦은 시점(서버가 요청을 받을 준비를 마친 뒤)에 실행됩니다.

```java
@EventListener(ApplicationReadyEvent.class)
public void warmUpClient() {
    client();   // 클라이언트 객체만 만들고 실제 API 호출은 하지 않는다
    log.info("Claude 클라이언트 준비 완료");
}
```

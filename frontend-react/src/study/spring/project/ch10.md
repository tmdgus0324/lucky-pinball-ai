핀볼 게임 백엔드는 MyBatis가 아니라 JPA(11장)를 씁니다. 그래서 이번 장은 "핀볼의 조회를 MyBatis로 쓰면 어떻게 되는지"로 비교합니다.

## 운세 캐시 조회

같은 이름+생년월일의 이전 결과를 찾는 조회입니다. JPA는 메서드 이름으로 SQL을 만듭니다.

```java
// JPA: fortune/FortuneResultJpaRepository.java
Optional<FortuneResultEntity> findFirstByNameAndBirthDateAndSourceInOrderByCreatedDateAsc(
        String name, LocalDate birthDate, Collection<String> sources);
```

MyBatis로 쓰면 SQL을 직접 적습니다.

```xml
<!-- MyBatis로 쓴다면 -->
<select id="findCachedFortune" resultType="FortuneResult">
    SELECT *
      FROM fortune_result_entity
     WHERE name = #{name}
       AND birth_date = #{birthDate}
       AND source IN
       <foreach collection="sources" item="s" open="(" separator="," close=")">#{s}</foreach>
     ORDER BY created_date
     FETCH FIRST 1 ROWS ONLY
</select>
```

| | JPA 메서드 이름 | MyBatis XML |
|---|---|---|
| 장점 | SQL을 안 써도 됨 | 실행될 SQL이 그대로 보임 |
| 단점 | 조건이 늘면 이름이 아주 길어짐(위 예처럼) | 단순한 조회도 SQL을 다 써야 함 |
| 운영에서 SQL 찾기 | 로그를 켜야 실제 SQL이 보임 | XML에 그대로 있음 |

## 이 프로젝트에 MyBatis가 맞았을까

핀볼의 조회는 대부분 "id로 하나 찾기", "조건 몇 개로 찾기"라서 JPA 메서드 이름으로 충분했습니다. 반대로 통계 화면처럼 조인과 집계가 많은 SQL이 중심이라면 MyBatis가 더 편합니다. 실무에서는 둘을 같이 쓰는 프로젝트도 많습니다(기본 저장·조회는 JPA, 복잡한 조회는 MyBatis).

## SQL 로그

핀볼은 SQL 로그를 켜 두지 않았습니다. JPA에서 SQL을 보려면 `logging.level.org.hibernate.SQL: debug`를 켭니다. 11장 실행 결과에서 JPA가 만든 SQL을 볼 수 있습니다.

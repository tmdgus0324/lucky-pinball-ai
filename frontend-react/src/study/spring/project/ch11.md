핀볼 게임 백엔드는 모든 DB 작업을 JPA로 합니다.

## 게임 엔티티

```java
// game/GameEntity.java
@Entity
public class GameEntity {

    @Id
    private String gameId;            // UUID를 그대로 기본 키로

    @Enumerated(EnumType.STRING)
    private GameStatus status;        // CREATED → STARTED → FINISHED

    private String selectedName;
    private Instant createdAt;
    private Instant startedAt;
    private Instant finishedAt;

    protected GameEntity() {
        // JPA
    }

    void start(Instant startedAt) {
        this.status = GameStatus.STARTED;
        ...
    }
}
```

정리에서 본 규칙이 그대로 들어 있습니다.

- 상태는 `@Enumerated(EnumType.STRING)`으로 글자 저장
- JPA용 기본 생성자는 `protected`
- 상태는 setter가 아니라 `start()` 같은 메서드로 바꿈

`gameId`를 숫자 자동 증가 대신 UUID 문자열로 둔 이유는, 이미 API 주소(`/api/game/result/{gameId}`)에 쓰이는 값이라 같은 역할의 컬럼을 둘 만들지 않으려는 것입니다.

## 운영 DB 설정

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: update
    open-in-view: false
```

핀볼은 `ddl-auto: update`로 운영하고 있습니다. 정리 6절에서 운영은 `validate`나 `none`이 맞다고 했는데, 이 프로젝트는 혼자 운영하는 작은 서비스라 편의를 택했습니다. 그 대가로 테이블 변경 이력이 남지 않는다는 점은 알려진 한계(devhelp/13)에 적어 두었습니다. 컬럼 이름 변경이나 삭제는 `update`가 해 주지 않으므로, 그런 변경이 생기면 Flyway를 도입하는 것이 다음 단계입니다.

## 엔티티를 응답으로 바로 내보내지 않는다

게임 결과 API는 `GameEntity`를 그대로 돌려주지 않고 `GameResultView` 같은 응답용 객체로 바꿔서 보냅니다(6장 4절). 엔티티에는 `participants`, `ranks` 같은 연관 객체가 있어서, 그대로 JSON으로 바꾸면 지연 로딩 오류가 나거나 필요 없는 데이터까지 나갑니다(13장).

## JPA를 쓰며 실제로 겪은 버그

devhelp/07에 JPA 버그 세 개를 기록했습니다. 13장에서 그중 지연 로딩과 N+1을 다룹니다.

- 메모리 저장소에서는 우연히 동작하던 코드가 JPA로 바꾸자 깨진 것
- 트랜잭션 밖에서 지연 로딩 컬렉션을 읽다가 난 `LazyInitializationException`
- 컬렉션 두 개를 한 번에 fetch join할 때 참가자가 중복으로 들어간 것(그래서 위 코드의 `Set`)

핀볼 게임 백엔드의 관리자 로그인은 세션이 아니라 토큰 방식입니다. 왜 그렇게 했는지가 이번 장의 좋은 비교 예입니다.

## 왜 세션(쿠키)을 쓰지 않았나

화면(Vercel, `lucky-pinball-ai.vercel.app`)과 백엔드(Render, `lucky-pinball-backend.onrender.com`)의 주소가 다릅니다. 이렇게 주소가 다르면 브라우저가 쿠키를 보낼지 말지를 정하는 규칙(`SameSite`, `Secure`, CORS의 credentials 설정)을 모두 맞춰야 해서 복잡합니다. 로컬 개발(http)과 운영(https)에서 동작이 달라지기도 합니다.

그래서 쿠키 대신, 로그인하면 토큰을 돌려주고 화면이 요청마다 헤더에 붙여 보내게 했습니다.

```
POST /api/admin/login   {"username":"admin","password":"..."}
→ {"token":"5f1c..."}

GET /api/admin/players
Authorization: Bearer 5f1c...
```

## 그래도 세션과 닮은 점

토큰 목록은 서버 메모리(`AdminSessionStore`)에 있습니다. 그래서 정리 6절의 세션 한계를 그대로 갖고 있습니다.

| | 이 프로젝트 |
|---|---|
| 서버 재시작 | 토큰이 모두 사라져서 관리자가 다시 로그인해야 함 |
| 서버 여러 대 | 서버마다 토큰 목록이 달라서 동작하지 않음 |

JWT처럼 서명된 토큰을 쓰면 서버가 목록을 들고 있지 않아도 되지만, 대신 발급한 토큰을 바로 무효화하기 어렵습니다. 서버 한 대짜리 프로젝트라 지금 방식으로 충분하다고 판단했습니다.

## 로그인 확인 위치

예제는 인터셉터로 로그인을 확인했지만, 핀볼은 필터(`AdminAuthFilter`)로 확인합니다. 토큰 확인은 어떤 컨트롤러가 처리하는지 알 필요가 없고, 요청 제한 필터와 같은 단계에서 일찍 막는 편이 단순해서입니다(5장 2절의 기준).

```java
// /api/admin/** 중 로그인 주소만 빼고 토큰을 확인한다.
if (!isAdminPath || isPreflight || LOGIN_PATH.equals(path)) {
    chain.doFilter(request, response);
    return;
}
```

`isPreflight`는 브라우저가 실제 요청 전에 보내는 CORS 확인 요청(OPTIONS)입니다. 여기에는 토큰이 없어서 막으면 안 되는데, 처음엔 이것까지 막아서 로그인 직후 모든 관리자 화면이 실패하는 버그가 있었습니다.

## 비밀번호 비교

관리자 비밀번호는 환경변수로 넣고 `String.equals`로 비교합니다. 회원 가입이 없는 관리자 한 명짜리라 해시 저장까지는 하지 않았습니다. 회원이 있는 서비스라면 정리 7절처럼 BCrypt로 저장해야 합니다.

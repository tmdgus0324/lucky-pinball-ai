핀볼 게임 백엔드는 Render에 Docker로 배포되어 있습니다. 로그를 남기고 찾는 방법을 이번 장의 순서대로 봅니다.

## 로그 패턴에 추적 ID만 끼워 넣었다

```yaml
# application.yml
logging:
  pattern:
    level: "%5p [%X{traceId:--------}]"
```

예제처럼 한 줄 전체(`logging.pattern.console`)를 바꾸지 않고, 레벨이 찍히는 부분(`logging.pattern.level`)만 바꿨습니다. 스프링 부트 기본 모양은 그대로 두고 레벨 뒤에 추적 ID만 붙습니다. 실제로 찍힌 로그입니다(앞부분 일부 생략).

```
 INFO [-------] ... [main]            c.luckypinball.LuckyPinballApplication : Started LuckyPinballApplication in 9.873 seconds
 INFO [70c7a377] ... [io-18082-exec-1] com.luckypinball.common.TraceIdFilter  : GET /api/players/reusable -> 200 (308ms)
 WARN [51c3624f] ... [io-18082-exec-2] c.l.common.GlobalExceptionHandler      : GET /api/game/result/no-such -> 404 Game not found: no-such
 INFO [51c3624f] ... [io-18082-exec-2] com.luckypinball.common.TraceIdFilter  : GET /api/game/result/no-such -> 404 (85ms)
```

요청 밖(서버 시작)에서는 `[-------]`가 찍힙니다. 설정의 `:-`가 "값이 없으면 뒤의 글자를 쓴다"는 뜻이라, 대시 8개를 적었어도 하나는 구분자로 쓰여 7개만 나옵니다. 설정 파일 주석에는 8개라고 적혀 있었는데, 이 장을 쓰면서 실제 로그를 보고 알았습니다.

## 화면의 "오류 ID"에서 서버 로그까지

정리 4절의 흐름이 화면까지 이어져 있습니다.

1. `TraceIdFilter`가 요청마다 8자리 ID를 만들어 MDC와 응답 헤더(`X-Trace-Id`)에 넣습니다(5장).
2. 처리 중 예외가 나면 `GlobalExceptionHandler`가 스택 트레이스는 로그에만 남기고, 응답에는 `{"error": ..., "traceId": ...}`만 보냅니다(8장).
3. 프론트는 5xx 오류일 때 메시지 뒤에 `(오류 ID: 3fa2c81d)`를 붙여 보여 줍니다.
4. 사용자가 이 ID를 알려 주면 서버 로그에서 그 ID로 검색해 요청 전체 흐름을 봅니다.

추적 ID는 항상 서버가 새로 만들고, 클라이언트가 보낸 값은 받지 않습니다. 외부 입력을 로그에 그대로 찍으면 줄바꿈을 넣어 가짜 로그 줄을 만들 수 있기 때문입니다. 같은 이유로 요청 로그에 쿼리 문자열은 남기지 않습니다.

## 파일 로그 대신 콘솔 로그

Render 같은 클라우드 플랫폼은 앱이 콘솔(표준 출력)에 쓴 로그를 모아서 웹 화면으로 보여 줍니다. 그래서 핀볼은 `logging.file.name`과 롤링 설정을 두지 않았습니다. 서버에 직접 jar를 올리는 회사 환경이라면 정리 2절처럼 파일과 롤링을 꼭 설정해야 합니다.

## 관리자 화면의 오류 로그는 DB에

플랫폼 로그는 양이 많고 검색이 불편합니다. 그래서 처리되지 않은 예외가 나면 경로, 메시지, 추적 ID를 DB에 따로 저장하고 관리자 화면에서 최근 오류 목록으로 보여 줍니다.

```java
// common/GlobalExceptionHandler.java
log.error("처리되지 않은 예외: {} {}", request.getMethod(), request.getRequestURI(), ex);
errorLogStore.record(request.getRequestURI(), ex.getMessage(), TraceId.current());
```

- 목록에서 오류를 보고, 목록에 있는 추적 ID로 플랫폼 로그를 검색해 스택 트레이스를 봅니다.
- 최근 1000건만 남기고 오래된 것은 저장할 때 함께 지웁니다. 로그 롤링의 `max-history`와 같은 생각입니다.
- 오류 기록이 실패해도 원래 응답을 망치지 않게 따로 트랜잭션을 엽니다(12장의 `REQUIRES_NEW`).

## Actuator는 쓰지 않았다

`/actuator/health` 대신 두 가지로 상태를 봅니다.

| 목적 | 방법 |
|---|---|
| 서버가 살아 있는지, 잠들지 않게 | 외부 스케줄러(cron-job.org)가 공개 주소 `/api/players/reusable`을 주기적으로 호출 |
| AI 연동이 되는지 | 관리자 화면의 "AI 연결 확인" 버튼(14장의 실패 분류 표) |

무료 플랜은 요청이 한동안 없으면 서버가 잠들어 첫 요청이 느립니다. 처음에는 GitHub Actions 스케줄로 깨우려 했지만 실제로는 1~2시간에 한 번꼴로만 실행되어서 전용 스케줄러로 옮겼습니다. Actuator를 붙인다면 `health`만 열고 `loggers`는 정리 5절처럼 외부에 열지 않아야 합니다.

## jar 실행과 인코딩

```dockerfile
# backend/Dockerfile
RUN chmod +x gradlew && ./gradlew --no-daemon bootJar
...
ENTRYPOINT ["java", "-Dfile.encoding=UTF-8", "-jar", "app.jar"]
```

정리 6절의 `bootJar`와 `java -jar` 그대로입니다. `-Dfile.encoding=UTF-8`은 한글 로그가 서버 환경에 따라 깨지지 않게 넣었습니다. 회사 서버의 실행 스크립트에서도 한글 로그가 깨지면 가장 먼저 볼 옵션입니다.

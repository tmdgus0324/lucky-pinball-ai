핀볼 게임 백엔드의 게임 API 컨트롤러입니다.

## GameController

```java
@RestController
public class GameController {

    @PostMapping("/api/game/create")
    @ResponseStatus(HttpStatus.CREATED)            // ResponseEntity 대신 애너테이션으로 201
    public GameCreateResponse create(@Valid @RequestBody GameCreateRequest request) { ... }

    @PostMapping("/api/game/start")
    public GameStartResponse start(@Valid @RequestBody GameIdRequest request) { ... }

    @PostMapping("/api/game/result")
    public GameResultView reportResult(@Valid @RequestBody GameResultRequest request) { ... }

    @GetMapping("/api/game/result/{gameId}")
    public GameResultView getResult(@PathVariable String gameId) { ... }

    // 요청·응답 DTO를 컨트롤러 안에 record로 둠
    public record GameCreateRequest(@NotEmpty List<Long> playerIds) {}
    public record GameIdRequest(@NotNull String gameId) {}
}
```

- 항상 201이면 `ResponseEntity` 대신 `@ResponseStatus(HttpStatus.CREATED)`로 간단히 쓸 수 있습니다.
- 요청·응답 DTO를 컨트롤러 안의 record로 두었습니다. 그 API에서만 쓰는 객체라 가까이 둔 것입니다.
- `@Valid`는 7장에서 봅니다.

## 아쉬운 점: REST 모양이 완전하지 않다

`/api/game/start`, `/api/game/result`는 게임 id를 주소가 아니라 본문에 넣습니다. 정리 1절의 기준으로 보면 이렇게 쓰는 편이 더 REST답습니다.

```
POST /api/games/{gameId}/start
POST /api/games/{gameId}/result
GET  /api/games/{gameId}/result
```

조회(GET)는 주소에 id를 넣고, 시작·결과 보고는 본문에 넣어서 규칙이 섞여 있습니다. 처음 API를 설계할 때 규칙을 먼저 정해 두지 않아서 생긴 일입니다.

핀볼 게임 백엔드에는 테스트가 109개 있고, GitHub에 push할 때마다 GitHub Actions가 모두 실행합니다. 이번 장의 내용이 어떻게 쓰였는지 봅니다.

## push할 때마다 자동 실행

```yaml
# .github/workflows/ci.yml
- name: 테스트 실행
  run: chmod +x ./gradlew && ./gradlew test --console=plain
```

프론트도 같은 파일에서 lint와 빌드를 확인합니다. 하나라도 실패하면 GitHub에 실패 표시가 남습니다.

## Mockito 대신 직접 만든 가짜

핀볼 테스트는 Mockito를 거의 쓰지 않고, 인터페이스를 직접 구현한 가짜를 씁니다. 그리고 예제의 `FridayClockConfig`와 똑같이 `@TestConfiguration` + `@Primary`로 진짜 Claude 호출 빈 대신 끼웁니다.

```java
// ApiFlowIntegrationTest.java
static class CountingFortuneService implements FortuneService {
    final AtomicInteger calls = new AtomicInteger();   // 몇 번 불렸는지
    volatile long delayMillis = 0;                     // 일부러 느리게

    @Override
    public FortuneResult analyze(String name, LocalDate birthDate) {
        calls.incrementAndGet();
        ...
        return new FortuneResult(77, 7, "테스트 운세");
    }
}

@TestConfiguration
static class FakeAiConfig {
    @Bean
    @Primary
    CountingFortuneService countingFortuneService() { return new CountingFortuneService(); }
}
```

직접 만든 이유는 확인하고 싶은 것이 "몇 번 불렸나"와 "느릴 때 어떻게 되나"였기 때문입니다. 같은 사람(이름+생년월일)의 요청 4건이 동시에 와도 Claude를 한 번만 부르는지(`calls`가 1인지) 확인하려면, 가짜가 일부러 늦게(0.4초) 응답해야 요청들이 겹칩니다. Mockito로도 할 수 있지만 이렇게 만드는 편이 읽기 쉬웠습니다.

Mockito는 "DB 저장이 실패하는 저장소"를 만들 때 한 곳(`ErrorLogStoreTest`)에서만 썼습니다. 오류 기록이 실패해도 원래 응답을 망치지 않는지 확인하는 테스트입니다.

## 진짜 Claude는 테스트에서 부르지 않는다

Claude 호출은 비용이 들어서, 테스트에서 실제 API를 부르지 않는 것을 규칙(`CLAUDE.md`)으로 정했습니다. 대신 세 가지를 씁니다.

| 가짜 | 쓰는 곳 |
|---|---|
| 규칙으로 점수를 만드는 `MockFortuneGenerator` | 점수 계산 단위 테스트 |
| 위의 `CountingFortuneService` 같은 가짜 구현 | 스프링을 띄우는 테스트 |
| JDK `HttpServer`로 띄운 가짜 Claude 서버 | 시간 초과, 401, 429, 500 같은 실패 처리(14장) |

## 테스트 종류별 예

| 종류 | 핀볼 테스트 | 확인하는 것 |
|---|---|---|
| 단위 | `BuffCalculatorTest` | 점수 차이로 시작 높이를 계산하는 규칙 |
| 단위(필터) | `TraceIdFilterTest` | `MockHttpServletRequest`로 필터만 실행해서 추적 ID가 붙고 지워지는지(15장) |
| 통합 | `FortuneQueryServiceTest` | Claude 실패 시 임시 점수로 대체하고, 그것을 캐시에 넣지 않는지(메모리 H2) |
| 통합(실제 포트) | `ApiFlowIntegrationTest` | `RANDOM_PORT`로 띄워서 필터 → 컨트롤러 → 예외 처리 → DB까지 실제 HTTP로 |
| 통합(쿼리 수) | `PlayerListQueryCountTest` | 참가자가 늘어도 쿼리 수가 같은지(13장의 N+1) |

## 환경에 따라 건너뛰는 테스트

"API 키가 없을 때 어떻게 되나"를 확인하는 테스트는 개발자 PC에 키 환경변수가 있으면 만들 수 없는 상황입니다. 그래서 키가 있으면 건너뛰게 했습니다.

```java
// 개발자 PC에 키 환경변수가 있으면 이 상황을 만들 수 없다(CI에서는 실행된다).
Assumptions.assumeTrue(System.getenv("ANTHROPIC_API_KEY") == null && System.getenv("ANTHROPIC_AUTH_TOKEN") == null);
```

`assumeTrue`가 거짓이면 실패가 아니라 "건너뜀(skipped)"이 됩니다. 그래서 마무리 점검 때는 키가 있는 조건과 없는 조건(CI와 같음) 둘 다로 돌렸습니다.

## 테스트를 만들다가 찾은 버그

- 오류 로그를 1000건만 남기는 삭제 쿼리가 실제로는 아무것도 지우지 않고 있었습니다. 정리가 되는지 확인하는 테스트를 만들다가 발견했습니다(12장).
- 오래 쉬었던 연결을 다시 쓰다가 끊기면 "연결 불가"로 잘못 보여 주던 것을 가짜 Claude 서버 테스트로 찾았습니다(14장).

둘 다 화면에서 눌러 보는 것만으로는 찾기 어려운 버그였습니다.

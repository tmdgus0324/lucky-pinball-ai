핀볼 게임 백엔드에서 N+1을 두 번 만났고, 서로 다른 방법으로 풀었습니다.

## 1) 게임 목록: fetch join

게임 하나에 참가자와 순위가 여러 개 있습니다(`@OneToMany` 두 개). 관리자 화면에서 게임 목록을 그냥 조회하면 게임마다 참가자 조회, 순위 조회가 따로 나갑니다.

```java
// game/GameJpaRepository.java
/**
 * findAll()만 쓰면 게임이 N개일 때 participants/ranks를 LAZY로 따로 불러오느라 쿼리가
 * N번(참가자) + N번(순위) 더 나가는 전형적인 N+1이 생긴다 — fetch join으로 한 번에 가져온다.
 */
@Query("SELECT DISTINCT g FROM GameEntity g LEFT JOIN FETCH g.participants LEFT JOIN FETCH g.ranks")
List<GameEntity> findAllWithDetails();
```

정리 4절 마지막의 "컬렉션 두 개를 한 번에 fetch join하면 중복이 생긴다"를 실제로 겪었습니다. 처음에 두 컬렉션이 `List`였을 때 참가자가 중복으로 들어갔고, `Set`으로 바꿔 해결했습니다(11장 이 프로젝트에서는).

## 2) 참가자 목록: 따로 조회해서 묶기

참가자와 운세 이력은 JPA 연관관계 없이 `player_id` 숫자로만 연결되어 있습니다. 그래서 fetch join을 쓸 수 없었고, 참가자마다 이력을 조회하는 N+1이 있었습니다.

해결은 "이력을 한 번에 다 읽어서 메모리에서 참가자별로 묶기"였습니다.

```java
// fortune/FortuneResultJpaRepository.java
default Map<Long, List<FortuneResultEntity>> findAllGroupedByPlayerId() {
    return findAllByOrderByCreatedDateAscIdAsc().stream()
            .filter(result -> result.getPlayerId() != null)
            .collect(Collectors.groupingBy(FortuneResultEntity::getPlayerId));
}
```

`groupingBy`는 18장(람다와 Stream)에서 다시 봅니다.

## 고치기 전에 숫자로 확인

두 번째 N+1은 고치기 전에 테스트로 먼저 재현했습니다. Hibernate가 실행한 SQL 수를 세는 테스트(`PlayerListQueryCountTest`)로, 참가자가 10명 늘면 쿼리도 10개 늘어나는 것(3 → 13)을 확인한 뒤 고쳤고, 고친 뒤에는 참가자 수와 상관없이 쿼리 수가 같아졌습니다.

```java
@SpringBootTest(properties = "spring.jpa.properties.hibernate.generate_statistics=true")
class PlayerListQueryCountTest {
    // 참가자 2명일 때와 12명일 때 실행된 SQL 수가 같아야 한다
}
```

"느려진 것 같다"가 아니라 "쿼리가 N개 나간다"로 확인하는 것이 운영에서 성능 문제를 설명할 때 가장 설득력 있습니다.

## 지연 로딩 오류를 피한 방법

게임 조회는 서비스(저장소) 안의 `@Transactional(readOnly = true)` 범위에서 엔티티를 응답용 객체로 바꿉니다(12장 이 프로젝트에서는). `open-in-view`는 `false`로 꺼 두었습니다.

요청 하나가 서버에 들어와서 컨트롤러까지 가는 길을 봅니다. 운영에서 "API가 안 된다"는 문의를 받으면, 요청이 이 길의 어디까지 왔고 어디서 막혔는지를 찾는 것이 첫 일입니다.

## 1. 전체 길

```
브라우저
  → 톰캣
  → 필터들            (서블릿 단계: 인코딩, 로그, 인증, 요청 제한)
  → DispatcherServlet (스프링 MVC의 입구)
      → HandlerMapping:  이 주소·메서드를 처리할 컨트롤러 찾기
      → 인터셉터 preHandle
      → 컨트롤러 메서드 실행 (요청 값 바인딩, 검증)
      → 인터셉터 postHandle
      → 응답 만들기 (객체 → JSON, 또는 화면 템플릿)
      → 인터셉터 afterCompletion
  → 필터들 (돌아가는 길)
  → 브라우저
```

DispatcherServlet은 모든 요청을 받는 입구 하나입니다(프론트 컨트롤러 패턴). 직접 일을 하지 않고 역할별 부품에 맡깁니다.

| 부품 | 하는 일 |
|---|---|
| HandlerMapping | 요청을 처리할 컨트롤러 메서드를 찾는다 |
| HandlerAdapter | 찾은 메서드를 실제로 호출한다 |
| HandlerExceptionResolver | 처리 중 난 예외를 응답으로 바꾼다(8장) |
| ViewResolver | 화면 이름을 실제 템플릿으로 바꾼다(16장) |

JSP 시절 `web.xml`에 서블릿과 URL을 하나씩 등록하던 일을, 지금은 DispatcherServlet 하나가 받아서 `@GetMapping` 같은 애너테이션으로 나눠 줍니다. 2장 실행 결과의 `Initializing Servlet 'dispatcherServlet'` 로그가 이 입구가 준비되는 순간입니다.

## 2. 필터와 인터셉터

둘 다 "컨트롤러 앞뒤에 끼워 넣는 공통 처리"인데, 실행되는 단계가 다릅니다.

| | 필터 | 인터셉터 |
|---|---|---|
| 소속 | 서블릿(톰캣) | 스프링 MVC |
| 위치 | DispatcherServlet 앞 | DispatcherServlet 안, 컨트롤러 앞뒤 |
| 어떤 컨트롤러가 처리할지 | 모름 | 앎(`handler`) |
| 등록 | `Filter` 빈이면 자동(`/*`) | `WebMvcConfigurer`에서 주소와 함께 등록 |
| 막는 방법 | `chain.doFilter`를 부르지 않고 응답 | `preHandle`에서 `false` |
| 자주 쓰는 곳 | 인코딩, 요청 로그, 추적 ID, 인증 토큰, 요청 제한 | 로그인 확인(9장), 권한 확인, 실행 시간 측정 |

정하기 어려우면 이렇게 고릅니다. 스프링이 컨트롤러를 찾기 전에, 모든 요청에 해야 하는 일이면 필터를 씁니다. 특정 주소의 컨트롤러 앞뒤에서 해야 하는 일이면 인터셉터를 씁니다.

## 3. 실행 결과로 보는 다섯 가지 경우

코드 탭의 실행 결과를 보면 경우마다 로그가 어디까지 찍히는지 다릅니다.

| 경우 | 응답 | 마지막으로 찍힌 곳 |
|---|---|---|
| 정상 | 200 | 필터 "요청 끝"까지 전부 |
| 컨트롤러에서 예외 | 500 | 인터셉터 afterCompletion. postHandle과 필터 "요청 끝"은 안 찍힘 |
| 없는 주소 | 404 | 컨트롤러 대신 정적 파일 처리기(`ResourceHttpRequestHandler`)가 받음 |
| 필터가 막음 | 503 | 필터. 인터셉터·컨트롤러 로그 없음 |
| 지원하지 않는 메서드 | 405 | 필터. 컨트롤러를 찾는 단계에서 막혀서 인터셉터도 안 찍힘 |

두 가지를 기억하세요.

- 예외가 나면 필터의 `chain.doFilter()` 다음 줄이 실행되지 않습니다. 필터에서 뒷정리(로그 마무리, 값 지우기)를 해야 하면 `try { chain.doFilter(...) } finally { ... }`로 감쌉니다.
- 404와 405는 컨트롤러 코드에 로그를 아무리 넣어도 찍히지 않습니다. 주소 오타, HTTP 메서드(GET/POST) 불일치를 먼저 의심합니다.

## 4. "어디서 막혔나" 찾는 순서

| 확인할 것 | 보이는 증상 | 의심할 곳 |
|---|---|---|
| 요청이 서버에 왔나 | 서버 로그에 아무것도 없음 | 주소·포트, 방화벽, 앞단 프록시(L4, Nginx) |
| 필터에서 막혔나 | 401, 403, 429, 503 | 인증·요청 제한 필터 |
| 컨트롤러를 찾았나 | 404, 405 | 주소 오타, HTTP 메서드, 컨트롤러 패키지 위치 |
| 인터셉터에서 막혔나 | 로그인 페이지로 이동, 401 | 로그인·권한 인터셉터 |
| 요청 값을 읽었나 | 400 | JSON 형식, 타입, 검증 규칙(6~7장) |
| 처리 중 예외인가 | 500 | 서버 로그의 스택 트레이스 |

## 5. 스택 트레이스 읽기

500 오류가 나면 서버 로그에 스택 트레이스가 남습니다. 수십 줄이지만 다 읽을 필요는 없습니다.

1. 맨 위의 예외 종류와 메시지를 봅니다: `java.lang.IllegalStateException: 객실 정보를 읽지 못했습니다`
2. `at ...` 줄 중 우리 패키지(`com.example...`)로 시작하는 첫 줄을 찾습니다: `at com.example.reservation.RoomController.broken(RoomController.java:24)`
3. 그 파일의 그 줄 번호로 갑니다.

`Caused by:`가 있으면 맨 아래 `Caused by:`가 진짜 원인인 경우가 많습니다. 예를 들어 DB 오류는 스프링 예외에 감싸여 올라오기 때문에, 아래쪽 `Caused by:`에서 실제 SQL 오류를 찾습니다.

## 확인 문제

1. 모든 요청에 추적 ID를 붙이는 일과, `/reservations/**`에서만 로그인을 확인하는 일은 각각 필터와 인터셉터 중 어디가 알맞나요?
2. 컨트롤러에서 예외가 났을 때 실행되지 않는 인터셉터 메서드는 무엇인가요?
3. API를 호출하면 405가 납니다. 컨트롤러에 로그를 넣었는데 아무것도 찍히지 않습니다. 무엇을 의심해야 하나요?
4. 필터에서 요청 처리 시간을 로그로 남기는데, 예외가 난 요청은 시간이 찍히지 않습니다. 어떻게 고치나요?
5. 스택 트레이스에서 가장 먼저 찾아야 할 줄은 무엇인가요?

## 정답

1. 추적 ID는 모든 요청에 적용하므로 필터, 특정 주소의 로그인 확인은 인터셉터가 알맞습니다.
2. `postHandle`. `afterCompletion`은 예외가 나도 실행되고 예외 객체를 받습니다.
3. HTTP 메서드가 맞지 않는 것입니다(예: GET으로 만든 주소에 POST). 컨트롤러를 찾는 단계에서 막혀서 컨트롤러가 실행되지 않습니다.
4. `chain.doFilter()`를 `try`로 감싸고, 시간 기록을 `finally`에 둡니다.
5. 맨 위 예외 메시지, 그리고 `at` 줄 중 우리 패키지로 시작하는 첫 줄입니다.

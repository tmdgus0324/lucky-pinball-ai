스프링의 가장 기본 개념인 IoC와 DI, 그리고 Bean을 봅니다. 예제는 1장의 컨트롤러를 컨트롤러·서비스·저장소 세 층으로 나눕니다.

## 1. 직접 new 하지 않는다 (IoC)

스프링을 쓰기 전에는 필요한 객체를 직접 만들었습니다.

```java
public class RoomController {
    private final RoomService roomService = new RoomService(new RoomRepository());
}
```

이렇게 하면 `RoomController`가 `RoomService`를 어떻게 만드는지까지 알아야 합니다. 저장소를 DB용으로 바꾸려면 컨트롤러 코드도 고쳐야 합니다.

스프링은 객체를 대신 만들고, 필요한 곳에 넣어 줍니다. 객체를 만드는 주도권이 개발자에서 스프링으로 넘어갔다고 해서 이것을 IoC(Inversion of Control, 제어의 역전)라고 부릅니다. 스프링이 만들어 관리하는 객체를 **빈(Bean)**, 빈을 보관하는 곳을 **스프링 컨테이너**라고 합니다.

## 2. 빈 등록: @Component 계열

클래스에 아래 애너테이션을 붙이면 컴포넌트 스캔(1장)이 찾아서 빈으로 등록합니다.

| 애너테이션 | 쓰는 곳 |
|---|---|
| `@Component` | 일반 빈 |
| `@Controller`, `@RestController` | 웹 요청을 받는 클래스 |
| `@Service` | 업무 규칙을 담는 클래스 |
| `@Repository` | 데이터를 저장·조회하는 클래스 |
| `@Configuration` | `@Bean` 메서드를 담는 설정 클래스 |

`@Service`, `@Repository`는 기능상 `@Component`와 거의 같습니다. 이름으로 역할을 나타내는 것이 주목적입니다. (`@Repository`는 DB 예외를 스프링 예외로 바꿔 주는 기능이 더 있습니다.)

## 3. 의존성 주입 (DI)

빈이 다른 빈을 필요로 할 때 스프링이 넣어 주는 것을 DI(Dependency Injection, 의존성 주입)라고 합니다. 방법은 세 가지지만, 생성자 주입을 씁니다.

```java
@Service
public class RoomService {
    private final RoomRepository roomRepository;

    public RoomService(RoomRepository roomRepository) {   // 생성자가 하나면 @Autowired 생략 가능
        this.roomRepository = roomRepository;
    }
}
```

| 방식 | 모양 | 판단 |
|---|---|---|
| 생성자 주입 | 생성자 파라미터로 받음 | 권장. `final`로 둘 수 있고, 테스트에서 직접 넣기 쉽다 |
| 필드 주입 | 필드에 `@Autowired` | 레거시 코드에 많다. 테스트할 때 넣기 어렵다 |
| setter 주입 | setter에 `@Autowired` | 바꿀 수 있어야 하는 드문 경우에만 |

운영 중인 레거시 코드에서는 필드 주입(`@Autowired private RoomService roomService;`)을 많이 보게 됩니다. 동작은 같으니 읽을 수 있으면 되고, 새로 짤 때는 생성자 주입을 씁니다.

## 4. @Bean: 남이 만든 클래스 등록하기

`java.time.Clock`처럼 우리가 만든 클래스가 아니면 `@Component`를 붙일 수 없습니다. 이럴 때는 `@Configuration` 클래스에 `@Bean` 메서드를 만듭니다.

```java
@Configuration
public class AppConfig {
    @Bean
    public Clock clock() {
        return Clock.systemDefaultZone();
    }
}
```

`RoomService`가 `LocalDate.now()` 대신 주입받은 `Clock`으로 날짜를 구하는 이유는 테스트 때문입니다. 테스트에서 "금요일로 고정된 Clock"을 넣으면 주말 가격 로직을 언제든 확인할 수 있습니다(17장).

## 5. 싱글톤과 생명주기

빈은 기본적으로 하나만 만들어집니다(싱글톤). 요청이 1000번 와도 `RoomService` 객체는 하나입니다. 그래서 빈에 요청마다 바뀌는 값을 필드로 두면 안 됩니다. 여러 요청이 같은 필드를 동시에 고치게 됩니다.

```java
@Service
public class BadService {
    private String currentUser;   // 위험: 모든 요청이 이 필드 하나를 같이 쓴다
}
```

빈의 생명주기는 이렇습니다.

1. 객체 생성(생성자 실행)
2. 의존성 주입
3. `@PostConstruct` 메서드 실행: 초기 데이터 준비 등
4. 사용
5. 서버 종료 때 `@PreDestroy` 메서드 실행: 연결 정리 등

필요한 빈부터 먼저 만들기 때문에, 실행 결과 로그에서 `RoomRepository`가 `RoomService`보다 먼저 준비됩니다.

## 6. 빈을 못 찾을 때

주입받을 빈이 없으면 서버가 아예 뜨지 않습니다. 실행 결과 맨 아래처럼 어떤 클래스의 몇 번째 파라미터에 무엇이 없는지 알려 줍니다.

```
Parameter 1 of constructor in com.example.reservation.room.RoomService
required a bean of type 'java.time.Clock' that could not be found.
```

이 메시지를 보면 확인할 것:

- 그 클래스에 `@Component` 계열 애너테이션이 붙어 있나
- main 클래스 패키지 아래에 있나(컴포넌트 스캔 범위)
- 남이 만든 클래스라면 `@Bean`으로 등록했나

같은 타입의 빈이 두 개면 `required a single bean, but 2 were found` 오류가 납니다. 이때는 하나에 `@Primary`를 붙이거나, 주입받는 쪽에 `@Qualifier("빈 이름")`을 붙입니다.

## 확인 문제

1. IoC와 DI를 각각 한 문장으로 설명해 보세요.
2. 생성자 주입을 권장하는 이유 두 가지는 무엇인가요?
3. `@Service` 클래스에 `private int count;` 필드를 두고 요청마다 `count++` 하면 어떤 문제가 생기나요?
4. `java.time.Clock`을 빈으로 쓰려면 어떻게 등록하나요?
5. 서버가 `required a bean of type ... that could not be found`로 뜨지 않습니다. 먼저 확인할 것 두 가지는?

## 정답

1. IoC는 객체를 만들고 연결하는 주도권을 스프링이 갖는 것이고, DI는 필요한 객체(의존성)를 스프링이 넣어 주는 것입니다.
2. 필드를 `final`로 둘 수 있어서 바뀌지 않음이 보장되고, 테스트에서 생성자로 가짜 객체를 바로 넣을 수 있습니다.
3. 빈은 하나(싱글톤)라서 모든 요청이 같은 `count`를 같이 고칩니다. 동시에 요청이 오면 값이 꼬입니다.
4. `@Configuration` 클래스에 `Clock`을 돌려주는 `@Bean` 메서드를 만듭니다.
5. 그 클래스에 `@Component` 계열 애너테이션이 있는지, 그리고 main 클래스 패키지 아래에 있는지입니다.

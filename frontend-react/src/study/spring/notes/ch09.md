레거시 웹 시스템의 로그인은 대부분 세션 방식입니다. 쿠키와 세션이 어떻게 함께 동작하는지, 그리고 로그인 확인을 인터셉터로 어떻게 하는지 봅니다. 실무에서는 Spring Security를 쓰는 경우가 많지만, 그 안에서도 원리는 같습니다.

## 1. HTTP는 이전 요청을 기억하지 못한다

HTTP 요청은 하나하나가 따로입니다. 서버는 "방금 로그인한 그 사람"이 다음 요청을 보냈는지 스스로 알 수 없습니다. 그래서 브라우저가 요청마다 "나는 누구다"라는 표시를 같이 보내야 하고, 그 표시가 쿠키입니다.

## 2. 쿠키와 세션

| | 쿠키 | 세션 |
|---|---|---|
| 저장 위치 | 브라우저 | 서버(톰캣 메모리) |
| 내용 | 짧은 글자(세션 ID 등) | 로그인 정보 같은 객체 |
| 주고받기 | 서버가 `Set-Cookie`로 주고, 브라우저가 요청마다 `Cookie`로 보냄 | 주고받지 않음. 서버 안에만 있음 |

둘을 같이 쓰는 흐름은 이렇습니다.

1. 로그인에 성공하면 서버가 세션을 만들고 로그인 정보를 넣습니다: `session.setAttribute("LOGIN_MEMBER", member)`
2. 톰캣이 세션 ID를 `JSESSIONID` 쿠키로 보냅니다(실행 결과 4).
3. 브라우저는 이후 요청마다 이 쿠키를 자동으로 붙입니다.
4. 서버는 쿠키의 세션 ID로 세션을 찾아 로그인 정보를 꺼냅니다(실행 결과 5).
5. 로그아웃하면 `session.invalidate()`로 서버의 세션을 지웁니다. 브라우저에 쿠키가 남아 있어도 그 ID의 세션이 없으므로 로그인이 풀립니다(실행 결과 7).

쿠키에 회원 번호나 이름을 직접 넣지 않는 이유가 여기 있습니다. 쿠키는 사용자가 마음대로 고칠 수 있습니다. 세션 ID는 길고 무작위라 추측하기 어렵고, 실제 정보는 서버에만 있습니다.

## 3. 세션 다루기

```java
HttpSession session = request.getSession();        // 없으면 만든다(로그인할 때)
HttpSession session = request.getSession(false);   // 없으면 null(확인만 할 때)

session.setAttribute("LOGIN_MEMBER", member);      // 넣기
session.getAttribute("LOGIN_MEMBER");              // 꺼내기
session.invalidate();                              // 지우기(로그아웃)
```

로그인 확인 코드에서 `getSession()`(인자 없음)을 쓰면, 로그인하지 않은 사람이 요청할 때마다 빈 세션이 만들어집니다. 서버 메모리가 낭비되니 확인할 때는 `getSession(false)`를 씁니다.

컨트롤러에서는 `@SessionAttribute("LOGIN_MEMBER") LoginMember member`로 바로 꺼내 쓸 수 있습니다.

## 4. 로그인 확인은 인터셉터로

컨트롤러마다 "로그인했나?"를 확인하면 빠뜨리는 곳이 생깁니다. 5장의 인터셉터로 한곳에서 확인합니다.

```java
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    HttpSession session = request.getSession(false);
    if (session == null || session.getAttribute(LoginMember.SESSION_KEY) == null) {
        response.setStatus(401);          // 화면이라면 response.sendRedirect("/login")
        return false;
    }
    return true;
}
```

```java
registry.addInterceptor(loginCheckInterceptor)
        .addPathPatterns("/reservations/**")
        .excludePathPatterns("/reservations/public");
```

로그인 화면, 정적 파일(css, js, 이미지), 오류 페이지를 제외 목록에 넣지 않으면, 로그인 화면조차 로그인을 요구하는 무한 이동이 생깁니다.

## 5. 세션 설정

```yaml
server:
  servlet:
    session:
      timeout: 30m              # 30분 동안 요청이 없으면 세션 삭제
      tracking-modes: cookie    # 세션 ID를 주소(;jsessionid=)에 붙이지 않음
      cookie:
        http-only: true         # 자바스크립트로 쿠키를 읽지 못하게
        same-site: lax          # 다른 사이트에서 보낸 요청엔 쿠키를 안 붙임
```

`tracking-modes: cookie`가 없으면, 쿠키를 못 쓰는 상황에서 톰캣이 세션 ID를 주소 뒤에 `;jsessionid=...`로 붙입니다. 이 주소가 로그나 공유된 링크로 새면 다른 사람이 로그인 상태를 가로챌 수 있습니다. 레거시 시스템 주소에서 이 글자를 본 적이 있다면 이 설정이 없었던 것입니다.

## 6. 세션 방식의 한계와 토큰 방식

세션은 서버 메모리에 있습니다. 서버가 두 대 이상이면 문제가 생깁니다. 1번 서버에서 로그인했는데 다음 요청이 2번 서버로 가면, 2번 서버에는 그 세션이 없습니다.

| 해결 방법 | 내용 |
|---|---|
| 스티키 세션 | 앞단 장비(L4, 로드밸런서)가 같은 사용자를 항상 같은 서버로 보냄 |
| 세션 저장소 공유 | 세션을 Redis·DB에 저장(Spring Session) |
| 토큰 방식 | 서버가 세션을 들고 있지 않고, 요청마다 토큰을 보내 확인(핀볼 예제, JWT) |

서버를 재시작해도 세션이 사라집니다. 배포할 때 사용자가 모두 로그아웃되는 것이 이 때문입니다.

## 7. 비밀번호 저장

예제는 비밀번호를 그대로 비교하지만, 실제로는 절대 그렇게 하지 않습니다. 비밀번호는 BCrypt 같은 단방향 해시로 바꿔 저장하고, 로그인할 때 입력값을 같은 방식으로 해시해서 비교합니다. DB가 유출돼도 원래 비밀번호를 알 수 없게 하기 위해서입니다. Spring Security의 `BCryptPasswordEncoder`가 이 일을 합니다.

## 확인 문제

1. 로그인 정보를 쿠키에 직접 넣지 않고 세션에 넣는 이유는?
2. 로그아웃할 때 브라우저의 쿠키를 지우지 않아도 로그인이 풀리는 이유는?
3. 로그인 확인 코드에서 `request.getSession()` 대신 `getSession(false)`를 쓰는 이유는?
4. 서버를 두 대로 늘렸더니 로그인이 자꾸 풀립니다. 원인과 해결 방법 하나는?
5. 레거시 시스템 주소에 `;jsessionid=8F3A...`가 붙어 있습니다. 어떤 위험이 있고 어떻게 막나요?

## 정답

1. 쿠키는 사용자가 고칠 수 있어서, 회원 번호 같은 값을 넣으면 다른 사람으로 바꿔치기할 수 있습니다. 세션에는 서버만 접근합니다.
2. `session.invalidate()`로 서버의 세션을 지웠기 때문입니다. 쿠키의 세션 ID로 찾을 세션이 없습니다.
3. `getSession()`은 세션이 없으면 새로 만들어서, 로그인하지 않은 요청마다 빈 세션이 쌓입니다.
4. 세션이 각 서버 메모리에만 있어서, 다른 서버로 간 요청은 세션을 찾지 못합니다. 스티키 세션이나 Redis 세션 공유, 토큰 방식으로 해결합니다.
5. 세션 ID가 주소에 노출되어 로그나 링크 공유로 새면 로그인 상태를 가로챌 수 있습니다. `server.servlet.session.tracking-modes: cookie`로 쿠키만 쓰게 합니다.

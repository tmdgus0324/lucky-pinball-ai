잘못된 입력을 컨트롤러 코드에 if문을 늘어놓지 않고 막는 방법을 봅니다. 화면에서 검사했더라도 서버에서 다시 검사해야 합니다. API는 화면을 거치지 않고도 호출할 수 있기 때문입니다.

## 1. 준비

`build.gradle`에 검증 starter를 추가합니다. Spring Boot 4의 웹 starter에는 검증이 들어 있지 않습니다.

```gradle
implementation 'org.springframework.boot:spring-boot-starter-validation'
```

## 2. 규칙 붙이기

요청 객체의 필드에 규칙 애너테이션을 붙이고, 컨트롤러 파라미터에 `@Valid`를 붙입니다.

```java
public record CreateReservationRequest(
        @NotNull Long roomId,
        @NotBlank(message = "예약자 이름을 입력해 주세요") @Size(max = 20) String guestName,
        @NotNull @FutureOrPresent LocalDate checkIn,
        @Min(1) @Max(14) int nights) {}

@PostMapping
public ResponseEntity<String> create(@Valid @RequestBody CreateReservationRequest request) { ... }
```

`@Valid`를 빠뜨리면 규칙을 붙여 놓아도 검사하지 않습니다. 가장 흔한 실수입니다.

## 3. 자주 쓰는 규칙

| 애너테이션 | 뜻 | 주의 |
|---|---|---|
| `@NotNull` | null 금지 | 빈 문자열 `""`은 통과 |
| `@NotEmpty` | null, 빈 값 금지 | 문자열, 목록에 씀. `" "`(공백)은 통과 |
| `@NotBlank` | null, 빈 값, 공백만 있는 값 금지 | 문자열 전용. 이름 같은 값에 가장 알맞다 |
| `@Size(min, max)` | 길이·개수 범위 | null은 검사하지 않음 |
| `@Min`, `@Max`, `@Positive` | 숫자 범위 | |
| `@Email`, `@Pattern(regexp)` | 형식 | null은 검사하지 않음 |
| `@Past`, `@Future`, `@FutureOrPresent` | 날짜가 과거·미래 | 생년월일, 체크인 날짜 |

`@Size`, `@Email` 같은 규칙은 값이 null이면 통과시킵니다. 필수 값이면 `@NotNull`이나 `@NotBlank`를 같이 붙입니다.

## 4. 검증에 실패하면

`@Valid`만 붙인 경우 컨트롤러 메서드는 실행되지 않고, 스프링이 `MethodArgumentNotValidException`을 내고 400으로 응답합니다(실행 결과 1). 응답에는 이유가 없고 서버 로그에만 남습니다.

이유를 응답에 담는 방법은 두 가지입니다.

| 방법 | 모양 | 판단 |
|---|---|---|
| 메서드마다 `BindingResult` 받기 | `@Valid` 바로 뒤에 `BindingResult` 파라미터 | 실행 결과 2. 메서드마다 같은 코드가 반복된다 |
| 한곳에서 처리 | `@RestControllerAdvice`에서 예외를 잡음 | 8장. 보통 이 방법을 쓴다 |

`BindingResult`는 반드시 `@Valid` 파라미터 바로 뒤에 둬야 합니다. 그래야 스프링이 400을 대신 응답하지 않고 결과를 넘겨줍니다.

## 5. 오류 문구와 언어

`message`를 주지 않으면 검증 라이브러리의 기본 문구를 씁니다. 기본 문구는 요청의 언어(`Accept-Language` 헤더)나 서버 기본 언어에 따라 바뀝니다. 실행 결과 3처럼 같은 요청도 영어 문구가 나올 수 있습니다. 직접 쓴 `message`는 항상 그대로입니다.

화면에 그대로 보여 줄 문구라면 `message`를 직접 적는 편이 안전합니다. 개발 PC(한국어 윈도우)에서는 한국어로 보이다가 운영 서버(영어 리눅스)에서 영어로 바뀌는 일이 생깁니다.

## 6. 주소·쿼리 값 검증

`@PathVariable`, `@RequestParam`에도 규칙을 붙일 수 있습니다.

```java
@GetMapping("/{id}")
public String get(@PathVariable @Positive Long id) { ... }
```

이때는 `HandlerMethodValidationException`이 나고 400으로 응답합니다. 그런데 이 경우 기본 로그 레벨에서는 서버 로그에 아무것도 남지 않습니다(실행 결과 4). 운영에서 "400이 나는데 로그가 없다"면 이런 경우일 수 있습니다. 8장처럼 예외를 직접 잡아서 로그를 남기면 해결됩니다.

## 7. 검증은 어디까지

`@Valid`는 "형식"을 검사합니다. "업무 규칙"은 서비스에서 검사합니다.

| 종류 | 예 | 어디서 |
|---|---|---|
| 형식 | 이름이 비었나, 박수가 1~14인가 | 요청 객체 + `@Valid` |
| 업무 규칙 | 그 날짜에 객실이 비었나, 회원 등급이 예약 가능한가 | 서비스(DB 조회 필요) |

업무 규칙 위반은 서비스에서 예외를 던지고 8장의 방법으로 409 같은 응답을 만듭니다.

## 확인 문제

1. `@NotNull`, `@NotEmpty`, `@NotBlank`에 각각 `" "`(공백 한 칸)을 넣으면 통과하나요?
2. 요청 객체에 규칙을 다 붙였는데 잘못된 값이 그대로 들어옵니다. 무엇을 빠뜨렸을까요?
3. `@Email String email`에 값을 안 보내면(null) 어떻게 되나요?
4. 개발 PC에서는 "널이어서는 안됩니다"로 보이던 오류 문구가 운영에서는 "must not be null"로 보입니다. 이유와 해결은?
5. "같은 날짜에 같은 객실이 이미 예약됐으면 거절"은 `@Valid`로 검사할 수 있나요?

## 정답

1. `@NotNull` 통과, `@NotEmpty` 통과, `@NotBlank`만 실패합니다.
2. 컨트롤러 파라미터의 `@Valid`입니다.
3. 통과합니다. `@Email`은 null을 검사하지 않습니다. 필수라면 `@NotBlank`를 같이 붙입니다.
4. 기본 문구가 서버 언어(또는 요청 언어)를 따르기 때문입니다. `message`를 직접 적으면 언어와 상관없이 같은 문구가 나옵니다.
5. 없습니다. DB를 조회해야 하는 업무 규칙이라 서비스에서 검사하고 예외를 던집니다.

예약 시스템은 결제(PG), 객실 관리(PMS), 알림톡 같은 외부 시스템을 많이 부릅니다. 이번 장은 RestClient로 다른 서버를 호출하고, 상대 서버가 느리거나 죽었을 때 우리 서버가 같이 멈추지 않게 하는 방법을 봅니다. 연동 장애는 운영에서 가장 자주 만나는 장애입니다.

## 1. HTTP 클라이언트 종류

| 이름 | 상태 | 비고 |
|---|---|---|
| `RestTemplate` | 레거시 코드에 가장 많음 | Spring 팀이 RestClient로 대체하겠다고 밝혔고, 최신 문서에는 deprecated로 표시됨 |
| `RestClient` | Spring 6.1부터, 새 코드는 이것 | 이번 장에서 씀 |
| `WebClient` | 비동기(WebFlux) | 비동기·스트리밍이 필요할 때 |
| `@HttpExchange` 인터페이스 | 인터페이스만 만들면 구현체를 만들어 줌 | MyBatis Mapper처럼 선언만 하는 방식 |

레거시에서 `RestTemplate`을 보면 같은 개념(주소, 메서드, 본문, 응답 타입)이라 읽을 수 있습니다. 새로 만들 때는 `RestClient`를 씁니다.

## 2. RestClient 기본

```java
RestClient restClient = RestClient.builder()
        .baseUrl("https://pg.example.com")
        .requestFactory(factory)              // 타임아웃 설정(4절)
        .build();

PayResponse response = restClient.post()
        .uri("/pay")
        .contentType(MediaType.APPLICATION_JSON)
        .body(request)                        // 객체 → JSON
        .retrieve()
        .body(PayResponse.class);             // JSON → 객체
```

상태 코드나 헤더가 필요하면 `.body(...)` 대신 `.toEntity(PayResponse.class)`로 `ResponseEntity`를 받습니다.

## 3. 실패를 종류별로 나누기

외부 호출은 실패하는 방식이 여러 가지이고, 종류마다 대응이 다릅니다.

| 실패 | 예외 | 뜻 | 대응 |
|---|---|---|---|
| 4xx 응답 | `onStatus`에서 직접 처리(기본은 `HttpClientErrorException`) | 요청이 거절됨(카드 한도 등) | 사용자에게 안내. 다시 보내도 같은 결과 |
| 5xx 응답 | `onStatus`에서 직접 처리(기본은 `HttpServerErrorException`) | 상대 서버 문제 | 잠시 뒤 다시 시도 |
| 연결 실패 | `ResourceAccessException`(원인 `ConnectException`) | 상대 서버가 꺼짐, 방화벽 | 상대 서버·네트워크 확인 |
| 응답 시간 초과 | `ResourceAccessException`(원인 `HttpTimeoutException` 등) | 상대가 느림 | 결제가 됐는지 모르므로 확인 필요 |

예제는 이 네 가지를 `PaymentException`의 `Reason`(REJECTED, SERVER_ERROR, UNAVAILABLE)으로 바꿔서 호출한 쪽이 판단하기 쉽게 했습니다.

응답 시간 초과는 특히 조심해야 합니다. 우리 쪽은 실패로 처리했는데 결제 서버는 사실 결제를 끝냈을 수 있습니다. 그래서 결제 연동에는 보통 "결제 결과 조회 API"가 따로 있고, 시간 초과가 나면 그것으로 다시 확인합니다. 같은 요청을 무조건 다시 보내면 이중 결제가 될 수 있습니다.

## 4. 타임아웃은 꼭 정한다

| 타임아웃 | 뜻 | 예제 값 |
|---|---|---|
| 연결 타임아웃(connect) | 상대 서버와 연결을 맺기까지 기다리는 시간 | 1초 |
| 응답 타임아웃(read) | 연결 뒤 응답을 기다리는 시간 | 2초 |

타임아웃이 없으면 상대 서버가 응답하지 않을 때 우리 요청 스레드가 하염없이 기다립니다. 그런 요청이 쌓이면 톰캣 스레드(기본 200개)가 모두 묶여서, 결제와 상관없는 다른 화면까지 응답하지 않게 됩니다. 외부 장애가 우리 장애로 번지는 가장 흔한 경로입니다.

실행 결과의 SLOW에서, 가짜 결제 서버는 5초 뒤에 응답하지만 우리 쪽은 2초(2007ms)에서 끊었습니다.

```java
HttpClient httpClient = HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(1)).build();
JdkClientHttpRequestFactory factory = new JdkClientHttpRequestFactory(httpClient);
factory.setReadTimeout(Duration.ofSeconds(2));
```

타임아웃 값은 상대 서버의 평소 응답 시간을 보고 정합니다. 너무 짧으면 정상 요청까지 끊기고, 너무 길면 장애 때 스레드가 오래 묶입니다.

## 5. 시간 초과가 어떤 예외로 오는지는 직접 확인한다

이 예제를 처음 만들 때 `SimpleClientHttpRequestFactory`를 썼더니, 시간 초과가 `ResourceAccessException`이 아니라 `RestClientException`으로 감싸져 올라왔습니다(실행 결과 맨 아래). 응답 헤더를 읽는 순간 시간 초과가 나서 다른 경로로 감싸졌기 때문입니다. 그래서 `catch (ResourceAccessException e)`를 빠져나가 500 오류가 됐습니다.

| HTTP 클라이언트 구현 | 시간 초과가 온 모양 |
|---|---|
| `SimpleClientHttpRequestFactory` | `RestClientException`(원인 `SocketTimeoutException: Read timed out`) |
| `JdkClientHttpRequestFactory` | `ResourceAccessException`(원인 `HttpTimeoutException`) |

교훈은 두 가지입니다.

- 장애 처리 코드는 실제로 장애를 만들어서 확인해야 합니다. 이 예제처럼 느린 가짜 서버를 두는 것이 가장 쉬운 방법입니다.
- 놓친 예외가 있어도 서비스 전체가 이상해지지 않게, 8장의 공통 예외 처리를 마지막 안전망으로 둡니다.

`RestClient.builder()`에 구현을 지정하지 않으면 클래스패스에 Apache HttpClient나 Jetty가 있으면 그것을, 없으면 JDK HttpClient를 씁니다.

## 6. 그 밖에 연동 코드에서 챙길 것

- 외부 API 주소, 키, 타임아웃은 설정 파일과 환경변수로 뺍니다(4장).
- 요청·응답을 로그로 남기되, 카드 번호·비밀번호 같은 값은 지우거나 가립니다.
- 다시 시도(retry)는 실패 종류를 보고 정합니다. 5xx·연결 실패는 다시 시도해도 되지만, 결제처럼 같은 요청이 두 번 처리되면 안 되는 API는 조심합니다.
- 상대가 계속 실패하면 잠시 호출 자체를 멈추는 서킷 브레이커(Resilience4j 등)도 있습니다.

## 확인 문제

1. 외부 API를 부를 때 타임아웃을 정하지 않으면 어떤 일이 생길 수 있나요?
2. 결제 요청이 시간 초과로 실패했습니다. 바로 같은 결제 요청을 다시 보내면 어떤 문제가 생길 수 있나요?
3. 4xx와 5xx 응답은 대응이 어떻게 다른가요?
4. 연결 타임아웃과 응답 타임아웃의 차이는?
5. `catch (ResourceAccessException e)`로 시간 초과를 잡았다고 생각했는데 500이 났습니다. 무엇을 확인해야 하나요?

## 정답

1. 상대 서버가 응답하지 않을 때 요청 스레드가 계속 기다리고, 그런 요청이 쌓이면 톰캣 스레드가 모두 묶여 다른 화면까지 응답하지 않게 됩니다.
2. 결제 서버는 사실 결제를 끝냈을 수 있어서 이중 결제가 될 수 있습니다. 결제 결과 조회로 먼저 확인합니다.
3. 4xx는 요청 자체가 거절된 것이라 다시 보내도 같고 사용자 안내가 필요합니다. 5xx는 상대 서버 문제라 잠시 뒤 다시 시도해 볼 수 있습니다.
4. 연결 타임아웃은 연결을 맺기까지, 응답 타임아웃은 연결 뒤 응답이 오기까지 기다리는 시간입니다.
5. 서버 로그의 실제 예외 종류입니다. HTTP 클라이언트 구현에 따라 시간 초과가 `RestClientException` 같은 다른 예외로 감싸져 올 수 있습니다.

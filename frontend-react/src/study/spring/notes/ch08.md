6~7장에서 본 기본 오류 응답은 이유가 없고 모양도 제각각이었습니다. 이번 장은 예외를 한곳에서 받아 오류 응답을 하나의 모양으로 맞춥니다. 운영에서 가장 고맙게 느끼는 코드 중 하나입니다.

## 1. 컨트롤러는 예외만 던진다

예외 처리 클래스가 없으면 컨트롤러마다 이런 코드가 반복됩니다.

```java
if (found == null) {
    return ResponseEntity.status(404).body(Map.of("message", "예약을 찾을 수 없습니다"));
}
```

대신 컨트롤러와 서비스는 예외를 던지기만 하고, 응답은 한곳에서 만듭니다.

```java
// 컨트롤러·서비스
if (found == null) {
    throw ReservationException.notFound(id);
}

// 한곳에서
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(ReservationException.class)
    public ResponseEntity<ErrorResponse> handleReservation(ReservationException e) {
        return ResponseEntity.status(e.getStatus()).body(ErrorResponse.of(e.getCode(), e.getMessage()));
    }
}
```

`@RestControllerAdvice`는 모든 컨트롤러에 적용되는 공통 처리 클래스입니다. `@ExceptionHandler(예외 클래스)`로 예외 종류마다 처리할 메서드를 정합니다. 던진 예외와 가장 가까운(구체적인) 처리기가 선택됩니다.

## 2. 오류 응답 모양 정하기

```json
{"code":"ROOM_ALREADY_BOOKED","message":"1번 객실은 2026-11-01에 이미 예약되어 있습니다","details":[]}
```

| 필드 | 쓰는 사람 | 용도 |
|---|---|---|
| `code` | 프로그램(화면, 연동 업체) | `code`별로 다르게 처리(예: 이미 예약됨이면 다른 날짜 추천) |
| `message` | 사람 | 화면에 그대로 보여 줄 문구 |
| `details` | 사람 | 검증 실패 필드 목록 |

정해진 답은 없지만, 프로젝트 안에서는 한 가지 모양으로 통일하는 것이 중요합니다. 실무에서는 여기에 추적 ID(핀볼 예제의 `traceId`)를 넣는 경우가 많습니다.

Spring에는 표준 형식(RFC 9457 Problem Details)도 있습니다. `spring.mvc.problemdetails.enabled=true`로 켜면 `{"type","title","status","detail","instance"}` 모양으로 응답합니다. 회사나 프로젝트에 정해진 형식이 있으면 그것을 따릅니다.

## 3. 예외를 나누는 기준

| 종류 | 예 | 상태 코드 | 로그 |
|---|---|---|---|
| 업무 규칙 위반 | 없는 예약, 이미 예약된 객실 | 404, 409 | WARN 한 줄 |
| 입력 오류 | 검증 실패, 깨진 JSON | 400 | WARN 한 줄 |
| 주소·메서드 오류 | 없는 주소, 지원하지 않는 메서드 | 404, 405 | 남기지 않거나 WARN |
| 예상하지 못한 오류 | NullPointerException, DB 연결 끊김 | 500 | ERROR + 스택 트레이스 |

로그 레벨을 나누는 이유는 운영 때문입니다. 400·404는 사용자가 잘못 보낸 것이라 매일 수없이 생깁니다. 이것까지 ERROR로 남기면, 정작 봐야 할 진짜 장애(500)가 묻힙니다. 오류 알림을 ERROR 기준으로 걸어 둔 회사라면 밤새 알림이 울리게 됩니다.

## 4. 함정: 모든 예외를 잡는 처리기

마지막 안전망으로 `@ExceptionHandler(Exception.class)`를 두는 것은 좋습니다. 그런데 이것만 두면 스프링이 원래 404·405로 처리하던 예외까지 여기에 걸립니다. 실행 결과 맨 아래처럼 없는 주소가 500 "서버 오류"가 되고 ERROR 로그와 스택 트레이스가 남습니다.

그래서 아래 예외는 따로 잡아 줍니다.

| 예외 | 원래 응답 |
|---|---|
| `NoResourceFoundException` | 404 없는 주소 |
| `HttpRequestMethodNotSupportedException` | 405 지원하지 않는 메서드 |
| `HttpMessageNotReadableException` | 400 깨진 JSON, 타입 변환 실패 |
| `MethodArgumentTypeMismatchException` | 400 주소·쿼리 값 타입 오류 |
| `MethodArgumentNotValidException` | 400 `@Valid` 실패 |
| `HandlerMethodValidationException` | 400 주소·쿼리 값 검증 실패(7장) |

## 5. 500 응답에 내부 사정을 싣지 않는다

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handleUnexpected(Exception e) {
    log.error("처리하지 못한 예외", e);        // 스택 트레이스는 로그에만
    return ResponseEntity.status(500).body(ErrorResponse.of("INTERNAL_ERROR", "잠시 후 다시 시도해 주세요"));
}
```

예외 메시지에는 SQL, 테이블 이름, 서버 경로가 들어 있을 수 있습니다. 응답에 그대로 보내면 공격자에게 내부 구조를 알려 주는 셈입니다. 응답에는 일반 문구만 주고, 원인은 로그에서 찾습니다. 로그에서 그 요청을 바로 찾을 수 있게 응답에 추적 ID를 넣어 주면 더 좋습니다(15장).

`log.error("...", e)`처럼 예외 객체를 마지막 인자로 넘겨야 스택 트레이스가 남습니다. `log.error("..." + e.getMessage())`로 쓰면 메시지 한 줄만 남아서 어디서 났는지 알 수 없습니다.

## 6. checked 예외와 unchecked 예외

| | checked | unchecked |
|---|---|---|
| 부모 클래스 | `Exception` | `RuntimeException` |
| `throws` 선언 | 꼭 해야 함 | 안 해도 됨 |
| 예 | `IOException`, `SQLException` | `NullPointerException`, `IllegalArgumentException` |

업무 예외는 보통 `RuntimeException`을 상속해서 만듭니다. 메서드마다 `throws`를 적지 않아도 되고, 12장 트랜잭션에서 볼 롤백 규칙과도 관계가 있습니다(기본은 unchecked 예외만 롤백).

## 확인 문제

1. `@RestControllerAdvice`를 쓰면 컨트롤러 코드에서 무엇이 사라지나요?
2. `@ExceptionHandler(Exception.class)`만 두었더니 없는 주소 요청이 500이 됩니다. 왜 그런가요?
3. 400, 404 응답을 ERROR 로그로 남기면 어떤 문제가 생기나요?
4. 500 응답 본문에 `e.getMessage()`를 그대로 넣으면 안 되는 이유는?
5. `log.error("실패: " + e.getMessage())`와 `log.error("실패", e)`의 차이는?

## 정답

1. 상태 코드와 오류 응답을 만드는 코드(`if ... return ResponseEntity.status(...)`)가 사라지고, 예외를 던지는 코드만 남습니다.
2. 스프링이 없는 주소를 `NoResourceFoundException`으로 알리는데, 이 예외가 `Exception` 처리기에 걸리기 때문입니다. 따로 잡아서 404로 응답해야 합니다.
3. 사용자 실수로 매일 생기는 오류가 ERROR로 쌓여서 진짜 장애를 찾기 어렵고, ERROR 기준 알림이 계속 울립니다.
4. SQL, 테이블 이름, 서버 경로 같은 내부 정보가 밖으로 나갈 수 있습니다.
5. 앞의 것은 메시지 한 줄만 남고, 뒤의 것은 스택 트레이스까지 남아서 오류가 난 줄을 찾을 수 있습니다.

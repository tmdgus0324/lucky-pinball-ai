JPA는 SQL을 직접 쓰는 대신 자바 객체를 저장·조회하면 SQL을 만들어 주는 방식입니다. 새로 만드는 Spring Boot 프로젝트에서 많이 쓰고, MyBatis와 같이 쓰는 프로젝트도 있습니다. 운영자라면 "JPA가 실제로 어떤 SQL을 실행했나"를 볼 수 있어야 합니다.

## 1. JPA, Hibernate, Spring Data JPA

| 이름 | 무엇인가 |
|---|---|
| JPA | 자바 표준 명세(인터페이스와 규칙). `jakarta.persistence` 패키지 |
| Hibernate | JPA를 실제로 구현한 라이브러리. SQL을 만들고 실행한다 |
| Spring Data JPA | Repository 인터페이스만 만들면 구현체를 만들어 주는 스프링 기능 |

`spring-boot-starter-data-jpa` 하나로 셋이 모두 들어옵니다.

## 2. 엔티티: 테이블과 연결된 클래스

```java
@Entity
public class Reservation {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 50)
    private String guestName;          // guest_name 컬럼

    @Enumerated(EnumType.STRING)
    private Status status;

    protected Reservation() {}         // JPA용 기본 생성자
}
```

| 애너테이션 | 뜻 |
|---|---|
| `@Entity` | 테이블과 연결되는 클래스. 테이블 이름은 클래스 이름(`reservation`) |
| `@Id`, `@GeneratedValue` | 기본 키와 만드는 방법(IDENTITY: DB 자동 증가, SEQUENCE: Oracle 시퀀스) |
| `@Column` | 컬럼 이름·길이·null 허용을 직접 정할 때 |
| `@Enumerated(EnumType.STRING)` | enum을 글자로 저장 |
| `@Table(name = "TB_RESERVATION")` | 테이블 이름이 클래스 이름과 다를 때(레거시 DB에 흔함) |

`@Enumerated`의 기본값은 숫자(순서) 저장입니다. 나중에 enum 중간에 값을 하나 끼워 넣으면 기존 데이터의 의미가 모두 바뀌므로, 항상 `STRING`으로 둡니다.

## 3. Repository

```java
public interface ReservationRepository extends JpaRepository<Reservation, Long> {
    List<Reservation> findByGuestNameContaining(String keyword);
    List<Reservation> findByRoomIdAndStatus(Long roomId, Reservation.Status status);
}
```

`JpaRepository`를 상속하면 `save`, `findById`, `findAll`, `deleteById`, `count`가 이미 있습니다. 직접 만든 메서드는 이름으로 SQL이 만들어집니다(쿼리 메서드).

| 메서드 이름 | 만들어지는 조건 |
|---|---|
| `findByGuestName(name)` | `where guest_name = ?` |
| `findByGuestNameContaining(k)` | `where guest_name like '%k%'` |
| `findByRoomIdAndStatus(id, s)` | `where room_id = ? and status = ?` |
| `findByCheckInGreaterThanEqual(d)` | `where check_in >= ?` |
| `...OrderByCheckInAsc` | `order by check_in asc` |
| `findFirstBy...`, `countBy...`, `existsBy...` | 첫 건, 개수, 있는지 |

조건이 많아 이름이 길어지면 `@Query`로 JPQL을 직접 씁니다. JPQL은 테이블·컬럼이 아니라 엔티티·필드 이름으로 씁니다.

```java
@Query("select r from Reservation r where r.status = :status and r.nights >= :minNights")
```

DB 전용 기능이 필요하면 `@Query(value = "...", nativeQuery = true)`로 SQL을 그대로 쓸 수도 있습니다.

## 4. 변경 감지 (dirty checking)

실행 결과의 취소 부분을 보세요. 서비스는 이것만 했습니다.

```java
@Transactional
public Reservation cancel(Long id) {
    Reservation reservation = repository.findById(id).orElseThrow(...);
    reservation.cancel();      // status를 CANCELED로 바꿈. save 호출 없음
    return reservation;
}
```

그런데 로그에는 `update reservation set ... where id=?`가 실행됐습니다. 트랜잭션 안에서 조회한 엔티티는 JPA가 처음 상태를 기억해 두고, 트랜잭션이 끝날 때 바뀐 것이 있으면 UPDATE를 실행합니다.

MyBatis에 익숙하면 가장 낯선 부분입니다. 반대로 말하면, 트랜잭션 안에서 엔티티의 값을 실수로 바꾸면 의도하지 않은 UPDATE가 실행됩니다. 엔티티에 setter를 열어 두지 않고 `cancel()`처럼 의미 있는 메서드로만 바꾸게 하는 이유입니다.

## 5. 실행된 SQL 보기

```yaml
logging:
  level:
    org.hibernate.SQL: debug              # 실행된 SQL
    org.hibernate.orm.jdbc.bind: trace    # ? 에 들어간 값
```

`spring.jpa.show-sql: true`로도 SQL이 보이지만 로그 시스템을 거치지 않고 화면에 바로 찍히므로, 로그 설정으로 보는 편이 낫습니다.

## 6. ddl-auto

| 값 | 하는 일 | 쓰는 곳 |
|---|---|---|
| `create` | 시작할 때 테이블을 지우고 새로 만듦 | 예제, 테스트 |
| `create-drop` | create + 종료할 때 지움 | 테스트 |
| `update` | 바뀐 부분(컬럼 추가 등)만 반영 | 개인 개발 |
| `validate` | 엔티티와 테이블이 맞는지만 확인 | 운영 |
| `none` | 아무것도 안 함 | 운영 |

운영 DB에 `create`가 켜진 채로 배포되면 모든 데이터가 지워집니다. 운영은 반드시 `validate`나 `none`으로 두고, 테이블 변경은 DBA 검토를 거친 SQL이나 Flyway로 합니다.

## 7. MyBatis와 비교

| | MyBatis | JPA |
|---|---|---|
| SQL | 직접 씀 | 자동으로 만들어짐(필요하면 직접) |
| 잘 맞는 곳 | 복잡한 조회, 통계, 기존 DB 구조가 복잡한 레거시 | 저장·수정이 많은 업무, 새로 설계하는 DB |
| 운영 때 SQL 찾기 | XML에 그대로 있음 | 로그를 켜야 보임 |
| 주의할 점 | `${}`, 반복되는 단순 SQL | 변경 감지, N+1(13장), 지연 로딩 |

## 확인 문제

1. `findByRoomIdAndStatus(1L, CONFIRMED)`는 어떤 WHERE 조건이 되나요?
2. 서비스 메서드에서 엔티티의 상태를 바꾸기만 하고 `save`를 부르지 않았는데 DB가 바뀌었습니다. 왜 그런가요?
3. `@Enumerated`를 생략하면 어떤 문제가 생길 수 있나요?
4. 운영 설정에 `ddl-auto: create`가 있으면 어떻게 되나요?
5. JPA가 실행한 SQL과 파라미터 값을 로그로 보려면 어떤 설정을 켜나요?

## 정답

1. `where room_id = ? and status = ?`
2. `@Transactional` 안에서 조회한 엔티티는 JPA가 변경을 감지해서, 트랜잭션이 끝날 때 UPDATE를 실행합니다.
3. 기본값(ORDINAL)으로 enum 순서 숫자가 저장됩니다. 나중에 enum 중간에 값을 추가하면 기존 숫자의 의미가 바뀝니다.
4. 서버를 시작할 때마다 테이블을 지우고 새로 만들어 운영 데이터가 모두 사라집니다.
5. `logging.level.org.hibernate.SQL: debug`와 `logging.level.org.hibernate.orm.jdbc.bind: trace`입니다.

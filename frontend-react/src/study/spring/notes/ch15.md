운영(SM) 업무에서 가장 많이 하는 일은 로그를 보는 일입니다. "어제 오후 3시쯤 예약이 안 됐다"는 문의가 오면 로그에서 그 요청을 찾아 원인을 봅니다. 이번 장은 로그를 남기는 방법, 파일로 쌓고 정리하는 방법, 서버 상태를 확인하는 Actuator, jar로 배포하고 끄는 방법을 봅니다.

## 1. 로그 레벨

| 레벨 | 언제 쓰나 | 예 |
|---|---|---|
| `ERROR` | 처리하지 못한 실패. 누군가 봐야 함 | 결제 실패, 처리되지 않은 예외 |
| `WARN` | 실패는 아니지만 이상함 | 외부 API 재시도, 잘못된 요청 |
| `INFO` | 중요한 흐름 | 서버 시작, 예약 완료, 요청 처리 시간 |
| `DEBUG` | 개발·장애 분석용 상세 정보 | 조회 조건, SQL |
| `TRACE` | 아주 상세한 정보 | SQL 파라미터 값 |

레벨을 정하면 그 레벨과 그보다 높은 레벨만 찍힙니다. 스프링 부트의 기본은 `INFO`라서 `DEBUG`, `TRACE`는 찍히지 않습니다. 실행 결과 3번에서 `log.debug(...)` 줄이 없던 이유입니다.

```yaml
logging:
  level:
    root: info                         # 전체 기본
    com.example.reservation: debug     # 우리 패키지만 자세히
    org.hibernate.SQL: debug           # JPA가 만든 SQL(11장)
```

`web`, `sql`처럼 스프링 부트가 미리 묶어 둔 그룹도 있어서 `logging.level.web: debug`처럼 쓸 수 있습니다.

로그를 쓸 때 지킬 것입니다.

```java
log.info("예약 조회 시작 id={}", id);              // {} 자리에 값이 들어간다
log.info("예약 조회 시작 id=" + id);               // 레벨이 꺼져 있어도 문자열을 만든다. 피한다
log.error("예약 번호 변환 실패 id={}", id, e);      // 예외는 마지막 인자. 스택 트레이스가 남는다(8장)
```

- `System.out.println`은 쓰지 않습니다. 레벨로 끌 수 없고, 로그 파일에 남지 않으며, 시간이나 요청 ID도 붙지 않습니다.
- 비밀번호, 카드 번호, 주민등록번호, API 키는 로그에 남기지 않습니다. 로그 파일은 여러 사람이 보고 오래 보관됩니다.

## 2. 파일 로그와 롤링

기본은 콘솔에만 찍힙니다. `logging.file.name`을 정하면 파일에도 씁니다. 콘솔 출력은 그대로 계속됩니다.

```yaml
logging:
  file:
    name: logs/reservation.log
  logback:
    rollingpolicy:
      max-file-size: 10MB        # 이 크기를 넘으면 새 파일로(예제는 10KB)
      max-history: 30            # 며칠 치를 남길지
      total-size-cap: 3GB        # 전체 크기 한도. 넘으면 오래된 것부터 지움
```

로그 파일이 하나로 계속 커지면 디스크가 가득 차서 서버가 멈출 수 있습니다. 그래서 일정 크기나 날짜마다 새 파일로 넘기고(롤링), 오래된 파일은 지웁니다. 실행 결과 5번에서 10KB마다 `.0.log.gz`, `.1.log.gz` ... 로 압축 파일이 생겼습니다.

| 설정 | 기본값 |
|---|---|
| `max-file-size` | 10MB |
| `max-history` | 7(일) |
| `total-size-cap` | 없음 |
| `file-name-pattern` | `${LOG_FILE}.%d{yyyy-MM-dd}.%i.gz` |

기본값 그대로 두면 일주일 치만 남습니다. "지난달 일을 확인해 달라"는 요청이 올 수 있는 서비스라면 보관 기간을 회사 기준에 맞게 늘려 둡니다.

로그 한 줄의 모양은 `logging.pattern.console`, `logging.pattern.file`로 바꿉니다.

```yaml
logging:
  pattern:
    console: "%d{HH:mm:ss.SSS} %-5level [%X{traceId:-}] %logger{20} : %msg%n"
```

| 기호 | 뜻 |
|---|---|
| `%d{...}` | 시간 |
| `%-5level` | 레벨(5칸 맞춤) |
| `%X{traceId:-}` | MDC의 traceId 값. 없으면 빈칸(4절) |
| `%logger{20}` | 로거 이름(패키지를 줄여서) |
| `%msg%n` | 메시지와 줄바꿈 |

## 3. 환경별로 다르게

4장의 프로필 파일로 환경마다 로그 설정을 다르게 둡니다.

```yaml
# application-local.yml : 내 PC
logging:
  level:
    com.example.reservation: debug
    org.hibernate.SQL: debug

# application-prod.yml : 운영 서버
logging:
  level:
    com.example.reservation: info
  file:
    name: /app/logs/reservation.log
```

운영에서 SQL까지 `DEBUG`로 찍으면 로그 양이 너무 많아지고, 개인정보가 섞일 수 있습니다.

더 세밀하게 설정해야 하면 `logback-spring.xml` 파일을 만들고 `<springProfile name="prod">`로 프로필별 설정을 나눕니다. 레거시 프로젝트에서 `logback.xml`이나 `log4j2.xml`을 보면 같은 역할의 파일입니다. 스프링 프로필 기능(`<springProfile>`)을 쓰려면 이름이 `logback-spring.xml`이어야 합니다.

## 4. 요청 추적 ID(MDC)

운영 서버에는 여러 사용자의 요청이 동시에 들어와서 로그가 뒤섞입니다. 어떤 줄이 어느 요청의 것인지 알 수 없으면 원인을 찾기 어렵습니다.

예제의 `TraceIdFilter`는 요청마다 8자리 ID를 만들어 MDC에 넣습니다. MDC는 스레드마다 값을 보관하는 저장소이고, 로그 패턴의 `%X{traceId}`가 그 값을 꺼내 줄마다 찍습니다.

```
21:51:59.236 INFO  [5b6a96f8] c.e.r.ReservationController : 예약 조회 시작 id=99
21:51:59.236 ERROR [5b6a96f8] c.e.r.ReservationController : 예약 번호 변환 실패 id=99
21:51:59.240 INFO  [5b6a96f8] c.e.r.w.TraceIdFilter : GET /reservations/99 -> 200 (4ms)
```

`grep 5b6a96f8`로 검색하면 이 요청의 로그만 모입니다. 응답 헤더(`X-Trace-Id`)나 오류 화면에 이 ID를 보여 주면, 사용자가 알려 준 ID로 바로 찾을 수 있습니다.

주의할 점이 두 가지 있습니다.

- 요청이 끝나면 `finally`에서 `MDC.remove`로 지웁니다. 톰캣 스레드는 재사용되므로 지우지 않으면 다음 요청 로그에 이전 ID가 찍힙니다(5장).
- `@Async`나 직접 만든 스레드에서는 MDC 값이 넘어가지 않습니다. 필요하면 값을 직접 넘겨줘야 합니다.

## 5. Actuator: 서버 상태 확인

`spring-boot-starter-actuator`를 추가하면 서버 상태를 보는 주소가 생깁니다.

| 주소 | 하는 일 |
|---|---|
| `/actuator/health` | 서버가 살아 있는지(UP/DOWN). DB 연결, 디스크 여유 공간도 확인 |
| `/actuator/info` | 앱 정보(버전 등) |
| `/actuator/loggers` | 로그 레벨 확인·변경 |
| `/actuator/metrics` | 요청 수, 메모리 같은 수치 |

L4 스위치, 쿠버네티스, 모니터링 도구가 `/actuator/health`를 주기적으로 불러서 서버가 정상인지 봅니다. DB 연결이 끊기면 `DOWN`이 됩니다.

`loggers`는 장애 때 유용합니다. 실행 결과 4번처럼 서버를 다시 켜지 않고 특정 패키지만 잠깐 `DEBUG`로 올려 상세 로그를 보고, 확인이 끝나면 다시 `INFO`로 내립니다. 바꾼 레벨은 서버를 다시 켜면 설정 파일 값으로 돌아갑니다.

보안 주의가 있습니다. 기본으로 웹에 열리는 것은 `health` 하나뿐이고, 상세 정보(`show-details`)도 기본값은 `never`입니다. `loggers`처럼 설정을 바꿀 수 있는 주소를 인터넷에 열어 두면 누구나 로그 레벨을 바꿀 수 있습니다. 공식 문서도 다른 주소를 열기 전에 방화벽 안에 두거나 Spring Security 등으로 막으라고 안내합니다. 보통 관리용 포트(`management.server.port`)를 따로 두고 내부망에서만 접근하게 합니다.

## 6. jar로 배포하고 끄기

스프링 부트는 톰캣이 들어 있는 jar 하나로 실행합니다. 외부 톰캣에 war를 올리던 방식과 다른 점입니다.

```bash
./gradlew bootJar                                  # build/libs/reservation-0.0.1-SNAPSHOT.jar 생성

java -jar reservation-0.0.1-SNAPSHOT.jar --spring.profiles.active=prod

# 터미널을 닫아도 계속 돌게 하고, 프로세스 번호(PID)를 파일에 남긴다
nohup java -jar reservation.jar --spring.profiles.active=prod > /dev/null 2>&1 &
echo $! > reservation.pid
```

로그는 `logging.file.name`의 파일에 쌓이므로 콘솔 출력은 버려도 됩니다(`> /dev/null`). 반대로 파일 설정이 없다면 콘솔 출력을 파일로 받아야 로그가 남습니다.

끌 때는 PID로 끕니다.

```bash
kill $(cat reservation.pid)       # SIGTERM. 처리 중인 요청을 마치고 종료
kill -9 $(cat reservation.pid)    # 강제 종료. 처리 중인 요청이 끊긴다. 마지막 수단
```

스프링 부트는 기본으로 정상 종료(graceful shutdown)가 켜져 있습니다. `kill`(SIGTERM)을 받으면 새 요청은 받지 않고, 처리 중인 요청이 끝나기를 기다렸다가 종료합니다. 단계별로 기다리는 시간은 기본 30초이고 `spring.lifecycle.timeout-per-shutdown-phase`로 바꿉니다. `kill -9`는 이 과정을 건너뛰므로 저장 중이던 예약이 끊길 수 있습니다.

`ps -ef | grep java`로 찾은 프로세스를 아무거나 끄면 같은 서버의 다른 앱을 끌 수 있습니다. PID 파일을 남기는 이유입니다.

## 7. 장애가 났을 때 로그 보는 순서

```bash
tail -f logs/reservation.log                         # 지금 쌓이는 로그 보기
grep "ERROR" logs/reservation.log                    # 오류만
grep "5b6a96f8" logs/reservation.log                 # 한 요청의 흐름
grep -A 30 "ERROR" logs/reservation.log | less       # 오류 뒤 30줄(스택 트레이스)
zgrep "ERROR" logs/reservation-2026-10-08.*.log.gz   # 압축된 지난 로그
```

1. 문의 내용에서 시간, 사용자, 화면(주소)을 확인합니다.
2. 그 시간대의 `ERROR`, `WARN`을 찾습니다.
3. 찾은 줄의 추적 ID로 같은 요청의 로그를 모두 봅니다.
4. 스택 트레이스에서 우리 패키지(`com.example...`)가 나오는 첫 줄과 맨 아래 `Caused by:`를 봅니다. 실제 원인은 보통 마지막 `Caused by:`에 있습니다.
5. 같은 오류가 언제부터, 얼마나 자주 났는지 셉니다(`grep -c`). 배포 시각과 겹치는지도 봅니다.

## 확인 문제

1. 운영 서버의 레벨이 `INFO`일 때 `log.debug(...)`는 찍히나요?
2. `log.info("id=" + id)` 대신 `log.info("id={}", id)`를 쓰는 이유는?
3. 롤링 설정 없이 파일 로그를 한 파일에 계속 쌓으면 어떤 문제가 생기나요?
4. MDC에 추적 ID를 넣고 `finally`에서 지우지 않으면 어떻게 되나요?
5. `/actuator/loggers`를 인터넷에 열어 두면 안 되는 이유는?
6. `kill`과 `kill -9`의 차이는?

## 정답

1. 찍히지 않습니다. `INFO` 이상(`INFO`, `WARN`, `ERROR`)만 찍힙니다.
2. 레벨이 꺼져 있으면 문자열을 만들지 않아 낭비가 없고, 코드도 읽기 쉽습니다.
3. 파일이 계속 커져 디스크가 가득 차면 서버가 멈출 수 있고, 큰 파일은 열거나 검색하기도 어렵습니다.
4. 톰캣 스레드가 재사용되므로 다음 요청의 로그에 이전 요청의 ID가 찍혀 잘못된 분석을 하게 됩니다.
5. 누구나 로그 레벨을 바꿀 수 있습니다. 상세 로그가 쏟아져 디스크가 차거나 민감한 정보가 남을 수 있습니다.
6. `kill`(SIGTERM)은 처리 중인 요청을 마치고 정상 종료하고, `kill -9`는 즉시 강제 종료해서 처리 중인 요청이 끊깁니다.

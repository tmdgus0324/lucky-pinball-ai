지금까지는 서버가 JSON만 돌려주고 화면은 React 같은 프론트가 그리는 방식이었습니다. 하지만 SI·SM 현장의 많은 시스템은 서버가 HTML 화면을 직접 만들어 보냅니다. 오래된 시스템은 대부분 JSP이고, 스프링 부트로 새로 만든 관리자 화면은 Thymeleaf를 많이 씁니다. 이번 장은 같은 예약 목록 화면을 Thymeleaf와 JSP로 만들어 비교합니다.

## 1. 화면을 만드는 두 가지 방식

| | 서버에서 HTML 만들기 | API + 프론트 |
|---|---|---|
| 서버가 보내는 것 | 완성된 HTML | JSON |
| 화면을 그리는 곳 | 서버(JSP, Thymeleaf) | 브라우저(React, Vue) |
| 컨트롤러 | `@Controller` | `@RestController` |
| 많이 쓰는 곳 | 사내 시스템, 관리자 화면, 레거시 | 사용자 화면, 모바일 앱과 같이 쓰는 서버 |

둘 중 하나가 낫다기보다 쓰임이 다릅니다. 핀볼 게임처럼 화면이 많이 움직이면 프론트 방식이 편하고, 표와 입력 폼 위주의 업무 화면은 서버 방식으로도 충분합니다.

## 2. @Controller와 Model

```java
@Controller
public class ReservationPageController {

    @GetMapping("/reservations")
    public String list(Model model) {
        model.addAttribute("reservations", store.findAll());
        return "reservation-list";      // → templates/reservation-list.html
    }
}
```

- `@RestController`는 반환값을 JSON으로 바꾸지만, `@Controller`는 반환한 문자열을 화면 이름으로 봅니다.
- Thymeleaf는 `src/main/resources/templates/` 아래에서 `화면이름.html`을 찾습니다.
- `Model`에 담은 값은 화면에서 `${이름}`으로 꺼냅니다. JSP 시절 `request.setAttribute("reservations", list)`와 같은 역할입니다.
- `"redirect:/reservations"`를 반환하면 화면 대신 그 주소로 리다이렉트합니다.

## 3. Thymeleaf 문법과 JSP 비교

Thymeleaf는 HTML 태그에 `th:` 속성을 붙이는 방식입니다. 파일 자체가 올바른 HTML이라서 서버 없이 브라우저로 열어도 모양이 보입니다(태그 안의 글자는 그때 보이는 견본 값입니다).

| 하는 일 | Thymeleaf | JSP(JSTL) |
|---|---|---|
| 값 출력 | `<td th:text="${r.guestName}">견본</td>` | `<td><c:out value="${r.guestName}"/></td>` |
| 반복 | `<tr th:each="r : ${reservations}">` | `<c:forEach var="r" items="${reservations}">` |
| 조건 | `<p th:if="${message}">` | `<c:if test="${not empty message}">` |
| 주소 | `th:href="@{/reservations/new}"` | `href="${pageContext.request.contextPath}/reservations/new"` |
| 폼 객체 | `<form th:object="${form}">` | `<form:form modelAttribute="form">` |
| 입력란 | `<input th:field="*{guestName}">` | `<form:input path="guestName"/>` |
| 오류 메시지 | `<span th:errors="*{guestName}">` | `<form:errors path="guestName"/>` |

`${...}`는 Model의 값, `*{...}`는 `th:object`로 정한 객체의 필드, `@{...}`는 주소입니다. 같은 화면을 두 방식으로 만든 파일이 코드 탭의 `reservation-list.html`과 `reservation-list.jsp`입니다.

## 4. 폼 처리 흐름

```java
@PostMapping("/reservations")
public String create(@Valid @ModelAttribute("form") ReservationForm form, BindingResult bindingResult,
                     Model model, RedirectAttributes redirectAttributes) {
    if (bindingResult.hasErrors()) {
        model.addAttribute("rooms", ROOMS);
        return "reservation-form";            // 같은 화면 다시. 입력값과 오류 메시지가 함께 나간다
    }
    store.save(...);
    redirectAttributes.addFlashAttribute("message", "저장되었습니다.");
    return "redirect:/reservations";          // 성공하면 리다이렉트
}
```

- `@ModelAttribute`는 `<form>`의 입력값(`name=값`)을 객체 필드에 채웁니다. 7장의 `@RequestBody`가 JSON을 받는 것과 같은 역할을 폼 입력에 하는 것입니다.
- `BindingResult`는 반드시 검증할 객체 바로 뒤에 둡니다. 그래야 검증 오류가 예외(400)로 나가지 않고 이 객체에 담깁니다. 오류가 있으면 같은 화면을 다시 보여 주고, `th:errors`가 필드별 메시지를 찍습니다(실행 결과 3번).
- 저장에 성공하면 화면을 바로 그리지 않고 목록으로 리다이렉트합니다. POST 응답 화면에서 새로고침을 누르면 브라우저가 POST를 다시 보내 예약이 두 번 저장되기 때문입니다. 이것을 PRG(Post-Redirect-Get) 패턴이라고 합니다.
- 리다이렉트하면 Model 값이 사라지므로, 다음 화면에 보여 줄 메시지는 flash 속성으로 넘깁니다. 세션에 잠깐 담았다가 한 번 꺼내면 지워집니다(실행 결과 5, 6번).

## 5. 세션과 주소 뒤의 ;jsessionid

flash 속성은 세션을 씁니다(9장). 실행 결과 4번의 리다이렉트 주소를 보면 뒤에 `;jsessionid=...`가 붙어 있습니다. 톰캣은 세션을 처음 만든 응답에서는 브라우저가 쿠키를 쓰는지 모르기 때문에, 쿠키와 함께 주소에도 세션 ID를 붙여 둡니다.

주소에 세션 ID가 있으면 주소를 복사해 남에게 보내거나 로그에 남을 때 세션이 새어 나갈 수 있습니다. 레거시 시스템 점검에서 자주 지적되는 항목입니다. 쿠키로만 세션을 쓰게 하면 붙지 않습니다.

```yaml
server:
  servlet:
    session:
      tracking-modes: cookie
```

이 설정으로 다시 실행하면 리다이렉트 주소가 `Location: http://localhost:8080/reservations`로 깔끔하게 나옵니다.

## 6. 출력할 때 이스케이프

사용자가 입력한 값을 화면에 그대로 넣으면, 그 안의 `<script>`가 다른 사용자 브라우저에서 실행될 수 있습니다(XSS). 그래서 `<`, `>` 같은 문자를 `&lt;`, `&gt;`로 바꿔(이스케이프) 글자로만 보이게 합니다.

| | 이스케이프함 | 이스케이프 안 함 |
|---|---|---|
| Thymeleaf | `th:text`(기본) | `th:utext` |
| JSP | `<c:out value="${...}"/>`, `${fn:escapeXml(...)}` | `${...}`를 그대로 씀 |

실행 결과의 2번 예약자 `<b>박지영</b>`이 차이를 보여 줍니다. Thymeleaf와 `c:out`은 글자 그대로 보였고, JSP에서 `${r.guestName}`을 그대로 쓴 칸은 태그가 살아서 굵게 나왔습니다. Thymeleaf는 기본이 안전하고, JSP는 개발자가 챙겨야 안전합니다. 레거시 JSP를 고칠 때 사용자 입력을 `${...}`로 바로 찍는 곳이 있는지 살펴봅니다.

## 7. 스프링 부트에서 JSP를 쓸 때

```groovy
plugins {
    id 'war'                                                      // jar가 아니라 war로
}
dependencies {
    implementation 'org.apache.tomcat.embed:tomcat-embed-jasper'   // JSP를 실행하는 엔진
    implementation 'jakarta.servlet.jsp.jstl:jakarta.servlet.jsp.jstl-api'
    implementation 'org.glassfish.web:jakarta.servlet.jsp.jstl'    // JSTL(c:forEach 등)
}
```

```yaml
spring:
  mvc:
    view:
      prefix: /WEB-INF/views/      # JSP는 src/main/webapp/WEB-INF/views/ 아래
      suffix: .jsp
```

공식 문서는 가능하면 JSP를 피하라고 하고, 실행 jar에서는 JSP를 지원하지 않는다고 적고 있습니다. war로 만들면 `java -jar`로도 실행되고 외부 톰캣에도 올릴 수 있습니다.

실행 결과 아래쪽처럼 jar로 만들어도 프로젝트 폴더에서 실행하면 화면이 나옵니다. 스프링 부트가 현재 폴더의 `src/main/webapp`을 찾아 쓰기 때문입니다. 그런데 jar 파일만 서버로 옮겨 실행하면 JSP 파일이 없어서 404가 납니다. 내 PC에서는 되는데 서버에서만 안 되는 문제가 생기면 이것부터 의심합니다.

레거시 프로젝트를 볼 때 알아 둘 것입니다.

- 외부 톰캣에 war를 올리는 프로젝트는 `SpringBootServletInitializer`를 상속한 클래스가 있습니다. 톰캣이 이 클래스로 스프링을 띄웁니다.
- 스프링 부트 3부터 `javax.servlet`이 `jakarta.servlet`으로 바뀌었습니다. JSTL 3.0부터는 taglib 주소도 `http://java.sun.com/jsp/jstl/core`에서 `jakarta.tags.core`로 바뀌었습니다. 옛 JSP를 옮길 때 자주 걸리는 부분입니다.

## 확인 문제

1. `@Controller`의 메서드가 `"reservation-list"`를 반환하면 어떻게 되나요? `@RestController`라면?
2. 폼 검증에서 `BindingResult`를 빼면 검증 실패 때 어떻게 되나요?
3. 저장 성공 뒤 화면을 바로 그리지 않고 리다이렉트하는 이유는?
4. JSP에서 `${r.guestName}`과 `<c:out value="${r.guestName}"/>`의 차이는?
5. JSP 화면이 내 PC에서는 나오는데, 서버에 jar를 올리니 404가 납니다. 왜 그럴까요?

## 정답

1. `templates/reservation-list.html` 화면을 그려서 HTML로 응답합니다. `@RestController`라면 문자열 "reservation-list"가 그대로 응답 본문이 됩니다.
2. 검증 오류가 예외로 처리되어 400 응답이 나갑니다. 입력 화면이 다시 나오지 않습니다.
3. POST 응답 화면에서 새로고침하면 같은 POST가 다시 전송되어 두 번 저장될 수 있기 때문입니다(PRG 패턴).
4. `${...}`를 그대로 쓰면 이스케이프하지 않아 입력값의 태그나 스크립트가 실행될 수 있고, `c:out`은 이스케이프해서 글자로만 보여 줍니다.
5. jar에는 `src/main/webapp`의 JSP가 들어가지 않습니다. 내 PC에서는 프로젝트 폴더의 파일을 찾아 써서 된 것처럼 보였습니다. war로 만들어야 합니다.

마지막 장은 스프링이 아니라 자바 문법입니다. Java 8에서 들어온 람다식과 Stream은 스프링 코드 곳곳에 나옵니다. 지금까지 본 예제에도 `orElseThrow(() -> ...)`, `.stream().map(...).toList()`가 계속 있었습니다. Java 7 이전 코드에 익숙하면 처음엔 낯설지만, 규칙 몇 가지만 알면 읽을 수 있습니다. 이 장은 "Stream 시각화" 탭에서 처리 순서를 한 단계씩 볼 수 있습니다.

## 1. 람다식이 필요한 이유

자바는 메서드에 "동작"을 넘기려면 객체를 넘겨야 했습니다. 그래서 예전에는 이름 없는 클래스(익명 클래스)를 그 자리에서 만들었습니다.

```java
// Java 7까지
reservations.sort(new Comparator<Reservation>() {
    @Override
    public int compare(Reservation a, Reservation b) {
        return Integer.compare(a.nights(), b.nights());
    }
});

// 람다
reservations.sort((a, b) -> Integer.compare(a.nights(), b.nights()));

// 메서드 참조
reservations.sort(Comparator.comparing(Reservation::nights));
```

세 줄 모두 하는 일이 같습니다. `Comparator`는 메서드가 `compare` 하나뿐이라, 어떤 메서드를 구현하는지 적지 않아도 됩니다. 그래서 매개변수와 몸통만 남긴 것이 람다식입니다.

## 2. 함수형 인터페이스

람다식은 추상 메서드가 딱 하나인 인터페이스(함수형 인터페이스) 자리에만 쓸 수 있습니다. 자주 쓰는 것은 `java.util.function`에 이미 있습니다.

| 인터페이스 | 모양 | 메서드 | 예 |
|---|---|---|---|
| `Predicate<T>` | T → boolean | `test` | `r -> r.nights() >= 2` |
| `Function<T, R>` | T → R | `apply` | `r -> r.guestName()` |
| `Consumer<T>` | T → 없음 | `accept` | `r -> System.out.println(r)` |
| `Supplier<T>` | 없음 → T | `get` | `() -> new ArrayList<>()` |
| `BiFunction<T, U, R>` | (T, U) → R | `apply` | `(price, nights) -> price * nights` |
| `Runnable` | 없음 → 없음 | `run` | `() -> log.info("시작")` |

직접 만들 수도 있습니다. `@FunctionalInterface`를 붙이면 추상 메서드가 둘 이상일 때 컴파일 오류로 알려 줍니다.

```java
@FunctionalInterface
interface PriceRule {
    int apply(int price);
}

PriceRule weekend = price -> price * 120 / 100;
```

## 3. 람다 문법

```java
r -> r.nights() >= 2                       // 매개변수 하나는 괄호 생략 가능, 식 하나면 return 생략
(a, b) -> Integer.compare(a, b)            // 매개변수 둘 이상은 괄호
() -> new Reservation(...)                 // 매개변수가 없으면 빈 괄호
r -> {                                     // 여러 줄이면 중괄호와 return
    boolean ok = r.status() == CONFIRMED;
    return ok;
}
```

매개변수 타입은 대부분 컴파일러가 알아서 정합니다.

람다 안에서 바깥의 지역 변수를 쓸 수 있지만, 그 변수는 값을 바꾸지 않아야 합니다(사실상 final). 바꾸면 컴파일 오류가 납니다(실행 결과 맨 아래).

```java
int minNights = 2;
Predicate<Reservation> atLeast = r -> r.nights() >= minNights;
minNights = 3;   // 컴파일 오류: ... must be final or effectively final
```

## 4. 메서드 참조

람다가 메서드 하나를 부르기만 하면 `클래스::메서드`로 줄여 씁니다.

| 종류 | 메서드 참조 | 같은 람다 |
|---|---|---|
| 객체의 메서드 | `Reservation::guestName` | `r -> r.guestName()` |
| static 메서드 | `Integer::parseInt` | `s -> Integer.parseInt(s)` |
| 특정 객체의 메서드 | `System.out::println` | `s -> System.out.println(s)` |
| 생성자 | `ArrayList::new` | `() -> new ArrayList<>()` |

## 5. Stream 기본

Stream은 목록을 "어떻게 돌지"가 아니라 "무엇을 할지"로 적는 방법입니다.

```java
// for문
List<String> names = new ArrayList<>();
for (Reservation r : reservations) {
    if (r.status() == CONFIRMED) {
        names.add(r.guestName());
    }
}

// Stream
List<String> names = reservations.stream()
        .filter(r -> r.status() == CONFIRMED)   // 확정만
        .map(Reservation::guestName)            // 이름으로 바꿔서
        .toList();                              // 리스트로
```

Stream은 세 부분으로 나뉩니다.

| 부분 | 하는 일 | 예 |
|---|---|---|
| 만들기 | 목록에서 Stream을 꺼낸다 | `list.stream()`, `Stream.of(...)` |
| 중간 연산 | 거르고, 바꾸고, 정렬한다. 여러 개 이어 붙인다 | `filter`, `map`, `sorted`, `distinct`, `limit` |
| 최종 연산 | 결과를 만든다. 이때 실제로 실행된다 | `toList`, `collect`, `count`, `sum`, `anyMatch`, `findFirst`, `forEach` |

자주 쓰는 것들입니다(실행 결과의 StreamBasics).

```java
.sorted(Comparator.comparing(Reservation::nights).reversed())   // 숙박 긴 순
.map(Reservation::room).distinct()                              // 중복 제거
.mapToInt(Reservation::nights).sum()                            // int로 바꿔 합계
.anyMatch(r -> r.nights() >= 4)                                 // 하나라도 있나
.filter(r -> r.room().equals("스위트")).findFirst()             // 첫 번째(Optional)
```

## 6. 처리 순서: 요소 하나씩 끝까지

Stream은 filter를 전부 끝낸 다음 map을 하는 것이 아닙니다. 요소 하나를 꺼내 filter → map → 결과까지 보낸 뒤 다음 요소를 꺼냅니다. 실행 결과의 StreamOrder와 "Stream 시각화" 탭에서 순서를 볼 수 있습니다.

```
1번 김민수 꺼냄
  filter 확정? 통과
  map → 김민수
2번 박지영 꺼냄
  filter 확정? 걸러짐
3번 이수진 꺼냄
  ...
```

이 방식이라 생기는 특징이 있습니다.

- 최종 연산이 없으면 아무것도 실행되지 않습니다. `filter`, `map`만 적어 두면 람다는 한 번도 불리지 않습니다.
- `limit(2)`, `findFirst()`, `anyMatch()`는 답이 나오면 바로 멈춥니다. 시각화의 limit 예제에서 4~6번은 꺼내지도 않았습니다.
- `sorted`는 예외입니다. 전부 받아야 순서를 정할 수 있어서, 모두 모은 뒤에야 다음 단계로 보냅니다.

## 7. 모으기: Collectors

```java
// 객실별 건수: {오션뷰=3, 스탠다드=2, 스위트=1}
Map<String, Long> countByRoom = reservations.stream()
        .collect(Collectors.groupingBy(Reservation::room, Collectors.counting()));

// 객실별 숙박 합
.collect(Collectors.groupingBy(Reservation::room, Collectors.summingInt(Reservation::nights)));

// 조건으로 둘로 나누기: {false=[...], true=[...]}
.collect(Collectors.partitioningBy(r -> r.status() == CONFIRMED));

// 문자열로 이어 붙이기
.map(Reservation::guestName).collect(Collectors.joining(", "));
```

`groupingBy`는 SQL의 `GROUP BY`와 비슷합니다. 다만 DB에서 할 수 있는 집계는 SQL로 하는 편이 낫습니다. 수만 건을 다 가져와서 자바에서 묶으면 느리고 메모리를 많이 씁니다.

## 8. 자주 만나는 예외

| 상황 | 예외 |
|---|---|
| 같은 Stream을 두 번 씀 | `IllegalStateException: stream has already been operated upon or closed` |
| `toList()` 결과에 add | `UnsupportedOperationException`. 바꿀 리스트가 필요하면 `new ArrayList<>(...)`로 감싼다 |
| `toMap`에서 키가 겹침 | `IllegalStateException: Duplicate key 오션뷰 (attempted merging values 김민수 and 이수진)`. 세 번째 인자로 합치는 방법을 준다 |
| `groupingBy` 키가 null | `NullPointerException: element cannot be mapped to a null key`. 먼저 `filter`로 null을 뺀다 |

`toMap` 예외는 운영에서 자주 만납니다. 개발할 때는 데이터가 겹치지 않다가, 실제 데이터에 같은 키가 생기는 순간 터지기 때문입니다.

`Collectors.toList()`와 `toList()`도 다릅니다. `toList()`(Java 16부터)는 바꿀 수 없는 리스트를 돌려주고, `Collectors.toList()`는 보통 `ArrayList`를 돌려줍니다. 레거시 코드를 고칠 때 바꾸면 add하던 곳에서 예외가 날 수 있습니다.

## 9. Optional

"값이 없을 수도 있다"를 null 대신 반환 타입으로 알려 줍니다. JPA의 `findById`(11장)도 `Optional`을 돌려줍니다.

```java
Optional<Reservation> found = repository.findById(9L);

found.map(Reservation::guestName).orElse("없음");                       // 없으면 기본값
found.orElseThrow(() -> new IllegalArgumentException("없는 예약입니다")); // 없으면 예외
found.ifPresent(r -> log.info("찾음 {}", r.guestName()));                // 있을 때만 실행
```

- `get()`은 값이 없으면 `NoSuchElementException`이 납니다. `orElseThrow`로 이유를 적어 주는 편이 낫습니다.
- `orElse(메서드())`는 값이 있어도 그 메서드를 먼저 실행합니다. 기본값을 만드는 데 DB 조회 같은 비용이 들면 `orElseGet(() -> 메서드())`를 씁니다(실행 결과의 OptionalBasics).
- `Optional`은 반환 타입에 씁니다. 필드나 매개변수에는 보통 쓰지 않습니다.

## 10. for문과 Stream 중 무엇을 쓸까

- 거르고, 바꾸고, 모으는 일은 Stream이 짧고 읽기 쉽습니다.
- 중간에 `break`, 예외 처리, 여러 변수를 함께 바꾸는 일이 많으면 for문이 낫습니다.
- 람다 안에서 바깥 리스트에 add하는 식(`forEach(r -> list.add(...))`)은 피하고, `toList()`나 `collect`로 모읍니다.
- 디버깅이 어려우면 중간에 `.peek(System.out::println)`을 넣어 지나가는 값을 찍어 봅니다. IntelliJ에는 Stream의 단계별 값을 보여 주는 디버거 기능도 있습니다.
- `parallelStream()`은 이유 없이 쓰지 않습니다. 웹 요청 처리 중에 쓰면 공용 스레드를 나눠 쓰게 되어 오히려 느려질 수 있습니다.

## 확인 문제

1. 람다식을 쓸 수 있는 인터페이스의 조건은?
2. `Predicate<T>`, `Function<T, R>`, `Supplier<T>`는 각각 어떤 모양의 함수인가요?
3. `reservations.stream().filter(...).map(...)`까지만 적고 실행하면 filter 안의 코드는 몇 번 실행되나요?
4. `filter → map → limit(2)`에서 조건에 맞는 요소가 1번과 3번이면, 4번 요소는 filter를 거치나요?
5. `Collectors.toMap(Reservation::room, Reservation::guestName)`이 운영에서 갑자기 예외를 냈습니다. 왜 그럴까요?
6. `orElse(findDefault())`와 `orElseGet(() -> findDefault())`의 차이는?

## 정답

1. 추상 메서드가 딱 하나인 인터페이스(함수형 인터페이스)여야 합니다.
2. `Predicate`는 값을 받아 true/false, `Function`은 값을 받아 다른 값, `Supplier`는 아무것도 받지 않고 값을 돌려줍니다.
3. 한 번도 실행되지 않습니다. 최종 연산이 있어야 실행됩니다.
4. 거치지 않습니다. 3번이 두 번째로 limit을 지나면 Stream이 멈춰서 4번은 꺼내지도 않습니다.
5. 같은 객실을 가진 예약이 둘 이상 생겨 키가 겹쳤기 때문입니다. 세 번째 인자로 합치는 방법을 주거나 `groupingBy`를 씁니다.
6. `orElse`는 값이 있어도 `findDefault()`를 먼저 실행하고, `orElseGet`은 값이 없을 때만 실행합니다.

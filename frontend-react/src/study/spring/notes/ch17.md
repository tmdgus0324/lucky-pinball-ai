운영 업무에서 코드를 고치면 "이걸 고쳤다가 다른 데가 깨지지 않을까"가 가장 걱정됩니다. 테스트는 그 걱정을 사람이 매번 손으로 확인하지 않고 명령 한 번으로 확인하게 해 줍니다. 이번 장은 3장의 "금요일 가격" 코드에 세 종류의 테스트를 붙여 봅니다.

## 1. 테스트의 종류

| 종류 | 무엇을 띄우나 | 속도 | 예제 |
|---|---|---|---|
| 단위 테스트 | 아무것도 안 띄움. 클래스 하나를 `new`로 만듦 | 가장 빠름 | `RoomServiceTest` |
| 슬라이스 테스트 | 필요한 계층만(`@WebMvcTest`는 웹, `@DataJpaTest`는 JPA) | 중간 | `RoomControllerTest` |
| 통합 테스트 | 애플리케이션 전체(`@SpringBootTest`) | 가장 느림 | `RoomPriceIntegrationTest` |

실행 결과 2번에서 단위 테스트 6개는 0.35초, 전체를 띄운 테스트 2개는 1.66초가 걸렸습니다. 업무 규칙(가격 계산, 상태 변경)은 단위 테스트로 많이 만들고, 계층을 잇는 부분만 통합 테스트로 몇 개 확인하는 것이 보통입니다.

## 2. JUnit 기본

```java
class RoomServiceTest {

    @BeforeEach                          // 각 테스트 전에 한 번씩
    void setUp() { ... }

    @Test
    @DisplayName("금요일에는 기본 가격보다 20% 비싸다")   // 결과에 보일 이름
    void fridayPrice() {
        // given: 준비
        RoomService roomService = new RoomService(roomRepository, fixedAt("2026-10-09"));
        // when: 실행
        int price = roomService.todayPrice(1L);
        // then: 확인
        assertThat(price).isEqualTo(216000);
    }
}
```

- given / when / then으로 나누면 무엇을 준비하고, 무엇을 하고, 무엇을 확인하는지 읽기 쉽습니다.
- 테스트는 서로 순서에 기대지 않아야 합니다. 테스트마다 필요한 것을 직접 준비합니다.
- `@ParameterizedTest`와 `@CsvSource`로 같은 테스트를 값만 바꿔 여러 번 돌릴 수 있습니다. 예제는 목·금·토·일 4가지를 한 메서드로 확인했습니다.

Boot 4.1.1에는 JUnit 6이 들어 있습니다(실행 결과 맨 아래). 위 애너테이션은 JUnit 5와 같습니다. 레거시 코드에서 보이는 JUnit 4는 모양이 조금 다릅니다.

| JUnit 4 | JUnit 5 이후 |
|---|---|
| `org.junit.Test` | `org.junit.jupiter.api.Test` |
| `@Before`, `@After` | `@BeforeEach`, `@AfterEach` |
| `@RunWith(SpringRunner.class)` | 필요 없음(`@SpringBootTest` 등에 포함) |
| 클래스와 메서드가 `public`이어야 함 | `public` 생략 가능 |

## 3. 확인하기: AssertJ

```java
assertThat(price).isEqualTo(216000);

assertThatThrownBy(() -> roomService.todayPrice(99L))
        .isInstanceOf(IllegalArgumentException.class)
        .hasMessage("없는 객실입니다: 99");
```

`assertThat(실제값).isEqualTo(기대값)` 순서로 읽혀서 문장처럼 보입니다. JUnit의 `assertEquals(기대값, 실제값)`도 같은 일을 하고 레거시 코드에 많습니다. 실패하면 이렇게 나옵니다(실행 결과 아래쪽).

```
expected: 216000
 but was: 180000
    at com.example.reservation.room.RoomServiceTest.fridayPrice(RoomServiceTest.java:50)
```

## 4. 가짜 객체: Mockito

`RoomService`를 단위 테스트하려면 `RoomRepository`가 필요합니다. 진짜 저장소를 쓰는 대신, 원하는 값을 돌려주는 가짜(mock)를 만듭니다.

```java
RoomRepository roomRepository = mock(RoomRepository.class);
when(roomRepository.findById(1L)).thenReturn(Optional.of(new Room(1L, "오션뷰 디럭스", 2, 180000)));

verify(roomRepository).findById(1L);     // 이 메서드가 이 값으로 불렸는지
verifyNoInteractions(roomService);       // 한 번도 불리지 않았는지
```

가짜를 쓰면 DB 없이도 빠르게 테스트할 수 있지만, 너무 많이 쓰면 "가짜끼리 잘 맞는지"만 확인하게 됩니다. 실행 결과 아래쪽에서 금요일 규칙을 깨뜨렸을 때, 서비스를 가짜로 바꾼 컨트롤러 테스트는 아무것도 모르고 통과했습니다. 가짜로 바꾼 부분은 그 테스트에서 확인되지 않는다는 뜻입니다.

## 5. 시간처럼 바뀌는 값은 주입받는다

`LocalDate.now()`를 코드 안에서 바로 부르면, 금요일 가격을 확인하려면 금요일까지 기다려야 합니다. 3장에서 `Clock`을 빈으로 받게 한 이유가 이것입니다. 테스트에서는 날짜가 멈춘 시계를 넣습니다.

```java
Clock.fixed(LocalDate.parse("2026-10-09").atTime(12, 0).atZone(SEOUL).toInstant(), SEOUL)
```

난수, 현재 시각, UUID처럼 실행할 때마다 바뀌는 값은 모두 같은 방법으로 테스트할 수 있게 만듭니다.

## 6. 컨트롤러 테스트: @WebMvcTest와 MockMvc

```java
@WebMvcTest(RoomController.class)
class RoomControllerTest {

    @Autowired MockMvc mockMvc;
    @MockitoBean RoomService roomService;

    @Test
    void rooms() throws Exception {
        when(roomService.findAll()).thenReturn(List.of(new Room(1L, "오션뷰 디럭스", 2, 180000)));

        mockMvc.perform(get("/rooms"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$[0].name").value("오션뷰 디럭스"));
    }
}
```

- `@WebMvcTest`는 컨트롤러, `@ControllerAdvice`, 필터, 인터셉터, `WebMvcConfigurer` 같은 웹 계층만 띄웁니다. `@Service`, `@Repository` 같은 일반 빈은 만들지 않습니다.
- 그래서 컨트롤러가 쓰는 서비스는 `@MockitoBean`으로 가짜를 넣어 줘야 합니다.
- `MockMvc`는 서버를 실제 포트로 띄우지 않고, 요청을 흉내 내서 DispatcherServlet(5장)에 바로 넣습니다. 주소 연결, JSON 변환, 상태 코드, 검증(7장), 예외 처리(8장)를 확인하기 좋습니다.
- 요청과 응답 전체를 보고 싶으면 `.andDo(print())`를 붙입니다.

Boot 3 이하 코드에서는 `@MockBean`을 많이 봅니다. Boot 4에서는 없어졌고 Spring Framework의 `@MockitoBean`으로 바꿔야 합니다.

## 7. 통합 테스트: @SpringBootTest

```java
@SpringBootTest
@AutoConfigureMockMvc
class RoomPriceIntegrationTest {

    @TestConfiguration
    static class FridayClockConfig {
        @Bean
        @Primary
        Clock fridayClock() { ... }
    }
    ...
}
```

- `@SpringBootTest`는 실제 실행과 같은 방식으로 모든 빈을 만듭니다. 컨트롤러 → 서비스 → 저장소가 진짜로 이어집니다.
- 일부 빈만 테스트용으로 바꾸려면 `@TestConfiguration`에 같은 타입의 빈을 등록하고 `@Primary`를 붙입니다. 같은 타입 빈이 둘이면 서버가 뜨지 않지만(3장), `@Primary`가 있으면 그것을 고릅니다.
- 기본은 실제 포트를 열지 않고 MockMvc로 요청합니다. `webEnvironment = RANDOM_PORT`를 주면 서버를 실제 포트로 띄우고 HTTP로 요청할 수 있습니다.

스프링은 설정이 같은 테스트끼리 컨텍스트를 재사용합니다. 그런데 테스트 클래스마다 `@MockitoBean`이나 `@TestConfiguration` 조합이 다르면 그때마다 새로 띄워서 전체 테스트가 느려집니다.

트랜잭션도 알아 둘 것이 있습니다.

- 테스트 메서드에 `@Transactional`을 붙이면 테스트가 끝날 때 롤백되어 DB가 깨끗하게 남습니다.
- `RANDOM_PORT`로 실제 HTTP 요청을 보내면, 서버 쪽 처리는 다른 스레드의 다른 트랜잭션이라 롤백되지 않습니다. 저장된 데이터가 다음 테스트에 남을 수 있습니다.

JPA 저장소만 확인할 때는 `@DataJpaTest`를 씁니다(`spring-boot-starter-data-jpa-test`). 엔티티와 저장소만 띄우고, 테스트마다 롤백하며, 메모리 DB가 있으면 그것을 씁니다.

## 8. 실행하고 결과 보기

```bash
./gradlew test                                # 전체
./gradlew test --tests "*RoomServiceTest"     # 클래스 하나
```

- 실패하면 빌드가 실패하고, `build/reports/tests/test/index.html`에 테스트별 결과와 실패 내용이 정리됩니다.
- IDE에서는 테스트 메서드 옆의 실행 버튼으로 하나씩 돌릴 수 있습니다.
- CI(GitHub Actions, Jenkins 등)에 `./gradlew test`를 넣어 두면, 테스트가 실패한 코드는 배포 단계로 넘어가지 않습니다.

## 9. 운영 업무에서 테스트를 쓰는 방법

- 버그를 고칠 때는 먼저 그 버그를 재현하는 테스트를 만들고, 실패하는 것을 확인한 뒤 고칩니다. 테스트가 통과하면 고쳐진 것이고, 같은 버그가 다시 생기면 테스트가 잡아 줍니다.
- 테스트가 거의 없는 레거시 시스템이 많습니다. 전체에 붙이려 하지 말고, 이번에 고치는 메서드부터 붙입니다.
- 결제, 문자 발송, AI처럼 비용이 들거나 실제로 무언가를 보내는 외부 API는 테스트에서 부르지 않습니다. 가짜 서버나 가짜 구현으로 바꿉니다(14장).
- 테스트가 가끔 실패했다 통과했다 하면 시간, 순서, 공유 데이터에 기대고 있지 않은지 봅니다.

## 확인 문제

1. 단위 테스트와 `@SpringBootTest`의 차이는? 어떤 것을 더 많이 만드나요?
2. `@WebMvcTest`로 컨트롤러를 테스트하는데 `RoomService` 빈이 없다는 오류로 시작하지 못합니다. 왜 그런가요?
3. `LocalDate.now()`를 바로 쓰는 코드는 왜 테스트하기 어렵나요?
4. 금요일 규칙을 깨뜨렸는데 `RoomControllerTest`는 통과했습니다. 왜 그런가요?
5. Boot 3 프로젝트를 Boot 4로 올렸더니 `@MockBean`이 컴파일되지 않습니다. 무엇으로 바꾸나요?
6. 버그를 고칠 때 테스트를 먼저 만들면 좋은 점은?

## 정답

1. 단위 테스트는 스프링 없이 클래스 하나만 확인해서 빠르고, `@SpringBootTest`는 애플리케이션 전체를 띄워서 느리지만 계층이 실제로 이어지는지 확인합니다. 단위 테스트를 더 많이 만듭니다.
2. `@WebMvcTest`는 웹 계층만 띄우고 `@Service` 빈은 만들지 않습니다. `@MockitoBean RoomService`로 가짜를 넣어야 합니다.
3. 실행하는 날짜에 따라 결과가 달라져서 원하는 요일(금요일)의 결과를 언제든 확인할 수 없습니다. `Clock`을 주입받으면 고정된 날짜를 넣을 수 있습니다.
4. 컨트롤러 테스트는 서비스를 가짜로 바꿨기 때문에 실제 가격 계산 코드를 실행하지 않습니다.
5. Spring Framework의 `@MockitoBean`으로 바꿉니다.
6. 버그가 실제로 재현되는지 확인할 수 있고, 고친 뒤 통과하면 고쳐진 것을 증명하며, 같은 버그가 다시 생기면 테스트가 잡아 줍니다.

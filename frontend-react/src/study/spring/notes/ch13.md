JPA에서 엔티티끼리 연결하는 방법(연관관계)과, 그 때문에 생기는 대표적인 성능 문제 N+1을 봅니다. "화면은 잘 나오는데 갑자기 느려졌다"의 흔한 원인입니다.

## 1. 연관관계

예약 여러 개가 객실 하나를 가리킵니다(N:1). 테이블에서는 `reservation.room_id` 외래 키입니다. JPA에서는 숫자 대신 객체로 연결합니다.

```java
@Entity
public class Reservation {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "room_id")
    private Room room;            // reservation.getRoom().getName()처럼 객체로 따라간다
}

@Entity
public class Room {
    @OneToMany(mappedBy = "room")
    private List<Reservation> reservations;   // 반대 방향(1:N). 필요할 때만 만든다
}
```

| 애너테이션 | 뜻 |
|---|---|
| `@ManyToOne` | 여러 개가 하나를 가리킴. 외래 키가 이쪽 테이블에 있음 |
| `@OneToMany(mappedBy = "...")` | 하나가 여러 개를 가짐. 외래 키는 상대 테이블에 있음 |
| `@JoinColumn(name = "room_id")` | 외래 키 컬럼 이름 |

`mappedBy`가 붙은 쪽은 "읽기 전용"입니다. 관계를 바꾸려면 외래 키를 가진 쪽(`Reservation.room`)을 바꿉니다.

## 2. 지연 로딩과 즉시 로딩

| | LAZY(지연) | EAGER(즉시) |
|---|---|---|
| 동작 | 예약만 조회. `room`은 처음 쓸 때 따로 조회 | 예약을 조회할 때 `room`도 같이 조회 |
| 기본값 | `@OneToMany` | `@ManyToOne`, `@OneToOne` |

실무에서는 `@ManyToOne`도 거의 항상 `LAZY`로 바꿉니다. EAGER는 필요 없는 화면에서도 매번 연관 객체를 가져오고, 목록을 조회할 때 예상하지 못한 추가 쿼리를 만듭니다. 필요한 화면에서만 아래 4절의 방법으로 같이 가져옵니다.

## 3. N+1 문제

실행 결과 1번을 보세요. 예약 목록을 가져온 뒤 예약마다 객실 이름을 읽자, 객실 조회가 따로 나갔습니다.

```
select ... from reservation               ← 1번
select ... from room where id=?           ← 예약마다(N번)
select ... from room where id=?
select ... from room where id=?
```

목록 1번 + 항목마다 N번이라서 N+1이라고 부릅니다. 예약이 1000건이면 쿼리가 1001번 나갑니다. 개발할 때는 데이터가 몇 건이라 모르고 지나가다가, 운영 데이터가 쌓이면서 갑자기 느려집니다.

N+1인지 확인하는 법은 SQL 로그를 켜고 같은 모양의 SELECT가 반복되는지 보는 것입니다(11장 5절).

## 4. 해결: 한 번에 같이 가져오기

| 방법 | 모양 | 특징 |
|---|---|---|
| fetch join | `@Query("select r from Reservation r join fetch r.room")` | JPQL로 직접. 가장 많이 씀 |
| `@EntityGraph` | `@EntityGraph(attributePaths = "room")` | 쿼리 메서드에 애너테이션만 붙임. left join으로 만들어짐 |
| 배치 크기 | `spring.jpa.properties.hibernate.default_batch_fetch_size: 100` | 객실을 `where id in (?, ?, ...)`로 묶어 가져옴. 1:N 컬렉션에 유용 |
| 따로 조회해서 묶기 | 목록 조회 1번 + 관련 데이터 조회 1번 후 메모리에서 묶기 | 연관관계가 없을 때(핀볼 예제) |

실행 결과 2, 3번처럼 쿼리가 1번으로 줄었습니다.

컬렉션(`@OneToMany`) 두 개를 한 번에 fetch join하면 행이 곱해져 중복이 생기거나 오류가 납니다. 컬렉션은 하나씩만 fetch join하고, 나머지는 배치 크기로 해결하는 것이 보통입니다.

## 5. LazyInitializationException

실행 결과 4번은 서비스(트랜잭션)가 끝난 뒤 컨트롤러에서 `room`을 읽었습니다.

```
org.hibernate.LazyInitializationException: Could not initialize proxy [...Room#1] - no session
```

지연 로딩은 DB 연결(세션)이 열려 있을 때만 할 수 있습니다. 트랜잭션이 끝나면 세션이 닫히므로 그 뒤에는 가져올 수 없습니다.

해결 방법:

- 서비스(트랜잭션 안)에서 필요한 값을 응답용 객체(DTO)로 다 꺼내서 넘긴다. 예제의 `ReservationView`가 그 방법입니다.
- 필요한 연관 객체를 fetch join으로 미리 가져온다.

`spring.jpa.open-in-view`를 켜면(기본값 true) 요청이 끝날 때까지 세션이 열려 있어서 이 오류가 나지 않습니다. 대신 화면을 그리는 내내 DB 연결을 붙잡고 있어서, 요청이 많을 때 연결이 모자랄 수 있습니다. 그래서 끄고(false) 서비스 안에서 처리하는 쪽을 권장합니다. Spring Boot는 이 값을 따로 정하지 않으면 시작할 때 이런 경고를 남깁니다(설정 없이 띄워 확인).

```
WARN  JpaBaseConfiguration$JpaWebConfiguration : spring.jpa.open-in-view is enabled by default.
      Therefore, database queries may be performed during view rendering.
      Explicitly configure spring.jpa.open-in-view to disable this warning
```

## 확인 문제

1. `@ManyToOne`의 기본 로딩 방식은 무엇이고, 실무에서 보통 무엇으로 바꾸나요?
2. 예약 100건 목록에서 예약마다 객실 이름을 읽으면 최대 몇 번의 쿼리가 나가나요?
3. N+1을 해결하는 방법 두 가지는?
4. 컨트롤러에서 `reservation.getRoom().getName()`을 부르자 `LazyInitializationException ... no session`이 났습니다. 원인과 해결은?
5. `open-in-view`를 켜면 4번 오류가 사라지는데도 끄는 이유는?

## 정답

1. EAGER입니다. 필요 없을 때도 같이 조회하는 문제가 있어서 LAZY로 바꿉니다.
2. 101번입니다(목록 1번 + 예약마다 1번). 같은 객실이 겹치면 그만큼 줄어듭니다.
3. fetch join(`join fetch`), `@EntityGraph`(그 밖에 배치 크기 설정)입니다.
4. 트랜잭션이 끝나 세션이 닫힌 뒤에 지연 로딩을 시도했기 때문입니다. 서비스 안에서 DTO로 값을 꺼내 넘기거나 fetch join으로 미리 가져옵니다.
5. 요청이 끝날 때까지 DB 연결을 붙잡고 있어서, 요청이 많으면 연결 풀이 모자랄 수 있기 때문입니다.

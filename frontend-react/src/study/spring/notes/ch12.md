트랜잭션은 "여러 DB 작업을 하나로 묶어서, 전부 성공하거나 전부 취소"하는 기능입니다. `@Transactional` 하나로 쓸 수 있어서 쉬워 보이지만, 롤백되리라 믿었는데 데이터가 남는 사고가 운영에서 자주 납니다. 실행 결과의 2번과 4번이 그 대표적인 두 경우입니다.

## 1. 왜 필요한가

예약과 결제를 생각해 봅니다.

1. 예약 저장
2. 결제 요청 → 실패

트랜잭션이 없으면 결제는 실패했는데 예약은 DB에 남습니다. 객실은 잡혔는데 돈은 안 낸 상태가 됩니다. 1, 2를 한 트랜잭션으로 묶으면 2가 실패할 때 1도 되돌아갑니다(롤백).

## 2. @Transactional

```java
@Service
public class ReservationService {
    @Transactional
    public void reserve(...) {
        repository.save(reservation);   // 1
        paymentClient.pay(...);         // 2: 예외가 나면 1도 롤백
    }
}
```

- 메서드가 시작될 때 트랜잭션을 열고, 정상으로 끝나면 커밋, 예외로 끝나면 롤백합니다.
- 보통 서비스 계층의 public 메서드에 붙입니다.
- 안에서 부르는 저장소 메서드는 같은 트랜잭션에 참여합니다(실행 결과의 `Participating in existing transaction`).
- 조회만 하는 메서드에는 `@Transactional(readOnly = true)`를 붙입니다. 읽기 전용임을 알려 JPA가 변경 감지를 하지 않는 등 불필요한 일을 줄입니다.

## 3. 함정 1: checked 예외는 롤백되지 않는다

스프링의 기본 규칙은 이렇습니다.

| 예외 종류 | 기본 동작 |
|---|---|
| `RuntimeException`(unchecked)과 `Error` | 롤백 |
| `Exception`을 상속한 checked 예외(`IOException`, 직접 만든 `PaymentException extends Exception` 등) | 커밋 |

실행 결과 2번이 그 모습입니다. 결제가 `PaymentException`으로 실패했는데 로그에는 `Initiating transaction commit`이 찍혔고, 예약이 DB에 남았습니다.

해결 방법:

```java
@Transactional(rollbackFor = Exception.class)   // checked 예외도 롤백
```

- 업무 예외를 `RuntimeException`으로 만들기(8장의 `ReservationException`처럼). 가장 흔한 방법입니다.
- checked 예외를 써야 하면 `rollbackFor`를 붙이기. 레거시 코드에서 `rollbackFor = Exception.class`가 거의 모든 메서드에 붙어 있다면 이 이유입니다.
- Spring 6.2부터는 `@EnableTransactionManagement(rollbackOn = ALL_EXCEPTIONS)`로 전체 기본값을 바꿀 수도 있습니다.

외부 시스템 연동 코드는 checked 예외(`IOException` 등)를 많이 던지므로 특히 조심해야 합니다.

## 4. 함정 2: 같은 클래스 안에서 부르면 적용되지 않는다

```java
@Service
public class ReservationService {
    public void reserveFromInside(String name) {
        saveAndFail(name);           // this.saveAndFail(...): 트랜잭션 없음!
    }

    @Transactional
    public void saveAndFail(String name) { ... }
}
```

실행 결과 4번에서 `saveAndFail` 안의 "트랜잭션 진행 중인가?"가 `false`였고, 예외가 났는데도 예약이 남았습니다.

이유는 스프링이 트랜잭션을 거는 방식에 있습니다. 스프링은 `ReservationService`를 감싼 대리 객체(프록시)를 빈으로 등록합니다. 컨트롤러가 서비스 메서드를 부르면 프록시가 먼저 받아 트랜잭션을 열고, 그다음 진짜 메서드를 부릅니다. 그런데 진짜 객체 안에서 `this.saveAndFail()`로 부르면 프록시를 거치지 않으므로 `@Transactional`이 무시됩니다.

```
컨트롤러 → [프록시: 트랜잭션 시작] → 진짜 서비스.reserveFromInside()
                                         └→ this.saveAndFail()   ← 프록시를 안 거침
```

해결 방법:

- 트랜잭션이 필요한 쪽(바깥 메서드)에 `@Transactional`을 붙인다. 가장 단순합니다.
- 트랜잭션 메서드를 다른 빈(클래스)으로 옮기고 그 빈을 주입받아 부른다.

같은 이유로, 프록시를 거치지 않는 경우에는 `@Transactional`이 적용되지 않습니다. `private` 메서드, 그리고 `new`로 직접 만든 객체가 그렇습니다.

## 5. 트랜잭션이 걸렸는지 확인하는 법

```yaml
logging:
  level:
    org.springframework.orm.jpa.JpaTransactionManager: debug     # JPA
    # org.springframework.jdbc.datasource.DataSourceTransactionManager: debug   # MyBatis, JDBC
```

`Creating new transaction with name [클래스.메서드]`가 그 메서드에서 찍히는지 봅니다. 기대한 메서드 이름이 아니라 `SimpleJpaRepository.save`가 보인다면(실행 결과 4번), 서비스의 트랜잭션이 적용되지 않은 것입니다.

코드 안에서는 `TransactionSynchronizationManager.isActualTransactionActive()`로 확인할 수 있습니다.

## 6. 전파 (propagation)

트랜잭션 메서드가 다른 트랜잭션 메서드를 부를 때 어떻게 할지 정합니다.

| 값 | 동작 |
|---|---|
| `REQUIRED`(기본) | 이미 있으면 참여, 없으면 새로 만듦 |
| `REQUIRES_NEW` | 항상 새로 만듦. 바깥 트랜잭션과 따로 커밋·롤백 |

`REQUIRES_NEW`는 "본 작업이 롤백돼도 남아야 하는 기록"에 씁니다. 오류 로그, 감사(이력) 로그가 대표적입니다.

## 확인 문제

1. `@Transactional` 메서드에서 `IOException`이 나면 기본 동작은 롤백인가요, 커밋인가요?
2. 결제 실패 예외를 `PaymentException extends Exception`으로 만들었습니다. 롤백되게 하는 방법 두 가지는?
3. 같은 클래스의 `@Transactional` 메서드를 `this`로 부르면 왜 트랜잭션이 적용되지 않나요?
4. 트랜잭션이 실제로 시작됐는지 로그로 확인하려면 무엇을 켜나요?
5. 예약 처리가 실패해 롤백되더라도 "실패 기록"은 남기고 싶습니다. 기록을 저장하는 메서드에 무엇을 붙이나요?

## 정답

1. 커밋입니다. checked 예외는 기본으로 롤백하지 않습니다.
2. `@Transactional(rollbackFor = Exception.class)`를 붙이거나, 예외를 `RuntimeException`을 상속하게 바꿉니다.
3. 트랜잭션은 빈을 감싼 프록시가 시작하는데, `this`로 부르면 프록시를 거치지 않고 진짜 객체의 메서드를 바로 부르기 때문입니다.
4. 트랜잭션 매니저 로그(`org.springframework.orm.jpa.JpaTransactionManager` 또는 `DataSourceTransactionManager`)를 debug로 켭니다.
5. `@Transactional(propagation = Propagation.REQUIRES_NEW)`를 붙여 별도 트랜잭션으로 저장합니다.

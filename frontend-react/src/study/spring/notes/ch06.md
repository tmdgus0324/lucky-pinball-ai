예약 API를 만들면서 REST 컨트롤러의 기본을 봅니다. 주소와 HTTP 메서드를 메서드에 연결하고, 요청 값을 받고, 알맞은 상태 코드로 응답합니다.

## 1. REST API의 모양

자원(명사)을 주소로, 하려는 일(동사)을 HTTP 메서드로 나타냅니다.

| 메서드 | 주소 | 하는 일 | 성공 응답 |
|---|---|---|---|
| GET | `/reservations` | 예약 목록 | 200 |
| GET | `/reservations/1` | 1번 예약 | 200 (없으면 404) |
| POST | `/reservations` | 예약 만들기 | 201 + `Location` 헤더 |
| DELETE | `/reservations/1` | 1번 예약 취소 | 204 (본문 없음) |
| PUT / PATCH | `/reservations/1` | 전체 / 일부 수정 | 200 |

`/getReservation.do?id=1`, `/cancelReservation.do` 같은 주소는 동사가 주소에 들어간 방식입니다. 레거시 시스템에서 흔히 보지만, 새로 만들 때는 위 표처럼 씁니다.

## 2. 주소 연결 애너테이션

| 애너테이션 | 쓰임 |
|---|---|
| `@RestController` | 메서드가 돌려주는 객체를 JSON 응답 본문으로 보낸다 |
| `@RequestMapping("/reservations")` | 클래스에 붙이면 아래 메서드 주소의 공통 앞부분 |
| `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping` | HTTP 메서드별 연결 |

`@Controller`는 화면(HTML)을 돌려줄 때 쓰고(16장), `@RestController`는 데이터(JSON)를 돌려줄 때 씁니다.

## 3. 요청 값 받기

| 값의 위치 | 예 | 받는 방법 |
|---|---|---|
| 주소 안 | `/reservations/1` | `@PathVariable Long id` |
| 쿼리 파라미터 | `/reservations?roomId=1` | `@RequestParam Long roomId` |
| 본문(JSON) | `{"roomId":1, ...}` | `@RequestBody CreateReservationRequest request` |
| 헤더 | `Authorization: Bearer ...` | `@RequestHeader("Authorization") String auth` |

- `@RequestParam`은 기본이 필수입니다. 없어도 되면 `required = false`나 `defaultValue`를 줍니다.
- `@RequestBody`는 JSON을 자바 객체로 바꿉니다. JSON 키 이름과 필드 이름이 같아야 들어갑니다. 이름이 다르면 오류 없이 `null`이 됩니다.
- 타입은 자동으로 바뀝니다. `"2026-11-01"`은 `LocalDate`로, `/reservations/1`의 `1`은 `Long`으로 바뀝니다. 바꿀 수 없으면 400입니다(실행 결과의 `/reservations/abc`, `"11월 1일"`).

## 4. 요청 객체와 응답 객체를 나누는 이유

예제는 요청용 `CreateReservationRequest`와 저장·응답용 `Reservation`을 따로 둡니다.

- 요청에 `id`가 없으니, 사용자가 `id`를 마음대로 정해서 보낼 수 없습니다.
- DB 엔티티(11장)를 그대로 응답하면, 엔티티에 필드를 하나 추가할 때마다 API 응답 모양도 바뀝니다.

이런 전달용 객체를 DTO(Data Transfer Object)라고 부릅니다. 자바 record로 만들면 짧게 쓸 수 있습니다.

## 5. 상태 코드 정하기: ResponseEntity

메서드가 객체를 그냥 돌려주면 200입니다. 다른 상태 코드나 헤더가 필요하면 `ResponseEntity`로 감쌉니다.

```java
return ResponseEntity.ok(found);                                     // 200
return ResponseEntity.notFound().build();                            // 404
return ResponseEntity.created(URI.create("/reservations/" + id))     // 201 + Location
                     .body(saved);
return ResponseEntity.noContent().build();                           // 204
```

자주 쓰는 상태 코드:

| 코드 | 뜻 | 언제 |
|---|---|---|
| 200 | 성공 | 조회, 수정 |
| 201 | 만들어짐 | POST로 새로 만듦 |
| 204 | 성공, 본문 없음 | 삭제 |
| 400 | 요청이 잘못됨 | 형식 오류, 검증 실패(7장) |
| 401 / 403 | 로그인 필요 / 권한 없음 | 9장 |
| 404 | 없음 | 없는 자원, 없는 주소 |
| 405 | 메서드 안 됨 | GET만 있는데 PUT으로 호출 |
| 409 | 충돌 | 이미 예약된 날짜 등 |
| 500 | 서버 오류 | 처리하지 못한 예외 |

## 6. 기본 오류 응답의 한계

실행 결과 아래쪽의 잘못된 요청들을 보면, 응답 본문은 모두 이런 모양입니다.

```json
{"timestamp":"...","status":400,"error":"Bad Request","path":"/reservations"}
```

왜 잘못됐는지는 응답에 없고 서버 로그(WARN)에만 있습니다. API를 쓰는 화면 개발자나 연동 업체는 이유를 알 수 없습니다. 7장(검증)과 8장(예외 처리)에서 응답 형식을 우리 것으로 바꿉니다.

## 확인 문제

1. `GET /reservations?roomId=1&status=CANCELED`에서 두 값을 받는 메서드 파라미터를 써 보세요.
2. 예약을 새로 만들었을 때 알맞은 상태 코드와 헤더는 무엇인가요?
3. JSON 본문의 `"guest_name"`이 `CreateReservationRequest`의 `guestName` 필드에 들어가지 않습니다. 오류가 나나요?
4. `/reservations/abc`를 호출하면 몇 번 응답이 오고, 이유는 무엇인가요?
5. 저장용 객체를 요청 본문으로 그대로 받으면 생길 수 있는 문제 한 가지는?

## 정답

1. `@RequestParam Long roomId, @RequestParam String status` (없어도 되면 `required = false`)
2. 201 Created와, 새로 만든 예약의 주소를 담은 `Location` 헤더입니다.
3. 오류는 나지 않고 `guestName`이 `null`이 됩니다. 이름을 맞추거나 `@JsonProperty("guest_name")`을 붙입니다. 이런 실수는 7장의 검증(`@NotBlank`)을 붙여야 잡힙니다.
4. 400입니다. `abc`를 `Long`으로 바꿀 수 없기 때문입니다(`MethodArgumentTypeMismatchException`).
5. 사용자가 `id`처럼 서버가 정해야 할 값을 마음대로 보내서 다른 데이터를 덮어쓸 수 있습니다.

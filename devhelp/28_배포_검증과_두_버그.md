# 28. 배포 검증과 두 버그 (Vercel SPA 404, 모바일 클리핑)

면접 전 "Phase 0" 체크리스트로 실제 배포(Render 백엔드 + Vercel 프론트)가 제대로 동작하는지 끝까지 훑었다. 코드만 보고 넘어갔으면 몰랐을, **실제 배포 환경에서만 재현되는 버그 두 개**를 이 과정에서 찾았다.

## Phase 0 체크리스트

1. 최신 커밋이 Render/Vercel에 실제로 반영됐는지 확인
2. 전체 데모 흐름(등록 → AI 운세 → 게임 → 결과 → 관리자)을 라이브 URL에서 직접 확인
3. 모바일 화면 대응 확인
4. GitHub 저장소를 public으로 전환 (커밋 이력에 시크릿이 없는지 먼저 스캔)

## 버그 1: Vercel에서 `/admin` 새로고침하면 404

### 증상
- 앱 안에서 `<Link>`로 `/admin`으로 이동하면 정상.
- 근데 `/admin`을 브라우저 주소창에 직접 치거나, `/admin` 페이지에서 새로고침(F5)하면 Vercel의 `NOT_FOUND` 페이지가 뜬다.

### 원인
React Router는 클라이언트 사이드 라우팅이라, 앱이 이미 로드된 상태에서 `<Link>` 클릭으로 이동하는 건 브라우저가 서버에 새 요청을 안 보낸다(JS가 알아서 화면만 바꿔치기). 근데 주소창 직접 입력이나 새로고침은 **브라우저가 그 경로로 진짜 HTTP 요청을 보낸다**. Vercel은 정적 파일 서버라 `/admin`이라는 실제 파일/폴더가 없으니 그대로 404.

### 해결
`frontend-react/vercel.json` 추가:

```json
{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
```

모든 경로 요청을 `index.html`로 돌려보내면, React Router가 그 안에서 다시 클라이언트 사이드로 라우팅을 처리한다. SPA를 정적 호스팅에 올릴 때 거의 항상 필요한 설정인데, 로컬 개발 서버(Vite dev server)는 이런 rewrite를 이미 알아서 해주기 때문에 로컬 테스트만으로는 절대 안 걸린다 — 실제 배포 환경에서만 드러나는 전형적인 케이스.

커밋: `22bcf7f`

### 검증
`/admin`에 직접 접속·새로고침을 반복해서 HTTP 200과 정상 화면이 뜨는지 확인 (로컬 재현이 안 되므로 라이브 URL로 직접 확인).

## 버그 2: 모바일에서 핀볼 보드가 약 39% 잘림

### 증상
모바일 화면(좁은 뷰포트)에서 핀볼 게임을 열면, 보드 오른쪽/아래쪽이 스크롤도 없이 그냥 잘려서 안 보인다.

### 원인
`.pinball-board`에 걸린 CSS `max-width: 100%`가 좁은 화면에서 컨테이너 폭을 물리 엔진의 원래 설계 폭(`cfg.boardWidth`, 560px)보다 작게 줄여버린다. 문제는 그 안의 `.pinball-scene`(실제 캔버스/DOM 요소들이 그려지는 곳)은 `position: absolute`로 배치돼 있어서 **부모가 줄어들어도 자기 크기(560px)는 그대로 유지**한다는 점이다. 결과적으로 `overflow: hidden`이 삐져나온 부분을 스크롤바도 없이 조용히 잘라버린다.

실제 측정: 보드 컨테이너 실제 폭 300px, 씬은 x=[47, 607] 즉 560px 폭 그대로 → 약 39%가 화면 밖으로 잘려나감.

### 해결
게임 시작 시점에 한 번, `boardEl.getBoundingClientRect().width`로 **CSS가 실제로 줄여놓은 진짜 렌더링 폭**을 측정해서 `fitScale = min(1, 렌더링폭 / cfg.boardWidth)`를 계산한다. 이걸 기존에 있던 카메라 확대/축소(`cameraScale`) 로직에 곱으로 얹었다 (`totalScale = fitScale * cameraScale`).

```ts
// engine.ts, applyCamera()
const totalScale = fitScale * cameraScale;
// 뷰포트 중앙 정렬 계산도 fitScale이 적용된 크기 기준으로
```

`frontend-react/engine.ts`에만 적용했고, 레거시 `frontend/js/game.js`는 이번 배포·데모 대상이 아니라서 건드리지 않았다 (물리 로직 변경이 아니라 순수 화면 맞춤 문제라, "물리 변경은 항상 양쪽에 반영" 원칙의 예외로 판단).

커밋: `f0cf60f`

### 검증
Playwright로 모바일 기기 에뮬레이션(로컬 + 실제 라이브 URL)해서, 최종 계산된 transform이 `matrix(0.535714, 0, 0, 0.535714, 0, 0)` — 정확히 `300/560`과 일치하는지 확인.

## 남은 것

모바일에서 운세 결과 카드 텍스트가 길면 잘리는 문제를 발견했으나 이번엔 수정하지 않고 다음으로 미뤘다 (`devhelp/00_개선로드맵.md`의 "다음에 고칠 것" 참고).

## 배운 점

두 버그 모두 **로컬 개발 서버에서는 재현되지 않고, 실제 배포 환경(정적 호스팅의 라우팅 방식, 실제 모바일 뷰포트 크기)에서만 드러났다.** "로컬에서 됐으니 끝"이 아니라, 배포 후 실제 URL로 직접 확인하는 단계가 왜 필요한지 보여주는 사례.

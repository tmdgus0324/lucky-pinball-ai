# 32. 관리자 로그인 추가

Phase 5의 마지막 항목. 관리자 화면(`/admin`)에 인증이 전혀 없던 걸(코드 주석에도 "인증 없음(MVP 한정)"이라고 대놓고 적혀 있었다) 로그인으로 막았다.

## 왜 IP 기반이 아니라 로그인인가

처음엔 "내 IP로 접속하면 관리자 메뉴가 자동으로 열리게" 하자는 아이디어가 있었다. 실제로 검토해보니 포트폴리오용으로는 안 맞았다:
- 면접관이 직접 관리자 화면을 눌러볼 수가 없다 (IP 허용 목록에 없으니까).
- 집/카페마다 IP가 바뀌어서 매번 재설정해야 하고, 정작 본인도 다른 곳에서 접속하면 못 들어간다.
- Render/Vercel처럼 프록시를 거치는 배포 환경에서 "진짜 클라이언트 IP"를 신뢰하기도 까다롭다(`RateLimitFilter`가 `X-Forwarded-For`를 쓰는 것과 같은 이유).

그래서 **아이디/비밀번호 로그인**으로 갔다. 면접관에게 데모 계정을 알려주면 어디서든 직접 눌러볼 수 있고, "왜 Spring Security를 안 썼나?"라는 질문에도 "관리자 계정이 환경변수로 고정된 하나뿐이라 그 정도 프레임워크는 과하다고 판단했다"고 답할 수 있다.

## 세션 쿠키 대신 토큰 헤더를 쓴 이유

백엔드(Render)와 프론트(Vercel)가 서로 다른 도메인이라, 쿠키 기반 세션은 `SameSite`/`Secure` 설정을 배포 환경에 정확히 맞춰야 하고 로컬 개발(http, 같은 브라우저의 다른 포트)에서는 또 다르게 동작해서 디버깅이 까다로울 걸로 예상됐다. 대신 로그인 성공 시 **불투명 토큰**을 발급해서 `Authorization: Bearer <토큰>` 헤더로 보내는 방식을 썼다 — 브라우저의 쿠키 정책과 완전히 무관해서 로컬/배포 환경 차이 없이 동일하게 동작한다.

- `AdminSessionStore`: 토큰을 메모리에 보관(TTL 12시간). RateLimitFilter와 같은 이유로 인메모리 — 서버가 여러 대로 늘어나면 Redis 등으로 옮겨야 한다.
- `AdminAuthController`: `POST /api/admin/login`(토큰 발급), `POST /api/admin/logout`(토큰 폐기).
- `AdminAuthFilter`: `/api/admin/**`(로그인 경로 제외) 요청마다 토큰 검사, 없거나 유효하지 않으면 401.
- 프론트: 토큰을 `localStorage`에 저장(새로고침해도 로그인 유지). XSS에 뚫리면 토큰도 같이 새는 절충이 있지만, 이 프로젝트는 `innerHTML`을 안 쓰고 React가 기본적으로 이스케이프해서 그 위험을 낮춰뒀다(devhelp/29).

## 비밀번호 기본값을 빈 문자열로 둔 이유

```yaml
admin:
  username: ${ADMIN_USERNAME:admin}
  password: ${ADMIN_PASSWORD:}
```

`ADMIN_PASSWORD`를 안 정하면 빈 문자열이 되는데, `AdminAuthController`가 **빈 비밀번호는 무조건 로그인 실패 처리**한다. 기본값을 아무 문자열로나 정해두면(예: `admin123`) 배포 시 환경변수 설정을 깜빡했을 때 "누구나 로그인 가능"이라는 훨씬 조용하고 위험한 사고로 이어진다 — 대신 "환경변수를 안 정하면 아예 로그인이 안 된다"가 안전한 실패 방식이다.

## DB TEST와의 충돌 — 공개 엔드포인트 분리

관리자 화면 로그인을 막다 보니, 참가자용 "DB TEST" 버튼이 문제였다. 이 버튼은 로그인 안 한 일반 참가자가 쓰는 기능인데, 기존에는 관리자 전용 `GET /api/admin/players`를 그대로 호출하고 있었다 — 그대로 두면 로그인 안 한 사람은 DB TEST를 못 쓰게 된다.

그래서 DB TEST 전용으로 **`GET /api/players/reusable`**이라는 별도 공개 엔드포인트를 새로 만들었다. 관리자용 엔드포인트보다 노출 필드를 좁혀서(이름·생년월일·운세 출처만, 운세 이력 전체는 안 줌) 정보 노출도 줄였다.

## 겪은 버그: CORS preflight를 막아버림

로그인까지는 됐는데, 로그인 직후 관리자 화면의 모든 표가 "Failed to fetch"로 전부 실패했다. 원인은 브라우저가 커스텀 헤더(`Authorization`)를 실제로 보내기 전에 먼저 **CORS preflight(OPTIONS) 요청**을 보내는데, 이 요청엔 당연히 토큰이 없으니 `AdminAuthFilter`가 401로 끊어버렸던 것 — 그러면 스프링의 CORS 응답 헤더 처리(`WebConfig`)까지 아예 못 가서, 브라우저가 실제 요청 자체를 보내지도 않고 막아버린다.

`RateLimitFilter`는 이 문제가 없었던 이유: 어떤 경우에도 요청을 막지 않고 `chain.doFilter()`로 넘겨서, 스프링의 CORS 처리가 뒤에서 정상적으로 실행됐기 때문이다. `AdminAuthFilter`는 진짜로 요청을 차단하는 필터라서 이 함정에 걸렸다.

**해결**: `OPTIONS` 메서드는 경로·토큰과 무관하게 항상 통과시킨다.

```java
boolean isPreflight = "OPTIONS".equalsIgnoreCase(request.getMethod());
if (!isAdminPath || isPreflight || LOGIN_PATH.equals(path)) {
    chain.doFilter(request, response);
    return;
}
```

회귀 방지용 테스트(`corsPreflightIsNeverBlockedEvenWithoutToken`)도 추가했다.

## 검증

Playwright로 실제 화면 흐름을 끝까지 확인했다:
1. `/admin` 접속 → 로그인 폼 노출
2. 잘못된 비밀번호 → 에러 메시지
3. 올바른 로그인 → 관리자 화면 진입, 참가자/게임/로그 표에 실제 데이터 정상 로드
4. 새로고침 → 로그인 유지(localStorage 토큰)
5. 로그아웃 → 로그인 폼으로 복귀
6. **로그인 전혀 안 한 상태**에서 AI TEST → 운세 확인 → DB TEST까지 정상 동작 확인 (공개 엔드포인트 분리가 제대로 됐는지 확인)

백엔드 유닛 테스트도 13개 추가(`AdminSessionStoreTest`, `AdminAuthFilterTest`, `AdminAuthControllerTest`) — 전부 통과.

## 배포 시 할 일

Render 환경변수에 `ADMIN_USERNAME`, `ADMIN_PASSWORD`를 설정해야 실제로 로그인이 가능해진다(설정 안 하면 의도한 대로 로그인이 항상 실패한다).

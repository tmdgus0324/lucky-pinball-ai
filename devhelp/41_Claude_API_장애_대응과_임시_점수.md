# 41. Claude API 장애 대응과 임시 점수 (로드맵 Phase 3)

Phase 2에서 로그를 깔아두고 보니, AI 호출이 실패할 때의 동작이 허술했다. 확인해 보니 문제가 세 가지였다.

1. **타임아웃이 사실상 없었다.** Anthropic Java SDK의 기본값은 요청 타임아웃 **10분**, 재시도 **2회**다(타임아웃·연결 오류·408/409/429/5xx가 재시도 대상). Claude가 멈추면 톰캣 스레드 하나가 최악의 경우 수십 분 붙잡힌다.
2. **실패 유형이 구분되지 않았다.** 서비스 오류 응답(`AnthropicServiceException`)만 잡고 있어서, 타임아웃·연결 오류는 그대로 500으로 떨어졌다.
3. **AI가 죽으면 게임 자체를 못 했다.** 운세 조회가 실패하면 게임 생성도 실패한다. 크레딧 소진이나 일시 장애 하나로 데모 전체가 멈춘다.

## 1. 타임아웃과 재시도

```yaml
anthropic:
  timeout-seconds: 10   # 평소 응답이 4초 안팎이라 여유를 둔 값
  max-retries: 1
```

`AnthropicOkHttpClient.builder().fromEnv().timeout(...).maxRetries(...)`로 적용한다. 최악의 대기는 10초 × (최초 + 재시도 1회) ≈ **20초**로 묶인다. 환경변수로 덮어쓸 수 있다(`ANTHROPIC_TIMEOUT_SECONDS`, `ANTHROPIC_MAX_RETRIES`).

## 2. 실패 유형별 응답

`ClaudeFortuneGenerator.translate()`가 SDK 예외를 상태 코드로 나눈다.

| 상황 | 상태 코드 | 사용자 문구 |
|---|---|---|
| 타임아웃(읽기/연결/전체 호출, `InterruptedIOException`이 원인 체인에 있음) | **504** | AI 응답이 늦어지고 있습니다. 잠시 후 다시 시도해주세요. |
| Claude 쪽 429(요청 과다) | **503** | AI 서비스에 요청이 몰려 있습니다. 잠시 후 다시 시도해주세요. |
| 그 외(인증 실패, 5xx, 연결 불가, 키 없음, 응답 파싱 실패) | **502** | AI 운세 서비스에 일시적인 문제가 있습니다. 잠시 후 다시 시도해주세요. |

- 사용자 응답에는 **일반 문구만** 싣는다. Claude의 원문 오류(예: `invalid x-api-key ...`)나 환경변수 이름은 `cause`로만 넘겨서 Phase 2의 ERROR 로그에서만 보이게 했다(테스트로 고정: 응답에 상세가 새지 않는다).
- `GlobalExceptionHandler`는 5xx를 ERROR+스택트레이스로 남기므로, 원인은 traceId로 로그에서 찾는다.

## 3. 임시 점수(FALLBACK)

AI 호출이 **5xx로 실패하면** 에러를 내는 대신 규칙 기반 생성기(`MockFortuneGenerator`)로 점수를 만들어 진행한다.

- **결정적이다**: 점수는 (이름, 생년월일, 오늘 날짜)로 정해지므로 같은 사람은 하루 동안 같은 임시 점수를 받는다. 게임마다 점수가 바뀌지 않는다.
- **운세처럼 보이지 않게 한다**: 규칙 기반 문구를 "운세"로 보여주지 않고 `AI 연결이 원활하지 않아 임시 점수로 진행합니다.`를 문구로 내려준다. 화면에서는 점수와 함께 ⚠ 안내로 표시된다.
- **폴백 대상은 외부 장애뿐이다**: 우리 코드의 버그(`IllegalStateException` 등)나 4xx(`ApiException` 중 5xx가 아닌 것)는 폴백으로 덮지 않고 그대로 드러낸다. 버그를 임시 점수로 가리면 영영 못 찾는다.
- **끌 수 있다**: `fortune.fallback-enabled: false`(`FORTUNE_FALLBACK_ENABLED`)면 502/503/504가 그대로 사용자에게 간다.
- **가려지지 않는다**: 사용자 응답은 200이라 예외 핸들러가 기록하지 않으므로, `FortuneQueryService`가 WARN 로그와 관리자 오류 로그("AI 호출 — 임시 점수로 대체: 원인")를 직접 남긴다. 관리자 참가자 표의 "AI 호출" 열에는 `임시`로 표시된다.

### 가장 중요한 설계: 임시 점수는 캐시가 아니다

이 프로젝트의 핵심은 "같은 이름+생년월일이면 AI를 다시 부르지 않고 DB 값을 재사용"하는 **신원 캐시**다. 임시 점수를 `source=FALLBACK`으로 저장하되, 캐시 조회 쿼리는 `source IN ('AI','CACHE')`만 대상으로 한다.

```java
findFirstByNameAndBirthDateAndSourceInOrderByCreatedDateAsc(name, birthDate, List.of("AI", "CACHE"))
```

- 이렇게 하지 않으면(= 이전 방식 그대로 이름+생년월일로만 찾으면) 장애 중에 한 번 받은 임시 점수가 그 신원의 "정답"으로 굳어서, AI가 복구돼도 영원히 가짜 점수를 쓴다.
- 반대로 AI 성공 결과가 이미 있는 신원은 캐시가 적중하므로 AI가 죽어 있어도 **진짜 결과**를 받는다.

### 두 경로의 차이

| 경로 | 동작 | 이유 |
|---|---|---|
| 사용자가 "운세 확인" (`getTodayFortune`) | 이전에 임시 점수를 받았어도 **AI를 다시 시도** | 복구됐는지 사용자가 다시 눌러 확인할 수 있어야 한다 |
| 게임 생성 (`getFortuneForGame`) | 이 참가자가 이미 받은 임시 점수가 있으면 **그대로 재사용**, AI 호출 생략 | AI가 느린 상태에서 8명을 다시 호출하면 8 × 최대 20초를 기다리고, 카드로 보여준 점수와 게임에 쓰인 점수가 달라질 수 있다 |

## 4. 검증

**자동 테스트(+13개, 전체 54개 중 실패 0 / 스킵 1)**

- `FortuneQueryServiceTest`(7): 성공 시 AI / 실패 시 FALLBACK과 오류 로그 기록 / **FALLBACK이 캐시를 오염시키지 않음** / 다시 눌러 AI 재시도 / 게임 경로 재사용(AI 호출 횟수 불변) / 폴백 끄면 예외 그대로 / 우리 버그·4xx는 폴백 안 됨. Claude 쪽은 성공·실패를 바꿔 끼우는 가짜 `FortuneService`로 교체했고, DB는 실제 쿼리를 타는 메모리 H2다.
- `ClaudeFortuneGeneratorTest`(6): JDK `HttpServer`를 "고장난 Claude"로 세워 실제 네트워크 호출로 확인 — 느린 응답은 설정한 1초 근처에서 504 / 재시도 횟수 / 429 → 503 / 401 → 502이며 응답에 원문 미노출, 401은 재시도 안 함 / 5xx는 재시도 / 키 없음 → 502. (SDK의 `fromEnv()`가 시스템 프로퍼티 `anthropic.baseUrl`/`anthropic.apiKey`를 먼저 읽는 점을 이용했다. "키 없음" 테스트는 개발 PC에 `ANTHROPIC_API_KEY`가 있으면 스킵된다.)
- 테스트용 `src/test/resources/application.properties`로 테스트가 개발용 파일 DB가 아니라 **메모리 DB**를 쓰게 했다. 로컬에서 서버를 띄운 채 테스트를 돌려도 그 데이터를 건드리지 않는다.

**실서버 확인**(별도 포트, 메모리 DB, AI 주소를 닫힌 포트로 지정): 운세 확인 → 200 + `source=FALLBACK`, 같은 사람 재확인 → 같은 점수, 게임 생성 0.5초 만에 완료(AI 재호출 없음), 관리자 로그에 "AI 호출" 항목(traceId 포함), 관리자 참가자 목록 `FALLBACK`.

## 5. 한계

- 임시 점수는 **이름+생년월일 기준 결정적 값**이라, 장애 중에는 사람마다의 개성 있는 운세가 아니라 점수만 의미가 있다(그래서 문구를 보여주지 않는다).
- 서킷 브레이커는 넣지 않았다. AI가 죽어 있으면 "운세 확인"마다 최대 약 20초를 기다린 뒤 폴백된다. 트래픽이 큰 서비스라면 연속 실패 시 일정 시간 AI 호출을 건너뛰는 서킷 브레이커가 필요하다.
- 오류 로그(`ErrorLogStore`)는 아직 메모리라 서버가 재시작되면 사라진다(다음 단계에서 DB로 영속화).

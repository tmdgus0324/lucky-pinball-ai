**포함된 기록**

- [구 37] 결과 배너를 맵 위로, 버튼을 제목 줄로, 빠른 추가 이름을 "N번"으로

> **AI 코멘트 — 화면에서 남은 개선점**
>
> **1. 같은 이름의 참가자가 있으면 실시간 순위 패널이 꼬인다** ([구 39])
>
> 순위 패널은 참가자 **이름**을 키로 색을 기억합니다(이름 → 색 `Map`). 그런데 서버는 한 판에 같은 이름을 두 번 등록하는 것을 막지 않아서, 예를 들어 "김민수"가 둘이면 한쪽 정보가 다른 쪽을 덮어씁니다. 원래 문서에도 "기존 한계"로 적혀 있습니다. 화면 쪽에서 이름 대신 **`playerId`를 키로** 쓰면 해결되고, 등록할 때 같은 판의 중복 이름을 막는 것도 방법입니다. DB TEST는 이미 같은 판에 있는 이름을 제외하고 등록하지만, 직접 입력하는 경우는 막지 않습니다.
>
> **2. 색만으로 구분하는 부분** ([구 39])
>
> 공 색 점은 이름과 함께 표시돼서 이름으로도 구분할 수 있습니다. 다만 공 위의 이름은 작아서 사실상 색으로 구분하게 되는데, 8색 중 초록·노랑·주황처럼 적록 색각 이상이 있으면 헷갈릴 수 있는 조합이 있습니다. 순위 패널처럼 번호(등록 순서)를 함께 보여 주면 색에만 의존하지 않게 됩니다. 이 부분은 색각 시뮬레이터로 실제 확인해 보지는 않았습니다.
>
> **3. 남아 있는 화면 과제**
>
> - 관리자 화면의 참가자·게임 표가 좁은 화면에 맞춰져 있지 않습니다(README의 보완 예정).
> - 레거시 `frontend/`는 예전 보라 팔레트 그대로입니다([구 38]). 레거시를 어떤 성격으로 둘지 정하는 문제와 같이 보면 됩니다(`devhelp/05` AI 코멘트).
> - [구 46]의 모바일 확인은 브라우저의 휴대폰 폭 흉내로만 했습니다. 실제 기기(특히 글꼴이 다른 iOS)에서 한 번 보는 것을 권합니다.
>
> **잘한 점 하나**: [구 38]에서 버튼 글자를 흰색에서 어두운 색으로 바꾼 근거를 "대비 2.6"처럼 숫자로 남긴 것은 좋은 습관입니다. 색 결정을 취향이 아니라 기준(WCAG 대비율)으로 설명할 수 있습니다.

## [구 37] 결과 배너를 맵 위로, 버튼을 제목 줄로, 빠른 추가 이름을 "N번"으로

직접 테스트해보다가 나온 화면 개선 3건이다. 전부 React 프론트(`frontend-react`)만 바꿨다 — 화면 구성 변경이라 물리 엔진을 공유하는 레거시 `frontend/`에는 반영하지 않았다(devhelp/02(구 25)의 "UI 전용 기능은 React만" 기준과 같다).

### 1. 당첨 결과를 맵 위 오버레이로

**문제**: 게임이 끝나면 아래에 "4. 결과" 패널이 새로 생겨서, 결과를 보려면 스크롤을 해야 했다.

**해결**: "4. 결과" 패널을 없애고, 같은 배너(🔔 + "N번 님 당첨!")를 **맵 위에 겹쳐서** 띄운다. 맵 위 ✕로 닫을 수 있다(겹쳐 있는 채로 계속 못 치우면 맵을 가리니까).

**위치를 정한 근거**
- 카메라는 선두 공을 **보드 요소의 세로 중앙(50%)** 에 고정해서 따라간다(`applyCamera`). 그래서 게임 끝 무렵에 사용자의 시선과 결승선은 보드 중앙 높이에 있다. 배너를 그 근처에 두면 스크롤이 필요 없다.
- 배너의 **아래쪽 가장자리**를 46%에 맞췄다(`top: 46%; transform: translateY(-100%)`). 처음엔 위쪽 가장자리를 36%에 맞췄는데, 보드가 축소되는 모바일(폭 300px → 높이 약 810px)에서는 배너가 상대적으로 커서 결승선을 가렸다. 아래쪽 기준으로 바꾸니 데스크톱·모바일 둘 다 결승선과 공이 보인다.
- `position: sticky`는 쓰지 않았다. 상위 `.main-content`에 `overflow-x: auto`가 있으면 그 요소가 스크롤 컨테이너가 돼서(세로도 `auto`로 계산됨) 페이지 스크롤에 sticky가 안 걸린다. 이 속성은 관리자 표의 가로 스크롤 때문에 있는 것으로 보여 건드리지 않았다.

**구조**: 배너를 보드(`.pinball-board`) 안에 넣으면 엔진이 `boardEl.innerHTML = ''`로 비울 때 같이 지워진다. 그래서 보드 옆 **형제 요소**(`.board-wrap` 안)로 두고, `PinballBoard`에 `overlay` prop을 추가해 `GamePage`가 결과 배너를 넘기게 했다. `#resultSection` id는 배너에 그대로 남겼다(테스트 스크립트가 이 id로 게임 종료를 판단). 배너의 게임 ID(UUID) 줄은 오버레이에서 뺐다 — 맵 위에서는 시각적 잡음이고, 관리자 화면에 남아있다.

### 2. 빠른 추가 이름: "게스트N" → "N번"

- 이름은 `1번, 2번, ...` 형식. 번호는 **현재 참가자 목록에 없는 가장 작은 번호**부터 채운다. 전체 초기화 후에는 항상 1번부터 나가고, 이미 1·2·3번이 있으면 4번부터 이어진다.
- "매번 무조건 1번부터"로 하지 않은 이유: 한 판에 같은 이름이 둘 생기면 엔진의 대기 목록 `pendingNames`가 이름 기준 `Set<string>`이라 순위 패널의 대기 인원·"당첨" 강조가 틀어진다(같은 이름이 하나로 합쳐짐). 전체 초기화 후에는 어차피 1번부터 나가니 사용자가 체감하는 동작은 같다.
- 이전엔 `useRef` 카운터가 계속 올라가서, 초기화해도 게스트9~16으로 이어졌다. 그 카운터를 없앴다.

**DB 영향: 수정 불필요.** 확인한 것:
- 백엔드에 "게스트"라는 이름 의존 코드가 없다.
- `PlayerEntity.name`에 유니크 제약이 없고, 이름은 그냥 문자열(`@Size(max=20)`)이다.
- 빠른 추가 참가자는 `birthDate`가 null이라 `FortuneQueryService.getTodayFortune`이 이름 기준 캐시 조회를 하기 전에 바로 `NONE`으로 반환한다. 서로 다른 판의 "1번"끼리 캐시가 섞일 일이 없다.
- 기존 DB에 남아있는 "게스트N" 행은 그대로 둬도 무해하다.

### 3. 운세 확인 / 게임 시작 버튼을 제목 줄 오른쪽으로

- 섹션 제목과 버튼을 한 줄(`.panel-head`)에 두고, 설명 문구는 그 아래로 내렸다. 별도 `actions-row`는 없앴다(등록 폼의 "전체 초기화"와 관리자 화면에서는 계속 쓴다).
- 처음엔 좁은 화면에서 버튼이 제목 아래로 내려가게(`flex-wrap`) 했는데, 모바일(390px)에서 제목이 어절 중간(`곳/에서`)에서 끊기고 버튼이 제목과 설명 사이에 끼어 어색했다. 버튼은 같은 줄 오른쪽에 고정하고(`flex: 0 0 auto`), 제목이 `word-break: keep-all`로 어절 단위로 접히게 바꿨다.

### 검증

실제 브라우저(Playwright)로 데스크톱 1280×900, 모바일 390×844에서 확인했다.

| 항목 | 결과 |
|---|---|
| 빠른 추가 3명 → +2명 → 전체 초기화 후 4명 | 1~3번 → 4·5번 → 1~4번, 화면 어디에도 "게스트" 없음 |
| 제목 줄에 버튼 | 데스크톱·모바일 모두 같은 줄 오른쪽 |
| 8명 게임 종료 시 배너 | `.board-wrap` 안, 별도 결과 패널 없음, 보드 폭 안, **스크롤 없이 화면 안**, ✕ 닫기 동작, 페이지 오류 없음 |
| 모바일 보드 축소(`fitScale`) | 보드 폭 300px로 정상 축소, 배너가 보드 밖으로 안 넘침 |

**테스트하다 틈이 났던 것**: 처음엔 배너가 화면 밖으로 나왔다고 측정됐는데, 코드 문제가 아니라 테스트 문제였다. `page.click('게임 시작')`이 버튼을 보이게 하려고 페이지를 위로 되돌려 스크롤해서, 미리 맞춰둔 "보드 중앙을 보는 상태"가 풀린 것이다. 실제 사용자처럼 시작을 누른 **뒤에** 보드 중앙으로 스크롤하도록 고쳐서 측정했다.

## [구 38] 팔레트를 보라에서 중립 다크 + 오렌지로 바꾼 과정

전체가 남보라 배경에 보라 버튼이라 "AI 기본 세팅" 같다는 지적에서 시작했다. 먼저 색이 왜 그렇게 됐는지부터 확인하고, 바꿀 방향이 참고 사이트와 겹치지 않는지 따져본 뒤 적용했다.

### 1. 보라는 어디서 왔나

- 첫 커밋(9/22)의 초기 목업(`plan/mockups/style.css`)에 이미 `#7c5cff`(보라 버튼), `#ffd166`(금색), 남보라 배경이 있었다. 색을 고른 이유나 사용자가 지정한 기록은 문서 어디에도 없다.
- 이후 React 마이그레이션까지 "디자인 결정이라 바꿀 이유가 없다"며(devhelp/01(구 08)) 그대로 이어받았다. 이 게임에 맞춰 고른 색이 아니라 초기 기본값을 계속 쓴 것이다.
- 이미지 파일은 없다. 화면은 전부 CSS와 이모지이고 공은 색 원이다. 다만 `public/favicon.svg`가 **Vite 기본 템플릿 로고(보라 번개)** 그대로였다.

### 2. 참고 사이트(lazygyu/roulette)와 겹치지 않는가

참고 사이트의 정체성은 **순검정 배경 + 시안 네온 글로우 + 중간 회색(#666 정도) 하단 패널 + 파란 토글 + 풀스크린 캔버스**다(스크린샷과 소스의 기본 도형색 `cyan/yellow/white`, 시안 블룸 기준).

| | 참고 사이트 | 새 팔레트 |
|---|---|---|
| 강조색 | 시안·파랑 | 오렌지(`#ff7a1a`) |
| 배경 | 순검정 | 어두운 무채색(`#0f1115`) |
| 글로우 | 네온 | 없음 |
| 구조 | 풀스크린 + 하단 패널 | 사이드바 + 카드 |

시안/파랑 포인트와 글로우를 쓰지 않았고, 패널도 중간 회색이 아니라 거의 검정에 가까운 회색(`#171a20`)에 얇은 테두리로 갔다. 후보 중 시안 네온(A안)이 참고 사이트와 가장 가까워서 제외했다.

### 3. 적용한 값 (`frontend-react/src/styles/style.css`)

| 변수 | 이전 | 이후 | 비고 |
|---|---|---|---|
| `--bg` / `--panel` / `--panel-2` | `#14121f` / `#1e1b2e` / `#262238` | `#0f1115` / `#171a20` / `#1f232b` | |
| `--border` | `#322c4a` | `#2a2f39` | |
| `--text` / `--muted` | `#f1eefc` / `#a79fc4` | `#eceff4` / `#9aa3b2` | |
| `--accent-2` (주요 버튼) | `#7c5cff` | `#ff7a1a` | |
| `--accent` (당첨·결승선) | `#ffd166` | 그대로 | |
| `--on-accent-2` (신규) | - | `#1a1208` | 주황 버튼 위 글자 |
| `--wall` (신규) | - | `#3a404c` | 맵의 벽·선반 (테두리색과 분리해서 맵에서 형체가 보이게) |

- 변수 밖에 박혀 있던 보라 계열 값도 정리: 보드 배경 그라데이션, 못 색, 공 글자색, 결과 배너 그라데이션·오버레이 배경. 회전 막대는 빨강→금에서 **주황→금** 그라데이션으로.
- 버튼 글자를 흰색에서 어두운 색으로: 흰 글자는 주황 위에서 대비가 약해서(2.6 정도) 어두운 글자로 바꿨다.
- 파비콘을 이 게임의 공(주황→금 그라데이션 공 + 못 3개)으로 교체하고, 모바일 주소창 색(`theme-color`)을 새 배경색에 맞췄다.
- **일부러 안 바꾼 것**: 운세 등급 색(`tier-3` 보라는 "에픽" 희귀도 관례), 공 8개의 구분용 팔레트(8색이 필요해서 보라·시안 포함), 로고의 🎱 이모지(OS 폰트가 그리는 색이라 CSS로 못 바꿈).

### 4. 검증

- **보라 잔여 자동 탐지**: 게임 화면과 관리자 화면의 모든 요소에서 계산된 색(글자·배경·테두리·outline)을 HSL로 바꿔 hue 250~295°, 채도 12%↑를 찾았다(공 팔레트와 `tier-3`은 제외). 결과 **0건**.
- **명암비**(WCAG): 주황 버튼의 글자 **7.1:1**(기준 4.5), 비활성 버튼 6.19:1, 설명 글자(`--muted`)가 패널 위에서 6.85:1.
- 게임 화면 → 8명 게임 진행 → 결과 오버레이 → 관리자 화면까지 화면 캡처로 확인했고 페이지 오류는 없었다.

### 5. 남은 것

- 레거시 `frontend/`는 보라 팔레트 그대로다. 주력은 React이고 레거시는 물리 동기화용으로만 유지 중이라 이번엔 건드리지 않았다.
- 색이 변수로 모여 있어서 다른 팔레트로 바꾸려면 `:root` 값과 위 4곳(보드·못·공 글자·배너)만 보면 된다.

## [구 39] 참가자별 공 색 표시, 참가자 등록 버튼 스타일 통일

### 1. 참가자 등록 버튼을 AI TEST와 같은 스타일로

"참가자 등록" 버튼만 주황 강조(primary)였는데, 포트폴리오 시연에서는 AI TEST를 주로 누르므로 AI TEST와 같은 보조(secondary) 스타일로 맞췄다(`className="secondary"` 한 줄). 이제 이 줄에는 주황 강조 버튼이 없고, 주황은 2번 섹션의 "운세 확인"과 3번 섹션의 "게임 시작"에만 남는다. AI TEST를 주황으로 강조하는 쪽을 원하면 같은 한 줄로 바꿀 수 있다.

### 2. "누가 무슨 색 공인지" 표시

**문제**: 맵이 작아서 공 위의 이름을 읽기 어려운데, 어떤 참가자가 어떤 색 공인지 화면 어디에도 안 나와 있었다.

**원리**: 공 색은 게임 시작 때 **참가자 순서(= 등록 목록 순서)** 대로 배정된다(`palette[index]`, 백엔드가 `playerIds` 순서 그대로 참가자를 돌려준다). 그래서 같은 순서·같은 색을 게임 시작 **전**의 화면에도 미리 보여줄 수 있다.

**구현**
- 팔레트를 `game/ballColors.ts`로 빼서 엔진과 화면이 같은 값을 쓴다(`BALL_COLORS`, `ballColorAt(index)`). 색마다 한글 이름(회색·초록·하늘…)이 있어 점에 마우스를 올리면 "초록 공"처럼 보인다.
- 색 점을 세 군데에 붙였다: **등록 목록 칩**(빠른 추가·AI TEST·DB TEST 모두), **운세 카드 이름 앞**, **실시간 순위 패널**(진행 중·완주 모두).
- 등록 칩과 운세 카드는 React 컴포넌트(`BallDot`), 순위 패널은 엔진이 DOM을 직접 그리므로 같은 `.ball-dot` 클래스의 `<span>`을 만들어 붙인다. 순위 패널이 이름 기준 `Set`이던 것을 이름 → 색 `Map`으로 바꿔 색 정보를 같이 들고 다닌다(참가자 이름이 같으면 서로 덮어쓰는 기존 한계는 그대로다).
- 8번째 색을 **청록(`#22d3ee`) → 흰색(`#e5e7eb`)** 으로 바꿨다. 하늘(`#38bdf8`)과 청록은 작은 공에서 구분이 안 돼서, "하늘 공 / 청록 공"으로 표기해봐야 소용이 없기 때문이다. 흰색은 나머지 7색과 밝기부터 다르다.

**알아둘 점**: 참가자를 중간에 삭제하면 뒤 참가자의 색이 한 칸씩 당겨진다(순서 기준이라서). 게임 시작 때 실제 공 색도 그 시점의 순서로 정해지므로, 화면에 보이는 색과 공 색은 항상 일치한다.

### 검증

실제 브라우저(Playwright)에서 빠른 추가 8명 → **"2번" 삭제(색이 밀리는 경우)** → 운세 확인 → 게임 시작 → 완주까지 진행하면서, 이름 기준으로 색을 서로 대조했다.

| 항목 | 결과 |
|---|---|
| 참가자 등록 버튼 vs AI TEST 버튼 (배경·테두리·글자색·테두리 두께) | 동일 |
| 등록 칩 8개 색 = 팔레트 순서 | 일치 |
| 삭제 후 칩 색이 한 칸씩 당겨짐 | 일치 |
| 운세 카드 색 = 칩 색 | 일치 |
| 실시간 순위(진행 중) 색 = 칩 색 | 일치 |
| 실제 공(`.ball`) 배경색 = 칩 색 | 일치 |
| 실시간 순위(완주 후) 색 = 칩 색 | 일치 |
| 페이지 오류 | 없음 |

테스트 도중 순위 패널 두 항목이 처음엔 불일치로 나왔는데, 코드 문제가 아니라 테스트의 이름 추출 정규식이 원인이었다(순위 패널의 이름 앞 공백을 flex 간격으로 바꾸면서 `?3번`처럼 붙어 정규식이 이름을 통째로 잘라냄). 위치별로 `.position`·`.ball-dot`을 지운 뒤 이름을 읽도록 고쳐서 다시 확인했다.

레거시 `frontend/`에는 반영하지 않았다(화면 구성 변경은 React만, devhelp/02(구 25) 기준).

## [구 46] 모바일 운세 카드 텍스트 잘림

배포 검증 때(devhelp/06(구 28)) "모바일에서 운세 카드 텍스트가 길면 잘린다"고 적어 두고 미뤘던 문제다. 기록이 한 줄뿐이라 먼저 재현부터 했다.

### 1. 재현 방법 — 백엔드 없이

Playwright로 화면을 열고, **API 응답을 브라우저에서 가짜로 바꿔 끼웠다**(`page.route`). 백엔드·Claude 없이 원하는 이름과 운세 문구를 마음대로 넣을 수 있다.

- 넣은 값: 평범한 이름 / **띄어쓰기 없는 긴 한글 이름** / **띄어쓰기 없는 긴 영문 이름** / 두 줄 넘는 긴 운세 문구 / 띄어쓰기 없는 긴 영문 문구
- 폭: 320 / 360 / 390 / 412px(휴대폰), 1280px(데스크톱)
- 측정: 카드마다 내용이 카드 폭을 넘는지(`scrollWidth > clientWidth`), 페이지 전체가 가로로 넘치는지

### 2. 원인 두 가지

1. **띄어쓰기 없는 긴 영문이 카드 밖으로 잘렸다.** 모든 폭에서 해당 카드의 내용이 카드 폭을 넘었고, 끝부분이 보이지 않았다. 영문은 띄어쓰기에서만 줄바꿈되기 때문이다.
2. **한글이 단어 중간에서 줄바꿈됐다.** "이어지는 날입니/다.", "하루/가", "보세/요."처럼 끊겨서 글자가 잘린 것처럼 보였다. 브라우저 기본값(`word-break: normal`)은 한글을 **아무 글자 사이에서나** 줄바꿈한다. 실제 Claude 문구는 한글이라 기록된 "잘림"은 주로 이쪽이었을 가능성이 높다.

페이지 전체가 가로로 넘치지는 않았다(카드 안에서만 문제).

### 3. 수정 — CSS 몇 줄

```css
.fortune-card {
  min-width: 0;              /* 그리드 칸이 긴 내용 때문에 늘어나지 않게(기본값 min-width: auto) */
  word-break: keep-all;      /* 한글은 띄어쓰기에서만 줄바꿈 */
  overflow-wrap: anywhere;   /* 그래도 한 줄에 안 들어가는 긴 단어만 강제로 줄바꿈 */
}

.fortune-card .name { display: flex; align-items: flex-start; }   /* 공 색 점 옆에서 이름이 줄바꿈 */
```

- `keep-all`만 쓰면 띄어쓰기 없는 긴 한글 이름이 통째로 한 단어가 되어 다시 넘친다. `overflow-wrap: anywhere`가 그 경우에만 끊어 준다. 두 규칙을 **같이** 써야 한다.
- 처음엔 긴 이름이 통째로 다음 줄로 넘어가 **공 색 점만 첫 줄에 혼자 남았다.** 이름 줄을 flex로 바꿔 점과 이름을 나란히 두었다.
- 앱의 다른 설명 문구(`.desc`)는 이미 `keep-all`을 쓰고 있었는데 카드에만 빠져 있었다.
- 레거시 프론트엔드(`frontend/`)의 같은 카드에도 줄바꿈 규칙을 똑같이 넣었다.

### 4. 검증

- 4가지 휴대폰 폭과 데스크톱에서 **모든 카드의 넘침 0**, 페이지 가로 넘침 없음.
- 화면으로 확인: "날입니다.", "보세요."가 한 덩어리로 유지되고, 긴 영문 이름·문구도 카드 안에서 줄바꿈되며, 공 색 점과 이름이 나란히 놓인다.
- `tsc`, `lint`, `build` 통과.
- 실제 휴대폰 기기로는 확인하지 않았다(브라우저의 휴대폰 폭 흉내로 확인).

## 관리자 목록 페이징(게임·오류 로그), 로그아웃 버튼 위치 (2026-10-04)

### 1. 무엇이 문제였나

- **오류 로그**: 서버가 최신 200건을 주는데 화면은 한 번에 전부 그렸다. 길게 스크롤해야 아래의 AI 연결 확인에 닿았다.
- **게임 결과 목록**: 확인해 보니 페이징이 **없었고, 순서도 정해져 있지 않았다.** 서버가 준 순서 그대로 그려서 최신 게임이 맨 아래에 붙었다.
- **로그아웃 버튼**: 관리자 화면 제목 줄에서 왼쪽에 붙어 있었다.

참가자 표에만 페이징(20건)이 있었다.

### 2. 수정

- **공통 훅 `hooks/usePagination.ts`**: 참가자 표 안에 있던 페이징 계산을 꺼내 세 목록이 같이 쓴다. 데이터가 다시 로드되어 목록이 줄면 현재 페이지를 마지막 페이지로 맞춘다(빈 페이지가 보이지 않게).
- **게임 목록**: 20건씩, `createdAt` 기준 **최신순**으로 정렬한다(정렬은 화면에서 함).
- **오류 로그**: 20건씩(200건이면 10페이지). 설명 문구도 "화면에는 최신 200건을 20건씩"으로 바꿨다.
- **페이지 번호 줄이기**(`Pagination.tsx`): 페이지가 많으면 버튼이 줄을 넘친다. **첫 페이지, 마지막 페이지, 현재 ±2**만 보이고 사이는 "…"로 줄인다(예: `1 … 3 4 5`, `1 2 3 … 10`).
- **로그아웃**: 이미 있던 CSS 규칙 `.actions-row.spread button { margin-left: auto; }`를 쓰도록 클래스만 붙였다. 새 CSS는 필요 없었다.

### 3. 검증

- Playwright로 API를 가짜 응답으로 바꿔(참가자 45명, 게임 33건, 오류 85건) 1280px·390px에서 확인했다.
  - 세 목록 모두 페이지당 20행, 게임은 최신순.
  - 오류 로그 페이지 버튼이 `1 2 3 … 5` / `1 … 3 4 5`로 줄어든다.
  - 로그아웃 버튼의 오른쪽 끝이 제목 줄 오른쪽 끝과 같다.
  - 가로 스크롤 없음, 페이지 오류 없음.
- `tsc`, `lint`, `build` 통과.

### 4. 남은 점

- 페이징은 **화면에서만** 한다. 서버는 여전히 게임 전체, 오류 로그 200건을 한 번에 보낸다. 게임이 수천 건으로 늘면 서버 페이징(`?page=&size=`, JPA `Pageable`)으로 바꾸는 게 맞다. 지금 규모에서는 화면 페이징으로 충분하다고 판단했다.
- 게임 목록의 정렬도 서버(`ORDER BY created_at DESC`)로 옮기는 것이 더 정확하다. 지금은 화면에서 정렬한다.

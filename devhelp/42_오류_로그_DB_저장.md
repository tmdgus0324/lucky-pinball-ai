# 42. 관리자 오류 로그를 DB에 저장하기

관리자 화면의 오류 로그(`/api/admin/logs`)는 `CopyOnWriteArrayList`에 담긴 인메모리 목록이었다. Render 무료 티어는 슬립·재배포로 서버가 자주 다시 뜨기 때문에, 정작 "어젯밤에 무슨 오류가 났지?"를 보려는 시점에는 목록이 비어 있었다. 게임·참가자·운세는 이미 DB(Neon)에 있으니 오류 로그도 같은 곳으로 옮겼다.

## 1. 구조

```
GlobalExceptionHandler / FortuneQueryService
        │ errorLogStore.record(path, message, traceId)   ← 호출 방식은 그대로
        ▼
ErrorLogStore ── (잘라서 맞춤) ──> ErrorLogJpaRepository ──> error_log_entity 테이블
        │                                  └ 저장할 때마다 오래된 행 정리
        └ recent(): 최신 200건 → ErrorLogEntry(기존 응답 모양 그대로)
```

- **호출하는 쪽과 API 응답 모양은 바꾸지 않았다.** `ErrorLogStore.record/recent`의 시그니처와 `ErrorLogEntry` 레코드를 유지해서 `GlobalExceptionHandler`, `AdminController`, 프론트는 손대지 않았다(안내 문구 한 줄만 수정). 저장소만 바꿔 끼운 것이다.
- **엔티티**(`ErrorLogEntity`): `id`(IDENTITY), `occurredAt`, `path`, `message`, `traceId`. 컬럼명을 `timestamp`로 하지 않은 이유는 DB마다 예약어/타입 이름이라서다. 테이블은 `ddl-auto: update`가 만든다(Neon에는 첫 배포 때 자동 생성).

## 2. 설계에서 신경 쓴 세 가지

**① 오류를 기록하다 또 오류가 나면 안 된다.** 이 저장소는 예외 핸들러 안에서 불린다. DB가 끊겨서 저장이 실패하면, 사용자는 원래 오류 응답 대신 엉뚱한 500을 받게 된다. 그래서 `record()`는 저장 실패를 삼키고 WARN 로그만 남긴다(테스트: 저장이 예외를 던지는 저장소로도 `record()`가 던지지 않는다). 대신 서버 로그에는 원래 오류와 저장 실패 원인이 같이 남는다.

**② 독립된 트랜잭션(`REQUIRES_NEW`).** 호출한 쪽 트랜잭션이 롤백돼도 오류 기록은 남아야 하고, 반대로 기록 실패가 호출한 쪽을 rollback-only로 만들어서도 안 된다.

**③ 무한히 쌓이지 않게 한다.** 인메모리일 때는 200건에서 잘렸는데, DB는 그냥 두면 계속 늘어난다(봇이 잘못된 요청을 계속 보내면 더 빠르게). 최근 1000건(`error-log.max-entries`)만 남기고, 저장할 때마다 `id <= 방금 저장한 id - 1000`인 행을 한 번에 지운다. id가 IDENTITY라 시간순으로 증가하므로 `count(*)` 없이 쿼리 한 번으로 정리된다. 화면에는 최신 200건만 내려준다.

그리고 컬럼 길이(경로 500자, 메시지 1000자)를 넘는 값은 저장 전에 잘라서 맞춘다. 길이를 넘으면 INSERT가 실패하고, 그러면 ①에 의해 조용히 기록이 사라지기 때문이다. `ex.getMessage()`는 null일 수도 있어서 그 경우도 그대로 저장되게 했다.

## 3. 테스트 중에 발견한 문제

정리용 `delete` 쿼리를 `@Query`로 직접 만들었는데, 이런 수정 쿼리에는 `save()` 같은 기본 메서드와 달리 **트랜잭션이 자동으로 붙지 않는다**. 운영에서는 `record()`의 `@Transactional` 안에서 불리니 동작하지만, 테스트에서 `ErrorLogStore`를 직접 `new`로 만들었더니(스프링 프록시를 안 거침) `TransactionRequiredException`이 났다. 그런데 이 예외를 ①에서 삼켜 버려서 **오래된 행이 안 지워지는 채로 아무 에러도 보이지 않았다.** 테스트(`오류 7, 6, 5만 남아야 한다`)가 실패해서 알았다.

- 해결: 리포지토리 메서드에 `@Transactional`을 직접 붙여서, 호출하는 쪽이 트랜잭션 안에 있다는 가정에 기대지 않게 했다.
- 교훈: 에러를 삼키는 코드는 "실패해도 티가 안 나는" 위험이 있어서, 삼키는 경로까지 포함해 결과(행 개수)를 검증하는 테스트가 필요하다.

## 4. 검증

- 자동 테스트 +6개(전체 60개 중 실패 0 / 스킵 1): 최신순 조회와 모든 필드, **DB에서 직접 읽어도 존재**(인메모리가 아니라는 증거), 개수 제한 정리, 긴 문자열 잘림, DB 장애에도 호출자 무사, null 메시지. `GlobalExceptionHandlerTest`는 DB 없이 기록 내용만 보는 대역으로 바꿨다.
- 실서버 확인(별도 포트 + 파일 DB): 깨진 JSON(400)과 없는 참가자(404)로 오류를 만들고 → 서버 프로세스를 종료 → 다시 기동 → 같은 로그 2건이 같은 traceId·시각으로 조회됨. 405 요청은 의도대로 저장되지 않음.

## 5. 한계

- 오류 로그를 **서버 로그(Render 로그)의 대체재로 쓰지 않는다.** 이쪽은 메시지 한 줄과 traceId만 가지고, 스택트레이스는 서버 로그에만 있다. 관리자 화면에서 traceId를 확인하고 서버 로그에서 같은 ID를 검색하는 흐름은 그대로다.
- 같은 오류가 폭주하면 최근 1000건이 전부 같은 오류로 채워져 다른 오류가 밀려난다. 중복 묶기(같은 메시지 횟수 집계)나 레벨별 분리는 하지 않았다.
- 오류 기록마다 INSERT + DELETE 쿼리가 나간다. 요청 제한(RateLimitFilter)이 앞에 있고 오류 빈도가 낮아서 무시했지만, 오류가 초당 수십 건씩 나는 서비스라면 비동기 배치 저장이 필요하다.

> **1. 요청 제한을 `X-Forwarded-For` 헤더로 우회할 수 있다** ([구 29]) — ✅ 2026-10-04 수정(이 문서 마지막 절)
>
> `RateLimitFilter`는 `X-Forwarded-For`의 **첫 번째 값**을 방문자 IP로 씁니다. 그런데 이 헤더의 첫 값은 클라이언트가 직접 넣어 보낼 수 있고, 프록시는 보통 실제 IP를 **맨 뒤에 덧붙입니다.** 그래서 요청마다 `X-Forwarded-For: 1.2.3.<임의값>`을 바꿔 보내면 IP마다 따로 세는 분당 20회 제한을 사실상 피할 수 있습니다. 비용이 드는 `/api/fortune`을 지키려고 만든 장치라 의미가 큽니다.
>
> - 고치는 방향: 신뢰할 수 있는 프록시가 붙인 값(목록의 **맨 뒤** 또는 플랫폼이 보장하는 헤더)만 쓰거나, Spring의 `server.forward-headers-strategy` 설정으로 프록시 헤더 처리를 서버에 맡깁니다. Render가 어떤 헤더를 어떻게 붙이는지는 배포 환경에서 확인이 필요합니다(저는 확인하지 못했습니다).
> - 그래도 마지막 방어선은 Anthropic 콘솔의 월 지출 한도($5)입니다([구 29]). 앱의 요청 제한이 뚫려도 청구 금액이 무한히 늘지는 않습니다.
>
> **2. 공개 데모 계정으로 참가자 개인정보가 보인다** ([구 32]) — 2026-10-05 검토 후 그대로 두기로 함(포트폴리오 데모 용도, 생년월일만 표시)
>
> 관리자 데모 계정(`admin` / `1234`)을 README에 공개했기 때문에, 누구나 관리자 화면에서 **참가자 이름과 생년월일 전체**를 볼 수 있습니다. 시연용 데이터만 있다면 괜찮지만, 실제 사람이 자기 생년월일을 넣으면 그대로 노출됩니다. 공개 데모를 유지한다면 관리자 화면에서 생년월일을 일부 가리거나(예: `1990-**-**`), 데모 계정은 가린 값만 보게 하는 정도를 검토할 만합니다.
>
> 같은 이유로, 데모 계정을 가진 누구나 관리자 화면의 "AI 연결 확인"으로 Claude를 호출할 수 있습니다. 5초 간격 제한이 있고 호출당 출력 1토큰이라 비용은 거의 없지만, "유료 호출 버튼이 공개되어 있다"는 점은 알고 있는 편이 좋습니다(`devhelp/09`(구 43)).
>
> **3. 관리자 로그인에 시도 횟수 제한이 없다** ([구 32]) — ✅ 2026-10-05 수정(IP당 분당 10회, 이 문서 마지막 절. 고정 시간 비교는 하지 않음)
>
> `/api/admin/login`은 요청 제한 대상이 아니라 비밀번호를 무한히 시도할 수 있습니다. 데모 비밀번호가 공개된 지금은 의미가 작지만, 비밀번호를 비공개로 바꾸면 로그인에도 같은 요청 제한(1번 문제를 고친 뒤)을 거는 것이 맞습니다. 비밀번호 비교는 `String.equals`인데, 응답 시간 차이로 비밀번호를 추측하는 공격까지 막으려면 `MessageDigest.isEqual` 같은 고정 시간 비교를 씁니다.
>
> **4. [구 34]의 교훈은 이후 작업에도 그대로 쓰였다**
>
> "필터가 직접 응답을 쓰면 스프링 MVC 설정이 적용되지 않는 사각지대가 된다"는 교훈은 나중에 요청 추적 ID를 넣을 때 그대로 반영됐습니다. 필터가 직접 쓰는 401·429 응답도 같은 오류 형식(`error`, `traceId`)을 갖도록 `ErrorBodies.json()`을 따로 만들었습니다(`devhelp/09`(구 40)). 한 번 겪은 버그를 "같은 모양의 다른 곳"에도 적용한 좋은 사례입니다.

## [구 29] 비용과 보안 방어 (Phase 1)

인증 없이 아무나 쓸 수 있는 공개 서비스이고, `/api/fortune`이 실제로 비용이 드는 Claude API를 호출한다. 이 조합이 갖는 두 가지 리스크(과금 폭탄, 악의적 입력)를 막는 최소한의 방어선을 깔았다.

### 왜 지금 하는가

- **DB 영속화(H2 → 실제 DB로 교체)보다 이걸 먼저 했다.** DB 영속화는 Render 무료 티어 자체가 영구 디스크를 지원하지 않아 재기동 시 초기화되는 "불편함"이지만, 이번 항목들은 지금 이 순간에도 공개 URL을 통해 실제로 노출돼 있는 리스크다. DB 마이그레이션은 핵심 계층을 건드리는 더 큰 작업이라, 면접 이후로 미뤘다.
- Anthropic 사용량 한도는 이 문서 범위 밖 — Anthropic 콘솔에서 본인이 직접 설정해야 하는 유일한 항목(월별 지출 한도 $5 + 자동충전 꺼둠으로 이중 방어 완료).

### 1. H2 콘솔 비활성화

`application.yml`:
```yaml
h2:
  console:
    enabled: ${H2_CONSOLE_ENABLED:false}   # 기본 false — 공개 배포 중이라 기본값을 꺼둔다
    path: /h2-console
```

#### 진행 중 있었던 일 (기록해둘 가치가 있어서 남김)

처음에 "H2 콘솔을 꺼야 한다"고 설명 없이 바로 코드부터 고치려다가 제지당했다 — *"H2 콘솔 비활성화를 왜 해야하는거야?? Phase 1은 왜 해야하는지도 같이 설명해줘"*. 설명 후 진행 승인을 받았는데, 그 다음에 실제로 라이브 `/h2-console`에 접속해서 H2 자체의 `webAllowOthers` 기본 방어("Sorry, remote connections are disabled")가 이미 원격 접속을 막고 있다는 걸 스크린샷으로 확인해서 역으로 지적받았다.

"지금 당장 뚫려있다"는 처음 설명은 틀렸고, 정확한 상태는:
- **지금**: H2의 기본 설정(`webAllowOthers=false`)이 이미 막고 있어서 당장 SQL을 직접 실행할 수 있는 건 아니다.
- **그래도 끄는 이유**: 이건 프레임워크의 기본값에 기대는 방어일 뿐이라, 나중에 실수로 `web-allow-others: true`를 추가하거나, 프록시 뒤에서 IP 체크가 우회되는 설정 변화가 생기면 바로 뚫린다. 공개 서비스에 관리용 콘솔을 애초에 열어둘 이유가 없으니, 로컬 개발 때만 켜고(`H2_CONSOLE_ENABLED=true`) 배포 환경은 기본으로 꺼두는 게 맞다.

### 2. 입력 검증

`PlayerController.RegisterPlayerRequest`:
```java
public record RegisterPlayerRequest(
        @NotBlank @Size(max = 20) String name,
        @Past LocalDate birthDate
) {}
```

- `@Size(max = 20)`: 이름 길이 제한 없이 받으면, 아주 긴 문자열이 그대로 Claude API 프롬프트에 들어가 불필요한 토큰 비용을 유발할 수 있다.
- `@Past`: 생년월일에 미래 날짜가 들어오면 "운세 계산"이라는 도메인 자체가 의미를 잃는다. `birthDate`는 선택 필드라 null이면 검증 자체가 스킵된다(Bean Validation 기본 동작).

### 3. XSS 방지

React 쪽은 검사해보니 이미 안전했다 — JSX는 텍스트를 기본적으로 이스케이프하고, `dangerouslySetInnerHTML`을 쓰는 곳이 없다는 걸 grep으로 확인. 다만 `engine.ts`의 랭킹 패널(`renderRankPanel`)이 `innerHTML`에 참가자 이름을 문자열로 이어붙이고 있어서, 이것만 `document.createElement` + `textContent`/`Node.append(문자열)` 방식으로 바꿨다(문자열을 `append`하면 항상 안전한 텍스트 노드가 생긴다).

레거시 `frontend/js/*.js`는 모듈이 아니라 각자 독립된 `<script>` 파일이라 `escapeHtml()` 헬퍼를 `main.js`, `admin.js`에 각각 똑같이 추가하고, `innerHTML` 템플릿에 사용자 입력(이름, 운세 메시지, 로그 경로/메시지 등)이 들어가는 모든 지점에 적용했다.

### 4. `/api/fortune` Rate Limiting

`RateLimitFilter` (IP당 분당 20회, 고정 창 방식):

```java
@Component
public class RateLimitFilter extends OncePerRequestFilter {
    private static final String LIMITED_PATH = "/api/fortune";
    private static final int MAX_REQUESTS_PER_WINDOW = 20;
    private static final long WINDOW_MILLIS = 60_000;
    private final Map<String, Window> windowsByIp = new ConcurrentHashMap<>();
    // ...
}
```

- 클라이언트 IP는 `X-Forwarded-For` 헤더를 우선 사용 — Render가 Cloudflare 등 프록시 뒤에 있어서 `getRemoteAddr()`만 쓰면 실제 방문자가 아니라 프록시 주소로 잡힌다.
- 인메모리 카운터라 서버가 여러 대로 늘어나면 IP별 카운트가 서버마다 따로 세어지는 한계가 있지만, 지금 규모(단일 인스턴스, 무료 티어)에는 충분하다. Redis 등으로 옮기는 건 트래픽이 실제로 늘었을 때 할 일.
- 한 판에 참가자가 최대 8명 정도라 20회 한도는 정상 사용을 막지 않으면서, 반복 스크립트로 긁는 시도만 막는 수준.

`RateLimitFilterTest`로 3가지 케이스 검증: 한도까지 통과 후 21번째부터 429, IP별로 카운트 독립, `/api/fortune` 외 경로는 영향 없음.

커밋: `afa4cdc`

라이브 검증: 같은 playerId로 20회 연속 POST → 200, 21~25번째 → 429. `/api/admin/players`, `/api/player`는 영향 없이 정상 동작 확인.

### 5. (덤) `GlobalExceptionHandler`가 404를 500으로 잘못 처리하던 버그

H2 콘솔 비활성화를 배포하고 나서 라이브 관리자 로그(`/api/admin/logs`)를 확인하다가 우연히 발견한, **이번 작업과 무관하게 원래 있던 버그**.

#### 증상
`/h2-console`, `/`, `/favicon.ico`처럼 존재하지 않는 경로에 요청이 오면 정상적으로 404가 나가야 하는데, 전부 `500 Unexpected error`로 응답하고 있었다. 게다가 이 요청들이 전부 관리자 오류 로그 화면(`/api/admin/logs`) — 이 프로젝트의 핵심 기능 중 하나 — 에 "장애"처럼 쌓이고 있었다.

#### 원인
```java
@ExceptionHandler(Exception.class)
public ResponseEntity<Map<String, String>> handleUnexpected(Exception ex, HttpServletRequest request) {
    errorLogStore.record(request.getRequestURI(), ex.getMessage());
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(errorBody("Unexpected error"));
}
```
`Exception.class`를 잡는 catch-all 핸들러가 Spring의 `NoResourceFoundException`(존재하지 않는 정적 리소스 요청에 대한 404 전용 예외)까지 전부 삼켜서 500으로 바꿔버리고 있었다.

#### 해결
더 구체적인 예외 타입의 핸들러가 우선 적용되는 Spring의 `@ExceptionHandler` 해석 규칙을 이용해서, `NoResourceFoundException` 전용 핸들러를 하나 추가했다 — 로그도 남기지 않고 조용히 404만 반환:

```java
// 존재하지 않는 경로 요청(예: /h2-console, /favicon.ico)은 정상적인 404 상황이지,
// 우리 서버가 잘못 동작한 게 아니다. Exception.class로 잡아버리면 이런 요청까지 전부
// "500 Unexpected error"로 둔갑하고, 운영 로그 화면(/api/admin/logs)이 실제 장애가
// 아닌 항목으로 가득 차서 정작 봐야 할 에러를 찾기 어려워진다 — 별도로 조용히 404만 낸다.
@ExceptionHandler(NoResourceFoundException.class)
public ResponseEntity<Void> handleNoResourceFound() {
    return ResponseEntity.notFound().build();
}
```

커밋: `2e7ecd0`

라이브 검증: `/`, `/h2-console`, `/favicon.ico` 모두 404로 응답 확인, `/api/admin/players` 등 정상 API는 계속 200, `/api/admin/logs`를 반복 호출해도 더 이상 새 항목이 쌓이지 않음(빈 배열 유지) 확인.

### 배운 점

"운영 로그" 기능을 포트폴리오의 핵심으로 내세우면서 정작 그 로그가 노이즈로 오염되고 있었다는 건, **기능을 만드는 것과 그 기능이 실제로 신뢰할 수 있는 데이터를 담고 있는지 확인하는 것은 별개**라는 걸 보여준다. 이번에도 로컬 테스트만으로는 안 걸리고, 라이브 배포 로그를 직접 들여다보다가 발견했다 — `devhelp/06`(구 28)에서 얻은 교훈과 같은 패턴.

## [구 32] 관리자 로그인 추가

Phase 5의 마지막 항목. 관리자 화면(`/admin`)에 인증이 전혀 없던 걸(코드 주석에도 "인증 없음(MVP 한정)"이라고 대놓고 적혀 있었다) 로그인으로 막았다.

### 왜 IP 기반이 아니라 로그인인가

처음엔 "내 IP로 접속하면 관리자 메뉴가 자동으로 열리게" 하자는 아이디어가 있었다. 실제로 검토해보니 포트폴리오용으로는 안 맞았다:
- 면접관이 직접 관리자 화면을 눌러볼 수가 없다 (IP 허용 목록에 없으니까).
- 집/카페마다 IP가 바뀌어서 매번 재설정해야 하고, 정작 본인도 다른 곳에서 접속하면 못 들어간다.
- Render/Vercel처럼 프록시를 거치는 배포 환경에서 "진짜 클라이언트 IP"를 신뢰하기도 까다롭다(`RateLimitFilter`가 `X-Forwarded-For`를 쓰는 것과 같은 이유).

그래서 **아이디/비밀번호 로그인**으로 갔다. 면접관에게 데모 계정을 알려주면 어디서든 직접 눌러볼 수 있고, "왜 Spring Security를 안 썼나?"라는 질문에도 "관리자 계정이 환경변수로 고정된 하나뿐이라 그 정도 프레임워크는 과하다고 판단했다"고 답할 수 있다.

### 세션 쿠키 대신 토큰 헤더를 쓴 이유

백엔드(Render)와 프론트(Vercel)가 서로 다른 도메인이라, 쿠키 기반 세션은 `SameSite`/`Secure` 설정을 배포 환경에 정확히 맞춰야 하고 로컬 개발(http, 같은 브라우저의 다른 포트)에서는 또 다르게 동작해서 디버깅이 까다로울 걸로 예상됐다. 대신 로그인 성공 시 **불투명 토큰**을 발급해서 `Authorization: Bearer <토큰>` 헤더로 보내는 방식을 썼다 — 브라우저의 쿠키 정책과 완전히 무관해서 로컬/배포 환경 차이 없이 동일하게 동작한다.

- `AdminSessionStore`: 토큰을 메모리에 보관(TTL 12시간). RateLimitFilter와 같은 이유로 인메모리 — 서버가 여러 대로 늘어나면 Redis 등으로 옮겨야 한다.
- `AdminAuthController`: `POST /api/admin/login`(토큰 발급), `POST /api/admin/logout`(토큰 폐기).
- `AdminAuthFilter`: `/api/admin/**`(로그인 경로 제외) 요청마다 토큰 검사, 없거나 유효하지 않으면 401.
- 프론트: 토큰을 `localStorage`에 저장(새로고침해도 로그인 유지). XSS에 뚫리면 토큰도 같이 새는 절충이 있지만, 이 프로젝트는 `innerHTML`을 안 쓰고 React가 기본적으로 이스케이프해서 그 위험을 낮춰뒀다(devhelp/08(구 29)).

### 비밀번호 기본값을 빈 문자열로 둔 이유

```yaml
admin:
  username: ${ADMIN_USERNAME:admin}
  password: ${ADMIN_PASSWORD:}
```

`ADMIN_PASSWORD`를 안 정하면 빈 문자열이 되는데, `AdminAuthController`가 **빈 비밀번호는 무조건 로그인 실패 처리**한다. 기본값을 아무 문자열로나 정해두면(예: `admin123`) 배포 시 환경변수 설정을 깜빡했을 때 "누구나 로그인 가능"이라는 훨씬 조용하고 위험한 사고로 이어진다 — 대신 "환경변수를 안 정하면 아예 로그인이 안 된다"가 안전한 실패 방식이다.

### DB TEST와의 충돌 — 공개 엔드포인트 분리

관리자 화면 로그인을 막다 보니, 참가자용 "DB TEST" 버튼이 문제였다. 이 버튼은 로그인 안 한 일반 참가자가 쓰는 기능인데, 기존에는 관리자 전용 `GET /api/admin/players`를 그대로 호출하고 있었다 — 그대로 두면 로그인 안 한 사람은 DB TEST를 못 쓰게 된다.

그래서 DB TEST 전용으로 **`GET /api/players/reusable`**이라는 별도 공개 엔드포인트를 새로 만들었다. 관리자용 엔드포인트보다 노출 필드를 좁혀서(이름·생년월일·운세 출처만, 운세 이력 전체는 안 줌) 정보 노출도 줄였다.

### 겪은 버그: CORS preflight를 막아버림

로그인까지는 됐는데, 로그인 직후 관리자 화면의 모든 표가 "Failed to fetch"로 전부 실패했다. 원인은 브라우저가 커스텀 헤더(`Authorization`)를 실제로 보내기 전에 먼저 **CORS preflight(OPTIONS) 요청**을 보내는데, 이 요청엔 당연히 토큰이 없으니 `AdminAuthFilter`가 401로 끊어버렸던 것 — 그러면 스프링의 CORS 응답 헤더 처리(`WebConfig`)까지 아예 못 가서, 브라우저가 실제 요청 자체를 보내지도 않고 막아버린다.

`RateLimitFilter`는 이 문제가 없었던 이유: 어떤 경우에도 요청을 막지 않고 `chain.doFilter()`로 넘겨서, 스프링의 CORS 처리가 뒤에서 정상적으로 실행됐기 때문이다. `AdminAuthFilter`는 진짜로 요청을 차단하는 필터라서 이 함정에 걸렸다.

**해결**: `OPTIONS` 메서드는 경로·토큰과 무관하게 항상 통과시킨다.

```java
boolean isPreflight = "OPTIONS".equalsIgnoreCase(request.getMethod());
if (!isAdminPath || isPreflight || LOGIN_PATH.equals(path)) {
    chain.doFilter(request, response);
    return;
}
```

회귀 방지용 테스트(`corsPreflightIsNeverBlockedEvenWithoutToken`)도 추가했다.

### 검증

Playwright로 실제 화면 흐름을 끝까지 확인했다:
1. `/admin` 접속 → 로그인 폼 노출
2. 잘못된 비밀번호 → 에러 메시지
3. 올바른 로그인 → 관리자 화면 진입, 참가자/게임/로그 표에 실제 데이터 정상 로드
4. 새로고침 → 로그인 유지(localStorage 토큰)
5. 로그아웃 → 로그인 폼으로 복귀
6. **로그인 전혀 안 한 상태**에서 AI TEST → 운세 확인 → DB TEST까지 정상 동작 확인 (공개 엔드포인트 분리가 제대로 됐는지 확인)

백엔드 유닛 테스트도 13개 추가(`AdminSessionStoreTest`, `AdminAuthFilterTest`, `AdminAuthControllerTest`) — 전부 통과.

### 배포 시 할 일

Render 환경변수에 `ADMIN_USERNAME`, `ADMIN_PASSWORD`를 설정해야 실제로 로그인이 가능해진다(설정 안 하면 의도한 대로 로그인이 항상 실패한다).

## [구 34] 필터가 직접 쓰는 401/429 응답에 CORS 헤더가 빠지던 버그

실제 배포 사이트(Vercel+Render)에서 관리자 로그인 후 참가자/게임/로그 목록이 전부 "Failed to fetch"로 실패하는 걸 발견했다. curl로는 정상 401이 오는데 브라우저에서만 실패해서, 전형적인 CORS 문제라고 의심하고 파고들었다.

### 증상 재현

브라우저가 보내는 것과 똑같이 `Origin` 헤더를 넣어서 직접 비교해봤다.

```bash
# OPTIONS(preflight) — 정상, CORS 헤더 있음
curl -i -X OPTIONS https://lucky-pinball-backend.onrender.com/api/admin/players \
  -H "Origin: https://lucky-pinball-ai.vercel.app" \
  -H "Access-Control-Request-Method: GET" \
  -H "Access-Control-Request-Headers: authorization"
# → 200, access-control-allow-origin: https://lucky-pinball-ai.vercel.app 있음

# 실제 GET(토큰 없음/만료) — 401은 오는데 CORS 헤더가 없음!
curl -i https://lucky-pinball-backend.onrender.com/api/admin/players \
  -H "Origin: https://lucky-pinball-ai.vercel.app"
# → 401 {"error":"로그인이 필요합니다."} — 근데 access-control-allow-origin 헤더 자체가 없음
```

브라우저는 응답에 `Access-Control-Allow-Origin`이 없으면 자바스크립트가 그 응답을 아예 못 읽게 막아버린다 — 그래서 실제로는 401이 왔는데도 `fetch()`는 그냥 "Failed to fetch"(TypeError)를 던진다. 상태 코드도, 에러 메시지도 프론트가 전혀 못 본다.

### 원인

`AdminAuthFilter`가 토큰이 없거나 유효하지 않으면 `chain.doFilter()`를 호출하지 않고 **직접** 401 응답을 쓰고 끝낸다:

```java
if (!sessionStore.isValid(token)) {
    response.setStatus(HttpStatus.UNAUTHORIZED.value());
    response.getWriter().write("{\"error\":\"로그인이 필요합니다.\"}");
    return;   // ← 여기서 끝. DispatcherServlet까지 안 간다.
}
```

`WebConfig`의 `addCorsMappings()` 설정은 스프링 MVC(DispatcherServlet) 계층에서 적용된다. 그런데 이 필터는 서블릿 필터 체인의 앞단에서 요청을 끊어버리기 때문에, **DispatcherServlet까지 아예 도달하지 않고, CORS 헤더를 붙여주는 로직도 실행되지 않는다.** OPTIONS(preflight)는 필터가 그냥 통과시켜서(`chain.doFilter()`) 문제가 없었지만, 실제 401을 낼 때만 이 구멍이 드러났다.

같은 패턴이 `RateLimitFilter`의 429 응답에도 있었다 — 아직 실제로 겪은 적은 없지만 잠재적으로 똑같이 터질 수 있어서 같이 고쳤다.

### 왜 지금 이 순간 드러났는가

`AdminSessionStore`가 인메모리라, **Render 서버가 재시작될 때마다(재배포는 물론, 무료 티어의 슬립→깨어남까지 포함) 발급된 토큰이 전부 사라진다.** 브라우저(localStorage)는 예전 토큰을 그대로 들고 있어서 `AdminPage`가 "로그인된 화면"을 렌더링하는데, 그 화면이 실제 데이터를 불러오려는 순간 서버는 그 토큰을 모르니 401을 내고, 이 CORS 버그 때문에 그게 "Failed to fetch"로 보인 것이다.

### 해결

#### 1. 필터가 직접 쓰는 응답에도 CORS 헤더를 수동으로 붙인다

```java
// WebConfig.java — 허용 출처 목록을 공개 상수로 빼서 필터에서도 재사용
public static final List<String> ALLOWED_ORIGINS = List.of(...);
```

```java
// CorsSupport.java — 새 공용 헬퍼
public static void applyCorsHeaders(HttpServletRequest request, HttpServletResponse response) {
    String origin = request.getHeader("Origin");
    if (origin != null && WebConfig.ALLOWED_ORIGINS.contains(origin)) {
        response.setHeader("Access-Control-Allow-Origin", origin);
        response.addHeader("Vary", "Origin");
    }
}
```

`AdminAuthFilter`의 401, `RateLimitFilter`의 429 응답 직전에 `CorsSupport.applyCorsHeaders(request, response)`를 호출하도록 추가했다.

#### 2. 프론트: 401을 받으면 자동으로 로그인 화면으로 돌려보낸다

CORS 헤더를 고쳐도, "서버 재시작으로 토큰이 만료됐다"는 상황 자체는 여전히 생긴다. 지금까지는 이럴 때 각 테이블이 "불러오기 실패"만 보여주고 화면은 계속 "로그인된 것처럼" 남아있어서 사용자가 헷갈렸다.

`api/client.ts`에 헬퍼를 추가:
```ts
export function isUnauthorizedError(error: unknown): boolean {
  return error instanceof ApiError && error.status === 401;
}
```

`PlayersTable`, `GamesTable`, `LogList`에 `onUnauthorized` 콜백을 추가해서, 데이터 조회가 401로 실패하면 `AdminPage`가 로컬 토큰을 지우고 로그인 폼으로 되돌린다:
```tsx
function handleUnauthorized() {
  void api.adminLogout(); // 서버 호출 실패해도 상관없다 — 로컬 토큰만 확실히 지운다.
  setLoggedIn(false);
}
```

### 검증

- 백엔드 유닛 테스트 추가: `AdminAuthFilterTest.the401ResponseIncludesCorsHeaderForAllowedOrigin` — Origin 헤더를 넣고 401 응답에 `Access-Control-Allow-Origin`이 제대로 붙는지 확인.
- 로컬에서 Playwright로 재현: `localStorage`에 가짜(만료된) 토큰을 미리 심어두고 `/admin` 접속 → 전에는 "Failed to fetch"가 그대로 남았는데, 수정 후엔 **자동으로 로그인 폼으로 돌아가는 것**을 확인.
- 배포 후 실제 Vercel 사이트에서도 curl로 CORS preflight+실제 요청을 재현해 헤더가 정상적으로 붙는지 재확인.

### 교훈

**서블릿 필터가 `chain.doFilter()`를 안 타고 직접 응답을 끝내는 지점은, 스프링 MVC 레벨의 설정(CORS, 예외 처리 등)이 전혀 적용되지 않는 "사각지대"가 된다.** 이 프로젝트에 필터가 두 개(`RateLimitFilter`, `AdminAuthFilter`) 있는데, 둘 다 이 패턴이라 둘 다 같은 버그를 안고 있었다 — 하나를 고치면서 "같은 모양의 코드가 또 있는지" 찾아본 덕분에 아직 안 터진 두 번째 버그도 같이 잡을 수 있었다.

## [구 47] 관리자 "가중치 임의 조정" 기능 제거

MVP 때부터 관리자 화면에 "가중치 임의 조정" 패널과 `POST /api/admin/fortune/override` API가 있었다. 실제로는 항상 `501 Not Implemented`를 돌려주는 **자리만 잡아 둔 스텁**이었다. 로드맵의 다음 순서로 구현하려다가 **하지 않기로 결정**하고 모두 걷어냈다.

### 왜 뺐나

- 구현하려면 "덮어쓴 점수를 한 판만 쓸지 계속 쓸지", "이력을 어떻게 남길지", "AI 캐시(같은 신원 재사용)와 어떻게 섞일지" 같은 규칙을 새로 정해야 했다. 게임의 재미나 포트폴리오 설명에 비해 얻는 것이 작았다.

- 이제 이 주소로 요청하면 404다(없는 경로).

## [2026-10-04] 요청 제한이 `X-Forwarded-For` 조작으로 우회되던 문제 수정

문서를 통합하며 다시 읽다가 발견한 문제다(위 AI 코멘트 1번). `/api/fortune`의 요청 제한(IP당 분당 20회)은 비용이 드는 Claude 호출을 지키는 장치인데, 방문자를 `X-Forwarded-For`의 **첫 번째 값**으로 구분하고 있었다.

### 1. 운영에서 먼저 재현했다

존재하지 않는 참가자 번호로 요청해서(404, Claude 호출 없음, 비용 0) 운영 서버에 두 번 연달아 보냈다.

| 실험 | 결과 |
|---|---|
| 대조군: 헤더 없이 25번 | 21번째부터 429 — 제한 자체는 정상 |
| 같은 1분 안에, `X-Forwarded-For: 198.51.100.N`을 매번 바꿔 25번 | **429가 한 번도 안 나옴** — 이미 제한에 걸린 상태였는데도 통과 |

원인: Render의 프록시는 클라이언트가 보낸 `X-Forwarded-For`를 **교체하지 않고 뒤에 덧붙인다.** 그래서 첫 값은 클라이언트가 마음대로 정할 수 있고, 요청마다 바꾸면 IP마다 따로 세어져 제한이 사실상 없어진다. (Render 공식 문서에서 직접 확인하지는 못했고, 같은 문제를 겪은 다른 프로젝트들의 이슈·PR 기록과 위 실험 결과로 판단했다.)

### 2. 수정

- `X-Forwarded-For`는 **아예 보지 않는다.**
- Render 앞단의 **Cloudflare가 넣는 `True-Client-IP`** 로 방문자를 구분한다. 클라이언트가 같은 이름의 헤더를 보내도 Cloudflare가 실제 IP로 덮어쓴다는 전제다(아래 3에서 운영 확인).
- 헤더가 없으면(로컬 개발 등) 연결 주소(`getRemoteAddr()`)를 쓴다.
- 헤더 이름은 `rate-limit.client-ip-header`(환경변수 `CLIENT_IP_HEADER`)로 바꿀 수 있다. 다른 플랫폼으로 옮기면 그곳이 보장하는 헤더로 바꿔야 한다.
- 테스트(+6개): 재현 테스트(헤더를 바꿔도 21번째에 막힘)를 **수정 전 코드에서 실패하는 것을 먼저 확인**했고, 같은 프록시 뒤의 다른 방문자는 따로 세는지, 같은 방문자가 다른 프록시로 와도 같이 세는지, 헤더가 없을 때와 설정이 비었을 때도 확인했다.

### 3. 배포 후 운영 확인

| 실험 | 수정 전 | 수정 후 |
|---|---|---|
| `X-Forwarded-For`를 매번 바꿔 25번 | 429 **0건** | 21번째부터 429 |
| 이어서 `True-Client-IP`를 직접 매번 바꿔 25번 | — | **25건 모두 429**(이미 제한에 걸린 실제 IP로 세어짐 → Cloudflare가 보낸 값을 덮어씀) |

**Render 로그로 최종 확인**: 위 결과는 "`True-Client-IP`가 아예 전달되지 않아 모든 방문자가 프록시 주소 하나로 묶이는 경우"에도 똑같이 나오기 때문에, Render 로그의 `요청 제한 초과: ip=...` 값을 확인했다.

- 새 버전의 차단 기록 30줄(첫 실험 5건 + 두 번째 실험 25건)이 **모두 실험한 PC의 공인 IP**로 찍혔다 → 서버가 프록시 주소가 아니라 실제 방문자 IP를 받고 있다.
- 두 번째 실험에서 `True-Client-IP`에 넣은 가짜 값(`198.51.100.101` 등)은 로그에 **한 번도 나오지 않았다** → Cloudflare가 클라이언트가 보낸 값을 실제 IP로 덮어쓴다.

즉 "모든 방문자가 한 묶음으로 막히는" 경우가 아니라는 것까지 확인됐다.

### 4. 남은 것

- 관리자 로그인(`/api/admin/login`)은 여전히 요청 제한 대상이 아니다(AI 코멘트 3번). 데모 비밀번호가 공개된 지금은 의미가 작아 이번에는 하지 않았다.
- 이 실험으로 관리자 오류 로그에 404가 약 100건 남았다(존재하지 않는 참가자 조회). 최근 1000건만 유지되므로 시간이 지나면 밀려난다.

## [2026-10-05] 관리자 로그인에 시도 횟수 제한 추가

위 절의 "남은 것" 첫 줄(AI 코멘트 3번)을 처리했다. 로그인은 비밀번호를 무한히 넣어 볼 수 있었다.

### 1. 방법 — 기존 요청 제한 필터를 넓혔다

새 필터를 만들지 않고 `RateLimitFilter`가 경로마다 한도를 갖게 했다.

```java
private static final Map<String, Integer> LIMITS_PER_WINDOW = Map.of(
        "/api/fortune", 20,
        "/api/admin/login", 10);
```

- **카운터 키를 `경로 + IP`로** 바꿨다. 같은 IP로 운세를 한도까지 불렀다고 관리자 로그인까지 막히면 안 되기 때문이다.
- 방문자 IP 판단(`True-Client-IP`, 위 절)과 429 응답 형식(`error`, `traceId`, CORS 헤더)은 그대로 쓴다.
- 화면은 서버 메시지를 그대로 보여 주므로 프론트엔드는 바꾸지 않았다.

### 2. 왜 분당 10회인가

- 사람이 비밀번호를 몇 번 틀리는 정도로는 걸리지 않는다.
- 자동으로 대입하는 속도는 분당 수천 번에서 10번으로 줄어든다.
- 성공·실패를 가리지 않고 **시도 횟수**로 센다. 실패만 세려면 응답 상태를 보고 나중에 세야 해서 필터가 복잡해진다. 로그인 성공은 한 번이면 끝나므로 같이 세도 문제가 없다.

### 3. 검증

`RateLimitFilterTest`에 2개를 추가했다(10 → 12개, 모두 통과).

- 같은 IP의 11번째 로그인 시도는 429, 다른 IP는 통과.
- 운세를 한도까지 부른 IP도 로그인은 통과(경로별로 따로 셈).

### 4. 남은 것

- 데모 비밀번호가 공개되어 있어서, 지금 이 제한이 실제로 막는 것은 "비공개 비밀번호로 바꾼 뒤"의 대입 공격이다.
- AI 코멘트 3번의 고정 시간 비교(`MessageDigest.isEqual`)는 하지 않았다. 네트워크를 거친 응답 시간 차이로 비밀번호를 알아내는 공격은 현실적으로 어렵고, 지금은 시도 횟수 제한이 더 효과가 크다고 판단했다.

# 43. 관리자 화면의 "AI 연결 확인"

AI가 안 될 때 원인을 찾으려고 게임을 돌려보는 건 비효율적이다(참가자 등록 → 운세 확인 → 게임 시작까지 해야 하고, Phase 3 이후로는 실패해도 임시 점수로 **성공처럼** 넘어가서 오히려 눈치채기 어렵다). 그래서 관리자 화면에 버튼 한 번으로 Claude API가 지금 되는지, 안 된다면 왜 안 되는지를 보여주는 점검 기능을 넣었다.

## 1. 동작

`POST /api/admin/ai-health` (관리자 토큰 필요) → Claude에 **출력 토큰 1개짜리 실제 요청** 한 번을 보내고 결과를 분류해서 돌려준다.

| status | 의미 | 관리자에게 보이는 조치 안내 |
|---|---|---|
| `OK` | 정상 | 응답 시간, 모델 |
| `KEY_MISSING` | **서버에 API 키가 설정돼 있지 않음** (Anthropic은 401로 응답) | `ANTHROPIC_API_KEY` 환경변수 확인 |
| `AUTH_FAILED` | 401/403 (키는 설정돼 있는데 거절됨) | 키 폐기·오타·만료 확인 |
| `CREDIT_EXHAUSTED` | **크레딧 부족** | Anthropic 콘솔 Billing에서 충전 |
| `RATE_LIMITED` | 429 | 잠시 후 재확인 |
| `TIMEOUT` | 제한 시간(기본 10초) 안에 응답 없음 | Anthropic 장애/네트워크 |
| `UNREACHABLE` | 연결 자체가 안 됨 | 서버 네트워크/Anthropic 장애 |
| `UPSTREAM_ERROR` | Anthropic 5xx | 잠시 후 재확인 |
| `ERROR` | 그 외 | 서버 로그 확인 |

응답에는 `upstreamStatus`(Anthropic이 준 HTTP 코드), `latencyMillis`, `model`, `timeoutSeconds`, `fallbackEnabled`(AI가 안 될 때 사용자가 임시 점수로 계속 진행하는지)도 들어간다. 점검 결과는 성공이든 실패든 **200**으로 내려준다 — "점검이 실패했다"는 것은 오류가 아니라 점검의 결과값이기 때문이다.

## 2. 설계에서 신경 쓴 점

**① 크레딧 부족을 인증 오류와 구분한다.** Anthropic은 크레딧이 바닥나면 401이 아니라 `400 invalid_request_error`("Your credit balance is too low...")로 응답한다. 상태 코드만 보면 "잘못된 요청"이라 관리자가 엉뚱하게 코드를 뒤지게 된다. 400이면서 메시지에 `credit balance`가 있을 때만 `CREDIT_EXHAUSTED`로 분류하고, 다른 400은 `ERROR`로 둔다(테스트로 고정).

**② 점검은 SDK 재시도를 끈다.** 일반 호출은 재시도 1회를 켜 두는데, 점검은 "지금 한 번 해봐서 되는가"를 보는 것이라 재시도가 일시적 실패(429, 5xx)를 가리면 안 된다. 요청 횟수가 1번인지 테스트로 확인한다.

**③ 비용과 오남용 방지.**
- 호출은 출력 1토큰이라 비용이 거의 0이지만 유료라, 점검 사이에 **5초 간격**을 둔다(연타하면 429 + "N초 뒤에 다시").
- POST로 만들었다(GET이면 브라우저 프리패치/캐시로 의도치 않게 실행될 수 있다).
- 관리자 토큰 없이는 401로 막힌다(`/api/admin/**` 필터). 토큰 없음/잘못된 토큰/GET 시도 모두 401임을 확인했다.
- 응답에 Claude의 원문 오류 본문이나 키 값은 싣지 않는다(관리자용이라 사용자용 문구보다 구체적이지만 비밀은 넣지 않는다).

## 3. 검증 중에 발견한 오진 — 풀에 남은 오래된 연결

처음 구현은 ②대로 재시도를 껐는데, 화면에서 시나리오를 돌리다가 **멀쩡한 서비스를 "연결 불가"로 판정**하는 경우가 나왔다(인증 실패를 만들었는데 `UNREACHABLE`, 3ms). 서버 로그의 원인은 `SocketException: 연결이 중단되었습니다`였다.

- 원인: 한동안 쉬는 사이 서버가 유휴 연결을 닫았는데, 클라이언트 풀에 남아 있던 그 연결을 재사용하다 실패. 재시도를 꺼 놨으니 그 **한 번의 실패가 곧 점검 결과**가 됐다.
- 실제로도 일어날 일이다: 관리자가 몇 분 쉬었다가 버튼을 누르면 같은 오진이 날 수 있다.
- 해결: **타임아웃이 아닌 연결 끊김(IO 오류)에 한해서만** 새 연결로 한 번 더 시도한다. 진짜로 연결이 안 되면 두 번 다 실패하고(연결 거부는 즉시 실패), 타임아웃과 HTTP 오류 응답은 재시도하지 않는다. 먼저 이 상황을 재현하는 테스트(첫 요청에서 연결을 끊는 가짜 서버)를 쓰고 **수정 전에 실패하는 것을 확인한 뒤** 고쳤다.

## 3-2. CI에서만 발견된 오진 — "API 키 없음"이 현실에서는 다르게 나온다

처음엔 "키가 없으면 클라이언트를 만들 때 실패한다"고 가정하고 `KEY_MISSING`을 그 경로에 연결했다. 그런데 이 시나리오를 검증하는 테스트는 **내 PC에 `ANTHROPIC_API_KEY` 환경변수가 있어서 계속 스킵**됐고, push 후 CI(환경변수 없음)에서 처음 실행되어 실패했다. 실제로 확인해 보니:

- SDK는 키가 없어도 **예외를 던지지 않고, 인증 없는 요청을 그대로 보낸다.** Anthropic이 **401**로 응답한다.
- 그래서 "키 없음"이 `AUTH_FAILED`("키가 유효하지 않거나 권한이 없습니다")로 나왔다 — 하필 이 기능이 가장 필요한 상황에서 틀린 조치(키를 새로 발급)를 안내하는 셈이다. 가정했던 `KEY_MISSING` 경로는 실제로는 발생하지 않았다.
- 수정: 401을 받았을 때 **서버에 키가 설정돼 있는지**(`anthropic.apiKey`/`ANTHROPIC_API_KEY`/인증 토큰) 확인해서, 설정이 없으면 `KEY_MISSING`, 있는데 거절됐으면 `AUTH_FAILED`로 나눈다. SDK가 직접 자격 증명 없음을 알리는 경우(`NoCredentialsException`)는 안전망으로 같이 처리한다.

교훈: **환경 때문에 스킵되는 테스트는 "통과"가 아니라 "검증 안 됨"이다.** 이제 `env -u ANTHROPIC_API_KEY`로 CI와 같은 조건을 만들어 전체 테스트를 한 번 더 돌린다(키 없음: 74개 전부 실행·실패 0 / 키 있음: 2개 스킵·실패 0).

## 4. 검증

- 자동 테스트 +14개(전체 74개, 키 환경변수가 있는 PC에서는 2개 스킵, 없는 환경(CI)에서는 전부 실행되어 실패 0): 정상(응답 시간·설정값), 출력 토큰 1개로 제한, 인증 실패(재시도 없음, 원문 미노출), 크레딧 부족 vs 일반 400, 429, 5xx, 타임아웃(설정한 1초 근처에서 종료), 연결 불가, 끊긴 연결 재시도, 키 없음 vs 틀린 키 구분(개발 PC에 환경변수가 있으면 스킵), 연타 거절(두 번째는 Claude까지 가지 않음), 폴백 설정 표시. 가짜 Claude는 JDK `HttpServer`라 진짜 API는 호출하지 않는다.
- 브라우저에서 확인(별도 포트, 가짜 Claude의 모드를 바꿔가며): 정상 → ✅ 정상 · 응답 시간 표시 / 5초 이내 재클릭 → "4초 뒤에 다시 시도" / 인증 실패 / 크레딧 부족 / 500 각각 올바른 제목·조치 문구·HTTP 코드. 페이지 오류 0건.

## 5. 한계

- 점검은 **"지금 이 서버에서 Claude까지 한 번 도달했는가"**만 말해준다. 이후에 장애가 나는지는 알려주지 않는다(자동 주기 점검·알림은 없다).
- 모델 호출 가능 여부만 본다. 운세 응답의 **품질**(JSON 구조화 출력이 제대로 나오는지)은 확인하지 않는다 — 구조화 출력까지 검증하려면 출력 토큰이 늘어 비용과 시간이 커진다.
- 점검 간격 제한은 서버 한 대 기준의 메모리 값이다(여러 대로 늘리면 서버마다 따로 센다. RateLimitFilter와 같은 한계).

## [구 40] 로깅과 요청 추적 ID (로드맵 Phase 2)

"에러가 났다"는 말을 들었을 때 원인을 찾을 수 없는 상태였다. 코드에 로그가 한 줄도 없었고(Logger 호출 0건), 예상 못 한 예외는 `handleUnexpected`가 메시지만 메모리 목록에 넣고 스택트레이스는 버렸다. README에는 "운영 로그를 본다"고 적어놨는데 코드가 그걸 못 받쳐주던 부분이다. 이번에 **요청마다 추적 ID를 붙여서, 사용자가 화면의 "오류 ID"를 알려주면 서버 로그에서 그 요청의 흐름을 바로 찾을 수 있게** 만들었다.

### 1. 구조

```
요청 → TraceIdFilter(ID 생성 → MDC, X-Trace-Id 응답 헤더)
     → 로그 줄마다 [ID] 자동 출력 (logging.pattern.level)
     → 에러 응답 {"error": ..., "traceId": ...}, 관리자 오류 로그에도 traceId 저장
     → 프론트: 5xx 메시지에 "(오류 ID: ...)", 관리자 로그 화면에 #ID 배지
```

- **필터 순서**: `@Order(HIGHEST_PRECEDENCE)`로 가장 먼저 돌린다. `RateLimitFilter`(429)와 `AdminAuthFilter`(401)는 컨트롤러까지 가지 않고 필터에서 직접 응답을 쓰는데(devhelp/08(구 34)), 이 응답과 로그에도 같은 ID가 찍혀야 해서다. 이 직접 쓰는 응답은 Spring의 JSON 변환기를 못 쓰므로 `ErrorBodies.json()`으로 같은 모양(`error`, `traceId`)을 직접 만든다.
- **ID는 서버가 항상 새로 만든다**(8자리 16진수). 클라이언트가 `X-Trace-Id`를 보내도 받지 않는다 — 외부 입력이 줄바꿈 등으로 가짜 로그 줄을 만드는 걸 막으려는 것이고, 테스트(`ignoresAnIdSentByTheClient`)로 고정했다. 8자리는 소리 내어 읽어줄 수 있을 만큼 짧고 이 규모에서는 겹칠 일이 거의 없다.
- **MDC는 반드시 비운다**: 톰캣 스레드는 재사용되므로 `finally`에서 지우지 않으면 다음 요청에 이전 ID가 새어 나간다(예외가 나도 지워지는지 테스트).
- 로그 패턴: `logging.pattern.level: "%5p [%X{traceId:--------}]"`. 요청 밖(서버 시작 등)은 `[-------]`로 찍힌다.

### 2. 무엇을 로그로 남기는가

| 위치 | 레벨 | 내용 |
|---|---|---|
| `TraceIdFilter` | INFO | 요청 한 줄 요약 `POST /api/fortune -> 200 (3759ms)` (OPTIONS 제외, 쿼리스트링 제외) |
| `ClaudeFortuneGenerator` | INFO | AI 호출 완료와 걸린 시간 / 클라이언트 준비, 키 미설정 시 WARN |
| `FortuneQueryService` | INFO | 캐시 적중(AI 생략) / 캐시 미스(AI 호출) |
| `GameService` | INFO | 게임 생성·시작·결과 확정(gameId, 인원, 당첨 playerId) |
| `PlayerService` | INFO | 참가자 등록(playerId, 생년월일 입력 여부) |
| `GlobalExceptionHandler` | 4xx WARN(스택 없음) / **5xx ERROR(스택 포함)** | 예상 못 한 예외는 `처리되지 않은 예외`로 스택트레이스까지 |
| `RateLimitFilter`, `AdminAuthFilter`, 관리자 로그인 | WARN | 요청 제한 초과, 관리자 API 인증 실패, 로그인 성공(INFO)/실패(WARN) |

**일부러 남기지 않는 것**: 이름·생년월일(개인정보 — 대신 `playerId`), 관리자 아이디·비밀번호·토큰, 쿼리스트링, Claude 프롬프트와 응답 본문. 당첨자도 이름 대신 `playerId`로 남긴다.

### 3. 에러 응답 규칙과 그 과정에서 고친 것

규칙: 응답은 `{"error": 일반 메시지, "traceId": ...}`이고, 서버 내부 사정(예외 메시지, 스택트레이스)은 응답에 싣지 않고 로그에만 남긴다.

테스트하다 이 규칙에 어긋나는 것 두 가지가 드러났다.

1. **깨진 JSON이 500으로 응답되고 있었다**(`HttpMessageNotReadableException`이 `Exception.class` 핸들러로 떨어짐). 405(잘못된 메서드), 415(`text/plain` 등)도 마찬가지. 이제 400/405/415로 돌려준다. 로그를 ERROR+스택으로 남기기 시작하면 클라이언트 실수나 봇의 탐색 요청이 전부 ERROR로 쌓이기 때문에 같이 고쳤다(devhelp/08(구 29)에서 `NoResourceFoundException`을 따로 처리한 것과 같은 종류의 문제). 405/415는 봇이 찔러본 경우가 대부분이라 관리자 오류 로그(`ErrorLogStore`)에는 넣지 않는다.
2. **Claude의 원문 오류가 사용자 응답에 그대로 실렸다.** 잘못된 API 키로 호출해보니 `Claude API 호출에 실패했습니다: 401: {... "API key is invalid." ...}`가 응답 본문에 있었다. 응답은 "AI 운세 서비스에 일시적인 문제가 있습니다. 잠시 후 다시 시도해주세요."로 바꾸고, 원문은 `ApiException`의 cause로 넘겨서 ERROR 로그의 `Caused by`에만 남긴다. API 키 미설정 안내(환경변수 이름 포함)도 같은 방식으로 정리했다.

### 4. 프론트

- `ApiError`에 `traceId`를 담고, **5xx일 때만** 메시지 끝에 `(오류 ID: c1a8412e)`를 붙인다. 4xx(입력 실수 등)에는 ID가 잡음이라 안 붙인다.
- 관리자 오류 로그 화면에 `#c1a8412e` 배지(고정폭, 클릭 한 번에 전체 선택). 화면의 오류 ID와 이 배지, 서버 로그의 `[c1a8412e]`가 같은 값이다.

### 5. 인코딩: 한글 로그가 깨져 보였다

로그 메시지를 한글로 쓰니 로컬에서 파일로 리다이렉트한 로그가 깨져 보였다. 같은 줄을 CP949로 디코딩하면 정상이었다 — Windows에서 `java -jar`는 기본 인코딩이 cp949라 콘솔 인코딩을 따라가고, 그래서 로컬 콘솔에서는 정상으로 보인다. 운영은 Linux 컨테이너라 기본이 UTF-8이지만 로케일에 기대지 않도록 `Dockerfile`의 ENTRYPOINT에 `-Dfile.encoding=UTF-8`을 명시했다. 같은 옵션으로 `java -jar`를 띄우면 한글 로그가 UTF-8로 정상 기록되는 것까지 확인했다(컨테이너 안에서의 확인은 아니다).

### 6. 검증

- **단위 테스트**: 신규 16개(`TraceIdFilterTest` 6, `GlobalExceptionHandlerTest` 8, 필터 401/429 본문 각 1), 전체 41개 통과. 로그 검증은 Logback `ListAppender`로 ERROR 레벨, 스택트레이스, MDC의 traceId, 원인 예외 체인(`Caused by`)을 직접 확인한다.
- **실서버**(운영과 같은 `java -jar`, 별도 포트·메모리 DB로 격리해서):

| 시나리오 | 결과 |
|---|---|
| 참가자 등록·운세 1회차(AI 호출)·2회차(캐시)·게임 생성 | 200/201, 요청마다 `X-Trace-Id`, 로그에 `캐시 미스 → Claude 호출 완료 3649ms`, `캐시 적중 — AI 호출 생략` |
| 깨진 JSON / 잘못된 메서드 / `text/plain` | 400 / 405 / 415 (이전엔 모두 500) |
| 없는 참가자, 이름 공백, 관리자 토큰 없음, 로그인 실패 | 404, 400, 401, 401 — 모두 본문 `traceId` = 응답 헤더 값 |
| `/api/fortune` 21번 연속 | 21번째 429, 본문에 `traceId`, WARN 로그 |
| 잘못된 Claude API 키 | 502, 응답은 일반 문구 + `traceId`, 서버 로그는 `캐시 미스 → ERROR → 502` 3줄과 `Caused by: UnauthorizedException: 401 ... API key is invalid` |
| 화면(Playwright) | 운세 화면에 `(오류 ID: c1a8412e)`, 관리자 로그에 같은 `#c1a8412e` 배지 |

이 ID로 `grep "\[c1a8412e\]"` 하면 그 요청의 로그가 전부 나온다.

### 7. 한계와 다음 단계

- `ErrorLogStore`(관리자 오류 로그)는 이 시점에는 인메모리였다. 이후 DB 저장으로 바꿨다(devhelp/09(구 42)).
- Claude 호출 중 네트워크 오류·타임아웃(`AnthropicIoException` 등)은 아직 따로 안 잡아서 `처리되지 않은 예외`(500)로 떨어진다. 타임아웃·재시도 설정과 함께 Phase 3에서 다룬다.
- 요청 한 줄 요약은 모든 요청을 INFO로 남기므로 Render의 슬립 방지 핑(10분마다 `GET /api/players/reusable`)도 로그에 찍힌다. 거슬리면 해당 경로만 DEBUG로 낮추면 된다.
- Render 무료 티어의 로그 보관 기간 안에서만 ID로 검색할 수 있다.

## [구 41] Claude API 장애 대응과 임시 점수 (로드맵 Phase 3)

Phase 2에서 로그를 깔아두고 보니, AI 호출이 실패할 때의 동작이 허술했다. 확인해 보니 문제가 세 가지였다.

1. **타임아웃이 사실상 없었다.** Anthropic Java SDK의 기본값은 요청 타임아웃 **10분**, 재시도 **2회**다(타임아웃·연결 오류·408/409/429/5xx가 재시도 대상). Claude가 멈추면 톰캣 스레드 하나가 최악의 경우 수십 분 붙잡힌다.
2. **실패 유형이 구분되지 않았다.** 서비스 오류 응답(`AnthropicServiceException`)만 잡고 있어서, 타임아웃·연결 오류는 그대로 500으로 떨어졌다.
3. **AI가 죽으면 게임 자체를 못 했다.** 운세 조회가 실패하면 게임 생성도 실패한다. 크레딧 소진이나 일시 장애 하나로 데모 전체가 멈춘다.

### 1. 타임아웃과 재시도

```yaml
anthropic:
  timeout-seconds: 10   # 평소 응답이 4초 안팎이라 여유를 둔 값
  max-retries: 1
```

`AnthropicOkHttpClient.builder().fromEnv().timeout(...).maxRetries(...)`로 적용한다. 최악의 대기는 10초 × (최초 + 재시도 1회) ≈ **20초**로 묶인다. 환경변수로 덮어쓸 수 있다(`ANTHROPIC_TIMEOUT_SECONDS`, `ANTHROPIC_MAX_RETRIES`).

### 2. 실패 유형별 응답

`ClaudeFortuneGenerator.translate()`가 SDK 예외를 상태 코드로 나눈다.

| 상황 | 상태 코드 | 사용자 문구 |
|---|---|---|
| 타임아웃(읽기/연결/전체 호출, `InterruptedIOException`이 원인 체인에 있음) | **504** | AI 응답이 늦어지고 있습니다. 잠시 후 다시 시도해주세요. |
| Claude 쪽 429(요청 과다) | **503** | AI 서비스에 요청이 몰려 있습니다. 잠시 후 다시 시도해주세요. |
| 그 외(인증 실패, 5xx, 연결 불가, 키 없음, 응답 파싱 실패) | **502** | AI 운세 서비스에 일시적인 문제가 있습니다. 잠시 후 다시 시도해주세요. |

- 사용자 응답에는 **일반 문구만** 싣는다. Claude의 원문 오류(예: `invalid x-api-key ...`)나 환경변수 이름은 `cause`로만 넘겨서 Phase 2의 ERROR 로그에서만 보이게 했다(테스트로 고정: 응답에 상세가 새지 않는다).
- `GlobalExceptionHandler`는 5xx를 ERROR+스택트레이스로 남기므로, 원인은 traceId로 로그에서 찾는다.

### 3. 임시 점수(FALLBACK)

AI 호출이 **5xx로 실패하면** 에러를 내는 대신 규칙 기반 생성기(`MockFortuneGenerator`)로 점수를 만들어 진행한다.

- **결정적이다**: 점수는 (이름, 생년월일, 오늘 날짜)로 정해지므로 같은 사람은 하루 동안 같은 임시 점수를 받는다. 게임마다 점수가 바뀌지 않는다.
- **운세처럼 보이지 않게 한다**: 규칙 기반 문구를 "운세"로 보여주지 않고 `AI 연결이 원활하지 않아 임시 점수로 진행합니다.`를 문구로 내려준다. 화면에서는 점수와 함께 ⚠ 안내로 표시된다.
- **폴백 대상은 외부 장애뿐이다**: 우리 코드의 버그(`IllegalStateException` 등)나 4xx(`ApiException` 중 5xx가 아닌 것)는 폴백으로 덮지 않고 그대로 드러낸다. 버그를 임시 점수로 가리면 영영 못 찾는다.
- **끌 수 있다**: `fortune.fallback-enabled: false`(`FORTUNE_FALLBACK_ENABLED`)면 502/503/504가 그대로 사용자에게 간다.
- **가려지지 않는다**: 사용자 응답은 200이라 예외 핸들러가 기록하지 않으므로, `FortuneQueryService`가 WARN 로그와 관리자 오류 로그("AI 호출 — 임시 점수로 대체: 원인")를 직접 남긴다. 관리자 참가자 표의 "AI 호출" 열에는 `임시`로 표시된다.

#### 가장 중요한 설계: 임시 점수는 캐시가 아니다

이 프로젝트의 핵심은 "같은 이름+생년월일이면 AI를 다시 부르지 않고 DB 값을 재사용"하는 **신원 캐시**다. 임시 점수를 `source=FALLBACK`으로 저장하되, 캐시 조회 쿼리는 `source IN ('AI','CACHE')`만 대상으로 한다.

```java
findFirstByNameAndBirthDateAndSourceInOrderByCreatedDateAsc(name, birthDate, List.of("AI", "CACHE"))
```

- 이렇게 하지 않으면(= 이전 방식 그대로 이름+생년월일로만 찾으면) 장애 중에 한 번 받은 임시 점수가 그 신원의 "정답"으로 굳어서, AI가 복구돼도 영원히 가짜 점수를 쓴다.
- 반대로 AI 성공 결과가 이미 있는 신원은 캐시가 적중하므로 AI가 죽어 있어도 **진짜 결과**를 받는다.

#### 두 경로의 차이

| 경로 | 동작 | 이유 |
|---|---|---|
| 사용자가 "운세 확인" (`getTodayFortune`) | 이전에 임시 점수를 받았어도 **AI를 다시 시도** | 복구됐는지 사용자가 다시 눌러 확인할 수 있어야 한다 |
| 게임 생성 (`getFortuneForGame`) | 이 참가자가 이미 받은 임시 점수가 있으면 **그대로 재사용**, AI 호출 생략 | AI가 느린 상태에서 8명을 다시 호출하면 8 × 최대 20초를 기다리고, 카드로 보여준 점수와 게임에 쓰인 점수가 달라질 수 있다 |

### 4. 검증

**자동 테스트(+13개, 전체 54개 중 실패 0 / 스킵 1)**

- `FortuneQueryServiceTest`(7): 성공 시 AI / 실패 시 FALLBACK과 오류 로그 기록 / **FALLBACK이 캐시를 오염시키지 않음** / 다시 눌러 AI 재시도 / 게임 경로 재사용(AI 호출 횟수 불변) / 폴백 끄면 예외 그대로 / 우리 버그·4xx는 폴백 안 됨. Claude 쪽은 성공·실패를 바꿔 끼우는 가짜 `FortuneService`로 교체했고, DB는 실제 쿼리를 타는 메모리 H2다.
- `ClaudeFortuneGeneratorTest`(6): JDK `HttpServer`를 "고장난 Claude"로 세워 실제 네트워크 호출로 확인 — 느린 응답은 설정한 1초 근처에서 504 / 재시도 횟수 / 429 → 503 / 401 → 502이며 응답에 원문 미노출, 401은 재시도 안 함 / 5xx는 재시도 / 키 없음 → 502. (SDK의 `fromEnv()`가 시스템 프로퍼티 `anthropic.baseUrl`/`anthropic.apiKey`를 먼저 읽는 점을 이용했다. "키 없음" 테스트는 개발 PC에 `ANTHROPIC_API_KEY`가 있으면 스킵된다.)
- 테스트용 `src/test/resources/application.properties`로 테스트가 개발용 파일 DB가 아니라 **메모리 DB**를 쓰게 했다. 로컬에서 서버를 띄운 채 테스트를 돌려도 그 데이터를 건드리지 않는다.

**실서버 확인**(별도 포트, 메모리 DB, AI 주소를 닫힌 포트로 지정): 운세 확인 → 200 + `source=FALLBACK`, 같은 사람 재확인 → 같은 점수, 게임 생성 0.5초 만에 완료(AI 재호출 없음), 관리자 로그에 "AI 호출" 항목(traceId 포함), 관리자 참가자 목록 `FALLBACK`.

### 5. 한계

- 임시 점수는 **이름+생년월일 기준 결정적 값**이라, 장애 중에는 사람마다의 개성 있는 운세가 아니라 점수만 의미가 있다(그래서 문구를 보여주지 않는다).
- 서킷 브레이커는 넣지 않았다. AI가 죽어 있으면 "운세 확인"마다 최대 약 20초를 기다린 뒤 폴백된다. 트래픽이 큰 서비스라면 연속 실패 시 일정 시간 AI 호출을 건너뛰는 서킷 브레이커가 필요하다.
- 오류 로그(`ErrorLogStore`)는 아직 메모리라 서버가 재시작되면 사라진다(다음 단계에서 DB로 영속화).

## [구 42] 관리자 오류 로그를 DB에 저장하기

관리자 화면의 오류 로그(`/api/admin/logs`)는 `CopyOnWriteArrayList`에 담긴 인메모리 목록이었다. Render 무료 티어는 슬립·재배포로 서버가 자주 다시 뜨기 때문에, 정작 "어젯밤에 무슨 오류가 났지?"를 보려는 시점에는 목록이 비어 있었다. 게임·참가자·운세는 이미 DB(Neon)에 있으니 오류 로그도 같은 곳으로 옮겼다.

### 1. 구조

```
GlobalExceptionHandler / FortuneQueryService
        │ errorLogStore.record(path, message, traceId)   ← 호출 방식은 그대로
        ▼
ErrorLogStore ── (잘라서 맞춤) ──> ErrorLogJpaRepository ──> error_log_entity 테이블
        │                                  └ 저장할 때마다 오래된 행 정리
        └ recent(): 최신 200건 → ErrorLogEntry(기존 응답 모양 그대로)
```

- **호출하는 쪽과 API 응답 모양은 바꾸지 않았다.** `ErrorLogStore.record/recent`의 시그니처와 `ErrorLogEntry` 레코드를 유지해서 `GlobalExceptionHandler`, `AdminController`, 프론트는 손대지 않았다(안내 문구 한 줄만 수정). 저장소만 바꿔 끼운 것이다.
- **엔티티**(`ErrorLogEntity`): `id`(IDENTITY), `occurredAt`, `path`, `message`, `traceId`. 컬럼명을 `timestamp`로 하지 않은 이유는 DB마다 예약어/타입 이름이라서다. 테이블은 `ddl-auto: update`가 만든다(Neon에는 첫 배포 때 자동 생성).

### 2. 설계에서 신경 쓴 세 가지

**① 오류를 기록하다 또 오류가 나면 안 된다.** 이 저장소는 예외 핸들러 안에서 불린다. DB가 끊겨서 저장이 실패하면, 사용자는 원래 오류 응답 대신 엉뚱한 500을 받게 된다. 그래서 `record()`는 저장 실패를 삼키고 WARN 로그만 남긴다(테스트: 저장이 예외를 던지는 저장소로도 `record()`가 던지지 않는다). 대신 서버 로그에는 원래 오류와 저장 실패 원인이 같이 남는다.

**② 독립된 트랜잭션(`REQUIRES_NEW`).** 호출한 쪽 트랜잭션이 롤백돼도 오류 기록은 남아야 하고, 반대로 기록 실패가 호출한 쪽을 rollback-only로 만들어서도 안 된다.

**③ 무한히 쌓이지 않게 한다.** 인메모리일 때는 200건에서 잘렸는데, DB는 그냥 두면 계속 늘어난다(봇이 잘못된 요청을 계속 보내면 더 빠르게). 최근 1000건(`error-log.max-entries`)만 남기고, 저장할 때마다 `id <= 방금 저장한 id - 1000`인 행을 한 번에 지운다. id가 IDENTITY라 시간순으로 증가하므로 `count(*)` 없이 쿼리 한 번으로 정리된다. 화면에는 최신 200건만 내려준다.

그리고 컬럼 길이(경로 500자, 메시지 1000자)를 넘는 값은 저장 전에 잘라서 맞춘다. 길이를 넘으면 INSERT가 실패하고, 그러면 ①에 의해 조용히 기록이 사라지기 때문이다. `ex.getMessage()`는 null일 수도 있어서 그 경우도 그대로 저장되게 했다.

### 3. 테스트 중에 발견한 문제

정리용 `delete` 쿼리를 `@Query`로 직접 만들었는데, 이런 수정 쿼리에는 `save()` 같은 기본 메서드와 달리 **트랜잭션이 자동으로 붙지 않는다**. 운영에서는 `record()`의 `@Transactional` 안에서 불리니 동작하지만, 테스트에서 `ErrorLogStore`를 직접 `new`로 만들었더니(스프링 프록시를 안 거침) `TransactionRequiredException`이 났다. 그런데 이 예외를 ①에서 삼켜 버려서 **오래된 행이 안 지워지는 채로 아무 에러도 보이지 않았다.** 테스트(`오류 7, 6, 5만 남아야 한다`)가 실패해서 알았다.

- 해결: 리포지토리 메서드에 `@Transactional`을 직접 붙여서, 호출하는 쪽이 트랜잭션 안에 있다는 가정에 기대지 않게 했다.
- 교훈: 에러를 삼키는 코드는 "실패해도 티가 안 나는" 위험이 있어서, 삼키는 경로까지 포함해 결과(행 개수)를 검증하는 테스트가 필요하다.

### 4. 검증

- 자동 테스트 +6개(전체 60개 중 실패 0 / 스킵 1): 최신순 조회와 모든 필드, **DB에서 직접 읽어도 존재**(인메모리가 아니라는 증거), 개수 제한 정리, 긴 문자열 잘림, DB 장애에도 호출자 무사, null 메시지. `GlobalExceptionHandlerTest`는 DB 없이 기록 내용만 보는 대역으로 바꿨다.
- 실서버 확인(별도 포트 + 파일 DB): 깨진 JSON(400)과 없는 참가자(404)로 오류를 만들고 → 서버 프로세스를 종료 → 다시 기동 → 같은 로그 2건이 같은 traceId·시각으로 조회됨. 405 요청은 의도대로 저장되지 않음.

### 5. 한계

- 오류 로그를 **서버 로그(Render 로그)의 대체재로 쓰지 않는다.** 이쪽은 메시지 한 줄과 traceId만 가지고, 스택트레이스는 서버 로그에만 있다. 관리자 화면에서 traceId를 확인하고 서버 로그에서 같은 ID를 검색하는 흐름은 그대로다.
- 같은 오류가 폭주하면 최근 1000건이 전부 같은 오류로 채워져 다른 오류가 밀려난다. 중복 묶기(같은 메시지 횟수 집계)나 레벨별 분리는 하지 않았다.
- 오류 기록마다 INSERT + DELETE 쿼리가 나간다. 요청 제한(RateLimitFilter)이 앞에 있고 오류 빈도가 낮아서 무시했지만, 오류가 초당 수십 건씩 나는 서비스라면 비동기 배치 저장이 필요하다.

## [구 43] 관리자 화면의 "AI 연결 확인"

AI가 안 될 때 원인을 찾으려고 게임을 돌려보는 건 비효율적이다(참가자 등록 → 운세 확인 → 게임 시작까지 해야 하고, Phase 3 이후로는 실패해도 임시 점수로 **성공처럼** 넘어가서 오히려 눈치채기 어렵다). 그래서 관리자 화면에 버튼 한 번으로 Claude API가 지금 되는지, 안 된다면 왜 안 되는지를 보여주는 점검 기능을 넣었다.

### 1. 동작

`POST /api/admin/ai-health` (관리자 토큰 필요) → Claude에 **출력 토큰 1개짜리 실제 요청** 한 번을 보내고 결과를 분류해서 돌려준다.

| status | 의미 | 관리자에게 보이는 조치 안내 |
|---|---|---|
| `OK` | 정상 | 응답 시간, 모델 |
| `KEY_MISSING` | **서버에 API 키가 설정돼 있지 않음** (Anthropic은 401로 응답) | `ANTHROPIC_API_KEY` 환경변수 확인 |
| `AUTH_FAILED` | 401/403 (키는 설정돼 있는데 거절됨) | 키 폐기·오타·만료 확인 |
| `CREDIT_EXHAUSTED` | **크레딧 부족** | Anthropic 콘솔 Billing에서 충전 |
| `RATE_LIMITED` | 429 | 잠시 후 재확인 |
| `TIMEOUT` | 제한 시간(기본 10초) 안에 응답 없음 | Anthropic 장애/네트워크 |
| `UNREACHABLE` | 연결 자체가 안 됨 | 서버 네트워크/Anthropic 장애 |
| `UPSTREAM_ERROR` | Anthropic 5xx | 잠시 후 재확인 |
| `ERROR` | 그 외 | 서버 로그 확인 |

응답에는 `upstreamStatus`(Anthropic이 준 HTTP 코드), `latencyMillis`, `model`, `timeoutSeconds`, `fallbackEnabled`(AI가 안 될 때 사용자가 임시 점수로 계속 진행하는지)도 들어간다. 점검 결과는 성공이든 실패든 **200**으로 내려준다 — "점검이 실패했다"는 것은 오류가 아니라 점검의 결과값이기 때문이다.

### 2. 설계에서 신경 쓴 점

**① 크레딧 부족을 인증 오류와 구분한다.** Anthropic은 크레딧이 바닥나면 401이 아니라 `400 invalid_request_error`("Your credit balance is too low...")로 응답한다. 상태 코드만 보면 "잘못된 요청"이라 관리자가 엉뚱하게 코드를 뒤지게 된다. 400이면서 메시지에 `credit balance`가 있을 때만 `CREDIT_EXHAUSTED`로 분류하고, 다른 400은 `ERROR`로 둔다(테스트로 고정).

**② 점검은 SDK 재시도를 끈다.** 일반 호출은 재시도 1회를 켜 두는데, 점검은 "지금 한 번 해봐서 되는가"를 보는 것이라 재시도가 일시적 실패(429, 5xx)를 가리면 안 된다. 요청 횟수가 1번인지 테스트로 확인한다.

**③ 비용과 오남용 방지.**
- 호출은 출력 1토큰이라 비용이 거의 0이지만 유료라, 점검 사이에 **5초 간격**을 둔다(연타하면 429 + "N초 뒤에 다시").
- POST로 만들었다(GET이면 브라우저 프리패치/캐시로 의도치 않게 실행될 수 있다).
- 관리자 토큰 없이는 401로 막힌다(`/api/admin/**` 필터). 토큰 없음/잘못된 토큰/GET 시도 모두 401임을 확인했다.
- 응답에 Claude의 원문 오류 본문이나 키 값은 싣지 않는다(관리자용이라 사용자용 문구보다 구체적이지만 비밀은 넣지 않는다).

### 3. 검증 중에 발견한 오진 — 풀에 남은 오래된 연결

처음 구현은 ②대로 재시도를 껐는데, 화면에서 시나리오를 돌리다가 **멀쩡한 서비스를 "연결 불가"로 판정**하는 경우가 나왔다(인증 실패를 만들었는데 `UNREACHABLE`, 3ms). 서버 로그의 원인은 `SocketException: 연결이 중단되었습니다`였다.

- 원인: 한동안 쉬는 사이 서버가 유휴 연결을 닫았는데, 클라이언트 풀에 남아 있던 그 연결을 재사용하다 실패. 재시도를 꺼 놨으니 그 **한 번의 실패가 곧 점검 결과**가 됐다.
- 실제로도 일어날 일이다: 관리자가 몇 분 쉬었다가 버튼을 누르면 같은 오진이 날 수 있다.
- 해결: **타임아웃이 아닌 연결 끊김(IO 오류)에 한해서만** 새 연결로 한 번 더 시도한다. 진짜로 연결이 안 되면 두 번 다 실패하고(연결 거부는 즉시 실패), 타임아웃과 HTTP 오류 응답은 재시도하지 않는다. 먼저 이 상황을 재현하는 테스트(첫 요청에서 연결을 끊는 가짜 서버)를 쓰고 **수정 전에 실패하는 것을 확인한 뒤** 고쳤다.

### 3-2. CI에서만 발견된 오진 — "API 키 없음"이 현실에서는 다르게 나온다

처음엔 "키가 없으면 클라이언트를 만들 때 실패한다"고 가정하고 `KEY_MISSING`을 그 경로에 연결했다. 그런데 이 시나리오를 검증하는 테스트는 **내 PC에 `ANTHROPIC_API_KEY` 환경변수가 있어서 계속 스킵**됐고, push 후 CI(환경변수 없음)에서 처음 실행되어 실패했다. 실제로 확인해 보니:

- SDK는 키가 없어도 **예외를 던지지 않고, 인증 없는 요청을 그대로 보낸다.** Anthropic이 **401**로 응답한다.
- 그래서 "키 없음"이 `AUTH_FAILED`("키가 유효하지 않거나 권한이 없습니다")로 나왔다 — 하필 이 기능이 가장 필요한 상황에서 틀린 조치(키를 새로 발급)를 안내하는 셈이다. 가정했던 `KEY_MISSING` 경로는 실제로는 발생하지 않았다.
- 수정: 401을 받았을 때 **서버에 키가 설정돼 있는지**(`anthropic.apiKey`/`ANTHROPIC_API_KEY`/인증 토큰) 확인해서, 설정이 없으면 `KEY_MISSING`, 있는데 거절됐으면 `AUTH_FAILED`로 나눈다. SDK가 직접 자격 증명 없음을 알리는 경우(`NoCredentialsException`)는 안전망으로 같이 처리한다.

교훈: **환경 때문에 스킵되는 테스트는 "통과"가 아니라 "검증 안 됨"이다.** 이제 `env -u ANTHROPIC_API_KEY`로 CI와 같은 조건을 만들어 전체 테스트를 한 번 더 돌린다(키 없음: 74개 전부 실행·실패 0 / 키 있음: 2개 스킵·실패 0).

### 4. 검증

- 자동 테스트 +14개(전체 74개, 키 환경변수가 있는 PC에서는 2개 스킵, 없는 환경(CI)에서는 전부 실행되어 실패 0): 정상(응답 시간·설정값), 출력 토큰 1개로 제한, 인증 실패(재시도 없음, 원문 미노출), 크레딧 부족 vs 일반 400, 429, 5xx, 타임아웃(설정한 1초 근처에서 종료), 연결 불가, 끊긴 연결 재시도, 키 없음 vs 틀린 키 구분(개발 PC에 환경변수가 있으면 스킵), 연타 거절(두 번째는 Claude까지 가지 않음), 폴백 설정 표시. 가짜 Claude는 JDK `HttpServer`라 진짜 API는 호출하지 않는다.
- 브라우저에서 확인(별도 포트, 가짜 Claude의 모드를 바꿔가며): 정상 → ✅ 정상 · 응답 시간 표시 / 5초 이내 재클릭 → "4초 뒤에 다시 시도" / 인증 실패 / 크레딧 부족 / 500 각각 올바른 제목·조치 문구·HTTP 코드. 페이지 오류 0건.

### 5. 한계

- 점검은 **"지금 이 서버에서 Claude까지 한 번 도달했는가"**만 말해준다. 이후에 장애가 나는지는 알려주지 않는다(자동 주기 점검·알림은 없다).
- 모델 호출 가능 여부만 본다. 운세 응답의 **품질**(JSON 구조화 출력이 제대로 나오는지)은 확인하지 않는다 — 구조화 출력까지 검증하려면 출력 토큰이 늘어 비용과 시간이 커진다.
- 점검 간격 제한은 서버 한 대 기준의 메모리 값이다(여러 대로 늘리면 서버마다 따로 센다. RateLimitFilter와 같은 한계).

## [구 45] 같은 신원 동시 요청 시 AI 중복 호출 방지 + 테스트 보강 (로드맵 Phase 4)

### 1. 문제 — check-then-act 경쟁 상태

운세 조회는 "캐시(같은 이름+생년월일의 이전 결과)가 있나 확인 → 없으면 Claude 호출 → 저장" 순서다. 확인과 저장 사이에 Claude 응답을 기다리는 수 초가 끼어 있어서, **같은 신원의 요청이 그 사이에 겹치면 전부 "캐시 없음"을 보고 각자 Claude를 호출**한다. 호출마다 비용이 나간다.

```
요청 A: 캐시 확인(없음) ──── Claude 호출(수 초) ──── 저장
요청 B:    캐시 확인(없음) ──── Claude 호출(수 초) ──── 저장   ← 중복 호출
```

### 2. 먼저 재현했다

수정하기 전에 문제를 보여주는 테스트를 썼다(`FortuneQueryServiceTest.simultaneousRequestsForTheSameIdentityCallTheAiOnlyOnce`).

- 같은 이름+생년월일로 참가자 6명을 등록하고, `CountDownLatch`로 6개 스레드를 **동시에 출발**시켜 운세를 조회한다.
- 가짜 Claude는 400ms 걸리게 해서 요청이 겹치는 구간을 만든다.
- **수정 전 결과: Claude 호출 6번**(`expected: <1> but was: <6>`). 비용이 6배로 나간다.

### 3. 대응 — 신원별 잠금(`KeyedLock`)

`FortuneQueryService`에서 "캐시 확인 → Claude 호출 → 저장"을 **신원(이름+생년월일) 단위로 한 번에 하나씩** 실행하게 했다.

```java
return identityLocks.withLock(new Identity(player.getName(), player.getBirthDate()),
        () -> resolveForIdentity(player, playerId, reuseOwnFallback));
```

- 첫 요청만 Claude를 호출하고, 기다리던 요청은 잠금을 얻은 뒤 **캐시를 다시 확인**해서 방금 저장된 결과를 재사용한다(source=`CACHE`).
- 이 메서드는 트랜잭션 밖이라 저장이 즉시 커밋된다. 그래서 다음 요청이 잠금을 얻는 순간 이미 결과를 볼 수 있다. (트랜잭션 안에서 잠갔다면 커밋 전에 잠금이 풀려 같은 문제가 남을 수 있다.)
- **수정 후: 6건 동시 → Claude 1번**, 1명은 `AI`, 5명은 `CACHE`, 점수도 모두 같다.

**`KeyedLock`을 직접 만든 이유**

| 방법 | 문제 |
|---|---|
| 메서드 전체를 `synchronized` | 서로 **다른** 사람의 요청까지 줄을 선다. Claude 응답이 수 초라 동시에 4명이 오면 4배로 느려진다 |
| 키마다 잠금을 만들어 Map에 계속 보관 | 신원 수만큼 잠금 객체가 **끝없이 쌓인다**(메모리 누수) |
| **키별 잠금 + 사용 중일 때만 보관** (채택) | 같은 신원만 줄을 서고, 마지막 사용자가 끝나면 Map에서 지운다 |

- 사용자 수는 `ConcurrentHashMap.compute` 안에서만 바꿔서 키 단위로 원자적이다.
- `ReentrantLock`이라 같은 스레드가 다시 잡아도 멈추지 않고, 작업이 예외로 끝나도 `finally`에서 반드시 풀린다.
- 테스트(`KeyedLockTest`): 같은 키는 동시에 하나만 / 다른 키는 병렬 / 끝나면 Map이 비어 있음(누수 없음) / 예외가 나도 풀림 / 재진입 가능.
- 서로 다른 신원 4명이 동시에 요청하면 약 500ms 안에 끝나는 것도 확인했다(줄을 서면 약 2000ms).

**한계 — 서버 한 대 안에서만 유효하다.** 잠금이 JVM 메모리에 있어서, 서버를 여러 대로 늘리면 서버마다 따로 잠근다. 지금은 Render 인스턴스 1대라 충분하다. 규모가 커지면 다음 중 하나가 필요하다.

- DB 수준: 캐시 결과를 별도 테이블로 분리하고 `(name, birth_date, created_date)` 유니크 제약 → 중복 저장 시 실패를 받아 기존 결과를 읽기
- 분산 잠금: Redis 등
- 요청 합치기: 진행 중인 호출의 `CompletableFuture`를 공유(single-flight)

또 하나: Claude가 죽어 있는 동안 같은 신원 요청이 몰리면, 잠금 때문에 **순서대로** 각자 Claude를 시도한다(임시 점수는 캐시하지 않으므로, devhelp/09(구 41)). 요청마다 최대 약 20초씩 기다릴 수 있다. 같은 신원이 동시에 몰리는 경우는 드물어서 그대로 두었다.

### 4. 테스트 보강

#### `GameService` 단위 테스트 (14개, DB·AI 없이)

메모리 저장소와 점수를 정해 두는 운세 대역으로 바꿔 끼워 규칙만 확인한다.

- 인원 2~8명 제한, 게임 생성은 `getFortuneForGame` 경로를 쓴다(임시 점수 재사용)
- **상대평가 시작 높이**: 최고점자는 0, 점수가 낮을수록 결승선에 가깝게, 티어는 절대 점수 기준 그대로, 생년월일 미입력자는 비교에서 제외
- 결과: 가장 늦게 도착한 사람이 당첨, 순위는 도착 순서, 결과는 한 번만, 도착 순서에 빠진 사람·중복·다른 사람·초과가 있으면 400이고 상태도 그대로

#### 테스트를 쓰다가 발견한 규칙 빈틈 → 수정

`start()`가 게임 상태를 확인하지 않았다.

- **이미 끝난 게임에 시작 요청을 보내면 상태가 `STARTED`로 되돌아갔다**(결과는 남은 채로). → `409`로 거절
- 시작 요청이 두 번 오면 시작 시각을 덮어썼다. → 이미 시작된 게임이면 **그대로 돌려줌**(재시도에 안전)
- 시작하지 않은 게임의 결과도 받았다. → `409`로 거절

두 프론트엔드(React, 레거시) 모두 "생성 → 시작 → 결과" 순서로만 부르는 것을 확인하고 넣은 규칙이라, 기존 화면 흐름은 바뀌지 않는다.

#### HTTP 통합 테스트 (`ApiFlowIntegrationTest`, 4개)

실제 포트로 서버를 띄워 HTTP로 호출한다. 필터(추적 ID·요청 제한·관리자 인증), 컨트롤러, 예외 처리, JPA 저장을 화면과 같은 경로로 지나고, Claude만 가짜다.

1. 전체 흐름: 등록(201) → 운세(AI) → 게임 생성(201, **Claude 재호출 없음**) → 시작 → 결과 → 결과 조회, 응답마다 `X-Trace-Id` 헤더
2. 오류 응답: 인원 부족 400(본문 `traceId` = 헤더 `X-Trace-Id`), 없는 게임·참가자 404, 시작 전 결과 409, 중복 순위 400, 결과 두 번 409, 끝난 게임 재시작 409, 깨진 JSON 400
3. **HTTP로도 동시 요청 4건 → Claude 1번**
4. 관리자 API는 토큰 없이 401, 틀린 비밀번호 401, 로그인 후 방금 만든 게임이 목록에 보임

참고: 처음엔 참가자 등록 응답을 200으로 기대해서 4개가 모두 실패했다. 실제 API는 `201 Created`라서 서버가 아니라 테스트의 가정을 고쳤다.

### 5. 검증

- 전체 백엔드 테스트 **99개**(이전 74개 + 25개). 키 환경변수가 없는 조건(CI와 같음)에서 전부 실행되어 실패 0, 있는 조건에서 2개 스킵·실패 0.
- 시간에 의존하는 동시성 테스트(병렬 여부를 시간으로 확인)가 가끔 실패하지 않는지 관련 테스트를 **5번 반복**해 모두 통과했다. 기준(1500ms)은 직렬 실행 시간(약 2000ms)과 병렬 실행 시간(약 500ms) 사이에 여유를 두고 잡았다.

## [구 09] 헤드리스 물리 테스트로 실제 버그를 발견한 과정

"작성했다"와 "동작한다"는 다르다는 원칙(`devhelp/01`(구 07)에서도 강조한 원칙)을 프론트엔드에도 그대로 적용했습니다. 다만 이번엔 문제가 하나 있었습니다 — **이 환경에는 Playwright 같은 브라우저 자동화 도구가 없어서, 실제 브라우저를 띄워 클릭해보며 확인할 수 없었습니다.** 이 문서는 그 상황에서 어떻게 검증했는지, 그리고 그 검증이 실제로 무엇을 찾아냈는지 기록합니다.

### 1. "브라우저 없이 Matter.js를 검증할 수 있을까?"

Matter.js는 물리 계산 자체는 순수 자바스크립트 로직이고, 화면에 그리는 부분만 DOM(`document.createElement` 등)에 의존합니다. 그렇다면:

- **jsdom**으로 브라우저의 DOM API를 흉내 낸 가짜 `document`/`window`를 Node.js 위에 만들고,
- 실제 npm 패키지인 **matter-js**를 그대로 불러와서,
- `frontend/js/game.js` 파일을 (수정하지 않고 그대로) 읽어와 실행하면

**진짜 프론트엔드 코드를, 진짜 물리 엔진으로, 브라우저 없이** 돌려볼 수 있겠다고 판단했습니다. 이건 실제 서비스 코드베이스에서도 종종 쓰는 기법입니다(UI 자동화 없이 로직만 빠르게 검증).

이 테스트는 프로젝트 폴더가 아니라 **스크래치패드(임시 작업 공간)**에 별도의 Node 프로젝트로 만들었습니다 — `frontend/`는 "빌드 도구 없는 순수 정적 파일"이라는 원칙을 지켜야 해서, 테스트용 `node_modules`를 그 안에 두고 싶지 않았기 때문입니다.

### 2. 테스트 시나리오

```js
runPinballGame({
  boardEl, rankListEl,
  participants: [ /* 버프 티어 0~4를 하나씩 포함한 5명 */ ],
  onComplete: (finishOrder) => {
    // finishOrder에 모든 참가자가 정확히 한 번씩 들어있는지,
    // 게임이 시작된 뒤 실제로 얼마 만에 끝났는지 확인
  },
});
```

`onComplete`이 호출되지 않으면 30초 뒤 강제로 실패 처리하도록 타임아웃을 걸어뒀습니다 — "게임이 언젠가는 반드시 끝나야 한다"는 것 자체가 검증 대상이었기 때문입니다.

### 3. 첫 실행 결과: 실패 (여기서부터가 진짜 검증입니다)

처음 돌려보니 **30초가 지나도 게임이 끝나지 않았습니다.** 로그를 추가해서 각 공의 위치를 계속 찍어보니:

```
tick 180 NoBuff@373, Tier1@625, Tier2@627, Tier3@627, Tier4@627
tick 210 NoBuff@373, Tier1@627, Tier2@627, Tier3@627, Tier4@627
... (이후 계속 같은 자리)
```

4개의 공은 바닥(y≈627)에 잘 도착했는데, **"NoBuff" 공 하나가 y=373 지점(못 배열 중간쯤)에서 완전히 멈춰버린 것**을 확인했습니다. 원인은 갈때기 모양으로 좁아지는 벽과 못 사이의 좁은 틈에 공이 기하학적으로 "끼어버리는" 현상 — Plinko/갈톤보드류 물리 시뮬레이션에서 실제로 흔히 발생하는 문제입니다. 반발계수와 마찰력만으로는, 공이 정확히 두 힘이 상쇄되는 위치에 놓이면 이론상 영원히 멈춰있을 수 있습니다.

### 4. 원인 진단 과정

1. 먼저 "Matter.js 자체가 이 Node/jsdom 환경에서 제대로 동작하는가"부터 의심하고, `game.js`와 무관한 최소 예제(공 하나 + 바닥 하나)로 따로 테스트 — **정상 동작 확인** (이 환경 자체의 문제는 아니라는 걸 먼저 배제).
2. `game.js`에 임시로 디버그 로그를 넣어 각 공의 위치를 프레임마다 출력 — 정확히 어떤 공이, 어디서, 언제부터 멈추는지 특정.
3. 멈춘 위치(y=373)가 못 배열 구간이고, 하필 가장 바깥쪽(왼쪽)에서 출발한 공이라는 점에서 "좁아지는 벽 + 못" 조합이 원인이라고 결론.

이 과정은 실제 버그 리포트를 받았을 때의 디버깅 순서와 같습니다 — **의심되는 범위를 좁혀가며(엔진 자체? 내 코드? 특정 조건?) 하나씩 배제**하는 방식입니다.

### 5. 해결 — "완벽한 기하학"보다 "안전장치"

이런 종류의 끼임 문제는 못 간격이나 벽 각도를 아무리 정교하게 계산해도 특정 랜덤 시드에서는 여전히 발생할 수 있습니다 (물리 시뮬레이션은 부동소수점 계산이라 완벽한 대칭이 오히려 불안정한 경우도 있습니다). 그래서 두 가지를 함께 적용했습니다.

1. **완화**: 못을 벽에서 조금 더 떨어뜨려 배치(여백 30px → 38px)해서 애초에 끼임이 발생할 여지를 줄임.
2. **안전장치(핵심 수정)**: 공의 속도(`body.speed`)가 일정 시간(약 0.75초, 45틱) 이상 거의 0에 가까우면, 완주하지 못한 공에 무작위 방향의 작은 충격을 줘서 강제로 다시 움직이게 만드는 로직을 추가했습니다 (`game.js`의 `adapter.nudge()` 참고).

```js
if (adapter.getSpeed(state.body) < 0.05) {
  state.stallTicks++;
  if (state.stallTicks > 45) {
    adapter.nudge(state.body);
    state.stallTicks = 0;
  }
}
```

이건 "버그를 원천 차단"하는 게 아니라 "버그가 나더라도 게임이 절대 멈추지 않도록 보장"하는 접근입니다. 물리 시뮬레이션처럼 모든 경우의 수를 수학적으로 증명하기 어려운 영역에서는, 실제 프로덕션 Plinko/갈톤보드 구현체들도 이런 식의 "정체 감지 후 흔들기" 안전장치를 흔히 사용합니다.

### 6. 수정 후 재검증

같은 헤드리스 테스트를 5명 기준 5회, 8명(최대 인원) 기준 여러 회 반복 실행:

| 참가자 수 | 실행 횟수 | 완료까지 걸린 시간 |
|---|---|---|
| 5명 | 5회 | 4.3초 ~ 11.3초 |
| 8명(최대) | 5회 | 8.8초 ~ 27.2초 |

전부 `plan/04_pinball-map-design.md`가 목표로 했던 "1분 내 종료"를 여유 있게 만족했고, 매 실행마다 참가자 전원이 정확히 한 번씩 완주 순서에 포함되는 것도 확인했습니다. 이 표는 실제 실행 결과이지, 추정치가 아닙니다.

### 7. 이 검증 방식의 한계 (정직하게 밝혀둠)

- **실제 브라우저에서의 시각적 확인(레이아웃, 색상, 애니메이션 부드러움, 반응형 등)은 하지 못했습니다.** 헤드리스 테스트는 "물리 로직이 올바르게 끝나는가"만 검증하며, 화면이 실제로 보기 좋은지는 사용자가 브라우저에서 직접 열어봐야 합니다.
- CORS/네트워크 관련 문제(브라우저의 실제 CORS 정책 적용)는 curl로 프리플라이트(OPTIONS) 요청을 흉내 내서 응답 헤더까지 확인했지만, 진짜 브라우저의 `fetch()` 동작과 100% 동일하다는 보장은 아닙니다.
- 이 저장소에는 자동화된 테스트로 남겨두지 않았습니다 (스크래치패드의 임시 스크립트였음) — 필요하면 `frontend`와는 별도로 `backend`처럼 자체 `package.json`을 가진 테스트 전용 폴더를 나중에 추가할 수 있습니다.

**결론적으로 사용자가 직접 브라우저(`http://localhost:5501`)에서 한 번 실행해보고, 레이아웃/애니메이션이 의도대로 보이는지 확인하는 과정은 여전히 필요합니다.**

## [구 11] 사용자 리포트로 찾은 "벽에 걸림" 버그

[구 09]에서 한 번 안전장치(정체 감지 후 흔들기)로 막아뒀던 문제가, 실제로는 완전히 해결된 게 아니라 **증상만 가려져 있었다**는 걸 사용자가 직접 실행해보고 알려준 덕분에 알게 된 과정입니다.

### 1. 사용자가 관찰한 현상

참가자 4명(1, 2, 3, 4)으로 게임을 돌렸을 때, 참가자 "1"이 당첨(가장 늦게 도착)됐는데 — 정상적으로 굴러 내려온 게 아니라 **"제일 왼쪽 끝에 걸려서 내려오는 식"**으로 움직였다는 리포트를 받았습니다. "걸리면 못 내려올 것 같은데 정상 동작이 맞냐"는 날카로운 질문이었습니다.

### 2. 정답: 아니요, 정상이 아니었습니다

`09` 문서에서 넣었던 안전장치를 다시 보면:

```js
if (adapter.getSpeed(state.body) < 0.05) {
  state.stallTicks++;
  if (state.stallTicks > 45) {
    adapter.nudge(state.body); // 살짝 흔들어서 강제로 이동시킴
    state.stallTicks = 0;
  }
}
```

이 로직은 "공이 완전히 멈추는 것"은 막아줬지만, **왜 자꾸 멈추는지(근본 원인)는 고치지 못한 상태**였습니다. 그 결과 화면에서는 "0.75초 정도 멈칫 → 강제로 튕겨나감 → 조금 가다 다시 멈칫 → 또 튕겨나감"이 반복되는, 사용자가 본 것과 정확히 일치하는 "걸렸다 풀렸다"하는 부자연스러운 움직임으로 나타났습니다. 게임 자체는 끝나지만(당첨자 결과는 유효), 물리적으로 매끄럽지 않았던 것 — **사용자의 관찰이 맞았습니다.**

### 3. 진짜 원인

`04_pinball-map-design.md`의 벽은 위(폭 전체)에서 아래(중앙으로 좁아짐)로 이어지는 깔때기 모양입니다. 그런데 못 배열을 만들 때 벽에서 못까지의 여백을 38px로만 뒀는데, **이 여백이 매 행(row)마다 거의 똑같아서, 벽을 따라 못들이 일렬로 늘어선 "레일"처럼 배치**돼 있었습니다. 공이 벽 쪽으로 붙어서 떨어지면, 벽과 그 옆 못 사이의 좁은 틈에 물리적으로 끼이기 쉬운 구조였던 것입니다 — 안전장치가 그걸 한 번씩 풀어줘도, 조금 내려가면 바로 다음 행의 못에서 또 같은 일이 반복됐습니다.

### 4. 수정

두 가지를 함께 고쳤습니다 (`frontend/js/game.js`).

1. **벽 근처에는 못을 아예 두지 않는 여유 구간을 크게 넓힘** (38px → 70px, `PEG_WALL_CLEARANCE` 상수로 명명). 이제 벽을 따라 내려가는 공이 못과 동시에 맞닿을 일이 훨씬 줄어듭니다.
2. **모든 물리 바디(공/못/벽)의 마찰력을 0으로 설정**. 마찰이 있으면 공이 벽/못 표면에 "달라붙듯" 저항을 받을 수 있는데, 마찰을 없애면 부딪히고 튕겨 나가기만 할 뿐 표면에 붙잡히지 않습니다.

기존의 "정체 감지 후 흔들기" 안전장치는 **그대로 남겨뒀습니다** — 이제는 실제로 거의 발동하지 않는, 정말 예외적인 경우를 위한 최후의 보험 역할입니다.

### 5. 수정 후 재검증

`09`에서 썼던 것과 같은 헤드리스 테스트 방식으로, 안전장치가 몇 번 발동하는지(nudge count)를 세어봤습니다.

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 8명 게임, 8회 반복 시 평균 완료 시간 | 약 9~27초 (안전장치가 자주 개입) | 약 2.8~3.0초 |
| 안전장치(nudge) 발동 횟수 | 게임당 여러 번 | **8회 전부 0번** |

완료 시간도 훨씬 짧고 일정해졌다는 것 자체가, 공이 더 이상 걸리지 않고 매끄럽게 굴러 내려온다는 걸 뒷받침합니다. 추가로 Playwright로 실제 브라우저에서 벽 근처 공(참가자 "1")의 움직임을 여러 프레임 연속으로 캡처해 확인했고, 벽과 못 사이에 눈에 띄는 여백이 생겨 더 이상 걸리는 모습 없이 자연스럽게 내려오는 것을 눈으로도 확인했습니다.

### 6. 배운 점

- 안전장치(재시도/복구 로직)는 "증상을 완화"할 수는 있지만, **근본 원인을 찾아 고치지 않으면 그 증상 자체가 버그로 남습니다.** `09`에서 "게임이 멈추지 않는다"는 것만 확인하고 넘어갔던 게 이번 리포트의 원인이었습니다 — 헤드리스 테스트가 "완료 여부"는 검증했지만 "움직임이 자연스러운가"까지는 검증하지 못했기 때문입니다.
- 이번에도 검증 지표를 하나 추가한 게 원인 확인에 결정적이었습니다 — "안전장치가 몇 번 발동했는가"라는 숫자 하나가 수정 전/후 차이를 명확하게 보여줬습니다.
- 사용자가 실제로 써보고 남긴 "이상한데?"라는 관찰이, 자동화된 테스트로는 못 잡아낸 문제를 잡아낸 사례입니다 — 자동 테스트와 실사용자 피드백은 서로 다른 종류의 버그를 잡아낸다는 걸 보여줍니다.

## [구 12] 반복 플레이 · 속도 조절 · 벽 근처 스폰 · 역전 카메라 연출

사용자가 실제로 여러 판을 플레이해보고 준 피드백 4가지를 반영한 기록입니다.

### 1. 게임을 반복해서 시작할 수 있게 (버그 수정)

`main.js`의 "게임 시작" 버튼은 클릭 시 `disabled = true`로 잠기는데, 게임이 끝난 뒤 **다시 풀어주는 코드가 없었습니다** — 그래서 한 판을 마치면 버튼이 영구히 비활성화됐습니다. `onComplete` 콜백의 `finally` 블록에서 다시 활성화하도록 고쳤습니다.

"다시 시작하면 다른 결과가 나와야 한다"는 요구는 사실 별도 조치 없이도 대부분 충족됩니다 — `POST /api/game/create`를 다시 호출하면 매번 새 `gameId`로 게임 세션이 만들어지고, 물리 시뮬레이션도 매번 처음부터 다시 돕니다. 다만 확실히 하기 위해 3번 항목에서 공의 출발 위치에 약간의 무작위 오차(jitter)도 추가해서, 완전히 똑같은 출발점에서 매번 똑같이 흘러가지 않게 보강했습니다.

### 2. 낙하 속도 1.5배 느리게

`CLASSIC_GALTON_MAP.gravityScale`을 `1.2 → 0.8`로 낮췄습니다 (1.2 ÷ 1.5 = 0.8).

### 3. 양 끝에서 출발한 공이 그냥 떨어져버리는 문제

`devhelp/02(구 11)`에서 "벽 근처 끼임"을 고치려고 벽 주변에 못이 없는 여유 구간(`PEG_WALL_CLEARANCE = 70px`)을 넉넉히 뒀었는데, 그 부작용으로 **양 끝에서 출발한 공이 못을 하나도 안 건드리고 그 빈 통로로 바로 떨어져버리는** 문제가 생겼습니다. `spawnX()`가 출발 위치를 계산할 때 이 여유 구간까지 포함한 전체 폭을 기준으로 삼았기 때문입니다.

고친 방법: 출발 위치의 기준 폭을 "못이 실제로 배치된 범위"(`PEG_WALL_CLEARANCE`만큼 안쪽)로 좁혀서, 양 끝에서 출발해도 반드시 못 배열 위에서 시작하도록 했습니다.

### 4. 맵 길이 확장 + "역전 시 확대" 카메라 연출

사용자가 참고한 [lazygyu의 Marble Roulette](https://lazygyu.github.io/roulette/)처럼 후반부에 긴박감을 주고 싶다는 요청이었습니다. 다만 검색해봐도 그 사이트의 카메라 연출을 구현한 소스 코드/문서는 찾지 못해서(공개된 세부 스펙 없음), 일반적인 "카메라 팔로우" 기법으로 직접 설계했습니다. 진행 전 사용자에게 맵 확장 폭과 "역전" 감지 방식을 확인받았습니다.

#### 4-1. 맵 길이: 8행 → 12행

`pegField.rows`를 늘리고, 그에 맞춰 `finishLineY`(470→670)와 `boardHeight`(640→770)도 같이 늘렸습니다.

#### 4-2. 화면을 두 겹으로 분리 (카메라 구조)

카메라로 확대/이동하려면 "보이는 틀"과 "그 안의 내용물"을 분리해야 합니다.

```
.pinball-board (뷰포트 — 크기 고정, overflow: hidden)
  └─ .pinball-scene (실제 못/벽/공이 그려지는 레이어 — 여기에만 scale/translate 적용)
```

기존에는 못/벽/공을 전부 `.pinball-board`에 직접 그렸는데, 이제 `.pinball-scene`이라는 안쪽 레이어를 하나 더 만들어서 그 위에 그립니다. 카메라를 확대하고 싶으면 `.pinball-scene`에만 `transform: translate(...) scale(...)`를 걸면 되고, 바깥 `.pinball-board`는 크기가 고정된 "창문" 역할만 합니다.

```js
function applyCamera(sceneEl, cfg, targetX, targetY, scale) {
  const dx = cfg.boardWidth / 2 - targetX * scale;
  const dy = cfg.boardHeight / 2 - targetY * scale;
  sceneEl.style.transform = `translate(${dx}px, ${dy}px) scale(${scale})`;
}
```

(targetX, targetY) 지점이 화면 중앙에 오도록 확대·이동시키는 공식입니다. `style.css`의 `.pinball-scene { transition: transform 0.25s ease-out; }` 덕분에, 매 프레임 목표 좌표만 바꿔줘도 브라우저가 알아서 부드럽게 이어서 움직여줍니다 — 직접 애니메이션 코드를 짤 필요가 없었습니다.

이 작업을 하면서 부수적으로 발견한 것: 기존에는 `.pinball-board`의 폭이 CSS flex 레이아웃에 의해 대략적으로만 정해져서(정확히 560px가 아니었음), 물리 좌표와 화면 좌표가 미세하게 안 맞을 수 있는 상태였습니다. 이번에 보드 크기를 JS에서 `cfg.boardWidth/boardHeight` 값 그대로 강제 지정하도록 바꿔서, 이 오차도 함께 없앴습니다.

#### 4-3. "역전" 감지 방식

사용자가 확인해준 방식대로, **결승선을 통과 못 한 공이 3명 이하로 줄어들면** 그중 **가장 덜 내려간(y가 가장 작은) 공** — 즉 "지금 이대로면 꼴찌가 될 후보" — 을 계속 추적하며 1.3배 확대합니다. 이 후보가 바뀌는 순간이 곧 "역전"이고, 카메라가 자연스럽게 새 대상 쪽으로 부드럽게 넘어가면서 역전을 표현합니다.

8명 전원이 남아있을 때부터 추적하지 않고 **3명 이하로 줄었을 때만** 켜지도록 한 이유: 초반에는 공들이 못 사이에서 계속 순서가 뒤바뀌는 게 정상이라, 그때부터 카메라가 계속 움직이면 오히려 산만해집니다. 순위가 어느 정도 추려진 막판에만 카메라가 개입해야 "긴박함"이라는 원래 의도에 맞습니다.

#### 검증

- 헤드리스 테스트(8명 기준 5회 반복)로 12행 확장 후에도 5.3~6.5초 안에 정상 종료되는 것을 확인했습니다(1분 목표 대비 여유 충분).
- Playwright로 실제 게임을 끝까지 돌려서, 결승선을 통과 못 한 인원이 2명으로 줄어드는 순간 실제로 화면이 확대되며 그 두 공을 따라가는 것을 스크린샷으로 확인했습니다. 게임이 끝난 뒤에도 확대된 채로 마지막 순간(당첨자가 결승선을 통과하는 장면)이 화면에 남아있어서, 결과 배너와 함께 봤을 때 연출 효과가 자연스럽게 이어집니다.

## [구 24] 핀휠 장애물 + 맵 확대, 선형 버프, 선두 추적 카메라, 관리자 개선

사용자 플레이테스트 피드백 4건을 한 번에 반영한 기록. 이번 건은 devhelp/05(구 22)(흐름도)·23(React 마이그레이션)과 이어지며, `frontend-react/src/game/engine.ts`와 레거시 `frontend/js/game.js` **양쪽 다** 수정했다 — 둘 다 아직 살아있는 별도 사본이라, 한쪽만 고치면 vanilla 버전이 새 `BuffCalculator` 값(최대 200)과 안 맞아 못 행과 스폰 위치가 겹치는 회귀가 생기기 때문이다.

### 1. 관리자 페이지네이션 — 처음/끝 버튼 + 최신순 정렬

- `Pagination.tsx`에 "처음"/"끝" 버튼 추가(기존 이전/다음 양옆에 배치).
- `PlayerJpaRepository`에 `findAllByOrderByCreatedAtDesc()` 추가, `AdminController.players()`가 이걸 쓰도록 변경 — **참가자 목록 자체**가 최근 등록순으로 보인다(각 참가자 안의 운세 이력 순서는 기존 그대로 오름차순 유지 — 이번 요청 범위 아님).

### 2. 운세 점수 → 시작 높이, 구간제 폐지하고 선형으로

`BuffCalculator.fromScore()`가 기존엔 20점 단위 5단계로 나눠서, 같은 구간 안(예: 61~79점)에서는 점수가 달라도 시작 높이가 완전히 같았다. `startY = (100 - score) * 2.0`로 바꿔서 **1점 차이도 항상 2px 차이**로 드러나게 했다(0점→200px, 100점→0px). `tier`(0~4)는 운세 카드 배지 색상 구분용으로만 남겨뒀다 — 게임 로직에는 더 이상 안 쓰인다.

### 3. 카메라 — "꼴찌 추적"에서 "선두 추적"으로

기존엔 완주 못 한 공이 3명 이하로 줄어들면 "가장 뒤처진(꼴찌 후보)" 공을 따라가며 역전 연출을 했다. 요청대로 **완주 안 한 공 중 가장 앞선(1등) 공을 계속 추적**하고, 그 공이 완주하면 자동으로 다음 선두(원래 2등)를 추적하도록 바꿨다 — 매 틱 "완주 안 한 공 중 y가 가장 큰 것"만 다시 찾으면 되므로 순위 전환마다 별도 상태 관리가 필요 없다.

추가로 "낙하 초반 구간은 제외하고 어느 정도 통과한 뒤부터 추적 시작"을 `zoomStartY`(못 5행 통과 지점)로 구현 — 그 전엔 항상 scale 1(전체 화면)을 유지한다.

### 4. 맵 확대 + 핀휠(회전 막대) 장애물

[lazygyu/roulette](https://lazygyu.github.io/roulette/)(MIT 라이선스) 소스를 실제로 확인해서(`src/data/maps.ts`), 회전 막대가 Box2D의 kinematic 바디(가늘고 긴 사각형에 `angularVelocity`만 부여, 물리적으로는 안 밀리지만 계속 회전)로 구현된 걸 확인하고 이 프로젝트(Matter.js) 방식으로 응용했다.

- 맵을 기존(770px, 12행) 대비 약 2배(1500px, 20행)로 확대.
- `pinwheelRowIndex`(10번 행)는 못 대신 핀휠이 차지하도록 `buildPegPositions`에서 스킵하고, `buildPinwheelPositions`가 그 행에 회전 막대를 못보다 넓은 간격(한 칸 건너)으로 배치. 인접 막대끼리는 회전 방향을 반대로(`angularSpeed` 부호 교대) — lazygyu 맵의 패턴과 동일.
- `MatterAdapter`에 `addKinematicRect()` 추가 — 생성은 static 바디로 하되(공에 안 밀리게), 어댑터 내부 `run()`의 매 틱마다 `Matter.Body.setAngle()`로 직접 각도를 갱신해서 계속 돌아가게 만든다. 렌더링은 `.spinner-bar` DOM 요소를 매 틱 `getAngle()` 값으로 회전시켜 동기화.

### 5. 검증

프론트엔드는 빌드(`npm run build`) 통과 확인 후, 백엔드+Vite를 실제로 띄워 Playwright로 검증했다. 이 과정에서 **실수 하나를 발견하고 고쳤다**: 검증용으로 새 `./gradlew bootRun`을 띄웠는데, 사용자가 이전에 본인 VSCode 터미널에서 직접 띄워둔 백엔드가 이미 8080 포트를 쓰고 있어서 새 프로세스가 기동에 실패했고, 실제로 응답 중이던 건 **이번 코드 변경 전의 예전 프로세스**였다 — 처음 확인했을 때 `startY`가 여전히 15(구간제 값)로 나와서 바로 알아챘다. 예전 프로세스를 종료하고 재기동한 뒤 재검증했다.

검증 내용(전부 실제 캐시된 운세 데이터로 재현 — AI 키 없이도 가능):
- 이름/생년월일이 같은 기존 캐시 데이터를 재사용해 76점·68점 참가자를 만들어 운세 카드에서 "시작 높이 +48"/"+64"로 **다르게** 표시되는 것 확인(이전이라면 둘 다 60~79 구간이라 완전히 같은 값이었을 조합).
- 5명 참가 게임을 돌리며 0.5초 간격으로 카메라 transform과 완주 인원을 콘솔에 기록 — t=2.0s부터 `scale(1.3)`로 전환(그 전엔 `scale(1)` 유지), 이후 완주 인원이 늘어날 때마다(1명→3명→4명→5명) `translate` 값이 계속 바뀌며 선두를 따라가는 것을 객관적으로 확인.
- 핀휠(`.spinner-bar`)의 `rotate(...)` 각도가 매 폴링마다 계속 증가하는 것 확인(멈추거나 튀지 않음).
- 관리자 화면: 방금 등록한 참가자 5명(E~A)이 맨 위에 최신순으로 표시됨, "끝" 버튼 클릭 시 마지막 페이지(5/5)로 바로 이동함을 확인.

검증에 쓴 테스트 서버는 이후 종료했다.

### 6. 남은 논의거리

- 카메라가 "낙하 초반"을 벗어났는지 판단하는 `zoomStartY`(현재: 못 5행 통과 지점)는 임의로 잡은 값이라, 실제 8명 풀 게임에서 초반 혼전이 얼마나 이어지는지 보고 조정이 필요할 수 있다.

- 이번 변경은 `frontend/js/game.js`(레거시)에도 동일하게 반영했지만, 앞으로 이 둘이 계속 분기되지 않으려면 plan/06의 7단계(기존 `frontend/` 교체) 논의를 너무 늦추지 않는 게 좋다.

## [구 25] 벽 가장자리 미끄러짐 수정(두 번의 실패 포함) + 빠른 참가자 추가

### 1. 문제: 양 끝 벽을 타고 미끄러져 게임이 너무 빨리 끝남

devhelp/02(구 24)에서 맵을 키우고 핀휠을 추가한 뒤, 실제 8명 플레이에서 공이 회전 막대에 맞아 벽쪽으로 튕겨나가면 그대로 벽을 따라 바닥까지 미끄러져 내려가 버리는 문제가 발견됐다(`PEG_WALL_CLEARANCE=70`이 만든 빈 통로가 원인). 사용자가 실제 화면에 직접 빨간 선으로 낙하 경로를 표시해 보여줬다.

### 2. 시도 1 — 벽을 지그재그(톱니)로: 실패

벽 자체를 짧은 각진 조각을 이어 붙인 지그재그로 바꾸고 `PEG_WALL_CLEARANCE`를 70→30으로 줄였다. 빌드는 통과했지만 실제 8명 플레이에서 **공 2개가 30초 넘게 전혀 움직이지 않는** 상태로 완전히 멈췄다. `nudge`(끼임 안전장치) 호출 횟수를 임시로 계측해보니 초당 1~2회씩 계속 발동하면서도 공을 전혀 빼내지 못했다 — devhelp/02(구 11)에서 이미 경고했던 "안전장치가 자주 발동하면 근본 원인을 못 고쳤다는 신호"가 그대로 재현됐다.

### 3. 시도 2 — 벽 표면에 둥근 돌기: 역시 실패

지그재그의 뾰족한 오목(concave) 모서리가 문제라고 판단해서, 벽은 매끈하게 되돌리고 대신 벽 표면에 볼록한 원형 돌기를 일정 간격으로 붙이는 방식으로 다시 만들었다(오목한 틈이 없는 볼록 형태라 안전할 것으로 예상). `PEG_WALL_CLEARANCE`는 30으로 유지한 채 재검증했는데, **똑같은 증상(공 2개 영구 정지, nudge 계속 헛발동)이 다시 나타났다.**

### 4. 진짜 원인 — 장애물 모양이 아니라 clearance 값 자체였다

두 시도 모두 실패한 공통점은 새 장애물의 모양이 아니라 **`PEG_WALL_CLEARANCE`를 70에서 30으로 줄인 것 자체**였다. devhelp/02(구 11)에서 이 값을 정확히 70으로 정한 이유가 "이보다 작으면 못과 벽 사이에 공이 낄 좁은 틈이 생긴다"는 실측 결과였는데, 이번에 그 안전 마진을 다시 건드린 셈이었다. 지그재그든 돌기든 상관없이, clearance를 줄이는 순간 devhelp/02(구 11)의 버그가 그대로 재발했다.

**최종 해법**: `PEG_WALL_CLEARANCE`는 70(devhelp/02(구 11)에서 검증된 값)으로 되돌리고, 대신 벽 자체의 **반발력(restitution)을 0 → 0.7로만 올렸다.** 새 장애물을 전혀 추가하지 않고 기존에 안전하다고 검증된 벽 형태·간격은 그대로 둔 채 파라미터 하나만 바꾼 것이라 리스크가 훨씬 낮다.

#### 검증

8명 참가 게임을 여러 번 돌려 매초 각 공의 y좌표와 nudge 발동 횟수를 기록했다.

- **수정 전(clearance 30 + 지그재그/돌기)**: nudge가 계속 발동하고 공 2개가 40초 넘게 완전히 멈춤.
- **수정 후(clearance 70 + 벽 반발력 0.7)**: nudge **0회**, 8명 전원 8초 만에 안전하게 완주. 스크린샷상으로도 공들이 벽에 붙어 미끄러지지 않고 보드 폭 전체에 고르게 퍼져서 떨어짐을 확인.

이 반발력 조정은 `frontend-react/src/game/engine.ts`와 레거시 `frontend/js/game.js` 양쪽에 동일하게 반영했다(둘 다 이번 세션에서 지그재그→돌기→반발력 순으로 같이 되돌리고 고쳤다).

### 5. 빠른 참가자 추가 (React 프론트엔드 전용)

참가자 등록 폼(1번 섹션)에 인원수 선택 셀렉트박스 + "빠른 추가" 버튼을 추가했다(`RegistrationForm.tsx`). 클릭하면 이름/생년월일 입력이나 AI 호출 없이 선택한 인원만큼(최대 8명) 즉시 "게스트N" 이름으로 참가자가 등록된다.

게임에서 여전히 높이 차등을 보여주기 위해, 등록 시점에 클라이언트에서만 무작위 점수(0~100)를 뽑아 `GamePage`의 `hiddenScores` 맵에 저장해둔다. 이 점수는:
- **오늘의 운세 화면(2번 섹션)에는 절대 노출하지 않는다** — 대신 "🎲 무작위로 배정된 시작 높이 — 게임에서만 확인할 수 있습니다"라는 가려진 카드만 보여준다(`FortuneSection.tsx`, `tier-quick` 스타일).
- **게임 시작 시점에만** `startYFromHiddenScore()`(백엔드 `BuffCalculator`의 `START_Y_PER_POINT=2.0`과 반드시 같은 값을 쓰는 프론트 전용 함수, `utils/quickAddBuff.ts`)로 변환해서 `game.participants`의 `buff.startY`를 클라이언트에서 덮어쓴다.

백엔드는 전혀 건드리지 않았다 — 빠른 추가 참가자는 서버 입장에서는 그냥 "생년월일 없는 일반 참가자"이고(`source: NONE`), 무작위 점수와 그 변환은 순전히 프론트엔드 안에서만 존재한다. 이번엔 React 프론트엔드에만 추가했고, 레거시 vanilla `frontend/`에는 반영하지 않았다 — 등록 폼 UI 전용 기능이라 두 프론트가 공유하는 물리 엔진 파일과는 무관하기 때문이다.

#### 검증

8명을 "빠른 추가"로 한 번에 채운 뒤 운세 확인을 눌러 8장 모두 점수 없이 가려진 카드로 나오는 것을 확인했고, 게임을 실행해 실제로 서로 다른 높이에서 출발하는 것을 스크린샷으로 확인했다.

### 6. 교훈

devhelp/02(구 11)의 교훈("안전장치가 자주 발동하면 근본 원인을 못 고쳤다는 신호")이 이번에도 그대로 들어맞았다 — 다만 이번엔 한 걸음 더 나아가서, **이미 실측으로 검증된 안전 마진(clearance 70)을 다른 목적(가장자리 통로 제거)으로 재활용하려다가 같은 버그를 두 가지 다른 형태로 재현**했다는 점이 새로운 교훈이다. 물리 파라미터 하나가 "왜 그 값인지" 기록이 없으면, 나중에 다른 문제를 풀다가 그 값을 무심코 건드려 이미 고친 버그를 되살릴 수 있다.

## [구 31] API 클라이언트 예열, 그리고 핀볼 가장자리 탈출 완화

### 1. Claude API 클라이언트 예열 (토큰 비용 없음)

배포 후 실제로 웹에서 써보니, 서버가 깨어있는 상태에서도 **첫 운세 요청**이 이후 요청들보다 눈에 띄게 느렸다. 원인은 `ClaudeFortuneGenerator`가 `AnthropicOkHttpClient`를 최초 호출 시점에 지연 생성하도록 만들어놨기 때문 — 이건 원래 "API 키가 없어도 서버는 정상적으로 뜨게" 하려고 일부러 넣은 설계였는데, 그 대가(클라이언트 생성 비용)를 실제 첫 사용자가 그대로 떠안는 구조였다.

```java
@EventListener(ApplicationReadyEvent.class)
public void warmUpClient() {
    try {
        client();
    } catch (ApiException e) {
        // ANTHROPIC_API_KEY 미설정 — 로컬 개발 등에서는 정상적인 상황이라 별도 처리 없이 넘어간다.
    }
}
```

서버가 완전히 뜬 직후(`ApplicationReadyEvent`)에 미리 `client()`를 한 번 호출해서 클라이언트 객체(OkHttp 커넥션 풀 등)를 만들어둔다. **중요한 건 이게 `client().messages().create(...)`가 아니라 `client()`까지만 호출한다는 점** — 즉 Anthropic에 실제 네트워크 요청을 보내는 게 아니라 로컬에서 "통신 준비"만 해두는 것이라 **토큰 비용이 전혀 들지 않는다.** 키가 없으면 기존 `client()`의 예외 처리가 그대로 걸려서 조용히 넘어가고, 실제 요청 시점에 사용자에게 같은 안내 메시지가 뜨는 기존 동작은 그대로 유지된다.

참고로 이건 Render 무료 티어의 "슬립 후 첫 요청 30~60초" 문제와는 별개다. 그건 컨테이너 자체가 꺼졌다 켜지는 호스팅 인프라 동작이라 애플리케이션 코드로는 줄일 수 없고, 이 예열은 "서버가 이미 깨어있는 상태에서 첫 API 호출"에만 효과가 있다.

### 2. 핀볼 맵 — 가장자리로 빠지면 재미없게 끝나는 문제

#### 증상
실제로 여러 판을 테스트해보니, 공들이 벽 쪽 빈 통로(여백)를 타고 못을 거의 안 건드리고 그대로 바닥까지 미끄러져 내려가는 경우가 있었다. 사용자가 직접 스크린샷에 빨간 선으로 그려서 보여준 그대로 — 양쪽 가장자리가 사실상 "치트키 통로"가 되어 게임이 재미없게 끝나버리는 문제.

#### 왜 여백 자체를 없애면 안 되는가
이 여백(`PEG_WALL_CLEARANCE = 70`)은 장식이 아니라 devhelp/02(구 11)·devhelp/02(구 25)에서 **두 번이나 실측으로 확인된 안전장치**다. 벽과 못 사이 틈이 좁으면(70 미만) 공이 그 틈에 반복적으로 끼어서 영영 못 빠져나오는 버그가 재발한다 — 지그재그 벽으로 시도했을 때도, 둥근 돌기로 시도했을 때도 똑같이 재발했다. 장애물 모양이 아니라 **틈 자체의 폭**이 원인이라는 게 이미 결론 난 사안이라, `PEG_WALL_CLEARANCE`는 절대 건드리지 않았다.

#### 이번에 한 것 — 안전한 부분과 실험적인 부분을 분리

**안전한 변경 (검증 불필요, 기존 메커니즘 재배치일 뿐)**
- 핀휠(회전 막대) 줄을 기존 중간(10행) 한 줄에서 **5행(더 위)** 으로 옮기고, **15행(하단)에 한 줄 추가**했다. 낙하 구간 전체에 걸쳐 핀휠과 마주칠 기회를 늘리는 목적.

**실험적인 변경 (별도 상수로 분리, 장시간 검증 완료)**
- 못 배치 기준 `PEG_WALL_CLEARANCE`(70)는 그대로 두고, **핀휠 전용 여백 상수** `PINWHEEL_WALL_CLEARANCE = 50`을 새로 만들어 핀휠만 벽에 20px 더 가깝게 배치했다.
- 근거: 못은 고정된 물체라 벽과의 좁은 틈이 "고정된 함정"이 되지만, 핀휠은 계속 회전해서 같은 자리에 계속 있지 않는다 — 그래서 같은 틈이라도 다른 물리적 상황일 수 있다는 가설.

```ts
const PINWHEEL_WALL_CLEARANCE = 50;
```

#### 검증
devhelp/02(구 25)와 같은 방식 — 8명 참가 게임을 여러 번 실제로 돌려서 전원이 안전하게 완주하는지 확인했다(이번엔 Playwright로 실제 브라우저를 띄워 자동화):

- 8명 게임 **5회 반복**, 매번 완주 여부와 소요 시간 기록
- 결과: **5회 전부 정상 완주**, 11.6~15.7초 (멈춘 공 없음, 타임아웃 없음)

devhelp/02(구 25) 때처럼 nudge(끼임 안전장치)가 계속 헛발동하는 징후도 없었다 — 5회 모두 비슷한 시간대에 안정적으로 끝났다는 것 자체가 특정 트라이얼에서 공이 걸려 붙잡히지 않았다는 간접 증거다.

#### 남은 한계
- 이번 검증은 "완전히 영구적으로 멈추는 최악의 경우"는 배제했지만, 가장자리로 빠지는 빈도 자체가 얼마나 줄었는지(예: 완주 순서 분포)까지는 정량적으로 측정하지 않았다. 체감상 개선되는지는 실제 플레이로 계속 지켜볼 부분.
- `PINWHEEL_WALL_CLEARANCE`를 더 줄이면(예: 35) 더 많은 영역을 커버하겠지만, 검증되지 않은 값이라 현재는 50에서 멈췄다. 더 줄이고 싶다면 이번과 같은 방식(여러 판 반복 실행 + 완주 여부 확인)으로 먼저 검증해야 한다.

### 3. 핀휠 2줄 → 4줄로 확장 (사용자가 스크린샷에 직접 표시)

2줄(5행/15행)로 해보니 두 줄 사이 9행(450px) 구간은 여전히 완전히 뚫려있어서, 사용자가 실제 스크린샷 위에 "이 높이들에도 뭔가 막아주면 좋겠다"고 직접 표시해줬다. 처음 제안은 **여백 통로 안에 고정된 갈고리 모양 장애물**을 추가하는 것이었는데, 이건 형태만 다를 뿐 devhelp/02(구 25)에서 이미 두 번 실패한 것과 같은 종류(여유 구간 안의 정적 장애물)라 그대로는 위험하다고 판단해서 반려했다.

대신 이미 검증된 핀휠(회전 장애물) 방식을 더 촘촘하게 배치하는 쪽으로 대안을 냈다: **5행/15행 두 줄 → 4행 간격으로 균등한 4행/8행/12행/16행 네 줄.**

```ts
pinwheelRowIndices: [4, 8, 12, 16],
```

#### 검증
같은 방식으로 8명 게임을 **총 10회** 반복 실행(2회의 5회 배치로 나눠 진행 — 핀휠 줄이 2개에서 4개로 늘어 위험 표면이 커진 만큼 처음보다 더 많이 돌려봤다):

- **10회 전부 정상 완주**, 13.6~19.8초 (멈춘 공 없음, 타임아웃 없음)
- 2줄일 때(11.6~15.7초)보다 평균적으로 조금 더 걸리는데, 핀휠과 부딪히는 횟수가 늘어난 자연스러운 결과로 보인다 — 나쁜 신호가 아니라 오히려 통로 전체에서 공이 더 많이 상호작용한다는 뜻.

`frontend-react/src/game/engine.ts`, `frontend/js/game.js` 양쪽에 동일하게 반영했다(물리 변경은 항상 두 프론트엔드에 동기화).

### 4. 좌우 비대칭 수정, 그리고 "벽에 거의 붙이기" 실패

#### 좌우 비대칭 — 안전하게 해결됨
사용자가 실제 화면을 보고 핀휠 줄이 좌우 대칭이 아니라고 지적했다. 원인은 `buildPinwheelPositions`가 `fieldLeft`부터 그리디하게 채우고 `spacing`으로 안 나눠떨어지는 나머지를 전부 오른쪽에 몰아주는 방식이었기 때문 — 왼쪽 여백은 항상 0, 오른쪽 여백만 들쭉날쭉했다.

실제로 들어갈 개수를 먼저 구하고, 그 묶음 전체를 `fieldLeft`~`fieldRight` 가운데에 정렬하도록 고쳤다. 벽과의 거리(`PINWHEEL_WALL_CLEARANCE`)와는 무관한 순수 배치 로직 변경이라 리스크가 없다.

#### "벽에 거의 붙을 정도로" — 실패, 원복함
사용자가 핀휠을 벽에 거의 닿을 정도로 가깝게 해달라고 요청해서, `PINWHEEL_WALL_CLEARANCE`를 50 → **15**로 줄여봤다. "회전하는 장애물이라 고정된 못과 달리 안전할 것"이라는 가설을 더 밀어붙여본 것.

**결과: 실패.** 8명 게임 5회 중 **4회가 120초 타임아웃**, 끝난 1회도 110초나 걸렸다(정상은 12~16초). 화면상 공이 눈에 띄게 오래 안 움직이는 것과 같은 증상이었다 — 회전 장애물도 벽에 특정 거리 이하로 가까워지면 고정된 못과 똑같이 위험해진다는 뜻이다. "회전하니까 안전하다"는 가설은 **정도의 문제였지, 무한정 적용되는 게 아니었다.**

바로 검증된 값(50)으로 되돌리고, 되돌린 상태로 5회 재검증(12.1~16.2초, 전부 정상 완주)해서 안전함을 다시 확인했다.

#### 교훈
- devhelp/02(구 25)의 교훈("여유 구간 자체를 줄이면 재발한다")이 **정적 장애물뿐 아니라 회전 장애물에도, 정도는 다르지만 결국 적용된다.** 70(못) → 50(핀휠, 안전) → 15(핀휠, 실패)로 이어지는 스펙트럼이 있는 것이지, "회전하면 무조건 안전"이 아니다.
- 50과 15 사이 어딘가에 실제 안전 한계선이 있겠지만, 이번 세션에서는 더 탐색하지 않았다. 더 가깝게 당기고 싶다면 같은 방식(8명 게임 여러 번 반복 + 완주 여부·소요 시간 확인)으로 값을 조금씩만 조정하며 검증해야 한다 — 한 번에 70→15처럼 크게 건너뛰지 않는 게 안전하다.

## [구 36] 벽 삼각 선반으로 "벽 통로 낙하" 막기 — 참고 사이트 분석부터 A/B 실험까지

공이 양쪽 벽을 따라 못을 거의 안 건드리고 그대로 바닥까지 내려오는 문제(devhelp/02(구 31)에서 스크린샷에 빨간 선으로 표시했던 것)를, 이번엔 **정적 장애물을 벽에 붙이는 방식**으로 다시 풀었다. devhelp/02(구 25)·31에서 이 종류의 시도가 두 번 실패했기 때문에, 이번엔 ① 참고 사이트 소스를 먼저 분석하고 ② 실패 경험에서 설계 규칙을 뽑고 ③ 코드를 바꾸기 **전에 기준값을 숫자로 측정**하고 ④ 규칙을 일부러 어긴 **음성 대조군**까지 돌려서 확인했다.

### 1. 문제를 숫자로 만들기 (기준값)

"벽 통로로 많이 내려온다"는 느낌을 지표로 바꿨다. 8명 게임을 실제 브라우저(Vite 개발 서버)에서 반복 실행하면서 16ms마다 공 좌표를 샘플링한다.

- **벽 통로 최대 낙하**: 벽 안쪽 면에서 공 중심까지 45px 이내를 벗어나지 않고 이어서 내려온 세로 거리의 최대값
- **공당 통로 낙하**: 공 1개가 통로 안에서 내려온 세로 거리 합의 평균
- **정체 이벤트**: 2px 이내에서 0.75초 이상 머문 구간(= `nudge` 안전장치가 발동하는 조건)

현재 맵 10회: **최대 낙하 평균 903px, 공당 평균 403px**. 판 하나에서 한 공이 1,000px 넘게 벽을 타고 내려온 경우가 흔했다. 전부 완주(11~16초), 정체는 0회.

### 2. 참고 사이트(lazygyu/roulette) 소스 분석

`src/data/maps.ts`의 BubblePop 맵을 뽑아서 구조를 봤다(공 지름 0.5, 벽 폭 7.25 = 지름의 14.5배. 우리는 560/26 ≈ 21.5배라 통로가 생길 여지가 더 크다).

- 격자 가장자리 못이 **벽 좌표 위에** 올라가 있다(x=9.25, 16.5). 빈 통로 자체가 없다.
- 3×3 큰 마름모(45°)가 벽에 박혀 **좌/우 번갈아**(y=39 왼쪽, y=43 오른쪽) 나온다. 채널 폭의 약 29%.
- 벽에서 1.5칸 떨어진 곳에서 회전 막대가 돈다. 아래쪽은 반발계수 1.5 원형 범퍼 격자.
- **벽의 반발계수는 0**. 안쪽으로 밀어내는 건 반발력이 아니라 **기울어진 면**이다.

> 이번에 참고한 건 **설계 원리**뿐이다. 좌표·치수·코드는 가져오지 않았고, 우리 엔진(Matter.js, px 단위) 기준으로 새로 설계했다.

### 3. 설계 규칙 (devhelp/02(구 25)·31 실패 경험에서 추출)

| 규칙 | 내용 | 근거 |
|---|---|---|
| **R1 간격** | 장애물끼리(또는 장애물과 벽)의 틈은 **0(접촉)이거나 50px 이상**. 그 사이는 금지 | 틈 30·15는 실패, 50·63·70은 통과 (공 지름 26의 약 2배) |
| **R2 웅덩이 금지** | 공이 올라앉는 윗면은 중앙 쪽으로 **내려가는 경사**(벽과의 각이 둔각) | 오목한 모서리는 공이 갇히는 "그릇"이 됨 |
| **R3 전체 덮기** | 공 반지름(13)만큼 부풀린 장애물이 모든 x를 덮어야 빈 통로가 없다 | 벽 쪽 x 13~50 구간은 못이 없어서 통로가 됨 |

**기존 결론의 구멍**: devhelp/02(구 25)는 "돌기 실패 = 간격 30이 원인, 모양은 무관"이라고 했는데, 모양만 바꿔 간격 70에서 따로 검증한 적은 없었다(두 시도 모두 간격 30이 섞여 있었음). 반원 돌기는 벽과 만나는 지점의 접선이 수평이라 평평한 턱이 생겨 R2를 어길 수도 있었다. 이번 실험은 이 혼재를 분리하는 목적도 있었다.

### 4. 설계: 벽 삼각 선반

```
|\                /|     꼭대기가 벽에 붙고, 아래 끝(팁)이 안쪽으로 40px 튀어나옴
| \              / |     윗면 45° 경사 → 벽과의 각 135° (둔각, R2 충족)
|__\            /__|     벽을 타고 내려오던 공이 윗면에 닿아 안쪽으로 굴러떨어짐
```

- 크기 40×40(45°), 반발계수는 벽과 같은 0.7. **반발계수를 2배로 올리는 안은 채택하지 않았다** — 1을 넘으면 튕길 때마다 에너지가 늘고, 경사면이면 0.7로도 충분히 안쪽으로 밀린다(참고 사이트도 벽 반발계수 0).
- 위치: 핀휠 행(4/8/12/16) 사이의 행 2/6/10/14/18, 양쪽 벽 모두(총 10개).
- 벽은 두께 16px짜리 회전 사각형이라 중심선이 아니라 **안쪽 면(중심선 + 8px)** 에 붙이고, 벽 쪽 꼭짓점은 4px 파묻어 이음새 틈을 없앴다.
- **R1을 코드로 강제**: 선반 팁에서 못 표면까지 틈이 50px 미만이 되는 못은 배치하지 않는다(`buildPegPositions`에서 점-다각형 거리로 검사). 숫자로 보면 선반 행의 벽 쪽 첫 못(중심선에서 70px)은 팁과의 틈이 약 23px라 제거되고, 인접 홀수 행의 첫 못(100px)은 약 53px라 유지된다.

### 5. 구현 요약

`frontend-react/src/game/engine.ts`, `frontend/js/game.js`(물리 변경은 항상 두 프론트에 동기화), 스타일 `.wall-wedge`.

- `MapConfig`에 `wedgeRowIndices: [2,6,10,14,18]`, `wedgeSize: 40`, 상수 `MIN_OBSTACLE_GAP = 50`, `WALL_THICKNESS = 16`(기존엔 `buildBoard` 안의 지역 변수)
- `buildWedgeSpecs()`: 행마다 좌/우 볼록 사각형 꼭짓점 계산
- `MatterAdapter.addStaticPolygon()`: `Matter.Bodies.fromVertices` — **넘기는 (x, y)가 무게중심으로 쓰이므로** `Vertices.centre()`로 중심을 구해서 넘긴다(그냥 중간점을 주면 모양이 어긋난다)
- 화면: 물리 바디와 같은 꼭짓점을 `clip-path: polygon(...)`(요소 크기 기준 %)으로 오려내고 색은 벽과 같게
- 못 배치: 선반과의 거리 검사로 R1 위반 못을 제외

모든 판은 같은 조건(8명, 빠른 추가, 실제 UI 흐름 → 게임 시작)이고 React 프론트에서 측정했다.

### 7. 알게 된 점

1. **같은 모양, 못 하나 유무로 결과가 갈렸다.** 선반 모양 자체는 문제가 아니고, R1(틈 ≥ 50)을 어기느냐가 끼임의 원인이다. devhelp/02(구 25)가 내린 "간격이 원인" 결론이 맞았다는 걸 이번에 대조군으로 직접 확인했다.
2. **통로를 막는 효과는 모양(기하)에서 나온다.** 음성 대조군에서도 통로 낙하 지표는 선반이 있는 쪽과 같았다(151px). 즉 선반이 막는 역할, R1이 끼임을 막는 역할이 분리돼 있다.
3. **아직 미검증**: "둥근 돌기도 틈 ≥ 50이면 괜찮았을까?"는 이번에 다루지 않았다. 지금 확인된 건 "45° 삼각 선반 + R1"이 안전하다는 것까지다.
4. 측정 때 개발 서버(HMR)를 돌리는 도중 코드를 바꾸면 진행 중인 판이 오염된다 — 측정과 수정을 번갈아 하지 않고, 대조군 실험 후엔 복원 뒤 재측정으로 최종 상태를 다시 확인했다.

### 8. 남은 것

- 선반 크기(40)와 행 배치(2/6/10/14/18, 양쪽 동시)는 시작값이다. 좌우 번갈아 배치하거나 크기를 키우는 변형은 같은 방식(기준값 대비 + 10회 이상)으로 검증하면 된다.
- 지표 측정 스크립트는 스크래치패드(임시 폴더)에 있어서 저장소에는 없다. 재사용하려면 `frontend-react/` 밖 별도 위치로 옮기는 게 좋다.

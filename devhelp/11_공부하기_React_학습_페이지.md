## 3. README를 어떻게 옮겼나

README는 1,482줄짜리 **들여쓴 텍스트 개요**(`(1)`, `->`)라서 마크다운으로 그대로 렌더링하면 들여쓴 줄은 코드 블록이 되고 나머지는 한 문단으로 합쳐진다. 그래서 챕터별 마크다운(`notes/chNN.md`)으로 다시 정리하고 **빌드에 포함**했다(GitHub에서 실행 시점에 가져오지 않음 — 서식 없는 원문이 보이고 네트워크에 의존하게 되므로).

- 내용은 원문 그대로 옮기되, **코드 오타는 바로잡았다**: `onChage`, `</lable>`, `evnet.target.cheched`, `toFahrengeit`, `lendth`, `class Toggle extend`, 닫히지 않은 따옴표·태그 등. `componentDidUnmount`는 실제 이름인 `componentWillUnmount`로 고치고 그 사실을 본문에 적었다.
- 원문에 없던 설명이나 빠진 코드(예: `useUserStatus` 구현, 합성/Context 예제 코드, `count && ...`가 `0`을 그리는 함정)는 처음엔 문장 중간에 "(보충)"이라고만 적었는데, 원문과 섞여 눈에 띄지 않아서 **"AI 코멘트" 블록**으로 모두 옮겼다(아래 5장).
- `## ` 제목 단위로 접이식(`<details>`)이 되고 첫 항목만 펼쳐 둔다.
- 한계: 이 복사본은 **한 번 옮겨 온 스냅샷**이다. React_basic의 README를 고쳐도 여기에는 자동 반영되지 않는다.

## 3-2. AI 코멘트와 코드 하이라이트

**AI 코멘트** — 사용자가 정리한 원문 아래에, AI가 덧붙이는 설명을 **색이 다른 말풍선 블록**으로 따로 둔다. 원문은 그대로 남고, 읽는 사람이 "직접 공부한 내용"과 "AI가 보완한 내용"을 구분할 수 있다.

- 마크다운 문법은 인용(`>`) 블록이고, 첫 문단이 정확히 `**AI 코멘트**`인 인용만 말풍선으로 렌더링한다(react-markdown의 `blockquote` 컴포넌트를 바꿔 끼움). 나머지 인용은 평범한 인용이다. 새 라이브러리는 쓰지 않았다.
- 정리 탭 위에 **"💬 AI 코멘트 보기" 스위치**가 있고 **기본은 보임**이다. 끄면 원문만 깨끗하게 읽을 수 있고, 선택은 브라우저에 저장된다(저장소를 못 쓰는 환경에서도 기본값으로 동작).
- 13개 챕터에 **총 50개**를 넣었다. 내용은 네 종류다: ① 왜 그런가(예: `useMemo`는 언제 쓰나) ② 자주 하는 실수(예: key에 index, `count && ...`의 `0`) ③ 요즘 기준(예: `ReactDOM.render` 제거, `useEffect`를 동기화로 이해, CRA 지원 종료) ④ 이 프로젝트 코드와의 연결(예: `GamePage`의 state 끌어올리기, `PinballBoard`의 `useRef`, key로 컴포넌트 재생성). 원문의 오류(`componentDidUnmount` 등)를 바로잡는 코멘트도 여기에 둔다.
- 코멘트에서 이 프로젝트 코드를 근거로 든 부분은 실제 코드를 열어 확인하고 썼다(`GamePage`의 `players`/`onRegistered`, `PinballBoard`의 ref, `LogList`만 index key, `.oxlintrc.json`의 rules-of-hooks 등).
- **챕터당 2~4개를 목표로 했지만 Hooks(7장)는 8개**로 가장 많다. 다루는 Hook이 많은 챕터라서다.
- 한계: AI가 쓴 글이라 **틀릴 수 있다.** 기술적 주장은 높은 확신이 있는 것만 썼지만, 사용자가 읽어 보고 확인하는 것이 전제다.

**코드 하이라이트** — `prism-react-renderer`로 색을 입힌다. 코드 탭(줄 번호 포함)과 정리 탭의 코드 블록 모두에 적용된다.

- **lazy**: 하이라이터는 약 86kB(gzip 27kB)라서 `React.lazy`로 코드를 처음 보여줄 때만 내려받는다. 핀볼 첫 화면(메인 번들 약 380kB)은 그대로다. 도착하기 전에는 같은 모양의 색 없는 코드가 먼저 보이고, 도착하면 색이 입혀진다.
- 이 라이브러리가 모르는 언어(`bash`)는 색 없이 그대로 보여준다.
- 코드는 `dangerouslySetInnerHTML` 없이 토큰을 React 요소로 그려서 별도의 이스케이프 걱정이 없다.

## 4. 만들면서 발견한 것

1. **원본 코드의 오타 import가 번들러에서는 실행 오류**: `chapter_11/SignUp.jsx`의 `import React, {userState, useState}`. CRA(웹팩)는 넘어가지만 Vite에서는 존재하지 않는 이름을 import하면 모듈 로딩이 실패한다. 복사본에서 이 한 줄만 고쳤고 화면 안내에도 적었다.
2. **개발 모드의 StrictMode가 생명주기 예제를 망친다**: 이 앱 전체가 `<StrictMode>`라서 개발 모드에서는 `componentDidMount`/`useEffect`가 두 번 실행된다. 6장의 로그가 `Mount → Unmount → Mount`로 어지럽게 찍혔는데, 원본에서 "17버전으로 다운"했던 이유와 같은 현상이다. **데모를 별도 React 루트(`IsolatedRoot`, StrictMode 밖)에서 실행**하도록 바꾸자 `Mount → Update → 다음 알림 Mount` 순서로 정상 출력됐다. 이렇게 하면 개발/배포 결과가 같고 React 17 동작과도 같다.
   - 같은 div에 `createRoot`를 두 번 부르면 경고가 나므로, 효과가 실행될 때마다 새 div에 새 루트를 만든다.
3. **콘솔 로그를 화면에 보여줘야 학습이 된다**: 6·7장은 `console.log`로 동작을 보여주는 예제다. `ConsolePanel`이 화면에 떠 있는 동안만 `console.log`를 가로채 화면에도 출력한다(원래 콘솔 출력은 유지, 떠날 때 원복).
4. **원본은 index.js에서 하던 일을 래퍼로 대신한다**: 4장 시계는 `setInterval`로 `root.render`를 1초마다 다시 호출했으므로 래퍼가 같은 효과를 낸다. 8장은 `ConfirmButton`(클래스)과 `ConfirmButton2`(함수)를 나란히 보여준다.
5. **전역 CSS가 예제에 번진다**: 앱의 `button { 주황색 … }`가 예제 버튼에 적용됐다. 데모 영역을 흰 상자로 만들고 그 안에서 `button, input, textarea, select { all: revert }`로 브라우저 기본 모양을 되돌렸다.
6. **14장은 `100vw × 100vh` 예제**라 데모 상자 안에서 줄여 보여주도록 CSS를 따로 두었다.
7. **15장은 원본 그대로 콘솔 경고가 두 가지** 뜬다(key 없음, styled-components v6가 `backgroundColor`를 DOM까지 넘김). 학습 자료라 고치지 않고 안내 문구로 설명했다(해결법은 `$backgroundColor` 같은 transient props).
8. **코드 탭에서 챕터를 넘기면 선택한 파일이 이전 챕터 것으로 남을 수 있었다**: 코드 탭의 "선택한 파일" 상태가 챕터가 바뀌어도 초기화되지 않았다. 챕터 id를 `key`로 줘서 챕터가 바뀔 때 새로 시작하게 했다(10장의 key 코멘트와 같은 원리다).
9. **이전/다음 챕터로 이동하면 보던 탭이 풀렸다**: 정리를 이어서 읽는 용도인데 매번 데모 탭으로 돌아갔다. 이동할 때 `?tab=`을 유지하도록 했다.
10. 린트: 복사한 예제는 학습 당시 코드 그대로 보여주는 용도라 `.oxlintrc.json`의 `ignorePatterns`로 제외했다. 새로 쓴 코드는 경고 0건이다.

## 6. 나중에 얹을 수 있는 C안 — Sandpack

**Sandpack**은 CodeSandbox가 만든 오픈소스 컴포넌트로, 브라우저 안에서 **코드를 직접 고치고 바로 실행**하는 에디터+미리보기를 제공한다. 지금의 [코드] 탭(읽기 전용)을 이걸로 바꾸거나 [직접 실행] 탭을 하나 더 두는 방식이다.

**확인한 사실**(npm 기준): `@codesandbox/sandpack-react` 2.20.0, 라이선스 Apache-2.0, React 16.8~19를 지원, 압축을 푼 패키지 크기 약 1.2MB(번들에 들어가는 크기가 아니라 패키지 크기다).

**지금 구조에 붙이는 방법**: 이미 실행되는 소스를 `?raw`로 읽고 있으므로 그 문자열을 그대로 Sandpack의 `files`에 넘기면 된다.

```tsx
<SandpackProvider
  template="react"
  files={{ '/Library.jsx': libraryRaw, '/Book.jsx': bookRaw, '/index.js': entry /* 데모를 렌더링하는 진입 파일 */ }}
  customSetup={{ dependencies: { react: '17.0.2', 'react-dom': '17.0.2' } }}
>
  <SandpackLayout><SandpackCodeEditor /><SandpackPreview /></SandpackLayout>
</SandpackProvider>
```

- 장점
  - 코드를 **직접 수정해 보며** 공부할 수 있다(지금은 읽기만 가능).
  - **React 17을 그대로 선택**할 수 있어서 원본 학습 환경과 가장 가깝다(지금은 React 19 위에서 격리해 흉내 낸다).
  - 챕터별 진입 파일만 만들면 되고, 코드 표시/실행이 한 곳에서 해결된다.
- 단점과 위험
  - **외부 의존**: Sandpack은 기본적으로 CodeSandbox가 호스팅하는 번들러를 iframe으로 불러와 실행하는 구조로 알고 있다(구현 전에 최신 동작 확인 필요). 그렇다면 CodeSandbox 서비스가 막히거나 느린 환경(사내망, 오프라인)에서는 데모가 안 뜬다. 지금 방식은 우리 서버 파일만 쓰므로 이런 의존이 없다.
  - **무겁다**: 에디터와 번들러 클라이언트가 커서 반드시 lazy 로딩해야 하고, 첫 실행에 몇 초가 걸릴 수 있다(실측하지 않았다).
  - **모바일에서 코드 편집이 불편**하다.
  - 15장 styled-components처럼 외부 패키지는 `customSetup`으로 따로 지정해야 하고, 6·7장의 `console.log` 패널은 Sandpack 내부 콘솔로 대체해야 한다.
- 예상 작업량: 반나절 안팎(탭 추가, 챕터별 진입 파일 13개, 의존성 지정, 로딩/오류 처리, 모바일 확인).
- **판단**: 지금은 필요하지 않다. 읽고 실행해 보며 공부하는 목적은 이미 충족하고, 외부 서비스 의존 없이 항상 같은 결과가 나온다는 장점이 더 크다. "직접 고쳐 보며 실습"이 정말 필요해질 때 [직접 실행] 탭으로 **추가**하는 것을 권한다(기존 [코드] 탭은 읽기용으로 남겨 두고, Sandpack이 안 뜨는 환경에서도 코드를 볼 수 있게).

## 7. 한계

- 예제는 React 17 기준으로 공부한 코드를 **React 19에서 실행**한다. 이번 예제에서는 차이가 없었지만(제거된 API를 쓰지 않음), 앞으로 예제를 추가하면 확인이 필요하다.
- 코드/정리 모두 원본과 **따로 존재하는 복사본**이다. 원본을 고쳐도 자동으로 따라오지 않는다.
- 하이라이트는 `prism-react-renderer`가 아는 언어만 색이 입혀진다(2026-10-06에 Java, Gradle, properties, bash를 추가했다).
- AI 코멘트는 AI가 쓴 글이라 틀릴 수 있다. 원문과 구분해 표시했고 스위치로 끌 수 있지만, 내용 검증은 읽는 사람의 몫이다.

## [2026-10-06] 공부하기 > Spring Boot 추가 (1장)

React 학습 페이지처럼, Spring Boot 기초를 공부하는 페이지를 만들었다. 이번에는 원본 자료가 없어서 Claude가 공식 문서를 보고 내용을 썼다.

### 1. 범위

- 1~2년차 개발자가 3주 정도 공부할 18장. 기초 위주이고 마지막 장은 람다식과 Stream이다.

### 2. React 페이지와 다른 점

브라우저에서 Java를 실행할 수 없어서 "데모" 탭 대신 아래처럼 만들었다.

|---|---|

| 직접 요청 | 6~8장에서 핀볼 백엔드에 실제 요청을 보내 응답을 보는 탭. 데이터를 저장하지 않는 요청만 쓴다 |

- prism-react-renderer에 Java가 기본으로 없어서 `prismjs`의 언어 파일(java, groovy, properties, bash)을 추가했다. 이 파일들은 전역 `Prism`에 등록하는 방식이라 `prismGlobal.ts`에서 먼저 전역에 걸어 둔다.

### 4. 검증

1280px·390px에서 목록, 1장의 세 탭, 실행 결과, 문법 색칠을 Playwright로 확인했다. React 공부하기도 그대로 동작한다. 늘어난 하이라이터 용량(약 11kB)은 코드를 열 때만 받는다.

## [2026-10-06] 공부하기 > Spring Boot 2~9장

스프링 기본(2~4장)과 웹 요청 처리(5~9장)를 만들었다. 모든 예제는 1장과 같은 방식으로 임시 폴더에서 빌드·실행하고 실제 출력을 실었다. 반복 작업이라 "예제 복사 → 빌드 → 실행 → 요청 → 로그 정리"를 스크립트 하나로 돌렸다(저장소에는 넣지 않음).

### 1. 실행해 보고 알게 된 것(정리에 반영)

예상과 다르거나, 실행해 봐야 알 수 있었던 것들이다.

| 장 | 알게 된 것 |
|---|---|
| 3 | 빈이 없으면 `Parameter 1 of constructor in ... required a bean of type 'java.time.Clock' that could not be found.`로 서버가 뜨지 않는다(실제 메시지를 실음) |
| 4 | 환경변수 `RESERVATION_MAXNIGHTS`, `RESERVATION_MAX_NIGHTS` 둘 다 반영됐다. 공식 권장 형식은 대시를 빼는 앞의 것 |
| 5 | 예외가 나면 필터의 `chain.doFilter()` 다음 줄이 실행되지 않는다. 405는 컨트롤러를 찾는 단계에서 막혀 인터셉터도 실행되지 않는다 |
| 6 | 기본 400 응답에는 이유가 없고 서버 WARN 로그에만 남는다 |
| 7 | 기본 검증 문구는 `Accept-Language`에 따라 한국어·영어로 바뀐다. 주소 값 검증 실패(`HandlerMethodValidationException`)는 기본 로그 레벨에서 아무 로그도 남지 않는다 |
| 8 | `@ExceptionHandler(Exception.class)`만 두면 없는 주소(404)와 지원하지 않는 메서드(405)가 500이 된다. 핀볼 백엔드가 실제로 겪었던 것과 같은 함정 |
| 9 | Boot 4에서도 `server.servlet.session.*` 설정 이름이 그대로다(응답의 `SameSite=Lax`로 확인) |

### 2. 직접 요청 탭

6~8장에 핀볼 운영 서버로 실제 요청을 보내는 항목 9개를 넣었다. 잘못된 JSON, 검증 실패, 없는 자원·주소처럼 데이터를 저장하지 않는 요청만 골랐고, 미리 curl로 응답을 확인했다. 깨진 JSON을 보낼 수 있게 `rawBody`를 추가했다.

### 3. 만들면서 겪은 것

- 윈도우 Git Bash에서 curl에 한글 JSON을 바로 넣으면 UTF-8이 깨져 400이 난다(예전에 겪은 것과 같은 문제). 본문을 UTF-8 파일로 만들어 `--data-binary @파일`로 보냈다. 실행 결과에 이 사실을 적어 두었다.
- 정리에 쓴 Jakarta 문서 링크 하나가 404여서 바꿨다. 노트의 링크 26개를 모두 열어 확인했다.
- 정리 4장의 비교표에 `@ConfigurationProperties`도 이름이 틀리면 시작 오류가 난다고 잘못 적었다가 고쳤다. 실제로는 오류 없이 빈 값(null, 0)으로 남는다.

### 4. 검증

1280px에서 1~9장의 정리·코드·이 프로젝트에서는 탭과 실행 결과, 직접 요청 9개(운영 서버 응답 200·404·400)를 Playwright로 눌러 확인했다. 390px에서도 3개 장을 확인했다. 가로 스크롤, 취소선, 화면 오류는 없었다.

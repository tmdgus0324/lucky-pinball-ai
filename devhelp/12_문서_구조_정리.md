## [구 48] README에 아키텍처 다이어그램과 "알려진 한계" 추가

로드맵 Phase 5의 마지막 두 항목이다. README는 채용 담당자가 가장 먼저 읽는 문서라서, "무엇을 만들었나"뿐 아니라 **"구조가 어떻게 생겼고, 어디까지가 한계인지"** 를 한눈에 보이게 했다.

### 1. 아키텍처 다이어그램 (Mermaid 2장)

GitHub는 README 안의 ` ```mermaid ` 코드 블록을 그림으로 그려 준다. 이미지 파일을 따로 관리하지 않아도 되고, 구조가 바뀌면 글자만 고치면 된다.

1. **전체 구성** — 브라우저(Vercel의 React SPA: 게임·관리자·공부하기) → Render의 Spring Boot(필터 → REST API → `FortuneQueryService`) → Neon PostgreSQL / Claude API, 그리고 슬립 방지용 cron-job.org.
2. **운세 요청 흐름** — 생년월일 입력 여부 → 신원별 잠금 → 캐시 확인 → (없으면) Claude 호출 → 성공은 `AI`로 저장 / 실패는 `FALLBACK` 임시 점수 → 상대평가 계산. 비용 절감(캐시·잠금)과 장애 대응(임시 점수)이 한 그림에 모인다.

**확인 방법**: GitHub와 같은 Mermaid 라이브러리를 브라우저에 띄워 README의 두 블록을 실제로 렌더링했다(문법 검사 + 화면 캡처).

**만난 문제 — 예약어**: 두 번째 그림이 `Parse error`로 그려지지 않았다. Claude 호출 노드의 이름을 `call`로 지었는데, `call`은 Mermaid에서 **클릭 동작용 예약어**다. 노드 이름을 `claudeCall`로 바꾸자 정상적으로 그려졌다. GitHub에 올리고 나서야 깨진 그림을 발견하는 일을 렌더링 확인으로 미리 막은 셈이다.

### 2. "알려진 한계" 섹션

devhelp 곳곳에 흩어져 있던 한계를 한 표로 모았다. 각 항목에 **"규모가 커지면 무엇을 할지"** 를 같이 적어서, 몰라서 안 한 것이 아니라 규모에 맞춰 판단했다는 점이 보이게 했다.

| 영역 | 요지 |
|---|---|
| 게임 결과 신뢰성 | 물리가 브라우저에서 돌아서, 서버는 도착 순서의 조작 여부를 알 수 없다(구성만 검증) |
| 서버 1대 전제 | 신원별 잠금·요청 제한·관리자 토큰이 메모리에 있음 |
| 관리자 인증 | 환경변수 계정 하나 + 메모리 토큰(12시간)의 간이 방식 |
| DB 스키마 관리 | `ddl-auto: update`, Flyway 미적용 |
| DB 엔진 차이 | 테스트는 H2, 운영은 PostgreSQL |
| AI 장애 대응 | 서킷 브레이커 없음(요청마다 최대 약 20초 후 임시 점수) |
| 운영·모니터링 | 오류 로그 최근 1000건, 알림·지표 없음 |
| 콜드 스타트 | Render 무료 티어 첫 요청 1~2분 |
| 테스트 범위 | 프론트엔드 자동 테스트 없음, 부하 테스트 없음 |
| 프론트엔드 두 벌 | Vanilla JS 버전 병행 유지 |

각 항목은 코드로 사실을 확인하고 썼다(관리자 토큰 TTL 12시간·메모리 보관, 요청 제한 분당 20회, 프론트엔드 `package.json`에 테스트 스크립트 없음, CI 단계 구성 등).

### 3. 같이 고친 것

- **README 첫 소개 문장이 실제와 반대였다.** "운세가 좋을수록 더 **낮은**(불리한) 위치에서 출발"이라고 되어 있었는데, 실제로는 운세가 좋을수록 결승선에서 먼 **위쪽**에서 출발한다(`BuffCalculator`: 최고점자 시작 높이 0 = 맨 위, 화면 문구도 "운세가 좋을수록 더 높은 곳에서"). 가장 먼저 읽히는 문장이라 바로잡았다.
- 기술 스택에 **테스트·CI** 줄을 추가했다(JUnit 99개: 단위·HTTP 통합·동시성·가짜 Claude 서버, GitHub Actions).

## [2026-10-04] README 축소, devdocs 신설, devhelp 48개 → 12개 통합

바로 위 절에서 README에 아키텍처 그림 2장과 한계 표 10줄을 넣었는데, 다시 보니 README가 약 150줄로 길어져 "1~2분 안에 훑어보는 문서"라는 역할에 비해 과했다. 또 devhelp가 기록마다 파일 하나씩이라 48개까지 늘어 찾아보기 어려웠다. 그래서 문서를 **읽는 사람과 목적**에 따라 세 갈래로 나눴다.

| 폴더 | 누구를 위한 것 | 성격 |
|---|---|---|

### 1. README

- 운세 요청 흐름도와 한계 표 전체는 `devdocs`로 옮기고, 구성도 1장만 남겼다(그것도 노드를 줄여 단순하게).
- 긴 "구조 특징" 목록을 **핵심 구현 포인트 6개**로 줄이고, 각각 devhelp 문서로 연결했다.
- 없던 **실행 방법**(백엔드·프론트 명령)을 추가했다.
- 코드를 다시 확인하다 고친 부정확한 표현: `MatterAdapter`는 인터페이스가 아니라 Matter.js 호출을 모은 **어댑터 클래스**다(이전 README는 "인터페이스로 분리"라고 적혀 있었다).

### 2. devdocs (5개 + 목차)

`01_아키텍처`(구성도·요청 경로·운세 흐름·게임 시퀀스·설계 판단), `02_API_명세`, `03_DB_스키마`(ERD), `04_알려진_한계와_개선_방향`, `05_테스트_전략`. 모두 컨트롤러·엔티티·테스트 결과를 직접 확인해서 썼고(예: 테스트 클래스별 개수는 최신 테스트 결과 파일에서 집계), 다이어그램 4장은 GitHub와 같은 Mermaid 라이브러리로 실제 렌더링해 문법을 확인했다.

### 3. devhelp 통합

주제가 같은 기록을 묶어 48개를 12개로 줄였다. 대응표는 `devhelp/README.md`에 있다.

- **내용은 지우지 않았다.** 원래 문서를 절로 이어 붙이고, 절 제목에 `[구 09]`처럼 원래 번호를 남겼다. 원래 제목 아래의 소제목은 한 단계씩 내렸다.
- **검증**: git에 남아 있는 원본 48개의 본문 2,061줄(제목·빈 줄 제외)이 새 문서에 모두 있는지 줄 단위로 대조했다 — 누락 0줄.
- **참조 정리**: 코드 주석·문서의 `devhelp/09` 같은 참조 약 60곳을 `devhelp/02(구 09)` 형식으로 바꿨다(새 문서와 원래 절을 둘 다 찾을 수 있게). 여러 번호를 이어 쓴 참조(`` `devhelp/09`, `11`, `25` ``)와 `../devhelp/13_...md` 같은 파일 링크는 스크립트가 못 잡아서 직접 고쳤다. 마지막으로 저장소 전체에서 없는 devhelp 파일을 가리키는 링크가 0개인지 검사했다.
- **처음 검사가 놓친 것**: 첫 링크 검사는 `devhelp/` 접두어가 붙은 참조만 봐서, 문서 안의 상대 링크(`[다음 문서](./02_백엔드_공통_설정.md)`)와 위키 링크(`[[28_배포_검증과_두_버그]]`)를 놓쳤다. 옛 파일 이름 48개와 정확히 일치하는 문자열을 전부 찾는 방식으로 다시 검사해 40곳을 고쳤다("다음 문서" 안내 줄은 절이 이어 붙어 있으니 삭제).
- 개인 메모(`00_*.md`, git 제외)는 합치지 않고 참조 번호만 맞췄다.

### 4. AI 코멘트 추가

통합한 문서 11개(01~11)의 맨 위에 "AI 코멘트"를 넣었다. 원문과 섞이지 않도록 인용 블록으로 구분했고, 내용은 대부분 **나중에 읽을 때 필요한 것**이다.

- 지금과 달라진 점 표(초기 기록이 현재 동작으로 오해되지 않게) — 01, 03, 05
- 흩어져 있던 판단을 한곳에 모은 표 — 02의 **물리 상수와 그 근거**, 06의 **코드 밖 설정 목록**, 09의 **장애 대응 절차표**
- 면접에서 쓸 수 있는 근거와 말하는 순서 — 01, 04, 07, 09

다시 읽으며 코드로 확인한 **실제 개선점**도 코멘트에 남겼다(이번 작업에서는 코드를 고치지 않음).

| 찾은 것 | 위치 |
|---|---|
| 요청 제한이 `X-Forwarded-For`의 첫 값을 믿어서, 헤더를 바꿔 보내면 분당 20회 제한을 우회할 수 있음 → **같은 날 수정** | `devhelp/08` |

### 5. 앞으로의 문서 규칙

- 기능 추가·버그 수정 기록은 **주제가 맞는 devhelp 문서 끝에 절로 추가**한다(절 제목에 날짜). 맞는 주제가 없을 때만 다음 번호로 새 문서를 만든다.
- 아키텍처·API·DB 구조가 바뀌면 **devdocs의 해당 문서도 함께 고친다** — devdocs는 "지금 기준" 설명서라 낡으면 오히려 해가 된다.

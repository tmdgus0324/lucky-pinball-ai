# 13. 알려진 한계

서버 1대, 한 판 최대 8명이라는 규모에 맞춰 일부러 단순하게 둔 부분과 아직 하지 않은 부분입니다. 다른 devhelp 문서와 달리 작업 기록이 아니라 지금 기준 목록이라, 한계가 해결되거나 새로 생기면 이 표를 고칩니다.

| 영역 | 한계 | 규모가 커지면 |
|---|---|---|
| 게임 결과 | 물리 시뮬레이션이 브라우저에서 돌아서, 서버는 도착 순서가 조작됐는지 알 수 없습니다 | 서버에서 같은 조건으로 시뮬레이션을 다시 돌려 확인 |
| 서버 1대 전제 | 동시 요청 잠금, 요청 제한 횟수, 관리자 토큰이 서버 메모리에 있습니다. 재시작하면 관리자는 다시 로그인해야 합니다 | Redis 같은 공유 저장소 |
| 관리자 인증 | 환경변수 계정 하나와 메모리 토큰을 쓰는 간단한 방식입니다. 데모 계정이 공개되어 있습니다 | Spring Security, 계정·권한 관리 |
| DB 변경 관리 | 테이블을 `ddl-auto: update`로 자동으로 맞춰서 변경 이력이 남지 않습니다 | Flyway (방법은 [07](./07_DB_영속화와_Neon.md) 6절) |
| DB 종류 차이 | 테스트는 H2, 운영은 PostgreSQL입니다 | Testcontainers로 PostgreSQL에서 테스트 |
| 인덱스 | 캐시 조회(이름, 생년월일)와 참가자별 이력 조회에 인덱스가 없습니다 | `(name, birth_date)`, `player_id` 인덱스 |
| 목록 크기 | 관리자 목록은 서버가 전체를 보내고 화면에서 20건씩 나눕니다 | 서버 페이징(`Pageable`) |
| AI 장애 | Claude가 죽어 있으면 요청마다 최대 약 20초 기다린 뒤 임시 점수로 넘어갑니다 | 연속 실패 시 호출을 잠시 건너뛰는 서킷 브레이커 |
| 모니터링 | 오류 로그는 관리자 화면에서 최근 것만 보고, 알림은 없습니다 | 로그 수집·알림 도구 |
| 첫 요청 지연 | Render 무료 티어라 오래 쉬면 첫 요청에 1~2분 걸립니다(평일 낮에는 주기적 요청으로 완화) | 유료 인스턴스 |
| 프론트 테스트 | 프론트엔드 자동 테스트와 부하 테스트가 없습니다 | Playwright 테스트, 부하 테스트 |
| 프론트엔드 두 벌 | 레거시 `frontend/`가 남아 있어 물리 코드를 두 곳에서 고쳐야 합니다 | 레거시 정리 |
| 관리자 화면 모바일 | 참가자·게임 표가 좁은 화면에 맞춰져 있지 않습니다 | 카드형 목록 |

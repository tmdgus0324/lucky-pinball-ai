## [구 13] Claude API로 실제 운세 연동

지금까지 `MockFortuneGenerator`(가짜 규칙 기반 생성기)로 대체해뒀던 자리에, 실제 Claude API를 붙여서 이름+생년월일을 분석하고 점수/행운의 숫자/메시지를 받아오도록 만들었습니다. 처음부터 `FortuneService` 인터페이스를 만들어둔 게 정확히 이 순간을 위한 것이었습니다 — 인터페이스를 구현하는 새 클래스 하나만 추가하면 됐고, 이걸 호출하는 다른 코드(`FortuneQueryService`, `FortuneController`, `GameService`)는 단 한 줄도 바뀌지 않았습니다.

### 1. 왜 "구조화된 출력(Structured Output)"을 썼는가

Claude에게 "점수, 행운의 숫자, 메시지를 알려줘"라고만 물어보면, 답변이 자유 텍스트로 와서 직접 파싱(정규식 등)해야 합니다 — 형식이 조금만 달라져도 파싱이 깨지기 쉽습니다. 대신 Claude Java SDK의 **구조화된 출력** 기능을 쓰면, 원하는 결과 형태를 자바 record로 미리 정의해두고 그 타입 그대로 돌려받을 수 있습니다.

```java
public record AiFortune(int score, int luckyNumber, String message) {}

StructuredMessageCreateParams<AiFortune> params = MessageCreateParams.builder()
    .model("claude-haiku-4-5")
    .outputConfig(AiFortune.class)   // 이 record 형태로 응답하도록 강제
    .addUserMessage("...")
    .build();

StructuredMessage<AiFortune> response = client.messages().create(params);
AiFortune result = response.content().stream()
    .flatMap(block -> block.text().stream())
    .findFirst()
    .map(StructuredTextBlock::text)   // 여기서 바로 AiFortune 타입으로 나옴
    .orElseThrow(...);
```

`@JsonPropertyDescription`으로 각 필드에 설명("0~100 사이 정수이며 높을수록 좋은 운세" 등)을 달아두면, Claude가 그 설명을 참고해서 값을 채웁니다.

#### SDK 클래스 이름을 어떻게 찾았는가

`StructuredMessageCreateParams<T>.build()`를 호출하면 `client.messages().create(...)`가 뭘 반환하는지 문서 예제만 봐서는 정확한 타입 이름(`Message`인지 다른 타입인지)이 애매했습니다. 처음엔 `Message`로 짜서 컴파일했더니, **컴파일러가 정확히 어떤 타입이 필요한지 에러 메시지로 알려줬습니다**(`StructuredMessage<T>`). 그다음 `jar tf`/`javap`로 SDK jar 안의 실제 클래스 구조를 직접 열어봐서 `StructuredMessage` → `StructuredContentBlock` → `StructuredTextBlock`으로 이어지는 정확한 메서드 체인을 확인하고 고쳤습니다. **SDK 사용법을 추측하지 않고, 실제로 컴파일해보면서 컴파일러 에러를 따라가는 방식**이 문서만 보고 추측하는 것보다 훨씬 빠르고 정확했습니다.

### 2. AI 호출을 아예 안 하는 경로도 있다 — 생년월일 선택사항

사용자 피드백에 따라 등록 흐름을 이렇게 바꿨습니다.

- **생년월일을 입력하지 않으면**: `POST /api/fortune`이 Claude를 전혀 호출하지 않고 즉시 "버프 없음"(시작 높이 +0) 결과를 돌려줍니다. `source: "NONE"`으로 표시됩니다. 비용이 0입니다.
- **생년월일을 입력하면**: 아래 3번 캐시 로직을 거쳐 Claude를 호출하거나, 과거 기록을 재사용합니다.

`FortuneQueryService.getTodayFortune()`이 이 분기를 담당합니다. `FortuneQueryResult`의 `fortuneScore`/`luckyNumber`/`fortuneMessage`를 `int`가 아니라 `Integer`(nullable)로 바꾼 이유가 이것 — "운세 자체가 없는 상태"를 표현해야 했기 때문입니다.

### 3. "같은 사주"면 Claude를 다시 안 부른다 — DB 캐시

이름+생년월일이 같으면(=같은 사람), **최초 1회만 Claude를 호출**하고 그 이후로는 DB에 저장된 값을 그대로 재사용합니다. 기획서 초기부터 있었던 "AI 토큰 절약" 목표가 이제 실제 비용이 드는 진짜 문제가 됐기 때문에, 이번에 제대로 구현했습니다.

```java
Optional<FortuneResultEntity> cached = fortuneResultJpaRepository
    .findFirstByNameAndBirthDateOrderByCreatedDateAsc(player.getName(), player.getBirthDate());

if (cached.isPresent()) {
    // DB에 저장된 점수/메시지를 그대로 재사용 (source = "CACHE")
} else {
    // Claude를 호출해서 새로 생성 (source = "AI")
}
```

**중요한 설계 포인트**: 이 캐시는 "오늘 하루만" 유효한 게 아니라 **영구적**입니다 — 날짜가 지나도 같은 이름+생년월일이면 계속 같은 결과를 씁니다 (기존에 계획했던 "하루 단위 캐시"보다 더 적극적인 절약 방식으로, 사용자가 이번에 직접 요청한 방식입니다). 그리고 이 캐시 키는 `player_id`가 아니라 **이름+생년월일 자체**입니다 — 그래서 `FortuneResultEntity`에 `player_id`뿐 아니라 `name`/`birthDate`도 함께 저장해뒀습니다 (비정규화). 서로 다른 등록 건(다른 `player_id`)이라도 이름+생년월일이 같으면 캐시를 공유해야 하는데, `player_id`로만 저장하면 이걸 할 수 없기 때문입니다.

캐시를 재사용한 경우에도 이번에 조회한 `player_id` 기준으로 이력을 한 줄 남겨두는데(값은 캐시에서 복사), `source` 컬럼에 `"AI"`/`"CACHE"`를 표시해서 관리자 화면이나 로그에서 구분할 수 있게 했습니다.

### 4. 서버가 API 키 없이도 뜨도록 만들기

`AnthropicOkHttpClient.fromEnv()`를 클래스 필드 초기화 시점(생성자)에서 바로 호출했다면, `ANTHROPIC_API_KEY`가 없는 환경에서는 **스프링 앱 자체가 뜨지도 못하고 죽었을 것**입니다 — 운세 기능을 아예 안 쓰는 요청(예: 참가자 목록 조회)까지 전부 영향을 받게 됩니다. 그래서 클라이언트 생성을 **실제로 처음 호출되는 순간까지 미뤄뒀습니다**(지연 초기화).

```java
private synchronized AnthropicClient client() {
    if (client == null) {
        client = AnthropicOkHttpClient.fromEnv();
    }
    return client;
}
```

실제로 테스트해보니 `fromEnv()` 자체는 키가 없어도 예외를 던지지 않고 클라이언트를 만들었고, 대신 실제 API를 호출하는 순간 Claude 서버가 `401 x-api-key header is required`로 응답했습니다 — 이것도 `AnthropicServiceException`으로 잡아서 `502 Bad Gateway` + 명확한 한글 에러 메시지로 바꿔 내려주도록 처리해뒀습니다. 서버는 정상적으로 계속 뜬 채로, 운세 기능만 명확한 에러를 내는 것을 실제로 확인했습니다.

### 5. 프론트엔드: 일부만 실패해도 전체가 막히면 안 된다

참가자 여러 명 중 일부만 생년월일을 입력했다면, `POST /api/fortune`을 병렬로 여러 번 호출하게 되는데, 원래 코드는 `Promise.all`을 썼습니다 — 이러면 **한 명이라도 실패(예: API 키 미설정)하면 전체가 실패 처리**되어 생년월일 없는(원래 성공했어야 할) 참가자의 카드까지 안 보였습니다. `Promise.allSettled`로 바꿔서, 성공한 참가자는 카드로 보여주고 실패한 참가자만 상태 메시지에 에러로 모아 보여주도록 고쳤습니다.

### 6. 실제로 확인한 것 (API 키 없이 확인 가능한 범위까지)

아직 Anthropic API 키를 발급받지 않은 상태라 실제 Claude 호출 자체는 확인하지 못했지만, 그 앞뒤 로직은 전부 실제로 돌려서 확인했습니다.

- 서버가 `ANTHROPIC_API_KEY` 없이도 정상 기동 (`./gradlew test`의 스프링 컨텍스트 로딩 테스트 통과 포함).
- 생년월일 없이 등록 → `POST /api/fortune` 호출 시 AI 호출 없이 즉시 `{"source":"NONE", "buff":{"tier":0,"startY":0}}` 응답.
- 생년월일 입력 후 조회 → API 키가 없어 `502` + 명확한 에러 메시지 (서버 다운 없음).
- Playwright로 생년월일 있는 참가자 2명 + 없는 참가자 2명을 섞어 등록 → "운세 확인" 클릭 시 없는 2명은 정상적으로 카드가 뜨고, 있는 2명만 에러 메시지로 안내되는 것을 화면으로 확인.

### 7. 앞으로 필요한 것 — API 키 발급

1. https://console.anthropic.com 에서 계정 생성/로그인 후 API Keys 메뉴에서 키 발급.
2. 백엔드를 실행하는 터미널에서 환경변수로 설정:
   ```bash
   export ANTHROPIC_API_KEY=sk-ant-...
   ./gradlew bootRun
   ```
   (Windows PowerShell이라면 `$env:ANTHROPIC_API_KEY="sk-ant-..."`)
3. 키는 **절대 코드/git에 커밋하지 않는다** — 환경변수로만 전달한다. `.gitignore`에 이미 `data/`, `build/` 등은 제외돼 있지만, 혹시라도 키를 파일에 적어두는 습관을 들이지 않는 게 중요하다.

키를 설정한 뒤 생년월일이 있는 참가자로 "운세 확인"을 눌러보면, 이번에는 실제 Claude가 생성한 점수/메시지가 나오는지 확인할 수 있습니다 — 같은 이름+생년월일로 두 번째 조회하면 `source: "CACHE"`로 바뀌면서 즉시(AI 호출 없이) 응답이 오는 것도 함께 확인해보면 좋습니다.

## [구 14] 생년월일 입력 방식 개선과 운세 다양성 확보

실제로 여러 명을 등록해서 써보신 사용자 피드백 2가지를 반영했습니다.

### 1. 생년월일 6자리 자동 변환

기존에는 브라우저 기본 `<input type="date">`를 썼는데, 화면에 "198902-02-13"처럼 어색하게 입력되는 문제가 있었습니다. 요청하신 대로 **6자리 숫자(YYMMDD) 입력**으로 바꿨습니다.

```js
function parseBirthDateShorthand(raw) {
  const digits = raw.replace(/\D/g, '');
  if (digits.length !== 6) return null;

  const yy = parseInt(digits.slice(0, 2), 10);
  const month = parseInt(digits.slice(2, 4), 10);
  const day = parseInt(digits.slice(4, 6), 10);
  if (month < 1 || month > 12 || day < 1 || day > 31) return null;

  const year = (yy >= 50 ? 1900 : 2000) + yy;
  return `${year}-${String(month).padStart(2, '0')}-${String(day).padStart(2, '0')}`;
}
```

말씀하신 규칙(YY가 50 이상이면 1900년대, 미만이면 2000년대 — 주민등록번호 앞자리와 같은 관례) 그대로 구현했습니다. `880324` → `1988-03-24`, `130101` → `2013-01-01`로 정확히 변환되는 것을 확인했습니다. 형식이 안 맞으면(6자리가 아니거나 월/일이 범위를 벗어나면) 등록 자체를 막고 안내 메시지를 보여줍니다.

입력 필드는 `<input type="date">`에서 `<input type="text" inputmode="numeric">`로 바꿔서, 모바일에서는 숫자 키패드가 뜨면서도 자유롭게 6자리 숫자를 타이핑할 수 있게 했습니다.

### 2. 운세 내용이 다 비슷해 보이는 문제

스크린샷을 보니 실제로 심각했습니다 — 4명 중 3명이 **"오늘은 새로운 기회가 찾아오는 날입니다. 긍정적인 마음으로 도전하면 좋은 결과를 얻을 수 있습니다."** 를 토씨만 다르게 그대로 받았더군요. 원인과 해결 과정을 기록합니다.

#### 원인: Claude에게 "차별화할 재료"가 없었다

기존 프롬프트는 `이름 + 생년월일`만 던져주고 "운세를 봐줘"라고 했는데, 이 정도 정보로는 Claude 입장에서 "이 사람만의 특징"을 잡을 실마리가 부족해서, 무난하고 안전한 일반적인 문구로 수렴하는 경향이 있었습니다. 게다가 API 호출은 매번 완전히 독립적(서로 다른 대화)이라, "방금 다른 사람에게 이미 비슷한 말을 했으니 이번엔 다르게 써야지" 같은 판단 자체를 할 수가 없는 구조입니다.

#### 해결 1: 사람마다 다른 "재료"를 직접 계산해서 프롬프트에 넣기

생년월일로부터 서버(Java)에서 미리 계산할 수 있는 정보를 뽑아서 프롬프트에 함께 넣었습니다.

- **띠**: `(년도 % 12)`로 12간지 계산
- **태어난 계절**: 월(月)로 봄/여름/가을/겨울 판단
- **오늘/생일의 요일**: `LocalDate.getDayOfWeek().getDisplayName(TextStyle.FULL, Locale.KOREAN)` — 자바 표준 라이브러리가 한국어 요일명을 바로 줘서 직접 매핑 코드를 짤 필요가 없었습니다.
- **생년월일 숫자의 합**(예: 1997-07-15 → 1+9+9+7+0+7+1+5 = 39): 사람마다 기계적으로 다른 값이 나오는 "계산 재료"를 명시적으로 던져주고, "이 숫자를 바탕으로 점수를 계산하듯 정해달라"고 요청했습니다.

그리고 스키마 설명(`@JsonPropertyDescription`)과 프롬프트 양쪽에 "뻔한 문구 금지, 띠/계절/요일을 활용해서 그 사람만을 위한 것처럼 구체적으로" 라는 지시를 명시했습니다.

#### 결과: 메시지는 확실히 좋아졌고, 점수는 여전히 한계가 있음

같은 날 5명을 연달아 조회해서 실제로 비교한 결과입니다.

| 이름 | 생년월일 | 점수 | 행운숫자 | 메시지(요약) |
|---|---|---|---|---|
| 박서준 | 1993-05-11 | 73 | 56 | 닭띠·봄·화요일 언급, 새 아이디어 |
| 최유리 | 1985-12-29 | 62 | 73 | 소띠·겨울 언급, 새 인연 |
| 정민재 | 2005-07-02 | 72 | 61 | 닭띠·여름 언급, 소통에서 좋은 결과 |
| 강나영 | 1978-04-16 | 74 | 72 | 말띠·봄 언급, 도전 기질 |
| 오태양 | 2010-09-08 | 73 | 47 | 호랑이 기백, 가을 언급 |

- **메시지**: 개선 전엔 거의 동일했던 문장이, 이제는 사람마다 확실히 다른 내용(띠/계절/요일이 자연스럽게 녹아든 문장)으로 나옵니다 — 원래 요청하신 부분은 확실히 해결됐습니다.
- **행운의 숫자**: 개선 전엔 4명 전원이 `47`로 완전히 동일했는데, 개선 후엔 56/73/61/72/47로 다양해졌습니다.
- **점수**: 62~74점 사이로 여전히 좁게 몰려있습니다. "0~100 전 구간을 활용해달라", "생년월일 숫자 합을 계산 재료로 써달라"고 명시적으로 요청했는데도, Haiku 4.5가 "무난하게 긍정적인 점수"로 수렴하는 경향 자체는 완전히 없애지 못했습니다 — **프롬프트만으로 개선할 수 있는 한계**에 도달한 것으로 보입니다.

#### 참고: 점수까지 더 다양하게 만들고 싶다면

프롬프트 개선만으로는 한계가 있으니, 다음 단계로는 서버에서 계산한 "생년월일 숫자 합" 같은 값을 점수 계산에 일부 직접 반영하는 방식(AI 점수와 결정론적 계산값을 섞는 하이브리드)을 고려할 수 있습니다. 다만 이건 "점수가 AI의 순수 판단"이라는 지금 컨셉을 살짝 바꾸는 설계 결정이라, 필요하시면 별도로 논의해서 진행하는 게 좋을 것 같습니다 — 이번에는 사용자가 지적하신 "메시지 내용의 다양성" 문제 해결에 집중했습니다.

## [구 26] 버프를 절대점수 대신 참가자 간 상대평가로

### 1. 문제 — AI 점수가 좁게 몰려서 선형 공식도 무의미해짐

devhelp/02(구 24)에서 `BuffCalculator`를 20점 단위 계단식에서 선형(`startY=(100-score)*2`)으로 바꿨지만, 새로 만든 "AI TEST" 버튼(devhelp/02(구 25).5)으로 4명을 한꺼번에 등록해서 실제로 테스트해보니 Claude가 매긴 점수가 72/76/74/74점처럼 4점 범위 안에 몰렸다. devhelp/03(구 14)에서 이미 예견됐던 "점수가 60~70점대로 쏠리는 경향"이 실제로 재현된 것 — 공식 자체는 선형이라도, 입력값(AI 점수)의 실제 분포가 좁으면 결과(시작 높이 차이)도 8px 정도로 사실상 안 보이는 수준이 된다.

### 2. 해법 — 절대 0~100점이 아니라 "이번 판 참가자 중 최고점자 대비 상대 순위"

사용자 제안: 점수를 절대값으로 안 쓰고, 같이 등록된 사람들끼리 비교해서 `최고점자 - 내 점수`만큼 공 개수 단위로 뒤에서 출발시킨다. 상대 차이가 너무 크게 벌어지는 걸 막기 위해 10점(=공 10개)에서 잘라낸다.

- `BuffCalculator.relativeStartY(myScore, maxScoreInGame)`: `gap = min(10, max(0, maxScore - myScore))`, `startY = gap * 26`(공 지름 px). 기존 `fromScore()`(절대점수→tier)는 카드 배지 색상용으로 그대로 남겨뒀다 — 이번 변경은 `startY`에만 적용된다.
- 계산 위치는 `GameService.createGame()` — 개별 조회 엔드포인트(`POST /api/fortune`)는 참가자 한 명씩 독립 호출이라 "이번 판에 누가 같이 뛰는지"를 모른다. `createGame()`은 이미 `playerIds` 전체를 한 번에 받아서 각자의 원점수를 조회하므로, 여기서 최고점을 구해 그룹 전체의 `startY`를 다시 계산해 끼워 넣는 두 번째 패스(`applyRelativeStartY`)를 추가했다.
- 생년월일 미입력(NONE, 점수 자체가 없음) 참가자는 비교 대상에서 빠지고 기존 `Buff(0,0)` 그대로 — 애초에 운세를 안 받았으니 상대 비교 자체가 성립하지 않는다.
- "빠른 추가" 참가자는 원래 서버에 점수를 안 보내는 구조(devhelp/02(구 25))라 이 로직과 완전히 무관 — 프론트(`GamePage.handleStartGame`)가 게임 생성 응답을 받은 뒤 이미 자체 숨김 점수로 `buff.startY`를 덮어쓰고 있고, 이번 변경 후에도 그 덮어쓰기가 마지막에 적용되므로 서로 간섭하지 않는다.

### 3. 안전 마진 재조정 — devhelp/02(구 25) 재발 방지

상대평가의 최대 시작 높이가 200(구 절대값 최대)에서 **260**(10×26)으로 커지면서, `spawnY = 20 + startY`의 최댓값도 220→**280**이 됐다. 그런데 `pegField.startY`(첫 못 행 y좌표)가 정확히 280이라 여유가 0이 되어 devhelp/02(구 25)에서 어렵게 고친 "공이 못 행과 겹쳐서 끼는" 문제가 재발할 뻔했다 — `pegField.startY`를 **340**으로 올려 60px 여유를 되찾았다(`zoomStartY` 리터럴도 같이 `340+5*50=590`으로 조정). `frontend-react/src/game/engine.ts`와 레거시 `frontend/js/game.js` 양쪽 다 반영 — 둘 다 같은 백엔드 응답을 그대로 쓰기 때문에 하나만 고치면 나머지가 다시 끼임 위험에 노출된다.

### 4. 2번 섹션(오늘의 운세) 미리보기도 같은 값을 보여줘야 함

`POST /api/fortune`은 참가자 한 명씩 독립 호출이라 상대평가를 모른 채 예전 절대값 `buff.startY`를 그대로 반환한다. 그대로 두면 2번 섹션 카드가 보여주는 숫자와 실제 게임에서 벌어지는 높이 차이가 서로 다른 값이 되어버린다(사용자에게 확인해서 "게임과 동일한 값을 미리 보여준다"로 확정) — 그래서 프론트에서 배치로 받은 점수들 중 최댓값을 구해 **같은 공식을 다시 계산**해서 화면에 보여준다.

- `frontend-react/src/utils/relativeBuff.ts`(신규) — `RELATIVE_GAP_CAP=10`, `BALL_DIAMETER_PX=26` 상수와 `computeRelativeStartY()`를 백엔드 `BuffCalculator`와 동일하게 복제(주석으로 동기화 필요성 명시 — `quickAddBuff.ts`가 이미 같은 패턴으로 다른 상수를 복제해둔 선례가 있음).
- `FortuneSection.tsx`(React), `main.js`의 `renderFortuneGrid()`(레거시) 둘 다 이 계산을 반영 — 두 프론트가 같은 백엔드 응답 포맷을 공유하므로 하나만 고치면 나머지 화면이 여전히 무의미한 절대값을 보여주게 된다.

### 5. 검증

AI TEST 버튼으로 4명 등록 → 실제 Claude 점수 62/76/72/68 → 2번 섹션 카드에 표시된 시작 높이가 **+260/+0/+104/+208**로, 계산식(`(76-내점수, 캡10)×26`)과 정확히 일치하는 것 확인. 게임 시작 후 실제 공 스폰 순서(개발자도구로 각 공의 `top` 값 측정)도 이 순서와 정확히 일치했다.

devhelp/02(구 25) 방식(nudge 발동 횟수 계측)으로 재발 여부도 확인 — AI TEST 4명 + 빠른 추가 4명을 섞은 8명 풀 게임에서 **nudge 0회, 11초 만에 정상 완주**. 안전 마진 조정이 제대로 됐고, 혼합 게임(실제 AI 점수 참가자 + 숨김 랜덤 점수 참가자)도 서로 간섭 없이 정상 동작함을 확인했다.

## [구 27] DB TEST 버튼(2회차 캐시 시연) + 관리자 "AI 호출" 컬럼 수정

### 1. 관리자 "AI 호출" 컬럼이 전부 N으로 나온 버그

컬럼이 "가장 마지막 조회의 출처"만 봤는데, 운세 확인 때 AI를 호출해도 게임 시작 시 `GameService`가 운세를 다시 조회하면서(`FortuneQueryService.getTodayFortune`) 항상 `CACHE` 행이 뒤에 붙는다. 그래서 게임을 한 번이라도 돌리면 마지막 행은 늘 CACHE → 전부 N. "이력 중 AI 호출이 한 번이라도 있으면 Y, 캐시만 있으면 N, 이력 없으면 -"로 고쳤고 필드명도 `lastFortuneSource` → `fortuneSource`로 바꿨다.

### 2. AI TEST만으로는 "2회차(DB 재사용)"를 시연할 수 없음

AI TEST는 매번 새 임의 신원을 만들기 때문에 항상 첫 방문(AI 호출)만 재현된다. 캐시 키는 playerId가 아니라 **이름+생년월일**이라, 이미 운세 결과가 DB에 있는 신원을 새 참가자 행(새 playerId)으로 다시 등록하면 그대로 캐시가 적중한다 — 실제로 "지난번 사람이 같은 정보를 다시 입력"하는 상황과 같다.

**"DB TEST" 버튼**(`RegistrationForm.tsx`, 백엔드 변경 없음): 기존 `GET /api/admin/players`로 참가자를 불러와 `birthDate`와 `fortuneSource`가 있는 신원만 후보로 삼고, 이름+생년월일 중복과 현재 판에 이미 있는 이름을 제외한 뒤, 선택 인원수만큼 무작위로 재등록한다. 후보가 없으면 "먼저 AI TEST로 등록하고 운세 확인을 해주세요" 안내, 후보가 부족하면 가능한 만큼만 등록한다. 기존 행을 재사용하지 않고 새 행으로 등록하는 이유는, 관리자 화면에 `AI 호출 = N`인 행이 뚜렷하게 남아 시연이 눈에 보이기 때문이다.

### 3. 검증

AI TEST 후 DB TEST 2명 → 운세 확인 카드가 둘 다 "이전 기록 재사용"이고 점수가 원래 신원과 동일(76점/74점), 관리자 화면에 재등록된 행(613, 614)은 `N · 기존 데이터`, 원래 행들은 `Y · AI 호출`.

시연 순서: AI TEST → 운세 확인(AI) → DB TEST → 운세 확인(재사용) → 관리자 화면. Render 무료 티어는 슬립 시 DB가 초기화되므로 이 순서를 끊지 않고 이어서 해야 한다.

# 09. 헤드리스 물리 테스트로 실제 버그를 발견한 과정

"작성했다"와 "동작한다"는 다르다는 원칙(`07_빌드와_테스트_검증.md`에서도 강조한 원칙)을 프론트엔드에도 그대로 적용했습니다. 다만 이번엔 문제가 하나 있었습니다 — **이 환경에는 Playwright 같은 브라우저 자동화 도구가 없어서, 실제 브라우저를 띄워 클릭해보며 확인할 수 없었습니다.** 이 문서는 그 상황에서 어떻게 검증했는지, 그리고 그 검증이 실제로 무엇을 찾아냈는지 기록합니다.

## 1. "브라우저 없이 Matter.js를 검증할 수 있을까?"

Matter.js는 물리 계산 자체는 순수 자바스크립트 로직이고, 화면에 그리는 부분만 DOM(`document.createElement` 등)에 의존합니다. 그렇다면:

- **jsdom**으로 브라우저의 DOM API를 흉내 낸 가짜 `document`/`window`를 Node.js 위에 만들고,
- 실제 npm 패키지인 **matter-js**를 그대로 불러와서,
- `frontend/js/game.js` 파일을 (수정하지 않고 그대로) 읽어와 실행하면

**진짜 프론트엔드 코드를, 진짜 물리 엔진으로, 브라우저 없이** 돌려볼 수 있겠다고 판단했습니다. 이건 실제 서비스 코드베이스에서도 종종 쓰는 기법입니다(UI 자동화 없이 로직만 빠르게 검증).

이 테스트는 프로젝트 폴더가 아니라 **스크래치패드(임시 작업 공간)**에 별도의 Node 프로젝트로 만들었습니다 — `frontend/`는 "빌드 도구 없는 순수 정적 파일"이라는 원칙을 지켜야 해서, 테스트용 `node_modules`를 그 안에 두고 싶지 않았기 때문입니다.

## 2. 테스트 시나리오

```js
runPinballGame({
  boardEl, rankListEl,
  participants: [ /* 버프 티어 0~4를 하나씩 포함한 5명 */ ],
  onComplete: (finishOrder) => {
    // finishOrder에 모든 참가자가 정확히 한 번씩 들어있는지,
    // 게임이 시작된 뒤 실제로 얼마 만에 끝났는지 확인
  },
});
```

`onComplete`이 호출되지 않으면 30초 뒤 강제로 실패 처리하도록 타임아웃을 걸어뒀습니다 — "게임이 언젠가는 반드시 끝나야 한다"는 것 자체가 검증 대상이었기 때문입니다.

## 3. 첫 실행 결과: 실패 (여기서부터가 진짜 검증입니다)

처음 돌려보니 **30초가 지나도 게임이 끝나지 않았습니다.** 로그를 추가해서 각 공의 위치를 계속 찍어보니:

```
tick 180 NoBuff@373, Tier1@625, Tier2@627, Tier3@627, Tier4@627
tick 210 NoBuff@373, Tier1@627, Tier2@627, Tier3@627, Tier4@627
... (이후 계속 같은 자리)
```

4개의 공은 바닥(y≈627)에 잘 도착했는데, **"NoBuff" 공 하나가 y=373 지점(못 배열 중간쯤)에서 완전히 멈춰버린 것**을 확인했습니다. 원인은 갈때기 모양으로 좁아지는 벽과 못 사이의 좁은 틈에 공이 기하학적으로 "끼어버리는" 현상 — Plinko/갈톤보드류 물리 시뮬레이션에서 실제로 흔히 발생하는 문제입니다. 반발계수와 마찰력만으로는, 공이 정확히 두 힘이 상쇄되는 위치에 놓이면 이론상 영원히 멈춰있을 수 있습니다.

## 4. 원인 진단 과정

1. 먼저 "Matter.js 자체가 이 Node/jsdom 환경에서 제대로 동작하는가"부터 의심하고, `game.js`와 무관한 최소 예제(공 하나 + 바닥 하나)로 따로 테스트 — **정상 동작 확인** (이 환경 자체의 문제는 아니라는 걸 먼저 배제).
2. `game.js`에 임시로 디버그 로그를 넣어 각 공의 위치를 프레임마다 출력 — 정확히 어떤 공이, 어디서, 언제부터 멈추는지 특정.
3. 멈춘 위치(y=373)가 못 배열 구간이고, 하필 가장 바깥쪽(왼쪽)에서 출발한 공이라는 점에서 "좁아지는 벽 + 못" 조합이 원인이라고 결론.

이 과정은 실제 버그 리포트를 받았을 때의 디버깅 순서와 같습니다 — **의심되는 범위를 좁혀가며(엔진 자체? 내 코드? 특정 조건?) 하나씩 배제**하는 방식입니다.

## 5. 해결 — "완벽한 기하학"보다 "안전장치"

이런 종류의 끼임 문제는 못 간격이나 벽 각도를 아무리 정교하게 계산해도 특정 랜덤 시드에서는 여전히 발생할 수 있습니다 (물리 시뮬레이션은 부동소수점 계산이라 완벽한 대칭이 오히려 불안정한 경우도 있습니다). 그래서 두 가지를 함께 적용했습니다.

1. **완화**: 못을 벽에서 조금 더 떨어뜨려 배치(여백 30px → 38px)해서 애초에 끼임이 발생할 여지를 줄임.
2. **안전장치(핵심 수정)**: 공의 속도(`body.speed`)가 일정 시간(약 0.75초, 45틱) 이상 거의 0에 가까우면, 완주하지 못한 공에 무작위 방향의 작은 충격을 줘서 강제로 다시 움직이게 만드는 로직을 추가했습니다 (`game.js`의 `adapter.nudge()` 참고).

```js
if (adapter.getSpeed(state.body) < 0.05) {
  state.stallTicks++;
  if (state.stallTicks > 45) {
    adapter.nudge(state.body);
    state.stallTicks = 0;
  }
}
```

이건 "버그를 원천 차단"하는 게 아니라 "버그가 나더라도 게임이 절대 멈추지 않도록 보장"하는 접근입니다. 물리 시뮬레이션처럼 모든 경우의 수를 수학적으로 증명하기 어려운 영역에서는, 실제 프로덕션 Plinko/갈톤보드 구현체들도 이런 식의 "정체 감지 후 흔들기" 안전장치를 흔히 사용합니다.

## 6. 수정 후 재검증

같은 헤드리스 테스트를 5명 기준 5회, 8명(최대 인원) 기준 여러 회 반복 실행:

| 참가자 수 | 실행 횟수 | 완료까지 걸린 시간 |
|---|---|---|
| 5명 | 5회 | 4.3초 ~ 11.3초 |
| 8명(최대) | 5회 | 8.8초 ~ 27.2초 |

전부 `plan/04_pinball-map-design.md`가 목표로 했던 "1분 내 종료"를 여유 있게 만족했고, 매 실행마다 참가자 전원이 정확히 한 번씩 완주 순서에 포함되는 것도 확인했습니다. 이 표는 실제 실행 결과이지, 추정치가 아닙니다.

## 7. 이 검증 방식의 한계 (정직하게 밝혀둠)

- **실제 브라우저에서의 시각적 확인(레이아웃, 색상, 애니메이션 부드러움, 반응형 등)은 하지 못했습니다.** 헤드리스 테스트는 "물리 로직이 올바르게 끝나는가"만 검증하며, 화면이 실제로 보기 좋은지는 사용자가 브라우저에서 직접 열어봐야 합니다.
- CORS/네트워크 관련 문제(브라우저의 실제 CORS 정책 적용)는 curl로 프리플라이트(OPTIONS) 요청을 흉내 내서 응답 헤더까지 확인했지만, 진짜 브라우저의 `fetch()` 동작과 100% 동일하다는 보장은 아닙니다.
- 이 저장소에는 자동화된 테스트로 남겨두지 않았습니다 (스크래치패드의 임시 스크립트였음) — 필요하면 `frontend`와는 별도로 `backend`처럼 자체 `package.json`을 가진 테스트 전용 폴더를 나중에 추가할 수 있습니다.

**결론적으로 사용자가 직접 브라우저(`http://localhost:5501`)에서 한 번 실행해보고, 레이아웃/애니메이션이 의도대로 보이는지 확인하는 과정은 여전히 필요합니다.**

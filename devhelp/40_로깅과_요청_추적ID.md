# 40. 로깅과 요청 추적 ID (로드맵 Phase 2)

"에러가 났다"는 말을 들었을 때 원인을 찾을 수 없는 상태였다. 코드에 로그가 한 줄도 없었고(Logger 호출 0건), 예상 못 한 예외는 `handleUnexpected`가 메시지만 메모리 목록에 넣고 스택트레이스는 버렸다. README에는 "운영 로그를 본다"고 적어놨는데 코드가 그걸 못 받쳐주던 부분이다. 이번에 **요청마다 추적 ID를 붙여서, 사용자가 화면의 "오류 ID"를 알려주면 서버 로그에서 그 요청의 흐름을 바로 찾을 수 있게** 만들었다.

## 1. 구조

```
요청 → TraceIdFilter(ID 생성 → MDC, X-Trace-Id 응답 헤더)
     → 로그 줄마다 [ID] 자동 출력 (logging.pattern.level)
     → 에러 응답 {"error": ..., "traceId": ...}, 관리자 오류 로그에도 traceId 저장
     → 프론트: 5xx 메시지에 "(오류 ID: ...)", 관리자 로그 화면에 #ID 배지
```

- **필터 순서**: `@Order(HIGHEST_PRECEDENCE)`로 가장 먼저 돌린다. `RateLimitFilter`(429)와 `AdminAuthFilter`(401)는 컨트롤러까지 가지 않고 필터에서 직접 응답을 쓰는데(devhelp/34), 이 응답과 로그에도 같은 ID가 찍혀야 해서다. 이 직접 쓰는 응답은 Spring의 JSON 변환기를 못 쓰므로 `ErrorBodies.json()`으로 같은 모양(`error`, `traceId`)을 직접 만든다.
- **ID는 서버가 항상 새로 만든다**(8자리 16진수). 클라이언트가 `X-Trace-Id`를 보내도 받지 않는다 — 외부 입력이 줄바꿈 등으로 가짜 로그 줄을 만드는 걸 막으려는 것이고, 테스트(`ignoresAnIdSentByTheClient`)로 고정했다. 8자리는 소리 내어 읽어줄 수 있을 만큼 짧고 이 규모에서는 겹칠 일이 거의 없다.
- **MDC는 반드시 비운다**: 톰캣 스레드는 재사용되므로 `finally`에서 지우지 않으면 다음 요청에 이전 ID가 새어 나간다(예외가 나도 지워지는지 테스트).
- 로그 패턴: `logging.pattern.level: "%5p [%X{traceId:--------}]"`. 요청 밖(서버 시작 등)은 `[-------]`로 찍힌다.

## 2. 무엇을 로그로 남기는가

| 위치 | 레벨 | 내용 |
|---|---|---|
| `TraceIdFilter` | INFO | 요청 한 줄 요약 `POST /api/fortune -> 200 (3759ms)` (OPTIONS 제외, 쿼리스트링 제외) |
| `ClaudeFortuneGenerator` | INFO | AI 호출 완료와 걸린 시간 / 클라이언트 준비, 키 미설정 시 WARN |
| `FortuneQueryService` | INFO | 캐시 적중(AI 생략) / 캐시 미스(AI 호출) |
| `GameService` | INFO | 게임 생성·시작·결과 확정(gameId, 인원, 당첨 playerId) |
| `PlayerService` | INFO | 참가자 등록(playerId, 생년월일 입력 여부) |
| `GlobalExceptionHandler` | 4xx WARN(스택 없음) / **5xx ERROR(스택 포함)** | 예상 못 한 예외는 `처리되지 않은 예외`로 스택트레이스까지 |
| `RateLimitFilter`, `AdminAuthFilter`, 관리자 로그인 | WARN | 요청 제한 초과, 관리자 API 인증 실패, 로그인 성공(INFO)/실패(WARN) |

**일부러 남기지 않는 것**: 이름·생년월일(개인정보 — 대신 `playerId`), 관리자 아이디·비밀번호·토큰, 쿼리스트링, Claude 프롬프트와 응답 본문. 당첨자도 이름 대신 `playerId`로 남긴다.

## 3. 에러 응답 규칙과 그 과정에서 고친 것

규칙: 응답은 `{"error": 일반 메시지, "traceId": ...}`이고, 서버 내부 사정(예외 메시지, 스택트레이스)은 응답에 싣지 않고 로그에만 남긴다.

테스트하다 이 규칙에 어긋나는 것 두 가지가 드러났다.

1. **깨진 JSON이 500으로 응답되고 있었다**(`HttpMessageNotReadableException`이 `Exception.class` 핸들러로 떨어짐). 405(잘못된 메서드), 415(`text/plain` 등)도 마찬가지. 이제 400/405/415로 돌려준다. 로그를 ERROR+스택으로 남기기 시작하면 클라이언트 실수나 봇의 탐색 요청이 전부 ERROR로 쌓이기 때문에 같이 고쳤다(devhelp/29에서 `NoResourceFoundException`을 따로 처리한 것과 같은 종류의 문제). 405/415는 봇이 찔러본 경우가 대부분이라 관리자 오류 로그(`ErrorLogStore`)에는 넣지 않는다.
2. **Claude의 원문 오류가 사용자 응답에 그대로 실렸다.** 잘못된 API 키로 호출해보니 `Claude API 호출에 실패했습니다: 401: {... "API key is invalid." ...}`가 응답 본문에 있었다. 응답은 "AI 운세 서비스에 일시적인 문제가 있습니다. 잠시 후 다시 시도해주세요."로 바꾸고, 원문은 `ApiException`의 cause로 넘겨서 ERROR 로그의 `Caused by`에만 남긴다. API 키 미설정 안내(환경변수 이름 포함)도 같은 방식으로 정리했다.

## 4. 프론트

- `ApiError`에 `traceId`를 담고, **5xx일 때만** 메시지 끝에 `(오류 ID: c1a8412e)`를 붙인다. 4xx(입력 실수 등)에는 ID가 잡음이라 안 붙인다.
- 관리자 오류 로그 화면에 `#c1a8412e` 배지(고정폭, 클릭 한 번에 전체 선택). 화면의 오류 ID와 이 배지, 서버 로그의 `[c1a8412e]`가 같은 값이다.

## 5. 인코딩: 한글 로그가 깨져 보였다

로그 메시지를 한글로 쓰니 로컬에서 파일로 리다이렉트한 로그가 깨져 보였다. 같은 줄을 CP949로 디코딩하면 정상이었다 — Windows에서 `java -jar`는 기본 인코딩이 cp949라 콘솔 인코딩을 따라가고, 그래서 로컬 콘솔에서는 정상으로 보인다. 운영은 Linux 컨테이너라 기본이 UTF-8이지만 로케일에 기대지 않도록 `Dockerfile`의 ENTRYPOINT에 `-Dfile.encoding=UTF-8`을 명시했다. 같은 옵션으로 `java -jar`를 띄우면 한글 로그가 UTF-8로 정상 기록되는 것까지 확인했다(컨테이너 안에서의 확인은 아니다).

## 6. 검증

- **단위 테스트**: 신규 16개(`TraceIdFilterTest` 6, `GlobalExceptionHandlerTest` 8, 필터 401/429 본문 각 1), 전체 41개 통과. 로그 검증은 Logback `ListAppender`로 ERROR 레벨, 스택트레이스, MDC의 traceId, 원인 예외 체인(`Caused by`)을 직접 확인한다.
- **실서버**(운영과 같은 `java -jar`, 별도 포트·메모리 DB로 격리해서):

| 시나리오 | 결과 |
|---|---|
| 참가자 등록·운세 1회차(AI 호출)·2회차(캐시)·게임 생성 | 200/201, 요청마다 `X-Trace-Id`, 로그에 `캐시 미스 → Claude 호출 완료 3649ms`, `캐시 적중 — AI 호출 생략` |
| 깨진 JSON / 잘못된 메서드 / `text/plain` | 400 / 405 / 415 (이전엔 모두 500) |
| 없는 참가자, 이름 공백, 관리자 토큰 없음, 로그인 실패 | 404, 400, 401, 401 — 모두 본문 `traceId` = 응답 헤더 값 |
| `/api/fortune` 21번 연속 | 21번째 429, 본문에 `traceId`, WARN 로그 |
| 잘못된 Claude API 키 | 502, 응답은 일반 문구 + `traceId`, 서버 로그는 `캐시 미스 → ERROR → 502` 3줄과 `Caused by: UnauthorizedException: 401 ... API key is invalid` |
| 화면(Playwright) | 운세 화면에 `(오류 ID: c1a8412e)`, 관리자 로그에 같은 `#c1a8412e` 배지 |

이 ID로 `grep "\[c1a8412e\]"` 하면 그 요청의 로그가 전부 나온다.

## 7. 한계와 다음 단계

- `ErrorLogStore`(관리자 오류 로그)는 아직 인메모리다. 서버를 재시작하면 목록이 비는데, 서버 로그 쪽에는 남아 있다. DB 영속화는 다음 단계(로드맵의 별도 항목).
- Claude 호출 중 네트워크 오류·타임아웃(`AnthropicIoException` 등)은 아직 따로 안 잡아서 `처리되지 않은 예외`(500)로 떨어진다. 타임아웃·재시도 설정과 함께 Phase 3에서 다룬다.
- 요청 한 줄 요약은 모든 요청을 INFO로 남기므로 Render의 슬립 방지 핑(10분마다 `GET /api/players/reusable`)도 로그에 찍힌다. 거슬리면 해당 경로만 DEBUG로 낮추면 된다.
- Render 무료 티어의 로그 보관 기간 안에서만 ID로 검색할 수 있다.

## [구 28] 배포 검증과 두 버그 (Vercel SPA 404, 모바일 클리핑)

면접 전 "Phase 0" 체크리스트로 실제 배포(Render 백엔드 + Vercel 프론트)가 제대로 동작하는지 끝까지 훑었다. 코드만 보고 넘어갔으면 몰랐을, **실제 배포 환경에서만 재현되는 버그 두 개**를 이 과정에서 찾았다.

### Phase 0 체크리스트

1. 최신 커밋이 Render/Vercel에 실제로 반영됐는지 확인
2. 전체 데모 흐름(등록 → AI 운세 → 게임 → 결과 → 관리자)을 라이브 URL에서 직접 확인
3. 모바일 화면 대응 확인
4. GitHub 저장소를 public으로 전환 (커밋 이력에 시크릿이 없는지 먼저 스캔)

### 버그 1: Vercel에서 `/admin` 새로고침하면 404

#### 증상
- 앱 안에서 `<Link>`로 `/admin`으로 이동하면 정상.
- 근데 `/admin`을 브라우저 주소창에 직접 치거나, `/admin` 페이지에서 새로고침(F5)하면 Vercel의 `NOT_FOUND` 페이지가 뜬다.

#### 원인
React Router는 클라이언트 사이드 라우팅이라, 앱이 이미 로드된 상태에서 `<Link>` 클릭으로 이동하는 건 브라우저가 서버에 새 요청을 안 보낸다(JS가 알아서 화면만 바꿔치기). 근데 주소창 직접 입력이나 새로고침은 **브라우저가 그 경로로 진짜 HTTP 요청을 보낸다**. Vercel은 정적 파일 서버라 `/admin`이라는 실제 파일/폴더가 없으니 그대로 404.

#### 해결
`frontend-react/vercel.json` 추가:

```json
{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
```

모든 경로 요청을 `index.html`로 돌려보내면, React Router가 그 안에서 다시 클라이언트 사이드로 라우팅을 처리한다. SPA를 정적 호스팅에 올릴 때 거의 항상 필요한 설정인데, 로컬 개발 서버(Vite dev server)는 이런 rewrite를 이미 알아서 해주기 때문에 로컬 테스트만으로는 절대 안 걸린다 — 실제 배포 환경에서만 드러나는 전형적인 케이스.

커밋: `22bcf7f`

#### 검증
`/admin`에 직접 접속·새로고침을 반복해서 HTTP 200과 정상 화면이 뜨는지 확인 (로컬 재현이 안 되므로 라이브 URL로 직접 확인).

### 버그 2: 모바일에서 핀볼 보드가 약 39% 잘림

#### 증상
모바일 화면(좁은 뷰포트)에서 핀볼 게임을 열면, 보드 오른쪽/아래쪽이 스크롤도 없이 그냥 잘려서 안 보인다.

#### 원인
`.pinball-board`에 걸린 CSS `max-width: 100%`가 좁은 화면에서 컨테이너 폭을 물리 엔진의 원래 설계 폭(`cfg.boardWidth`, 560px)보다 작게 줄여버린다. 문제는 그 안의 `.pinball-scene`(실제 캔버스/DOM 요소들이 그려지는 곳)은 `position: absolute`로 배치돼 있어서 **부모가 줄어들어도 자기 크기(560px)는 그대로 유지**한다는 점이다. 결과적으로 `overflow: hidden`이 삐져나온 부분을 스크롤바도 없이 조용히 잘라버린다.

실제 측정: 보드 컨테이너 실제 폭 300px, 씬은 x=[47, 607] 즉 560px 폭 그대로 → 약 39%가 화면 밖으로 잘려나감.

#### 해결
게임 시작 시점에 한 번, `boardEl.getBoundingClientRect().width`로 **CSS가 실제로 줄여놓은 진짜 렌더링 폭**을 측정해서 `fitScale = min(1, 렌더링폭 / cfg.boardWidth)`를 계산한다. 이걸 기존에 있던 카메라 확대/축소(`cameraScale`) 로직에 곱으로 얹었다 (`totalScale = fitScale * cameraScale`).

```ts
// engine.ts, applyCamera()
const totalScale = fitScale * cameraScale;
// 뷰포트 중앙 정렬 계산도 fitScale이 적용된 크기 기준으로
```

`frontend-react/engine.ts`에만 적용했고, 레거시 `frontend/js/game.js`는 이번 배포·데모 대상이 아니라서 건드리지 않았다 (물리 로직 변경이 아니라 순수 화면 맞춤 문제라, "물리 변경은 항상 양쪽에 반영" 원칙의 예외로 판단).

커밋: `f0cf60f`

#### 검증
Playwright로 모바일 기기 에뮬레이션(로컬 + 실제 라이브 URL)해서, 최종 계산된 transform이 `matrix(0.535714, 0, 0, 0.535714, 0, 0)` — 정확히 `300/560`과 일치하는지 확인.

### 남은 것

모바일에서 운세 결과 카드 텍스트가 길면 잘리는 문제를 발견했으나 이번엔 수정하지 않고 다음으로 미뤘다 (`devhelp/00_개선로드맵.md`의 "다음에 고칠 것" 참고).

### 배운 점

두 버그 모두 **로컬 개발 서버에서는 재현되지 않고, 실제 배포 환경(정적 호스팅의 라우팅 방식, 실제 모바일 뷰포트 크기)에서만 드러났다.** "로컬에서 됐으니 끝"이 아니라, 배포 후 실제 URL로 직접 확인하는 단계가 왜 필요한지 보여주는 사례.

## [구 30] GitHub Actions CI 추가

Phase 5의 첫 항목. `git push`할 때마다 백엔드 테스트와 프론트엔드 빌드가 자동으로 돌아가도록 CI를 붙였다.

### 왜 필요한가

지금까지는 테스트를 항상 로컬에서 손으로 실행했다. 실수로 테스트가 깨지는 코드를 그대로 푸시해도, 누가 직접 `./gradlew test`를 돌려보기 전까지는 아무도 모른다. CI는 그 확인 과정을 자동화해서, 커밋마다 "빌드/테스트가 통과했는지"를 GitHub이 대신 보여주게 한다.

### 사전에 확인한 것

CI에 `ANTHROPIC_API_KEY` 같은 시크릿을 넣어야 하는지부터 확인했다. 기존 테스트(`RateLimitFilterTest`, `BuffCalculatorTest`, `MockFortuneGeneratorTest`, 컨텍스트 로딩 테스트) 중 실제 Claude API를 호출하는 건 없었다. `ClaudeFortuneGenerator`가 API 클라이언트를 최초 호출 시점에 지연 생성하도록 이미 만들어져 있어서, 키가 없어도 스프링 컨텍스트 자체는 정상적으로 뜬다. 그래서 **CI 저장소에 시크릿을 등록할 필요가 없었다.**

### 구성

`.github/workflows/ci.yml`에 두 잡을 병렬로 구성:

| 잡 | 내용 |
|---|---|
| `backend-test` | JDK 17(Temurin) 설치 → Gradle 캐시 복원 → `./gradlew test` |
| `frontend-build` | Node 20 설치 → `npm ci` → `npm run lint`(oxlint) → `npm run build`(`tsc -b && vite build`, 타입 에러도 여기서 잡힘) |

`master`로의 push와 `master` 대상 pull request에서 동작하도록 설정했다. 지금은 혼자 작업하는 저장소라 PR 트리거는 당장 쓰이지 않지만, 나중에 브랜치를 나눠 작업하게 되면 그대로 활용할 수 있다.

Gradle 캐시는 `~/.gradle/caches`, `~/.gradle/wrapper`를 `backend/**/*.gradle*`과 wrapper 설정 파일 해시로 키를 잡아서, 의존성이 안 바뀌면 다음 실행부터 빠르게 돈다.

### README 배지

```
[![CI](https://github.com/tmdgus0324/lucky-pinball-ai/actions/workflows/ci.yml/badge.svg)](...)
```
README 맨 위에 추가해서, 저장소를 열어보는 사람이 바로 "테스트가 자동으로 돌아가는 프로젝트"라는 걸 알 수 있게 했다.

### 검증

워크플로우를 추가하기 전에 로컬에서 세 가지를 먼저 확인했다 — `./gradlew test`, `npm run lint`, `npm run build` 모두 종료 코드 0으로 통과. 실제 GitHub Actions에서의 동작은 푸시 후 Actions 탭에서 최종 확인했다.

### 남은 것

관리자 화면 인증은 Phase 5의 나머지 항목으로 남겨뒀다(이번 작업 범위 밖).

## [구 33] 평일 낮 시간대 슬립 방지 (GitHub Actions → cron-job.org로 교체)

Render 무료 티어는 일정 시간 요청이 없으면 인스턴스가 완전히 슬립 상태가 되고, 깨어나는 데 30~60초가 걸린다. 면접·시연 시간대에 이 지연을 없애기 위해, **정해진 시간대에만** 주기적으로 서버를 깨워두는 워크플로우를 추가했다.

### 왜 24시간 내내 안 켜두는가

Render 무료 티어는 계정당 월 가동시간 한도가 있다(대략 750시간/월로 알려져 있음 — 정확한 최신 수치는 Render 대시보드에서 확인 필요). 24시간 내내 깨워두면 한 달 내내 켜진 것과 같아서 이 한도에 훨씬 빨리 가까워진다.

계산:
- 처음엔 10시~17시로 검토했다가, 이후 **9시 시작 + 주말 제외**로 조정했다.
- 평일 9시~17시(하루 9시간) × 약 22일(주말 제외) = **약 200시간/월** — 한도 대비 여유 있음
- 주말은 면접·시연이 있을 확률이 낮아서 아예 제외했다.
- 점심시간(11:30~13:00)을 빼고 더 쪼개는 것도 검토했지만, 아껴지는 시간에 비해 cron 규칙이 두 개로 늘어나는 복잡함이 더 커서 단순한 연속 구간으로 결정했다.

### 왜 UptimeRobot 같은 외부 서비스 대신 GitHub Actions인가

- **새 계정이 필요 없다** — 이미 CI에 쓰고 있는 GitHub Actions 그대로 재사용.
- **시간대 제한이 가능하다** — UptimeRobot 같은 업타임 모니터링 서비스의 무료 플랜은 보통 "항상 몇 분 간격으로" 방식이라 "낮 시간에만" 같은 스케줄 제한이 어렵다. GitHub Actions의 `schedule`(cron)은 시간대를 그대로 지정할 수 있다.
- **완전 무료** — public 저장소는 GitHub Actions 실행 시간이 무제한이라 별도 비용이 없다.

### 구성

```yaml
on:
  schedule:
    # 10분마다, UTC 00:00~08:59(한국시간 09:00~17:59) · 요일 1~5(월~금)
    - cron: '*/10 0-8 * * 1-5'
  workflow_dispatch:

jobs:
  ping:
    runs-on: ubuntu-latest
    steps:
      - name: Ping backend
        run: curl -sf --max-time 60 https://lucky-pinball-backend.onrender.com/api/players/reusable || true
```

- **cron은 UTC 기준**이라 한국시간(KST, UTC+9)으로 환산해서 넣어야 한다 — 9~17시(KST) = 00~08시(UTC).
- **요일도 UTC 기준**이지만, 이 핑 시간대(UTC 00:00~08:59)는 날짜가 안 바뀌는 구간이라 UTC 요일과 한국 요일이 동일하다 — 그래서 `1-5`(월~금)를 그대로 써도 된다. 만약 시간대가 자정을 걸쳐 있었다면 요일이 하루씩 밀리는 걸 감안해야 했을 것.
- 핑 대상은 `/api/players/reusable` — 로그인 없이 항상 200을 반환하는 공개 엔드포인트(DB TEST용으로 이미 만들어둔 것, devhelp/08(구 32))라 별도 인증 처리 없이 그냥 호출하면 된다.
- `workflow_dispatch`를 같이 넣어서, 스케줄과 무관하게 필요할 때 수동으로도 즉시 실행해볼 수 있게 했다.
- GitHub Actions의 스케줄 실행은 부하 상황에 따라 몇 분 정도 오차가 날 수 있다는 점은 감안해야 한다(공식 문서에 명시된 제약).

### 검증

`workflow_dispatch`로 수동 실행해서 실제로 백엔드에 핑이 가고 응답을 받는지 확인.

### 추가 (2026-09-30): 실측 결과 불안정 — cron-job.org로 교체

배포하고 하루 지켜본 결과, **`*/10` 간격으로 설정해도 실제로는 1~2시간에 한 번꼴로만 실행됐다.** 예를 들어 어느 날은 자정부터 오전 9시 넘어서까지 약 2시간 반 동안 자동 실행이 단 한 번도 없었다 — GitHub Actions 공식 문서의 "스케줄 이벤트는 부하가 크면 지연되거나 건너뛸 수 있다"는 경고가 실제로 심하게 나타난 사례다. 10분 간격처럼 촘촘한 스케줄은 GitHub 쪽에서 우선순위가 낮게 처리되는 것으로 보인다.

Render의 슬립 전환 시간(무활동 후 짧은 시간 내)보다 이 공백이 훨씬 길어서, 사실상 "낮 시간 내내 안 잠들게" 하려는 목적을 달성하지 못했다.

**대응**: **cron-job.org**(정시성이 훨씬 더 보장되는 전용 스케줄링 서비스, 무료)로 실제 핑 역할을 옮겼다. 설정은 cron-job.org 대시보드에서 직접 함(코드 아님) — 타임존을 `Asia/Seoul`로 맞추면 UTC 환산 없이 9~17시·월~금을 그대로 입력할 수 있어서 GitHub Actions의 cron 표현식보다 설정도 더 직관적이다.

GitHub Actions 워크플로우(`keep-alive.yml`)는 **자동 스케줄(`schedule`)은 제거하고 `workflow_dispatch`(수동 실행)만 남겨뒀다** — cron-job.org에 문제가 생겼을 때 비상용으로 Actions 탭에서 수동으로 한 번 깨우는 용도.

#### 교훈

똑같은 "10분마다 핑 보내기"라는 요구사항도, **어떤 스케줄러로 구현하느냐에 따라 실제 신뢰도가 크게 달라진다.** GitHub Actions는 CI처럼 "언젠가 한 번 실행되면 되는" 용도엔 충분하지만, "정확한 시간 간격을 지켜야 하는" 용도(이번 같은 헬스체크/킵얼라이브)엔 전용 스케줄링 서비스가 낫다는 걸 실측으로 확인했다.

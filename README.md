# 🎱 AI Lucky Pinball

> 오늘 운이 없는 사람에게 작은 행운을.
> 이름과 생년월일을 입력하면 AI(Claude)가 오늘의 운세를 분석해 "버프"를 부여하고, 참가자들은 물리 엔진 기반 핀볼 맵에서 결승선을 향해 경쟁합니다. 가장 마지막에 결승선을 통과한 사람이 "당첨자"가 되는 웹 기반 추첨 게임입니다.

이 프로젝트는 단순한 미니게임이 아니라, **AI API 연동을 실제 서비스 로직(게임 밸런스)에 결합하는 것**과 **운영 관점에서 바로 쓸 수 있는 구조(로그 추적, 유연한 확장성)를 갖춘 백엔드를 설계하는 것**을 목표로 한 포트폴리오 프로젝트입니다.

## 왜 이 프로젝트를 만들었는가

### 1. 기획의 출발점

이 프로젝트는 [`AI_Lucky_Pinball_Project.md`](./AI_Lucky_Pinball_Project.md)라는 짧은 기획서에서 시작했습니다. 처음 구상한 내용은 대략 이랬습니다.

> 참가자가 이름과 생년월일을 입력하면 AI가 오늘의 운세를 분석하고, 운세가 좋지 않은 참가자에게는 "행운 버프"를 부여한다. 물리 엔진 기반 게임에서 마지막까지 살아남은(혹은 특정 조건을 만족한) 참가자가 최종 당첨자가 된다 — "오늘 운이 없는 사람에게 작은 행운을."

이 아이디어를 실제로 구현하면서, 초기 기획서에 있던 몇 가지 설계(HP 기반 서바이벌 방식, OpenAI 연동, MySQL/Redis)는 개발 과정에서 더 나은 대안으로 의도적으로 바꿨습니다 — 예를 들어 승부 방식은 참고 사례([lazygyu의 Marble Roulette](https://lazygyu.github.io/roulette/))를 검토한 뒤 "결승선 통과 순서 경쟁" 방식으로 재설계했고, AI는 Claude API(Haiku 4.5)로 연동했습니다. 이런 결정들의 배경은 전부 [`plan/`](./plan)과 [`devhelp/`](./devhelp) 문서에 왜 그렇게 바꿨는지까지 기록해뒀습니다.

### 2. 실무 경험에서 가져온 문제의식

5년간 시스템 운영 업무를 담당하면서 반복적으로 마주쳤던 두 가지 문제가 있었습니다.

- **운영 중 문제가 생겼을 때 원인을 추적할 로그/이력이 관리자 화면에 충분히 없는 경우가 많았습니다.** "언제, 누구에게, 무슨 일이 있었는지"를 바로 조회할 수 있는 것과 없는 것은 장애 대응 속도에서 큰 차이를 만듭니다.
- **시스템을 고도화(기능 추가/외부 연동 교체)하려 할 때, 초기 설계가 유연하지 못해 코드를 광범위하게 뜯어고쳐야 하는 경우가 많았습니다.** 처음부터 교체 지점을 인터페이스로 분리해뒀다면 훨씬 적은 리스크로 확장할 수 있었을 문제들이었습니다.

그래서 이 포트폴리오 프로젝트는 재미있는 게임을 만드는 것과 별개로, **이 두 가지를 의도적으로 신경 써서 설계**했습니다. 자세한 내용은 바로 아래 항목에 정리했습니다.

## 핵심 기능

- **참가자 등록**: 이름 + 생년월일(선택) 등록. 생년월일을 입력하지 않으면 AI 호출 없이 무료로 즉시 참여할 수 있습니다.
- **AI 운세 분석**: Claude API(Haiku 4.5)가 이름·생년월일·오늘 날짜·띠·계절 등을 바탕으로 운세 점수(0~100)·행운의 숫자·개인화된 메시지를 생성합니다.
- **비용 최적화 캐시**: 동일한 이름+생년월일 조합은 최초 1회만 AI를 호출하고, 이후로는 DB에 저장된 결과를 영구적으로 재사용합니다.
- **버프 시스템**: 운세 점수에 따라 핀볼 맵에서의 시작 위치(높이)가 달라집니다 — 운세가 안 좋을수록 결승선에 더 가깝게 출발합니다.
- **실시간 물리 시뮬레이션 게임**: Matter.js 기반 갈톤보드(Plinko) 스타일 핀볼 맵에서 참가자들이 결승선을 향해 경쟁하고, 최후반부에는 "역전 상황"을 자동으로 감지해 카메라가 확대·추적합니다.
- **관리자 화면**: 참가자별 운세 조회 이력, 게임 결과 이력, 서버 오류 로그를 조회할 수 있습니다 (아래 아키텍처 항목 참고).

## 아키텍처에서 특히 신경 쓴 부분

### 1. 로그 · 이력 관리 (운영 경험에서 나온 설계)

- `GET /api/admin/logs` — 서버 전역 예외 핸들러(`GlobalExceptionHandler`)가 발생하는 모든 오류를 자동으로 수집해 조회할 수 있게 했습니다. 컨트롤러마다 로깅 코드를 따로 넣을 필요 없이, 에러 처리 로직 한 곳에서 자연스럽게 축적됩니다.
- `GET /api/admin/players` — 참가자별 운세 조회 이력을 "언제, 몇 점, AI가 새로 분석했는지(AI) 아니면 기존 기록을 재사용했는지(CACHE)"까지 구분해서 보여줍니다 — AI 비용이 실제로 어떻게 쓰이고 있는지 운영 관점에서 바로 확인할 수 있습니다.
- `GET /api/admin/games` — 게임 결과 이력 조회.

### 2. 고도화에 유연한 구조 (인터페이스 기반 교체 지점)

아래 지점들은 전부 **처음부터 인터페이스로 분리해서, 실제로 구현체를 교체하는 경험까지 검증**했습니다.

| 교체 지점 | 인터페이스 | 실제로 있었던 교체 |
|---|---|---|
| AI 운세 생성기 | `FortuneService` | `MockFortuneGenerator`(규칙 기반) → `ClaudeFortuneGenerator`(실제 Claude API) — **호출부 코드 변경 없이 교체 완료** |
| 참가자/게임 저장소 | `PlayerJpaRepository`, `GameRepository` | 지금은 각각 H2/인메모리 구현체이며, 실제 DB(MySQL 등)로 바꿀 때 이 구현체만 교체하면 되도록 설계 |
| 물리 엔진 | `MatterAdapter` (어댑터 패턴) | 지금은 Matter.js 기반이며, 게임 로직은 이 어댑터의 메서드만 호출하므로 나중에 Box2D 등으로 교체할 여지를 남겨둠 |
| 핀볼 맵 | `PinballMapConfig` | 지금은 "클래식 갈톤보드" 1종이지만, 설정 객체만 추가하면 새 맵을 추가할 수 있는 구조 |
| 관리자 기능 확장 지점 | `POST /api/admin/fortune/override` | 아직 미구현이지만, 엔드포인트와 화면을 먼저 만들어두고 `501 Not Implemented`로 명확히 응답하도록 해서 "구현 안 된 기능"과 "존재하지 않는 기능"을 구분함 |

이런 설계 하나하나가 "나중에 바꿀 수도 있으니까"라는 막연한 이유가 아니라, **실제로 한 번씩 교체를 실행해서 검증한 결과**라는 점이 이 프로젝트에서 가장 신경 쓴 부분입니다 (Mock → Claude API 교체가 대표적인 예시입니다).

## 로컬에서 실행하기

**백엔드**
```bash
cd backend
export ANTHROPIC_API_KEY=sk-ant-...   # Claude API 키 (없으면 생년월일 미입력 참가자만 무료로 플레이 가능)
./gradlew bootRun                      # http://localhost:8080
```

**프론트엔드**
```bash
cd frontend
npx serve . -l 5501                    # http://localhost:5501
```

## API 개요

전체 엔드포인트 명세는 [`plan/02_api-spec.md`](./plan/02_api-spec.md)에 정리돼 있습니다. 주요 엔드포인트:

| Method | Path | 설명 |
|---|---|---|
| POST | `/api/player` | 참가자 등록 (생년월일 선택) |
| POST | `/api/fortune` | 오늘의 운세 + 버프 조회 |
| POST | `/api/game/create` | 게임 세션 생성 |
| POST | `/api/game/result` | 완주 순서 보고 (물리 시뮬레이션은 클라이언트에서 진행되므로) |
| GET | `/api/admin/players` / `/games` / `/logs` | 관리자 조회 |

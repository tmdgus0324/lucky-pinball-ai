# 05. 테스트 전략

백엔드 JUnit 테스트 **99개**(16개 클래스)가 GitHub Actions에서 push마다 실행됩니다. 프론트엔드는 CI에서 `lint`와 `build`(타입 검사 포함)만 확인합니다.

## 1. 원칙

- **진짜 Claude API는 테스트에서 절대 호출하지 않습니다**(비용). 대신 세 가지 대역을 씁니다.
  - 성공·실패를 마음대로 바꾸는 **가짜 `FortuneService`** — 캐시·임시 점수·동시성 로직 확인
  - JDK `HttpServer`로 띄운 **가짜 Claude 서버** — 타임아웃·401·429·500·끊긴 연결 같은 **실제 네트워크 실패** 재현(SDK가 시스템 프로퍼티 `anthropic.baseUrl`을 먼저 읽는 점 이용)
  - 규칙 기반 `MockFortuneGenerator` — 결정적인 점수
- 테스트는 **메모리 H2**를 씁니다(`src/test/resources/application.properties`). 로컬에서 서버를 켜 둔 채 테스트해도 개발 DB를 건드리지 않습니다.
- **버그는 재현 테스트를 먼저 쓰고**, 수정 전에 실패하는 것을 확인한 뒤 고칩니다(예: 동시 요청 시 AI 6번 호출, 쉬었다 누르면 "연결 불가" 오진).

## 2. 테스트 구성

| 종류 | 클래스(개수) | 확인하는 것 |
|---|---|---|
| **HTTP 통합** | `ApiFlowIntegrationTest`(4) | 실제 포트로 서버를 띄워 필터·컨트롤러·예외 처리·JPA까지: 전체 게임 흐름, 오류 응답과 추적 ID, HTTP 경유 동시 요청, 관리자 인증 |
| 서비스 + DB | `FortuneQueryServiceTest`(9), `ErrorLogStoreTest`(6) | 캐시·임시 점수·캐시 오염 방지·**동시 요청 시 AI 1번**·잠금 병렬성 / 오류 로그 저장·정리·잘림·DB 장애 시에도 안전 |
| 외부 API 실패 | `ClaudeFortuneGeneratorTest`(6), `AiHealthServiceTest`(14) | 가짜 Claude 서버로 타임아웃·재시도 횟수·오류 변환(504/503/502), 크레딧 부족·키 없음·끊긴 연결 구분 |
| 도메인 단위 | `GameServiceTest`(14), `BuffCalculatorTest`(4), `MockFortuneGeneratorTest`(3), `KeyedLockTest`(5) | 인원 제한, 상대평가 시작 높이, 게임 상태 규칙, 결과 검증 / 버프 계산 / 결정적 점수 / 키별 잠금(직렬·병렬·누수 없음·예외 시 해제) |

| 기동 | `LuckyPinballApplicationTests`(1) | 스프링 컨텍스트가 뜨는지 |

## 3. 두 가지 환경 조건으로 실행

`ANTHROPIC_API_KEY` 환경변수가 있는 개발 PC에서는 "키 없음" 시나리오 테스트 2개가 스킵됩니다. 이 스킵 때문에 CI에서만 실패한 적이 있어서(키 없음이 실제로는 401로 나오는 것을 놓침), 지금은 **환경변수를 뺀 CI와 같은 조건으로도 한 번 더** 돌립니다.

```bash
cd backend
./gradlew cleanTest test                                          # 키 있음: 99개 중 2개 스킵
env -u ANTHROPIC_API_KEY -u ANTHROPIC_AUTH_TOKEN ./gradlew cleanTest test   # CI 조건: 99개 전부 실행
```

`cleanTest`를 붙이는 이유: 소스가 그대로면 Gradle이 이전 결과를 재사용해서 환경만 바꾼 재실행이 실제로 돌지 않습니다.

## 4. 시간에 의존하는 테스트

동시성 테스트 일부는 "병렬이면 빨리 끝난다"를 시간으로 확인합니다(예: 4명 동시 요청이 1500ms 안에 끝나는지, 직렬이면 약 2000ms). 가끔 실패하지 않는지 관련 테스트를 5번 반복해 모두 통과하는 것을 확인했고, 기준은 직렬·병렬 시간 사이에 여유를 두고 잡았습니다.

## 5. 프론트엔드 확인 방법과 빈틈

- 자동 테스트는 없습니다. 기능을 바꿀 때 **Playwright 스크립트로 브라우저를 직접 조작**해서 확인했습니다(예: 13개 챕터 실행, 관리자 화면 패널, 휴대폰 폭별 카드 넘침 측정). 백엔드 없이 API 응답을 가짜로 바꿔 끼우는 방식(`page.route`)도 썼습니다.
- 이 스크립트들은 저장소에 넣지 않았습니다. 프론트엔드 테스트를 자동화한다면 이것들을 Playwright 테스트로 옮기는 것이 첫 단계입니다.
- 부하 테스트는 하지 않았습니다.

## 1. 이번 프로젝트에서 배운 것

### 잘 된 것 — 다음에도 그대로

- **코딩 전에 계획과 목업부터.** plan/01~04와 `mockups/`를 먼저 만들고 검토한 뒤 코딩했습니다. 목업의 CSS는 실제 화면에 그대로 쓰였습니다.

- **바뀔 곳을 인터페이스 뒤에 두기.** `FortuneService`(Mock → Claude), `GameRepository`(메모리 → JPA)는 호출부를 고치지 않고 실제로 교체했습니다.

- **작업마다 기록 남기기(`devhelp/`).** 나중에 "왜 이렇게 했나"를 설명할 수 있습니다.

### 아팠던 것 — 다음엔 미리

| 겪은 일 | 원인 | 다음엔 |
|---|---|---|
| 버프 공식을 세 번 다시 만듦(구간 → 선형 → 상대평가) | AI 점수가 어떻게 나오는지 확인하지 않고 설계 | 외부 서비스는 설계 전에 **작은 실험**으로 실제 출력을 본다 |
| 관리자 인증·요청 제한·장애 대응·로그가 배포 직전·직후에 몰림 | 계획에 운영 항목이 없었음 | 계획에 **운영 계획** 문서를 둔다 |
| 같은 물리 코드를 두 벌 유지(`engine.ts`, `game.js`) | 바닐라로 시작 후 React 전환, 옛 버전을 지울 기준이 없었음 | **최종 스택으로 시작**하고, 옛 버전을 남기면 종료 기준을 적는다 |
| 계획 문서에 변경 이력이 쌓여 지금 상태를 알기 어려움 | 계획·현재 상태·작업 기록이 한 문서에 섞임 | 처음부터 **세 곳으로 분리**(2절) |
| 백로그의 "완료" 설명이 사실과 어긋남 | 문서로 손으로 관리 | **GitHub Issues**로 관리 |
| 필터의 401/429 응답에 CORS 헤더가 빠져 브라우저에서 "Failed to fetch" | 오류 응답 규칙과 인증 경계를 늦게 정함 | API **공통 규칙을 먼저** 정한다 |
| 배포 후에야 SPA 새로고침 404, 모바일 잘림 발견 | MVP를 다 만든 뒤 처음 배포 | **빈 화면일 때 첫 배포** |
| CI에서만 실패한 테스트(로컬은 API 키 때문에 스킵) | 로컬과 CI의 환경 조건이 달랐음 | 테스트 계획에 **실행 조건**까지 적는다 |

## 4. TODO 앱에 적용하면

### 4.1 첫날 정할 것 — 나중에 바꾸면 비싼 것

| 질문 | 왜 첫날인가 | 이번 경험 |
|---|---|---|
| **로그인(사용자 구분)이 있나?** | 있으면 모든 테이블에 `user_id`, 모든 API에 "내 것만 보기·고치기" 확인이 들어간다. 나중에 넣으면 전부 다시 고친다 | 관리자 로그인을 나중에 넣다가 공개 API를 떼어 내고, CORS 버그를 만났다 |
| **DB와 스키마 변경 방법** | 로컬/운영 DB 분리, Flyway를 첫 테이블부터 | `ddl-auto: update`로 시작해 운영 DB 변경 이력이 없다 |
| **오류 응답 형식** | 프론트의 오류 표시와 테스트가 모두 이 형식에 맞춰진다 | `{ error, traceId }`가 나중에 생겨 여러 곳을 고쳤다 |
| **배포 대상과 환경변수** | CORS 허용 도메인, API 주소, 비밀 값 위치가 정해진다 | GitHub Pages → Vercel로 바뀌었고, 배포 후 버그가 몰렸다 |
| **프론트 스택** | 전환은 비싸다 | 바닐라 → React 전환 후 두 벌 유지 |
| **테스트 방식** | 외부 의존성(AI 등)을 가짜로 바꿀 자리를 처음부터 만든다 | 가짜 Claude 서버는 장애 대응 단계에서야 만들었다 |

### 4.2 MVP 범위 예시

| 포함 | 미룸 |
|---|---|
| 할 일 추가·수정·삭제 | 카테고리·태그 |
| 완료 체크 | 드래그로 순서 바꾸기 |
| 목록 필터(전체·진행 중·완료) | 알림 |
| 마감일 | 공유·협업 |
| 새로고침해도 유지(DB 저장) | AI 기능(예: 할 일 쪼개기 제안) |
| 로그인 — **4.1에서 "있음"으로 정했다면 MVP에 포함** | |

AI 기능을 넣는다면 이번처럼 **캐시, 비용(요청 제한), 장애 시 대체 동작**을 같은 계획 안에서 같이 정합니다. AI 호출을 붙이는 것보다 이 세 가지에 시간이 더 들었습니다.

### 4.3 완료 기준 예시

| 기능 | 완료 기준 | 확인 방법 |
|---|---|---|
| 할 일 추가 | 빈 제목·200자 초과는 400, 추가 후 새로고침해도 남아 있음 | 통합 테스트 + 화면 확인 |
| 완료 체크 | 상태가 DB에 저장됨. 로그인이 있다면 다른 사람의 할 일은 바꿀 수 없음(404) | 통합 테스트 |
| 목록 | 필터 3종 동작, 할 일이 100건이어도 쿼리 수가 같음 | 통합 테스트(쿼리 수 측정, 이번 N+1 테스트와 같은 방식) |
| 첫 배포 | 운영 주소에서 추가·체크·새로고침·직접 URL 접속이 됨 | 배포 후 화면 확인 |

### 4.4 운영 계획 체크리스트

- [ ] 비밀 값은 환경변수로만. `.gitignore`와 커밋 전 키 검사(이번에 쓴 pre-commit 훅)
- [ ] CORS 허용 목록(로컬 포트 + 배포 도메인). **필터가 직접 쓰는 오류 응답에도** CORS 헤더
- [ ] 입력 길이 제한(제목, 메모)
- [ ] 요청 제한이 필요한 API(로그인, 비용이 드는 API). 방문자 IP는 플랫폼이 보장하는 헤더로만 판단(`X-Forwarded-For` 첫 값은 조작 가능)
- [ ] 추적 ID와 오류 로그(관리자가 볼 수 있는 곳)
- [ ] 무료 티어 제약(서버 슬립, DB 용량)과 대응

### 4.5 작업 순서 예시

1. **뼈대**: 저장소, `CLAUDE.md`, CI. 빈 API 하나 + 빈 화면 + 테스트 1개가 CI에서 통과.
2. **첫 배포**: 빈 화면 상태로 운영에 올린다. SPA 새로고침, CORS, 환경변수 문제를 여기서 다 만난다.
3. **DB와 할 일 API**: Flyway 첫 마이그레이션, CRUD API, 통합 테스트.
4. **화면**: 목록·추가·완료 체크.
5. **미룸 항목**: Issues에서 하나씩 꺼내 진행.

## 5. Claude Code와 계획을 세울 때

- **계획은 plan 모드에서 받습니다.** 코드를 바꾸지 않고 계획만 받아서 검토한 뒤 진행합니다. 이번에도 plan 문서를 먼저 만들고 승인한 뒤 코딩했습니다.
- **"가정을 먼저 적어 줘", "선택지와 추천을 같이"를 요청합니다.** 이번 생년월일 노출 항목처럼 결정이 필요한 곳에서 멈추고 물어보게 됩니다.
- **항목마다 "어떻게 확인할지"를 같이 요구합니다.** 핀볼 끼임 버그는 밀기 횟수를 세는 측정 방법이 생긴 뒤에야 확실히 풀렸습니다.
- **어렵게 알아낸 규칙은 바로 `CLAUDE.md`에 적습니다.** 예: `PEG_WALL_CLEARANCE`(70)는 줄이면 안 된다. 다음 대화에서도 같은 실수를 하지 않습니다.
- **커밋은 기능 단위로, 문서도 같은 커밋에.** 코드와 기록이 따로 놀지 않습니다.

- 작업마다 기록을 남겼습니다(`devhelp/`). 나중에 "왜 이렇게 했나"를 설명할 수 있습니다.

### 다음에는 미리 할 것

| 겪은 일 | 원인 | 다음에는 |
|---|---|---|
| 버프 공식을 세 번 다시 만듦 | AI 점수가 실제로 어떻게 나오는지 보지 않고 설계함 | 외부 서비스는 설계 전에 몇 번 호출해서 실제 결과를 본다 |
| 인증, 요청 제한, 장애 대응, 로그가 배포 직전·직후에 몰림 | 계획에 운영 항목이 없었음 | 계획에 운영 항목을 넣는다 |
| 같은 물리 코드를 두 벌 유지 | 바닐라 JS로 시작해 React로 옮기고, 옛 버전을 지울 기준이 없었음 | 처음부터 쓸 기술로 시작한다 |
| 계획 문서에 변경 이력이 쌓여 지금 상태를 알기 어려움 | 계획, 현재 설명, 작업 기록이 한 문서에 섞임 | 처음부터 폴더를 나눈다(2절) |
| 백로그 문서의 "완료" 표시가 실제와 어긋남 | 문서에서 손으로 관리함 | GitHub Issues로 관리한다 |
| 필터가 보낸 오류 응답에 CORS 헤더가 빠져 "Failed to fetch" | 오류 응답 규칙을 늦게 정함 | API 공통 규칙(오류 형식, 인증, CORS)을 먼저 정한다 |
| 배포한 뒤에야 새로고침 404, 모바일 잘림을 발견 | 다 만든 뒤 처음 배포함 | 빈 화면일 때 먼저 배포한다 |
| CI에서만 실패한 테스트 | 내 PC와 CI의 환경변수가 달랐음 | 테스트 계획에 실행 조건까지 적는다 |
| 문서가 프로젝트에 비해 무거워짐 | 산출물을 큰 프로젝트처럼 만듦 | 프로젝트 크기에 맞게 문서 수를 정한다 |

## 4. TODO 앱에 적용하면

### 4.1 첫날 정할 것

나중에 바꾸면 비싼 것들입니다.

| 질문 | 왜 첫날인가 | 이번 경험 |
|---|---|---|
| 로그인(사용자 구분)이 있나? | 있으면 모든 테이블에 `user_id`, 모든 API에 "내 것만" 확인이 들어간다 | 관리자 로그인을 나중에 넣다가 공개 API를 따로 떼어 냈다 |
| DB와 스키마 변경 방법 | 로컬/운영 DB를 나누고, Flyway를 첫 테이블부터 쓴다 | `ddl-auto: update`로 시작해 운영 DB 변경 이력이 없다 |
| 오류 응답 형식 | 화면의 오류 표시와 테스트가 이 형식에 맞춰진다 | `{ error, traceId }`가 나중에 생겨 여러 곳을 고쳤다 |
| 배포할 곳과 환경변수 | CORS 허용 주소, API 주소, 비밀 값 위치가 정해진다 | 배포 대상이 바뀌었고, 배포 후 버그가 몰렸다 |
| 프론트 기술 | 나중에 바꾸면 비싸다 | 바닐라 → React 전환 후 두 벌 유지 |
| 테스트 방식 | 외부 서비스(AI 등)를 가짜로 바꿀 자리를 처음부터 만든다 | 가짜 Claude 서버를 장애 대응 단계에서야 만들었다 |

### 4.2 MVP 범위 예시

| 포함 | 미룸 |
|---|---|
| 할 일 추가·수정·삭제 | 카테고리·태그 |
| 완료 체크 | 드래그로 순서 바꾸기 |
| 목록 필터(전체·진행 중·완료) | 알림 |
| 마감일 | 공유·협업 |
| 새로고침해도 남음(DB 저장) | AI 기능(예: 할 일 쪼개기 제안) |
| 로그인(4.1에서 "있음"으로 정했다면) | |

AI 기능을 넣는다면 캐시, 비용(요청 제한), 실패했을 때의 대체 동작을 같은 계획 안에서 정합니다. 이번에는 AI를 붙이는 것보다 이 세 가지에 시간이 더 들었습니다.

### 4.3 완료 기준 예시

| 기능 | 완료 기준 | 확인 방법 |
|---|---|---|
| 할 일 추가 | 빈 제목·200자 초과는 400, 새로고침해도 남아 있음 | 통합 테스트, 화면 확인 |
| 완료 체크 | DB에 저장됨. 로그인이 있다면 남의 할 일은 못 바꿈 | 통합 테스트 |
| 목록 | 필터 3종 동작, 할 일이 100건이어도 쿼리 수가 같음 | 통합 테스트(이번 N+1 테스트와 같은 방식) |
| 첫 배포 | 운영 주소에서 추가·체크·새로고침·주소 직접 입력이 됨 | 배포 후 화면 확인 |

### 4.4 운영 체크리스트

- [ ] 비밀 값은 환경변수로만 넣는다. `.gitignore`와 커밋 전 키 검사(이번에 쓴 pre-commit 훅)
- [ ] CORS 허용 목록(로컬 포트 + 배포 주소). 필터가 직접 보내는 오류 응답에도 CORS 헤더
- [ ] 입력 길이 제한(제목, 메모)
- [ ] 요청 제한이 필요한 API(로그인, 비용이 드는 API). 방문자 IP는 배포 플랫폼이 넣어 주는 헤더로만 판단(`X-Forwarded-For` 첫 값은 바꿔 보낼 수 있음)
- [ ] 추적 ID와 오류 로그
- [ ] 무료 플랜의 제약(서버 슬립, DB 용량)

### 4.5 작업 순서 예시

1. 뼈대: 저장소, `CLAUDE.md`, CI. 빈 API 하나, 빈 화면, 테스트 1개가 CI에서 통과
2. 첫 배포: 빈 화면 그대로 운영에 올린다. 새로고침 404, CORS, 환경변수 문제를 여기서 만난다
3. DB와 할 일 API: Flyway 첫 마이그레이션, CRUD API, 통합 테스트
4. 화면: 목록, 추가, 완료 체크
5. 미룬 항목: Issues에서 하나씩 꺼내서 진행

## 5. Claude Code와 계획을 세울 때

- 계획은 plan 모드에서 받습니다. 코드를 바꾸지 않고 계획만 받아서 검토한 뒤 진행합니다.
- "가정을 먼저 적어 줘", "선택지와 추천을 같이 줘"라고 요청하면, 결정이 필요한 곳에서 멈추고 물어봅니다.
- 항목마다 "어떻게 확인할지"를 같이 요청합니다. 핀볼 끼임 버그는 측정 방법이 생긴 뒤에야 확실히 풀렸습니다.
- 어렵게 알아낸 규칙은 바로 `CLAUDE.md`에 적습니다. 다음 대화에서 같은 실수를 하지 않습니다.
- 커밋은 기능 단위로 하고, 문서도 같은 커밋에 넣습니다.

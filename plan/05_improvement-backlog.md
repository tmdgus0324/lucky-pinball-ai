# AI Lucky Pinball — 개선 백로그 (착수 전, 계획만)

> 이 문서는 **지금 바로 진행하는 게 아니라**, 나중에 사용자가 "이제 이거 진행해줘"라고 말하면 그때 시작할 항목들을 미리 정리해둔 목록입니다. 각 항목은 실제 설계에 들어가기 전 단계라, 세부 구현 방법은 착수 시점에 다시 논의합니다.

---

## A. 사용자 요청 항목

### A1. 좌측 메뉴(사이드바) 내비게이션으로 전환
현재는 화면 상단에 "참가자/게임 화면"·"관리자 화면" 두 개가 알약 모양 탭으로 있는데, 이걸 **왼쪽 사이드바 메뉴**로 옮긴다.
- 고려할 점: 사이드바가 가로 공간을 차지하므로, 좁은 화면(모바일)에서는 접었다 펼 수 있는 형태가 필요할 수 있음.
- 지금 두 화면(`index.html`, `admin.html`)이 완전히 분리된 정적 페이지라서, 사이드바 UI(HTML/CSS)를 양쪽에 중복 배치하거나 공용 컴포넌트로 뺄지 결정 필요.

### A2. 관리자 화면 별도 인증(로그인) 추가
지금은 `admin.html`에 인증이 전혀 없어서 누구나 접속 가능 — 계속 미뤄왔던 항목을 실제로 진행.
- **카카오톡 무료 인증 사용 가능 여부 확인 결과**: 카카오 로그인(OAuth 기반 소셜 로그인) 자체는 **무료**입니다 — 개인 프로젝트든 상용 서비스든 로그인 건당 비용이 없습니다. Kakao Developers에 앱을 등록하고 REST API 키를 발급받아 사용하는 구조입니다. (단, 로그인 이후 "친구 목록 조회"나 "카카오톡 메시지 전송" 같은 **부가 API는 별도 유료**인 경우가 있으니, 착수 시점에 정확히 어떤 카카오 API를 쓸지에 따라 developers.kakao.com에서 최신 정책을 다시 확인해야 합니다.)
- 대안도 함께 고려 가능: 가장 간단하게는 관리자 비밀번호 하나만 거는 방식(세션/쿠키 기반)도 있고, 카카오 로그인처럼 소셜 로그인으로 "특정 카카오 계정만 관리자로 허용" 하는 방식도 있음 — 착수 시점에 어느 쪽으로 할지 정하기.

### A3. 관리자 화면 참가자 목록 페이징 처리 — ✅ 완료
`GET /api/admin/players`를 페이지당 20건, `Pageable` 방식으로 페이징 처리하고 프론트에 페이지 이동 UI를 추가했다. 게임 결과 목록(`GET /api/admin/games`)은 아직 페이징하지 않음 — 참가자 수 추이를 보고 필요해지면 진행.

### A4. 별도 DB로 관리 + 테스트 데이터 구성
지금까지 개발/테스트하면서 쌓인 데이터가 섞여 있는 로컬 H2 파일(`backend/data/luckypinball.mv.db`) 대신, **정리된 테스트 전용 DB 환경**을 구성.
- 목적으로 말씀하신 부분: **재조회(2회차)** 시 정말로 DB 캐시만 쓰고 **AI를 다시 호출하지 않는지**를 깨끗한 데이터로 명확하게 검증하고 싶다는 것으로 이해했습니다 — 맞다면, 테스트 시나리오(예: 특정 이름+생년월일로 1차 조회 → AI 호출 확인 → 2차 조회 → 로그/응답의 `source` 필드가 `CACHE`인지, 그리고 실제로 Claude API가 호출되지 않았는지)를 문서로 만들고 재현 가능하게 스크립트화하는 작업이 될 것 같습니다.
- "별도 DB"가 (a) 지금의 개발용 H2 파일을 초기화하고 깨끗하게 다시 쓰는 것인지, (b) 개발용과는 별개로 테스트 전용 H2/파일을 하나 더 두는 것인지, (c) 아예 MySQL 같은 실제 DB로 전환하는 것인지는 착수 시점에 다시 확인이 필요합니다.

## B. Claude가 제안하는 개선 항목

이번까지 개발하면서 실제로 관찰했거나, 이미 알려진 한계 중에서 다음 단계로 다룰 만하다고 판단한 것들입니다.

### B1. 운세 점수 분포 개선 (하이브리드 방식 검토)
`devhelp/14`에서 기록한 대로, 메시지/행운의 숫자는 다양해졌지만 **점수는 여전히 60~70점대로 쏠리는 경향**이 남아있습니다. 프롬프트만으로는 한계에 도달한 것으로 보여서, AI 점수에 생년월일 기반 결정론적 계산값을 일부 섞는 하이브리드 방식을 검토해볼 만합니다. 다만 "점수가 AI의 순수 판단"이라는 지금 컨셉을 바꾸는 결정이라 사용자 확인이 필요합니다.

### B2. 오류 로그 영속화 — ✅ 완료 (devhelp/42)
(아래는 당시 배경 설명)
`GET /api/admin/logs`가 지금은 인메모리 리스트라 서버를 재시작하면 기록이 전부 사라집니다. 실제로 문제를 추적하려면 DB(또는 최소한 파일)에 남겨야 재시작 후에도 조회할 수 있습니다.

### B3. 게임 결과(GameResult) DB 영속화
참가자/운세 이력은 H2에 저장되지만, 게임 세션·결과(`GameSession`, `GameResult`)는 아직 인메모리라 서버를 재시작하면 "지금까지 어떤 게임들이 있었는지"가 전부 사라집니다. A4(별도 DB 정리)를 진행하는 김에 같이 승격하면 자연스러울 것 같습니다.

### B4. 관리자 "가중치 임의 조정" 기능 실제 구현 — ❌ 하지 않기로 함 (2026-10-04, `devhelp/47`)
(아래는 당시 배경 설명. 스텁 API와 화면은 제거했다.)
`POST /api/admin/fortune/override`가 아직 501(미구현) 스텁 상태입니다. 실제로 구현하려면 "덮어쓴 점수를 얼마나 유지할지(1회성인지 영구인지)", "덮어쓴 이력을 어떻게 남길지" 같은 세부 규칙을 먼저 정해야 합니다.

### B5. 모바일/좁은 화면 대응 — 🟡 부분 완료
핀볼 보드는 고정 픽셀 크기(560×770)로 물리 좌표를 맞추는데, `fitScale` 계산을 추가해 좁은 화면에서도 잘리지 않고 축소되어 보이도록 고쳤다(`devhelp/28`). 운세 결과 카드 텍스트 잘림은 해결(`devhelp/46`). 남은 것: 관리자 화면 표(테이블)의 좁은 화면 대응.

# AI Lucky Pinball — 핀볼 맵 설계

## 0. 게임 규칙 (2026-09-22 개정: 결승선 통과 순서 경쟁)

사용자가 참고한 [lazygyu의 "Marble Roulette"](https://lazygyu.github.io/roulette/)에 맞춰, 승부 방식을 **HP 생존제 → 결승선 통과 순서 경쟁**으로 바꿨다. HP·충돌 데미지 개념은 없다 — 모든 구슬이 핀볼 맵을 통과해 결승선까지 도달하고, **가장 마지막에 결승선을 통과한 참가자가 "당첨자"**로 결정된다 (`01_mvp-plan.md` §3.6 참고). lazygyu의 원본은 절차적으로 생성되는 미로형 장애물 코스를 쓰지만, 이번 MVP는 구현 범위를 줄이기 위해 기존에 설계했던 갈톤보드(못 배열) 구조에 결승선만 추가하는 방식으로 단순화한다.

## 1. 참고 레퍼런스

핀볼 맵의 장애물(못) 배치는 가장 대표적이고 검증된 레이아웃인 **갈톤 보드(Galton board) / 플린코(Plinko) 스타일의 삼각형 페그(못) 배열**을 기준으로 삼는다. 삼각형으로 어긋나게 배치된 못은 Plinko가 가장 널리 쓰는 방식이고, Matter.js로 구현한 다수의 공개 예제(Coding Train, CodePen 등)가 모두 "행마다 반 칸씩 어긋난 열" 방식으로 못을 배치한다.

참고한 자료:
- [Marble Roulette (lazygyu.github.io)](https://lazygyu.github.io/roulette/) — 승부 방식(결승선 통과 순서 경쟁)의 원 아이디어
- [GitHub - lazygyu/roulette](https://github.com/lazygyu/roulette) — Box2D(WASM) 기반, 구슬이 서로/장애물과 충돌하며 진행
- [Plinko with Matter.js / The Coding Train](https://thecodingtrain.com/challenges/62-plinko-with-matterjs/)
- [Matter JS Plinko (CodePen)](https://codepen.io/borntofrappe/pen/QWWwOWO)
- [Why Plinko Uses Triangular Pegs](https://www.slingo.com/blog/guides/why-plinko-uses-triangular-pegs/)

> 참고: lazygyu의 구현은 Box2D-wasm을 쓰지만, 우리는 WASM 빌드체인 없이 순수 JS로 바로 쓸 수 있는 **Matter.js**를 그대로 유지한다 (기획서 원안과도 일치). 다만 나중에 더 정교한 물리감을 위해 Box2D(box2d-wasm)로 엔진 자체를 교체할 가능성을 열어두기로 했다 — §5 참고.

## 5. 확장성: 나중에 물리엔진을 Box2D로 교체할 수 있을까?

**결론: 가능하지만, "설정 하나 바꾸면 끝"인 완전 투명한 교체는 아니다.** Matter.js와 Box2D는 API/좌표계/초기화 방식이 서로 달라서, 엔진을 바꾸면 물리 관련 코드는 다시 짜야 한다. 대신 아래처럼 **엔진 종속 코드를 한 군데로 몰아두는 얇은 어댑터**를 지금부터 설계해두면, 나중에 교체할 때 영향 범위를 `game.js` 안의 어댑터 구현체 하나로 좁힐 수 있다.

```
PhysicsAdapter {
  init(): Promise<void>            // Box2D는 WASM 로딩이 비동기라, Matter.js도 처음부터 async로 통일
  createBall(x, y, radius, options): BallHandle
  createStaticBody(shapeDef): void  // 못, 벽 등
  step(deltaMs): void
  getPosition(ball): { x, y }
  dispose(): void
}
```
- 지금 만들 `MatterAdapter`는 위 인터페이스를 Matter.js로 구현.
- 나중에 필요해지면 같은 인터페이스를 구현하는 `Box2dAdapter`(box2d-wasm 사용)를 추가하고 교체.
- 결승선 통과 판정(§0)은 엔진 이벤트가 아니라 매 프레임 `getPosition(ball).y`를 확인하는 방식으로 설계해서, 애초에 엔진에 종속되지 않게 한다.

**교체 시 실제로 다시 손봐야 하는 부분** (완전 무료 교체가 아니라는 점을 명확히 하기 위해 명시):
- **비동기 초기화**: Box2D-wasm은 `.wasm` 파일을 비동기로 로드해야 함 — 그래서 `MatterAdapter.init()`도 지금부터 `Promise`를 반환하도록 만들어 나중에 호출부 코드는 안 바꿔도 되게 함.
- **좌표/단위계**: Box2D는 보통 미터 단위(작은 값)로 튜닝해야 안정적이고, Matter.js는 픽셀 단위를 그대로 써도 된다 — 어댑터 내부에서 픽셀↔미터 변환을 감춰야 함.
- **물리 파라미터 재튜닝**: 중력 배율/반발계수 같은 값은 엔진마다 체감이 달라서 그대로 이식되지 않는다 — 이 문서 §3의 파라미터는 Matter.js 기준값이며, Box2D로 바꾸면 다시 실측 튜닝이 필요하다.
- **번들링**: box2d-wasm은 `.wasm` 글루 코드가 필요해서, 지금의 "빌드 도구 없는 순수 정적 파일" 구성에 스크립트 태그 + wasm 파일 서빙 정도는 추가해야 한다 (라지지우처럼 Parcel 같은 번들러까지는 필요 없을 가능성이 높음).

즉, 지금은 위 어댑터 인터페이스만 지키면서 `MatterAdapter`로 구현해두면, 나중에 "물리엔진 교체" 자체는 새 어댑터 파일 하나를 추가하는 작업으로 국한된다 — 다만 물리 파라미터 튜닝과 초기 로딩 처리는 교체 시점에 별도 작업이 필요하다는 점은 미리 알아두는 게 좋다. (실제 구현은 이번 MVP 범위가 아니라 Phase 2 이후.)

## 2. 여러 맵을 지원하기 위한 구조 (지금은 설계만)

나중에 맵을 여러 개 추가할 수 있도록, 맵 하나를 아래와 같은 설정값 묶음(`PinballMapConfig`)으로 표현한다. 지금은 이 구조를 문서로만 정의하고, **`classic-galton` 맵 하나만** 실제로 만든다.

```
PinballMapConfig {
  id: string                  // 예: "classic-galton"
  name: string                 // 예: "클래식 갈톤보드"
  boardWidth, boardHeight      // 캔버스 크기
  pegField: {
    rows, spacing, radius,     // 못 배열 (행 수, 간격, 못 반지름)
    startY, endY                // 못 배열이 시작/끝나는 세로 범위
  }
  walls: [...]                  // 좌우 벽 좌표 (아래로 갈수록 좁아지는 깔때기 모양)
  spawnZone: { minY, maxY }     // 참가자가 버프에 따라 시작할 수 있는 Y 범위
  finishLineY: number           // 결승선 Y 좌표 — 이 지점을 통과하면 "완주"로 기록
}
```

나중에 새 맵을 추가할 때는 이 설정 객체 하나를 더 만들고 선택 UI(예: 게임 생성 시 맵 드롭다운)만 추가하면 되는 구조 — 코드를 다시 짤 필요가 없다.

## 3. 1차 맵: "클래식 갈톤보드" (`classic-galton`)

### 구조
```
┌───────────────────────────┐  y=0
│      낙하 시작 구역         │  y=0~90    (버프별 시작 Y가 이 구간 안에서 차등, §4 참고)
├───────────────────────────┤
│  ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲       │  y=90      못 1행
│ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲      │  y=140     못 2행 (반 칸 오프셋)
│  ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲       │  y=190     못 3행
│           ...              │            (총 8행)
│  ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲       │  y=440     못 8행
├───────────────────────────┤
│                             │  y=440~470  못 구간을 빠져나온 구슬이 결승선까지 흐르는 구간
╞═══════════════════════════╡  y=470     결승선 (finishLineY) — 통과 순간 순위 기록, 구슬은 계속 진행
│                             │  y=470~640  결승 이후 여유 공간(화면에서 자연스럽게 빠져나가는 구간)
└───────────────────────────┘  y=640
```

### 구체적 파라미터 (1차안, 실제 코딩 후 미세조정 전제)

| 항목 | 값 | 비고 |
|---|---|---|
| 캔버스 크기 | 560 × 640 px | 세로로 긴 실제 핀볼/플린코 비율 |
| 못 행 수 | 8행 | 짝수 행은 반 칸(spacing/2) 오프셋 → 삼각형 격자 |
| 못 간격(spacing) | 60px | |
| 못 반지름 | 7px | |
| 못 배열 구간 | y = 90 ~ 440 | |
| 공 반지름 | 13px | 못보다 확연히 커서 한 번에 여러 못 사이를 오가지 않도록 함 |
| 좌우 벽 | 위쪽 폭 560px → 아래로 갈수록 폭 460px까지 완만히 좁아짐 | 못 구간을 통과하며 구슬들이 중앙으로 모여 서로 부딪히게 유도 (완주 순서를 뒤섞는 요소) |
| 결승선(finishLineY) | y = 470 | 이 지점을 처음 통과하는 순간을 완주 시각으로 기록. 구슬은 통과 후에도 화면 하단으로 계속 흘러가며 자연스럽게 퇴장 |
| 중력 배율 | 1.2× (Matter.js 기본 대비) | 낙하를 다소 빠르게 해서 전체 진행 시간 단축 |
| 반발계수(restitution) | 0.45 | 너무 오래 튕기지 않으면서도 핀볼 특유의 통통 튀는 느낌 유지 |

### "1분 내 종료"를 겨냥한 설계 의도
- 못 8행 + 중앙으로 좁아지는 벽 → 구슬들이 못 구간에서 서로 자주 부딪히며 순서가 뒤섞여, 단순히 "먼저 출발한 순서 그대로 도착"하지 않고 매번 다른 결과가 나오게 함 (추첨 도구로서의 재미 요소).
- 결승선을 못 구간 바로 아래(y=470)에 둬서, 마지막 구슬까지 도착하는 데 걸리는 총 시간을 짧게 제한.
- 중력을 살짝 높이고 반발계수를 중간값으로 둬서 구슬이 무한히 튕기며 완주를 지연시키지 않도록 함.
- **참고**: 정확히 60초 안에 끝난다는 보장은 실제 Matter.js로 돌려보기 전까지는 물리 시뮬레이션 특성상 확정할 수 없다. 이 표의 값들은 "1분 내외"를 목표로 한 출발점이며, 실제 코딩 단계에서 몇 판 시뮬레이션해보고 중력/반발계수/못 배치를 조정하는 튜닝 과정이 필요하다는 점을 명시해둔다.

## 4. 버프와 맵의 연결

버프는 **시작 높이(Y)** 한 가지만 차등을 둔다 (`01_mvp-plan.md` §3.3 참고). 시작 Y는 위 "낙하 시작 구역"(y=0~90) 안에서 버프 티어별로 나뉜다:

- **운세가 좋을수록(버프 없음)** → 시작 구역의 맨 위(y=0 부근)에서 출발 → 결승선까지 가는 거리가 가장 길어 완주가 늦어지는 경향 → 당첨(가장 마지막 도착)에 가까워짐.
- **운세가 안 좋을수록(버프 4)** → 시작 구역의 아래쪽(y=60 부근, 못 1행에 가까운 지점)에서 출발 → 결승선까지 거리가 짧아 먼저 도착하는 경향 → 당첨에서 멀어짐.

단, 중간에 못 구간에서 서로 부딪히며 순서가 섞이기 때문에, 시작 높이가 결과를 100% 결정하지는 않는다 — "오늘 운 없는 사람에게 유리한 확률적 이점"을 주는 정도로 설계된 것이며, 이 점이 추첨 도구로서의 랜덤성/재미와 버프 시스템을 동시에 만족시킨다.
